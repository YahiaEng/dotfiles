## Held boundary (OP-4) — read before starting

Tasks 1-7 leave `hyprlock` **installed, configured and reachable**. Only Task 8
removes it, and **Task 8 must not be started until the operator has confirmed
live lock + unlock.**

Why this is not ordinary caution: every prior surface this project migrated
(waybar, swaync, swayosd, wleave, walker) failed *visibly and recoverably* — a
missing bar is an annoyance. A broken lock screen strands the session behind a
compositor that, per `ext-session-lock-v1`, is **required** to keep the session
locked and paint a blank surface if the lock client dies. The desktop is never
exposed — the protocol protects the secret — but the unlock UI is gone and the
only recovery is a VT switch (`--vt N`, the same escape hatch that came out of
the hyprshutdown work). Caelestia accepts this same trade.

The executor states this boundary explicitly in the SUMMARY.

## Architecture

```
quickshell/.config/quickshell/modules/lock/
  qmldir                 declares every type below (qml-import-check enforces:
                         an undeclared sibling in a qmldir-bearing dir is
                         unresolvable)
  Lock.qml               Scope: WlSessionLock + LockPam + screencopy pre-warm
  LockPam.qml            PamContext wrapper — buffer, handleKey, state, message
  LockSurface.qml        WlSessionLockSurface: backdrop + focus owner + layout Loader
  LockClock.qml          shared clock primitive
  LockField.qml          shared password field
  LockStatus.qml         shared state/error message (caps lock, failures)
  LockContinuity.qml     layout B  (Task 1)
  LockCaelestia.qml      layout A  (Task 2)
  LockRail.qml           layout C  (Task 3)
  LockSplit.qml          layout D  (Task 4)
  LockFocus.qml          layout E  (Task 5)
```

**Layout resolution.** `LockSurface.qml` reads `Prefs.getValue("lock.layout")`
and maps it through a `switch` whose `default:` returns the continuity Component.
It **never** returns `undefined` — per `qml-undefined-branch-destroys-binding.md`,
`cond ? X : undefined` on a real property sticks at 0 forever because `cond` is
false at construction time.

**Backdrop.** Also keyed on the layout string, in a plain data map inside
`LockSurface.qml` — **not** read off the loaded item. Per
`qml-configured-after-construction.md`, a Loader configures its item *after*
construction, so asking the item what backdrop it wants is a construction-order
bug waiting to happen. `caelestia` / `continuity` / `focus` blur a live
`ScreencopyView`; `rail` / `split` show `~/.local/state/theme/current.jpg`
unblurred (the study's directions C and D deliberately sidestep screencopy).

**Screencopy pre-warm is unconditional.** `Lock.qml` carries the Caelestia hack
verbatim (`caelestia-lock/Lock.qml:29-41`): an asynchronous `Loader` that
instantiates one throwaway `ScreencopyView { captureSource: Quickshell.screens[0] }`
at shell start and immediately sets `active = false`. The compositor refuses
capture once locked, so if the lock is the *first* screencopy request the backend
is still loading asynchronously and the capture fails. It stays unconditional
even though two layouts do not need it, because the operator can switch layouts
at any moment and the warm has to have already happened.

**One focus owner, not five.** Caelestia puts `focus: true` + `Keys.onPressed` on
its `PasswordInput` because it has exactly one layout. We have five, so the key
handler lives once in `LockSurface.qml` as a non-visual `Item` with
`focus: true`, `onActiveFocusChanged: if (!activeFocus) forceActiveFocus()`, and
`Keys.onPressed: e => root.pam.handleKey(e)`. This is a structural adaptation
forced by the five-layout requirement, not a taste divergence from the reference
(`reference-wins-over-my-taste.md`) — every *value* below is still Caelestia's.

**Layout Components close over scope.** Each layout is instantiated from an
inline `Component` inside `LockSurface.qml` that references `root.pam` /
`root.lock` / `root.screen` directly by closure. A Loader cannot pass properties
to its `sourceComponent`, and doing it via `onLoaded` reintroduces exactly the
construction-order trap above.

**Default layout: `continuity`.** While hyprlock is still the held fallback,
`continuity` is the only layout that preserves the old-vs-new equivalence check
— a regression is mechanical to spot against the table above. The operator flips
it in one click once Task 6 lands; that flip is item 9 on the operator checklist.
