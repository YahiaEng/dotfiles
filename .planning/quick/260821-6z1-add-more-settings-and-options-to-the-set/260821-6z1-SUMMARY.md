### WR-01 — search box stale after first keystroke (checklist item 1, highest priority)

**Root cause:** `NavRail.qml`'s search `TextField` was `text: root.sState.searchText` PLUS a manual `onTextChanged` write-back — a one-way binding plus write-back combo. Per QML semantics, `TextInput`'s own internal `setText()` on the user's first keystroke is itself a property write, which destroys any declarative binding currently on that property. From that point on the field's displayed text was a plain unbound property, never tracking `sState.searchText` again — so after clicking a search result (`selectSearchResult()` clears `searchText` to close the result list), the box kept showing the stale query even though the rail had already reverted to the page list.

**Fix:** Removed the `text:` binding; `onTextChanged` still propagates typing up to `sState` as before, and a new `Connections { target: root.sState; function onSearchTextChanged() { ... } }` block propagates back down whenever `searchText` changes for any other reason. The `!==` guard makes both directions idempotent (no ping-pong).

**Verified:** Shell log clean of resolution/incubation errors across a restart and full IPC deep-link walk (the `Connections` block is syntactically valid QML — a typo here would have thrown at construction). The click-driven clear path itself (type + click a result) still needs the operator's own hands — no synthetic mouse click exists on this host, exactly as Task 15 already names for checklist item 1.

Commit: `29be657e`

### WR-03 — registry index-lock checked by length only, not identity

**Root cause:** `PageCompRegistry.qml`'s own header calls the `PageRegistry.pages[]`/`PageCompRegistry.comps[]` index-lock load-bearing, but `Component.onCompleted` only asserted `comps.length === PageRegistry.pages.length` — a same-length REORDER of either array would pass silently. `settings-index-check` derived its own page mapping solely from `PageCompRegistry.qml` and never read `PageRegistry.qml` at all, so it could not catch a cross-registry ordering drift either — a different invariant from the one the verifier already proved the gate enforces (RowIndex/page-row completeness via the NetworkPage falsification test).

**Fix:** `PageCompRegistry.qml` gained a parallel `compSlugs` array (one string per `comps[]` entry, same order) and a per-index identity assertion against `PageRegistry.pages[i].slug`. `settings-index-check` gained **CHECK E**, independently reading both files' own ordered slug data and asserting element-for-element equality, named by index on mismatch.

**Falsification proven** (per this module's own established practice — Task 3 did the same for CHECK A-D): swapped two entries in `compSlugs` (same length) → gate FAILed, naming both mismatched indices (2 and 3) → reverted → gate PASSed again. `settings-index-check` now reports **100/100** (up from 99/99).

Commit: `1674cfed`

### WR-05 — `Prefs.setValue()` had no value-shape validation

**Root cause:** `setValue()` validated the key against the closed allowlist but never checked the VALUE's own type — that guard existed only on the read side (`getValue()`'s `typeof v !== typeof def` check). A bad IPC call (`qs ipc call prefs set osd.hideDelayMs abc`) coerced to a string and was accepted and persisted, returning `true` and misrepresenting the write as valid; the junk value then sat permanently in `prefs.json` with no way for the operator to notice (never read back wrong, since `getValue()`'s guard masks it forever).

**Fix:** `setValue()` now reuses the exact same `typeof value !== typeof root._defaults[path]` check, refusing with `console.warn` + `return false` — mirroring the existing unknown-key refusal immediately above it.

**Live-verified:** `qs ipc call prefs set notifs.historyCap abc` → `false`, readback unchanged (`100`); `qs ipc call prefs set notifs.historyCap 42` → `true`, readback `42`; restored to `100`, confirmed. Log shows the new warning verbatim: `Prefs: refusing to set notifs.historyCap — expected number, got string ("abc")`.

Commit: `8d7145e7`

Commit: `741d8ad4`
