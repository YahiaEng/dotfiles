## Summary

This diff expands the settings window into a ten-page control panel and adds
non-interactive `--set`/`look`/`devices`/`device` surfaces to five shell
scripts. The security-sensitive paths singled out in the review brief were
traced in full and hold up:

- Every `Process.command` in every new page is a fixed-argv array; no
  `bash -c` string concatenation was found anywhere in the diff (checked
  WallpaperPage, AppearancePage, DisplayPage, InputPage, WindowManagerPage,
  SessionPage against their target scripts).
- `hypr-overrides.sh`'s VALIDATE → APPLY LIVE → VERIFY → PERSIST ordering is
  intact on all five subcommands (`monitor`, `input`, `look`, `devices`,
  `device`), including the new `look`/`device` paths — every field is
  bounds/shape-checked, verified against `hyprctl -j` (never the `ok`
  reply), and only persisted after live verification succeeds.
- The `gaps_in`/`gaps_out` field-name bug class (`.css` 4-tuple vs `.int`)
  that already shipped once on this surface does **not** recur: both the
  shell script's `_first_css_token()` and `WindowManagerPage.qml`'s
  `_firstCssToken()` correctly parse the `.css` field, while every other
  boolean/int/float field consistently uses `.bool`/`.int`/`.float`. No `//`
  jq default swallowing a legitimate `false` was found anywhere in the diff.
- The four picker scripts' `--set` paths all re-validate the caller's
  argument against a freshly-enumerated real set (exact string match, never
  a regex/prefix check) before doing anything with it.

Seven residual issues were found, all in the newer QML-side feature
surfaces (search, per-index page coupling, the Prefs store, and the
hand-rolled slider) rather than in the shell-script security boundary.
None are data-loss or security-severity — hence zero Critical findings —
but two (the search-box desync and the keyboard-activation gap) are
user-visible regressions in this diff's own new features.

## Warnings

### WR-01: Search box does not visually clear after selecting a result

**File:** `quickshell/.config/quickshell/modules/settings/NavRail.qml:49-53`
**Issue:** The search `TextField` is wired as
```qml
text: root.sState.searchText
onTextChanged: root.sState.searchText = text
```
This is a one-way QML property binding (`text:`) combined with a manual
write-back (`onTextChanged`). Per standard QML binding semantics, the first
time the user types a character, `TextInput` internally calls its own
`setText()`, which is a property **write** — and any write to a property
that currently holds a declarative binding destroys that binding. From that
point on, `searchField.text` is a plain, unbound property; it no longer
tracks `sState.searchText`.

`SettingsState.selectSearchResult()` (called when a search result is
clicked) does `root.searchText = ""` to close the result list and land on
the target page — this write correctly propagates to every other consumer
of `sState.searchText` (`pageColumn.visible`, `flick.contentHeight`, the
search-results Column), because those are genuine live bindings on
`sState.searchText` directly. But the TextField's own displayed text was
never rebound after the user's first keystroke, so it keeps showing the
stale typed query even though the rail has already reverted to the normal
page list. The user sees a search box with old text sitting over a
non-search view.

**Fix:** Explicitly re-sync the field whenever the backing state changes
externally, e.g.:
```qml
Connections {
    target: root.sState
    function onSearchTextChanged() {
        if (searchField.text !== root.sState.searchText)
            searchField.text = root.sState.searchText;
    }
}
```

### WR-02: Two-pane keyboard focus draws a ring but wires no activation to any row

**File:** `quickshell/.config/quickshell/modules/settings/Settings.qml:153-166`, `quickshell/.config/quickshell/modules/settings/Pages.qml:57-174`
**Issue:** `Settings.qml`'s `Keys.onUpPressed`/`onDownPressed` move
`contentRowIdx` between rows, and `Keys.onLeftPressed`/`onRightPressed` move
focus between the rail and the content pane. `Pages.qml._applyRowFocusVisual()`
only toggles each row's `rowFocused` boolean (a visual ring — see
`ToggleRow.qml:83-90`, `SliderRow.qml:39-43`, `NavRow.qml:18-23`). No row
type declares a `Keys.onReturnPressed`/`onSpacePressed` handler, and no row
ever receives real QML `activeFocus` (`rowFocused` is a plain externally-set
property, not `Item.focus`) — confirmed against `ToggleRow.qml` (toggling
only happens via its `switchPill`'s own `MouseArea.onClicked`), `NavRow.qml`
(navigation only via `hoverArea.onClicked`), and the new `SliderRow.qml`
(value changes only via `dragArea`'s mouse handlers). A keyboard-only user
can move the ring onto any row but has no way to actually change that row's
value or activate a `NavRow`.

This diff's own new search-jump feature
(`Pages.qml:_swapTo()`, lines 143-174) makes this more visible: typing a
query and pressing Enter/clicking a result lands keyboard focus directly on
the matched row (a `SliderRow`, `ToggleRow`, etc.), advertising "you found
it, keyboard nav works" — but the user still cannot act on it without
reaching for the mouse.

**Fix:** Give each row type a minimal keyboard activation path — e.g. a
shared `Keys.onReturnPressed`/`Keys.onSpacePressed` dispatched from
`Settings.qml`'s `escCatcher` to whichever row currently holds
`contentFocused`/`contentRowIdx` (`toggled(!checked)` for ToggleRow,
`activated()` for NavRow, `moved(value ± stepSize)` for SliderRow on
Left/Right once inside a row). At minimum, document this as a known
limitation if left for a follow-up task.

### WR-03: Page-registry index coupling is checked by length only, not by identity

**File:** `quickshell/.config/quickshell/modules/settings/PageCompRegistry.qml:75-78`, `quickshell/.config/quickshell/modules/settings/pages... (settings-index-check gate)`
**Issue:** `PageCompRegistry.qml`'s own header states "Index N here is the
page rendered for PageRegistry.pages[N] — the two lists MUST stay the same
length and order; a mismatch renders the wrong page with no error," and the
`Component.onCompleted` check that follows only verifies
`comps.length === PageRegistry.pages.length`. It does **not** verify that
`comps[i]` actually corresponds to `pages[i]` (e.g. by slug or label) — a
future edit that reorders one list but not the other (same length) passes
this check silently and reproduces exactly the failure mode the comment
warns about. Separately, `settings-index-check` (the gate meant to keep
`RowIndex.qml` and the page files in step) derives its own `pageIdx -> file`
mapping directly from `PageCompRegistry.qml`'s `comps:` array — it never
reads `PageRegistry.qml` at all, so it cannot detect a `PageRegistry`
vs. `PageCompRegistry` ordering drift either. Today the two lists are
correctly ordered (verified by inspection and by running the gate against
the deployed tree — 99/99 checks pass), but no automated check actually
enforces the one invariant both files' own comments call load-bearing.
**Fix:** Key each `PageCompRegistry.comps` entry (and/or `PageRegistry.pages`
entry) with an explicit `slug`, and assert `comps[i].slug === pages[i].slug`
in the `Component.onCompleted` block instead of a bare length comparison.

### WR-04: `hypr-overrides.sh` documents a reset-to-default QML affordance that was never built

**File:** `hypr/.config/hypr/scripts/hypr-overrides.sh:711-717`, `quickshell/.config/quickshell/modules/settings/pages/InputPage.qml`
**Issue:** The `cmd_device` scroll-factor comment states: "the `-1 = inherit
global` sentinel is NOT writable back through this script. A settings row's
own 'reset to default' must write the current GLOBAL `input:scroll_factor`
value instead (RESEARCH.md §5.3) — that substitution happens at the QML
call site (Task 7), not here." `InputPage.qml` (this diff's own Task 7
deliverable) implements the per-device scroll-factor `SliderRow` with no
reset affordance at all (`grep -n "reset" InputPage.qml` — no hits). The
comment describes a feature that does not exist in the shipped code, which
will mislead a future reader trying to reconstruct the full per-device
scroll-factor contract from the script's own header.
**Fix:** Either add the described reset control to `InputPage.qml`, or
correct the comment to state plainly that no reset-to-default UI exists yet.

### WR-05: `Prefs.setValue()` has no value-shape validation, only a key allowlist

**File:** `quickshell/.config/quickshell/modules/Prefs.qml:193-205`, `quickshell/.config/quickshell/shell.qml:289-326`
**Issue:** `setValue(path, value)` checks `path` against `_allowedKeys` and
that the store has finished its initial load, then writes `value` verbatim
— it never checks `typeof value` against `_defaults[path]`'s type (that
guard exists only on the **read** side, in `getValue()`). The new `prefs`
`IpcHandler` (`shell.qml`) exposes `set(key, value)` to any local IPC
caller, coercing the string argument via a small heuristic
(`_coerce()`) and passing the coerced result straight to `setValue()`. A
call like `qs ipc call prefs set osd.hideDelayMs abc` coerces to the string
`"abc"` and `setValue()` happily accepts and persists it — `setValue()`
returns `true` (no error surfaced to the caller). `getValue()`'s own
`typeof v !== typeof def` guard means the wrong-typed value is never
actually *read back* incorrectly (it silently falls back to the numeric
default every time), so this is not currently exploitable into a visible
bug — but the junk value is now permanently written into
`~/.local/state/quickshell/prefs.json` with no way for the operator to
notice or clean it up, and `setValue()`'s `true` return misrepresents the
write as fully valid.
**Fix:** Have `setValue()` reuse the same `typeof value !== typeof
root._defaults[path]` check `getValue()` already performs, refuse and
`console.warn` + return `false` on a mismatch (mirroring the existing
unknown-key refusal), so a bad IPC `set()` call surfaces the same way a bad
key does.

### IN-01: SliderRow's click/drag hit-test uses a different value↔position mapping than the rendered handle

**File:** `quickshell/.config/quickshell/modules/settings/common/SliderRow.qml:120,146,162-171`
**Issue:** The visible handle is positioned at
`track.ratio * (track.width - handle.width)` (inset by the handle's own
18px so it never overflows the track), but `dragArea._emitFromX()` maps a
click/drag `x` back to a value via `r = x / track.width` — the FULL track
width, with no equivalent inset. The two mappings agree exactly at the
extremes (r=0 and r=1) but diverge by up to ~9px in between, so clicking
precisely on the visual center of the handle when it sits mid-track does
not reproduce the value the handle is currently displaying. This is
self-correcting under continuous dragging (the cursor is tracked 1:1
regardless), so it is a minor precision/hit-test quirk rather than a
functional defect.
**Fix:** Subtract `handle.width` from the denominator the same way the
`ratio` binding does: `r = Math.max(0, Math.min(1, (x - handle.width / 2) / (track.width - handle.width)))`, or accept the current behaviour as intentional (it matches "QQC2 Slider's own click-to-position convention" per the file's own comment) and note the tradeoff explicitly.

### IN-02: WindowManagerPage.qml repeats twelve near-identical `Process` blocks

**File:** `quickshell/.config/quickshell/modules/settings/pages/WindowManagerPage.qml:137-278`
**Issue:** Each of the twelve `hyprctl getoption ... -j` reads
(`gapsInProc`, `gapsOutProc`, `gapsWorkspacesProc`, `borderSizeProc`,
`roundingProc`, `blurEnabledProc`, `blurSizeProc`, `blurPassesProc`,
`inactiveOpacityProc`, `shadowEnabledProc`, `wbfProc`, `awcProc`) is a
hand-copied `Process` + `StdioCollector` + `onExited` +
`Component.onCompleted` block differing only in the option key, the parse
expression (`.css`/`.int`/`.float`/`.bool`), and the target property. This
is a large, mechanically-duplicated surface that a small reusable
`GetOptionProc`-style component (option key, parser kind, target property
as declared parameters) would collapse to roughly a fifth of the line
count, reducing the chance a future field addition copies the wrong
`.css`/`.int`/`.bool` parser by mistake.
**Fix:** Optional refactor — extract a small reusable component/JS-array
loop; not required for correctness, since every existing instance was
independently verified correct.
