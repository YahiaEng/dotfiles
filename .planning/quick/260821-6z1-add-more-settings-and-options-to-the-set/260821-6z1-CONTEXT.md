# Quick Task 260821-6z1: add more settings and options to the settings window, making it a complete control panel - Context

**Gathered:** 2026-08-21
**Status:** Ready for planning

<domain>
## Task Boundary

Expand the in-shell Quickshell settings window (`quickshell/.config/quickshell/modules/settings/`)
from its current 4 pages / ~19 controls into a complete desktop control panel.

**Measured starting point** (read from the tree during discussion, not assumed):

| Page | Controls today |
|---|---|
| Appearance | Theme (SelectRow) · Wallpaper / Icon theme / Font (NavRow → external pickers) · Bar orientation |
| Audio & connectivity | Audio / Wi-Fi / Bluetooth — all three NavRow → existing in-shell panels |
| Display & input | per-monitor Resolution+refresh, Scale · Keyboard layout · Follow mouse · Pointer sensitivity · Natural scroll · Open nwg-displays |
| Shell behaviour | Motion preset · Do not disturb · 5 idle/lock timings · Open in editor |

Supporting structure that already exists and must be reused, not replaced:
- `PageRegistry.qml` (ordered `{label, icon, description, category}` metadata) and
  `PageCompRegistry.qml` (parallel `list<Component>`). **Index N in one must match index N
  in the other** — a mismatch renders the wrong page with no error.
- `NavRail.qml` — already a scrollable `Repeater` with category grouping expressed as
  corner radii (`isCategoryStart`/`isCategoryEnd` compare `category` to neighbours), so
  adding pages is cheap and needs no new nav machinery.
- `common/` row primitives: `NavRow`, `SelectRow`, `SliderRow`, `ToggleRow`,
  `SettingsSection`, `PageBase`. New controls should compose these, not invent new ones.
- `hypr-overrides.sh` — the compositor write path. Owns
  VALIDATE (closed allowlist) → APPLY LIVE (`hyprctl eval`) → VERIFY (`hyprctl -j`,
  never the `ok` reply) → PERSIST (atomic write). Currently accepts only
  `monitor` and `input` subcommands.
- `idle-overrides.sh` — the hypridle write path (idle/lock timings).

**Out of the box today but NOT reachable from the window** (candidate material):
`gaming-mode-toggle.sh`, `bar-visibility.sh`, `wallpaper-visibility.sh`, `record-toggle.sh`,
`fastfetch-logo-picker.sh` (F-06), per-device input (F-03), settings search (F-01),
and every shell-internal knob (notification timeout/position/history, OSD duration,
dashboard panels, weather/news source) — none of which has any persistence store at all.

</domain>

<decisions>
## Implementation Decisions

### Domains to cover — ALL FOUR bundles, in this task

Operator selected every bundle. Scope is deliberately large; this is not to be
silently narrowed.

1. **Compositor look & feel** — gaps, rounding, border size/colour, blur,
   animation speed, workspace behaviour. Requires extending `hypr-overrides.sh`'s
   closed allowlist past `monitor`/`input`.
2. **Shell internals** — bar auto-hide + which capsules show, notification
   timeout / position / history limit, OSD duration / position, dashboard panel
   toggles, weather + news source.
3. **System & session** — gaming mode, wallpaper visibility, screen-recording
   defaults, power-menu behaviour, fastfetch logo (F-06), autostart/service status.
   Mostly wiring existing scripts to rows.
4. **Deepen existing pages** — per-device keyboard/mouse (F-03), inline audio
   mixer instead of nav-out, wallpaper/icon/font pickers inline instead of
   launching walker, monitor position + primary.

### Persistence — HYBRID, two stores each owning what it can safely own

- **Shell-internal knobs → a new `Prefs` singleton** over a JSON `FileView`
  (Caelestia's `Config` pattern; the repo's reference-shell default). This is the
  store that does not exist today and must be built.
- **Compositor knobs → extend `hypr-overrides.sh`'s allowlist.** They MUST keep
  the existing validate → apply-live → verify → persist chain. A value never
  proven live must not reach the file the compositor `require`s at boot — that
  guard is what stops a bad value bricking the session into blank-at-every-boot.
  Do NOT move that validation into QML.
- Existing per-feature state files (`bar-orientation`, `motion.json`,
  `idle-overrides.conf`, `overrides.json`, `font-choice`, `icon-theme`) stay where
  they are. Do not migrate working settings into `Prefs` as part of this task.

### Navigation — more nav pages + a search bar

Split the nav rail into roughly eight entries, keeping the existing `category`
grouping so the corner-radius grouping still reads. Add F-01's fuzzy search over
every row — with ~60 controls, search is what makes the panel findable.

Operator-selected layout (their own words, via preview):

The eight page names above are the operator's selected shape, not a suggestion to
re-derive. `category` keys are the deep-link keys `shell.qml`'s
`openSettingsPage(name)` resolves against — existing keys
(`appearance`/`connectivity`/`display`/`shell`) must keep resolving after the split.

### Sequencing — foundation first, then all four bundles

One plan, ordered. The **Prefs singleton, the nav split, and the search bar land and
are verified FIRST** — everything else hangs off them. The four bundles then fill in
on top of proven scaffolding. Every bundle still ships in this task; this is ordering,
not scope reduction. Rationale the operator endorsed: the previous settings task took
nine post-plan fix waves, and discovering a Prefs-store design flaw after six pages
already depend on it is exactly that failure mode.

### Claude's Discretion

- Exact per-page allocation of the ~40-60 controls across the eight pages.
- Row-primitive choices (`SelectRow` vs `SliderRow` vs `ToggleRow`) per control.
- Prefs JSON schema shape and file location under `~/.local/state/`.
- Search implementation (fuzzy vs substring), as long as it covers every row on
  every page, not just page titles.
- Whether `PageRegistry`/`PageCompRegistry` gain a per-row search index or the
  search walks live page instances.

<specifics>
## Specific Ideas

**Load-bearing lessons from quick task 260820-sqd, which built this same surface.
Read `.planning/quick/260820-sqd-build-an-in-shell-qml-settings-menu-cont/260820-sqd-SUMMARY.md` "Post-Plan Live-Pass Saga"
before touching this code.** Both named follow-ups bite exactly this task:

1. **`colour-lint` (GATE-04) cannot see default-styled QQC2 popups.** The gate stayed
   green while every dropdown in the window shipped with the system palette instead of
   `Colours.qml`. Any new `SelectRow`/`Menu`/`ComboBox` must be explicitly styled from
   `Colours.qml`; the gate passing is not evidence.
2. **The restart-then-edit deployment trap.** A quickshell restarted BEFORE the final
   edit serves stale compiled pages. Incubated settings pages need a FULL quickshell
   restart AFTER the last edit — hot-reload is not trustworthy for this surface.
3. **Confirm WHICH element a visual report names with a screenshot BEFORE fixing.**
   Three of the nine fix waves fixed the popup while the operator meant the page rows.
4. **Verify visuals by pixel-sampling, never by role name.** Four controls shipped
   surfaceVariant-on-surfaceVariant — invisible by construction, with correct-looking
   role names. `grim -g` REGION capture of the settings toplevel is PROVEN SAFE on this
   host (13+ captures); full-screen `grim` is NOT (it SIGSEGVs the compositor).
5. **Drive the real UI path with the operator's real values** — never synthetic
   injections below the UI layer.
6. **When agent trials pass while the operator fails, STOP and instrument.** Both
   endgame diagnoses last time came from the operator's own trace, not any synthetic trial.

Deferred-feature IDs from that task, now in scope: **F-01** (settings fuzzy search),
**F-03** (per-device keyboard/mouse — note `hyprctl devices -j` reports 7 keyboards and
6 mice on this host, most of them phantom sub-devices of the same physical hardware, so
the list needs filtering), **F-06** (fastfetch logo picker). **F-04** (drill-down
sub-pages) was NOT selected — the operator chose flat pages + search instead.

Other hard constraints already established in this repo:
- `hyprctl keyword` is a silent no-op under this repo's Lua config manager. Every
  compositor write is `hyprctl eval`.
- `colour-lint` rejects hardcoded colours in QML — read from `Colours.qml`.
- Motion goes through `Motion.qml`; `motion-lint` gates it.
- This host has no backlight-class device, so brightness paths cannot be exercised here.

</specifics>
