## The blind spot, demonstrated

Same inputs — a kernel with no NVIDIA module and zero DKMS modules registered
(the prebuilt-package configuration):

```
--- OLD (dkms-verify) ---
dkms-verify: no DKMS modules registered — nothing to check.
OLD exit=0

--- NEW (kernel-module-verify) ---
  kernel 9.9.9-arch1-1  ←  nvidia module missing entirely
      sudo pacman -S nvidia-open
NEW exit=1
```

The suggested package is derived from the kernel's own `pkgbase`
(`linux` → `nvidia-open`, `linux-lts` → `nvidia-open-lts`).

## Design

Two independent passes:

1. **DKMS registration** — unchanged from 260728-3na. Still enumerates kernels by
   `pkgbase`, still matches `dkms status` **output text** rather than exit code
   (dkms 3.4.1 exits 0 and prints `<mod>: added` for a never-built kernel), still
   honours `BUILD_EXCLUSIVE_KERNEL`.
2. **Driver presence, source-agnostic** — new. `modinfo -k <kver> -F filename nvidia`
   resolves `updates/dkms/` and `extramodules/` transparently, so it is indifferent to
   how the module got there. Gated on `nvidia-utils` being installed, so it stays
   correct on non-NVIDIA machines.

Pass 2 separates two real failures with different remedies: no `.ko` anywhere
(install it) versus `.ko` present but absent from `modules.dep` (`depmod`). A module
missing from the index is not loadable by udev, so a stale index is a genuine failure,
not cosmetic.

The hook deliberately drops `Depends = dkms` — pass 2 must run on systems with no DKMS
installed, which is exactly the configuration it protects.

## Known, accepted

On a DKMS system a genuinely missing module is reported twice — once by each pass, with
the same remedy. The passes are independent checks answering different questions
(registered vs. present), so the duplication is left rather than special-cased.
