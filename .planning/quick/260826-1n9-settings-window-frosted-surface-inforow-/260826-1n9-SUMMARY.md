## Decisions Made

- **`qml-import-check`'s resolution model derives everything from the installed modules' own manifests, never a hand-written allowlist** — a module's resolvable type set is the union of its `*.qmltypes` exports AND its qmldir's own directly-declared types (needed for QML-composed types like Quickshell.Io's `FileView` and QtQuick.Controls.Basic's `TextField`, both declared only via a qmldir `TypeName Version File.qml` line, never a C++ export), reached by recursively following each module's own `import`/`default import`/`optional import` qmldir lines (never `depends`, which is documented as build-time-only). This was necessary engineering discovered empirically while measuring the baseline (see Deviations below) — the plan specified the resolution model conceptually but the two-source-per-module union and the qmldir-vs-depends distinction were measured, not assumed.
- **Rule 2 (auto-add missing critical functionality): NavRow and SelectRow both gained a defaulted `icon` property**, not listed in the plan's own `files_modified` frontmatter. The plan's own settled decisions (D-5 — "prominence via the download glyph… not by leaving the row system" for Updates' `NavRow`; Task 7's "Weather location mode — icon `cloud`" for a `SelectRow`) require a real, rendered glyph on those specific row types, and neither primitive had an icon slot before this task — qmllint rejects assigning an undeclared property, so this was necessary, not optional. Both additions use the IDENTICAL defaulted-empty-string pattern D-2 established for `InfoRow.icon`: every existing call site (10 `NavRow`, 39 `SelectRow`) renders byte-identically since none of them set `icon` today.
- **The weather-city resolving/resolved state on the settings page is derived from a Prefs-only before/after snapshot, not a live signal from `WeatherBackend`.** The settings window has no direct handle to the shell-root `WeatherBackend` instance (unlike `audioBackend`/`wifiBackend`/`bluetoothBackend`, it was never relayed through `SettingsState`), so Prefs (a shared singleton both files read) is the only channel available. Comparing the CURRENT `region.weatherLat`/`Lon` against a snapshot taken at commit time — rather than against a fixed sentinel like `0` — is what keeps this correct even though `0,0` is itself a real, legitimate coordinate pair.
- **`AppsPage.qml`'s dead `_appModel` property (`value: e.id`) was removed**, not just left alongside the new filtered models — it had zero remaining consumers once both `SelectRow`s moved to `_terminalModel`/`_audioModel`, and its literal presence would have failed the plan's own `value: e.id` absence check.

## Issues Encountered

- **Pre-existing gate imprecision, NOT a regression:** the URL-uniqueness verify check in Task 7 (`grep -ohE 'https://[a-z0-9.]+' quickshell/.config/quickshell/modules/dashboard/GeocodeBackend.qml | sort -u | wc -l -eq 1`) reports **2**, not 1. - **`\-\>` in the Task 5 verify block does not match literal `"->"` text** — in GNU `grep -E`, `\>` is a word-boundary anchor, not a literal `>`, so the check's own regex can never match the `"->"` text it appears intended to find, regardless of what the file contains. Confirmed directly: `echo 'a -> b' | grep -cE '\-\>'` returns 0, while `grep -cE -- '->'` (a correct literal match) returns 1 against the same input. The file DOES contain `"->"` at three points (the parse regex itself, its doc comment, and the display text) — verified by direct `grep -n -- '->'`. Not wrapped in a `test -eq` assertion in the plan, so it never gated pass/fail; noted here as a measured quirk, not a failure.
