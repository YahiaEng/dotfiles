# Quick Task 260728-3na — DKMS verification hook

## Why

On 2026-07-28 a `pacman -Syu` installed kernel 7.1.5-arch1-1 but the DKMS alpm hook
never built `nvidia-open-dkms` for it. With no driver claiming the RTX 3070, Hyprland
rendered on **simpledrm** (the EFI framebuffer) and the kernel oopsed in
`drm_fb_memcpy` → black screen after SDDM login, no `DP-1`, wrong resolution.

Two defects made this possible, and `install.sh` currently reproduces both on a fresh
machine:

1. `kernel-modules-hook` (install.sh:247) preserves each running kernel's module tree
   across upgrades but its reaper, `linux-modules-cleanup.service`, ships **disabled**.
   Nothing ever collected them — 13 orphaned trees, 6.8 GB.
2. `/usr/share/libalpm/scripts/dkms` derives its build list from `all_kver()`, which
   globs every `/usr/lib/modules/*/build/`. Because the orphans were *complete* trees
   (headers included) none were filtered out, so the list grew from 1 kernel to 14,
   iterated in arbitrary bash hash order with no priority for the live kernel. The run
   died after three dead-kernel builds, never reaching 7.1.5.

Nothing in the pipeline noticed. The failure surfaced only at the next boot.

## Goal

A fresh install can never again reach a reboot with an installed kernel that is missing
its DKMS modules — and if it somehow does, the operator is told loudly **before** the
reboot, with the exact remedy.

## Tasks

### Task 1 — `system/usr/local/bin/dkms-verify`

**Files:** `system/usr/local/bin/dkms-verify` (new)

**Action:** POSIX-ish bash script that cross-checks installed kernels against registered
DKMS modules.

- Enumerate kernels by their `pkgbase` marker file (`/usr/lib/modules/*/pkgbase`), NOT
  by directory glob. Verified on this system: only the real, package-owned kernel tree
  carries `pkgbase`; the 13 orphans did not. This is what makes the check immune to the
  orphan-accumulation defect that caused the incident.
- Enumerate DKMS modules by parsing `PACKAGE_NAME` / `PACKAGE_VERSION` out of
  `/usr/src/*/dkms.conf` with `sed`. Deliberately **not** `source`d — these files
  contain command substitution (nvidia's `MAKE[0]` runs `` `nproc` ``) and a
  PostTransaction hook should not execute them.
- Honour `BUILD_EXCLUSIVE_KERNEL` the same way the upstream alpm hook does, so a module
  that legitimately excludes a kernel is not reported as missing.
- **Match on output text, not exit status.** Verified: `dkms status -m nvidia -v <ver>
  -k <nonexistent>` exits **0** and prints `nvidia/<ver>: added`. Keying off `$?` would
  silently pass and reproduce the exact bug being guarded against. Require a line
  matching `^<name>/<ver>, <kver>, .*: installed`.
- Collect every miss, then print a loud banner naming each kernel + module and the exact
  `sudo dkms install <name>/<ver> -k <kver>` remedy. Exit 1.
- No misses → one quiet confirmation line, exit 0.

**Verify:** Runs clean against current state (7.1.5-arch1-1 + nvidia/610.43.03).
Detects a synthetic miss when pointed at a fabricated kernel tree.

**Done:** Script exists, executable, both cases behave as specified.

### Task 2 — `system/etc/pacman.d/hooks/99-dkms-verify.hook`

**Files:** `system/etc/pacman.d/hooks/99-dkms-verify.hook` (new)

**Action:** PostTransaction hook, `Type = Path`, targets `usr/lib/modules/*/modules.order`
and `usr/src/*/dkms.conf` — the same triggers the upstream install hook uses, so it fires
on exactly the transactions that can break this. `99-` prefix sorts after `70-dkms-install`.
`Depends = dkms`.

**Verify:** `pacman --print` style dry inspection; hook file parses and sorts last.

**Done:** Hook file exists with correct trigger and ordering.

### Task 3 — Wire into `install.sh`

**Files:** `install.sh`

**Action:** In `section_hardware()`, after the NVIDIA block:

- `sudo install -Dm755` the verify script to `/usr/local/bin/dkms-verify` and
  `sudo install -Dm644` the hook to `/etc/pacman.d/hooks/99-dkms-verify.hook`.
- `sudo systemctl enable linux-modules-cleanup.service` — guarded on the unit existing,
  non-fatal, matching the existing swayosd/ollama precedent at install.sh:422/436.
  `enable` only, not `--now`: the reaper deletes module trees for non-running kernels and
  should do that at boot, not mid-install.

Both live outside `$HOME`, so they are **not** stow-managed — `stow.sh`'s `PACKAGES`
array is explicit, so the new top-level `system/` directory is never stowed.

**Verify:** `bash -n install.sh`; new block sits inside `section_hardware`.

**Done:** install.sh places both files and enables the reaper on a fresh machine.

## must_haves

**Truths:**
- Kernel enumeration uses `pkgbase`, never a directory glob.
- Missing-module detection matches `dkms status` output text, never its exit code.
- The hook sorts strictly after `70-dkms-install.hook`.
- Nothing owned by pacman is modified.

**Artifacts:**
- `system/usr/local/bin/dkms-verify`
- `system/etc/pacman.d/hooks/99-dkms-verify.hook`
- `install.sh` wiring in `section_hardware()`

**Key links:**
- `/usr/share/libalpm/scripts/dkms` — upstream logic being backstopped
- `install.sh:247` — `kernel-modules-hook` in AUR_PKGS
- `install.sh:422` — `sudo systemctl enable` precedent

## Out of scope

- `NVIDIA_PKGS` lists `nvidia-dkms` (proprietary) while this machine runs
  `nvidia-open-dkms`. Real discrepancy, separate task — flagged, not fixed here.
- Hyprland `.conf` → 0.57 format migration.
