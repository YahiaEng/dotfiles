## Decisions this plan makes, and why

**D-1 — Sub-page files stay flat in `pages/`.** Caelestia nests them (`pages/apps/`,
`pages/bluetooth/`) because they have ~30 page files; we will have 20. Flat keeps
`settings-index-check`'s `$PAGES_DIR/$name.qml` mapping working unchanged and avoids two new
`qmldir` manifests and two new imports. Names carry the grouping instead: `AllAppsPage.qml`,
`AppInfoPage.qml`, `BtDeviceInfoPage.qml`.

**D-2 — `comps[i]` becomes a `StackPage` only for pages that have sub-pages.** The other
twelve stay bare page Components. `compSlugs` stays exactly 1:1 with registered pages, so
CHECK C/D/E need no change at all.

**D-3 — `StackPage` proxies `flickable`.** `readonly property var flickable: currentItem ? currentItem.flickable : null`
means `Pages.qml:_scrollRowIntoView`'s `root.currentItem.flickable` keeps working for both
shapes with zero edits to that function.

**D-4 — Sub-page rows ARE indexed, and the gate is extended to prove it.** This is the honest
answer to the coordinator's question, and it is not free: `settings-index-check` derives its
pageIdx→file map from `PageCompRegistry.qml` by taking the *first* `/[A-Za-z_][A-Za-z0-9_]*Page/`
match after each `property Component <name>:` line. With a `StackPage` wrapper that first match
becomes the literal `StackPage`, the gate looks for `pages/StackPage.qml`, and CHECK A fails
with "mapped file does not exist". So the gate must change regardless — leaving sub-page rows
unindexed would *not* even keep it passing. The smallest change that keeps every existing check
meaningful:

- `RowIndex.rows` gains an **optional** `subPageIdx` field. Absent means 0, the root page — so
  **all 113 existing entries need no edit**, and their literal text `pageIdx: N, section:` stays
  the exact grep key CHECK A already uses.
- The comp→file parser collects *every* `*Page` identifier inside a comp's declaration in
  order, skipping the literal `StackPage`: index 0 is the root file, 1..N the sub-pages.
- **CHECK A** is keyed on the `(pageIdx, subPageIdx)` pair: root rows counted with
  `grep -c "pageIdx: $i, section:"`, sub-page rows with
  `grep -c "pageIdx: $i, subPageIdx: $s, section:"`, each compared against the row-primitive
  count in that pair's mapped file.
- **CHECK B** extracts with `pageIdx: [0-9]+(, subPageIdx: [0-9]+)?, section: "…", label: "…"`
  and greps the label in the pair's mapped file.
- **New CHECK F**: every sub-page component named in `PageCompRegistry.qml` resolves to a file
  that exists in `pages/` and is declared in `pages/qmldir`.
- CHECK C (pageIdx in range), CHECK D (non-zero page floor) and CHECK E (slug order) are
  untouched.

**D-5 — Search deep-links into sub-pages, with one extra optional field.** A row also carries an
optional `jumpSubPageIdx`, defaulting to its `subPageIdx`. It exists because a
selection-dependent sub-page cannot be opened cold: jumping straight to App info with no
`selectedApp` lands on a page Caelestia's own `onAppChanged` immediately auto-closes. So the
App info rows carry `subPageIdx: 2` (which file CHECK A/B grep) and `jumpSubPageIdx: 1` (where
search actually lands — All apps, where the user picks an app). One field, exactly expressing
the difference between "where this row lives" and "how deep you can get without choosing
something first".

**D-6 — Default-app rows: two real controls, two honest InfoRows.** All four of Caelestia's
categories ship, but only Terminal and Audio have measured consumers in this tree (listed
above). File manager already routes through `xdg-open`, and nothing here launches a media
player. Those two ship as `InfoRow`s naming what actually happens, following this window's
established InfoRow-for-a-non-delivery pattern — the same principle the operator applied to the
weather units: a picker that cannot take effect is worse than no picker.

**D-7 — `DefaultRow` maps onto our existing `SelectRow`.** Caelestia's `PopupRow` (an
icon+name+comment list popup) has no equivalent here, and adding one would mean a new
`common/` type that `settings-index-check` does not count as a row primitive. `SelectRow`
already has `model: [{value, display}]`, `currentValue`, `onSelected(value)`, `busy` and
`openMenu()`, and it is counted. Favourites still sort to the top of the model, per the
reference.

**D-8 — Bluetooth uses the mechanism for the device-info sub-page only.** Caelestia has two
(`BtDeviceInfo` at `openSubPage(1)`, `BluetoothPairing` at `openSubPage(2)`). Our existing
Bluetooth surface already does discovery start/stop and pairing **inline**, operator-verified,
and porting their separate pairing sub-page would duplicate a working surface rather than close
a gap. Device info is the genuinely missing level, so that is the one we build.

**D-9 — `StepperRow` is ported; poll intervals are steppers, unit pickers stay `SelectRow`.**
Checked against the vendored source: Caelestia uses `StepperRow` for every polling value
(`ServicesPage.qml:100` media position in ms, `:111` "CPU, memory and GPU update interval
(seconds)", `:121` "How often available networks are rescanned (seconds)"), for all four input
increments and for the visualiser bar count, and reserves `SelectRow` for genuine
pick-from-a-list choices (`:137` lyrics source, `:146` preferred media player). A poll interval
is a continuous numeric value with an increment; rendering it as a fixed menu changes the
interaction, not just the widget. The standing rule is that Caelestia's convention wins, so the
primitive gets ported (Task 5) before the page that consumes it (Task 6). The weather unit
pickers stay `SelectRow` — celsius/fahrenheit and metric/imperial are enumerations, exactly what
the reference uses `SelectRow` for.

**Do not wrap QQC2's `SpinBox`.** The reference's `StepperRow` wraps their own `StyledSpinBox`,
but this tree has a measured reason not to follow that part: `common/SliderRow.qml`'s header
records that the QQC2 `Slider` it used to wrap **rendered nothing at all** — no track, no handle,
not even its own overridden delegates' explicit-pixel Rectangles — on every page that used it,
and it was hand-rolled from plain Rectangles + MouseArea instead, "rather than a THIRD QQC2
interactive primitive risking a THIRD blind spot". A SpinBox would be exactly that third
primitive. Hand-roll the stepper the way `ToggleRow`'s switch pill and `SelectRow`'s dropdown
pill already are.
