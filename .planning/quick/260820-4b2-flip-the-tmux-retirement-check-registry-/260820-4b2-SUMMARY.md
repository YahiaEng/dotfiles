### Deviation from the plan's must_haves — corrected here

The plan asserted `theme-doctor` would "stay 595 passed / 0 failed". It did not stay
595; it is **608**. This is the flip working as designed, not a regression: arming the
tier converts tmux's blocking classes from uncounted `[REPORT]` lines into counted
`[PASS]` checks (+12 — thirteen classes minus the one that legitimately SKIPs). The
count that had to hold was **failed = 0**, and it held. Writing a pass-count into a
must-have when the change's whole purpose is to add checks was a bad criterion; the
falsifiable claim is the failure count.

Host-side state at completion: `pacman -Q tmux` and `pacman -Q tmux-plugin-manager`
both miss, `tmux` is off PATH, no process is running, `~/.local/share/tmux` and
`~/.config/tmux` are absent. Sole residue is the stale socket `/tmp/tmux-1000/default`
from the killed server — cleared on reboot, matches nothing any gate scans.

## Findings worth keeping

**1. Two of STATE.md's carried operator follow-ups were stale, and one was wrong in a
way that would have broken the uninstall.**
`~/.config/tmux` did not exist at all — not a dangling symlink, nothing to `rm -rf`.
And "4 orphaned tpm clones" was not clones: tpm was the pacman package
`tmux-plugin-manager` 3.1.0-1, which **depends on `tmux>=1.9`**. `pacman -Rns tmux`
alone would have failed on the dependency; both packages had to go in one transaction.
A follow-up note carried across sessions describes the host as it was *believed* to be
at write time — re-probe before acting on one.

**2. The gate cannot match its own prose — verified, not assumed.**
This edit adds the literal word `tmux` to a file the tmux scan greps. That is safe only
because `SELF_EXCLUDE = {self_realpath}` (retirement-check:199) drops the script's own
realpath from every `grep_hits` call. Confirmed by reading that line before editing,
since the general failure mode — a banned-identifier gate matching its own comment — is
a known trap in this repo. A note preserving that invariant is now in the header, so the
next person adding a surface does not remove it.

**3. The header comment was stale on a half nobody scoped.**
The task named only the tmux paragraph. `git blame` showed lines 78-87 (eww/wlogout)
came from `3284248e`, 2026-08-11, Phase 18 — and were *also* stale, still asserting
"Every real surface ships `pending` in this phase" and "RETIRE-07 (Phase 20) is where
they flip", both long past. The tmux paragraph cited that text as its precedent
("the same eww/wlogout precedent described above"), so restating one half alone would
have left a comment pointing at a precedent the reader could no longer find. Both were
restated together. Blaming the lines before deciding scope is what surfaced this.

**4. `pending` is a staging state, and the header now says so explicitly.**
The two releases so far had genuinely different triggers — eww/wlogout by a
STALE-GREP-HIT this repo could edit away, tmux by a HOST-PACKAGE reference the repo has
no authority over. The restated comment names both, so the next surface's author can
tell which kind they have.
