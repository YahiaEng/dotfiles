# Context — 260823-65s

Source todo: `.planning/todos/pending/2026-08-23-add-system-tray-capsule-to-the-quickshell-bar.md`

Decisions below were settled by the operator before planning. **They are locked —
do not revisit or re-derive them.** The measured-facts section corrects two
instructions the source todo gets wrong; follow the measurements, not the todo.

## Operator decisions

### D-1 — Overflow: inline up to 3, then a chevron opening a popout

The capsule renders the first **3** tray items inline. Any beyond that collapse
behind a chevron carrying the overflow count (`⌄2`), which opens a popout listing
the remainder with icon + title.

*Why:* bar width stays bounded no matter how many apps launch. This is what both
reference shells do (Caelestia ships "system tray with overflow menu",
`FEATURES.md:37`) and what `FEATURES.md:131` already scoped as the requirement
("Needs `SystemTray` Quickshell API + overflow-menu handling"). Rejected: unbounded
inline (pushes the clock leftward as apps launch) and always-collapsed (costs a
click to reach the Steam close this todo exists to fix).

The popout must reuse the existing `PopoutController.qml` / `SectionPopout.qml`
machinery rather than introducing a second popout mechanism.

### D-2 — Show every tray item regardless of SNI status

`Passive`, `Active` and `NeedsAttention` items all render. `NeedsAttention` gets a
visual accent; `Passive` is **not** hidden and **not** dimmed.

*Why:* the SNI spec says hide `Passive`, but apps set it inconsistently and Steam
is a known offender. Hiding `Passive` risks making Steam vanish from the tray —
which is the exact fault this todo was filed to fix. The retired waybar was
configured to show all items here, so this preserves prior behaviour rather than
changing it.

### D-3 — Placement: own capsule in `zoneEnd`, between mediaConnectivity and clockActions

A new `systemTray` capsule is appended to `BarEntryModel.capsules` **declared
between `mediaConnectivity` and `clockActions`** — declaration order is render
order (`BarEntryModel.qml:224`), so this puts the tray immediately before the
clock. That matches Caelestia's canonical entry order (`… tray, clock,
statusIcons, power`, `FEATURES.md:20`).

Not folded into an existing capsule: tray children are **dynamic** (they come and
go with running apps), so they cannot have static per-entry `bar.entries.*`
toggles the way every existing capsule's children do.

### D-4 — It gets a `bar.capsules.systemTray` toggle

Added to **both** `_allowedKeys` and `_defaults` in `Prefs.qml`, defaulting to
`true`.

*Why this is consistent with the 2026-08-21 retirement of
`bar.capsules.clockActions` / `bar.capsules.system`* (`Prefs.qml:78-81`): those two
parent rows were removed **because all their children already had per-entry
toggles**. Per D-3 the tray's children are dynamic and have no per-entry toggles,
so the parent row is the only way to hide it — the retirement rationale argues
*for* this key, not against it.

## Measured facts — ground truth, verified on this host

Read from `/usr/lib/qt6/qml/Quickshell/Services/SystemTray/quickshell-service-statusnotifier.qmltypes`
(quickshell 0.3.1-1). Not inferred.

`SystemTray` singleton — one property: `items` (`UntypedObjectModel`, readonly).

`SystemTrayItem` properties: `id`, `title`, `status` (`Passive`/`Active`/`NeedsAttention`),
`category` (`Hardware`/`SystemServices`/`ApplicationStatus`/`Communications`),
`icon` (QString), `tooltipTitle`, `tooltipDescription`, `hasMenu`,
`menu` (`DBusMenuHandle`), `onlyMenu`.

`SystemTrayItem` methods: `activate()`, `secondaryActivate()`,
`scroll(delta, horizontal)`, `display(parentWindow, relativeX, relativeY)`.

### CORRECTION 1 — the todo's icon instruction is wrong; do not follow it

The todo says icon resolution "must use the `Quickshell.hasThemeIcon()`-gated chain
(`NotifGroup.qml:133-150`)". **That chain is built for notification `appIcon`
strings**, which are raw theme names or file paths that may not exist.

`SystemTrayItem.icon` is a **resolved image source supplied by Quickshell** (an
`image://` provider URI). Feeding it through `Quickshell.iconPath()` is a category
error. Bind it to the `Image`/`IconImage` source directly, and provide a fallback
only for the genuinely-empty case (`icon === ""`).

If the tray icon renders as a broken-texture glyph during implementation, that is a
real defect to diagnose against the live item — **not** a signal to reinstate the
`hasThemeIcon` chain.

### CORRECTION 2 — there is no right-click method

`SystemTrayItem` exposes **no** `rightClick`/`openMenu` method. The context menu is
opened by calling `item.display(parentWindow, relativeX, relativeY)`; Quickshell
builds the popup from the DBusMenu itself.

Do **not** hand-roll a QML menu tree over the `menu` (`DBusMenuHandle`) property.
The `Quickshell.DBusMenu` import is a *dependency of* the SystemTray module
(declared in its `qmldir`), not a widget toolkit to render manually.

### CORRECTION 3 — `onlyMenu` gates left-click

When `item.onlyMenu` is `true`, the item has no activate action and left-click must
fall through to `display()` rather than calling `activate()` and doing nothing
visible.

## Interaction contract

| Gesture | Behaviour |
|---|---|
| Left click | `item.activate()`, or `item.display(...)` when `item.onlyMenu` is true |
| Right click | `item.display(parentWindow, x, y)` |
| Middle click | `item.secondaryActivate()` |

## Live-state caveat

`busctl --user list` currently shows **no** `StatusNotifierWatcher` on the session
bus — nothing hosts SNI since waybar was retired. So there are **zero tray items to
render until the shell restarts** with this capsule in place and apps re-register.

Consequence for verification: the overflow threshold, icon rendering and all three
click gestures **cannot be statically gated**. They need a shell restart plus a real
tray app. Four tray-capable apps are installed: `steam`, `discord`,
`blueman-applet`, `nm-applet`. Hand the interactive checks to the operator — there
is no input-injection tooling on this host.

## House rules that bind this work

- Colours from `Colours.qml` / `BarRoles.qml` only — `colour-lint` (GATE-04)
  rejects literals.
- Motion through `Motion.qml`'s declared token pairs. Verify each token **resolves**,
  not merely that a token is read — an undeclared singleton property resolves to
  `undefined` and Qt silently substitutes its own 250ms default.
- Read `~/.cache/quickshell.log` after the QML edits; three green lint gates cannot
  see a bad QML import.

## AMENDMENT (post-planning) — D-5: exclude the two applets that duplicate the connections capsule

Added after `260823-65s-PLAN.md` was written. **This amends the plan.** The plan's
objective block claims it "supersedes Phase 18.1 D-15" but engages only D-15's
*conclusion*, never its *reason*. The reason is still true.

### What D-15 actually found

`.planning/milestones/v4.0-REQUIREMENTS.md:20` — requirement QBAR-05:

> **Withdrawn (superseded by 18.1 D-15):** the tray was deliberately dropped in phase
> 18.1 to match Athena, whose own config records removing it because **nm-applet and
> blueman icons duplicated the connections group**; the connections capsule continues
> to surface that state, so the capability is superseded rather than lost.

That finding is still live: `mediaConnectivity` renders `network` and `bluetooth`
entries today (`BarEntryModel.qml`, the `mediaConnectivity` capsule's entry list), two
capsules to the left of where the tray now goes. Both applets are installed on this
host. With D-1's 3 inline slots, they can occupy two of three with redundant icons and
push Steam — the app this todo was filed for — into the overflow popout.

So D-15 was **half right**, and this task reinstates only the half that was genuinely
lost: tray items for apps that have **no other surface in the bar**.

### The decision

Exclude `nm-applet` and `blueman-applet` from the tray model. Every other item renders
per D-1/D-2.

- The exclusion is a **named, commented constant** in the capsule's model, not an
  inline condition. The comment must cite 18.1 D-15 and QBAR-05 by name and state that
  these two are excluded *because the connections capsule already surfaces them* — or
  a later reader deletes it as arbitrary. This is the same failure mode the `qmldir`
  D-15 note was written to prevent.
- Match on the item's `id`, case-insensitively, and tolerate vendor suffixes.

### Unverifiable-by-construction, and it must fail in the safe direction

There is **no `StatusNotifierWatcher` running**, so the exact `id` strings these two
applets register under **cannot be measured before shipping**. Do not write the filter
as though the id strings are known facts.

Design it so a **miss is harmless**: a non-matching item still renders. The failure
mode of an over-narrow match is a duplicated icon (cosmetic, exactly today's status
quo). The failure mode of an over-broad match is a hidden app (severe). **Never widen
the match to a substring so loose it could swallow an unrelated item.**

The operator checklist must add an explicit item: confirm the two applets are absent
from the tray while their icons still show in `mediaConnectivity`. If they still
appear, the id strings differ from the guess — report the real ids rather than
widening the pattern blindly.

### Consequence for the plan's operator checklist

The plan's live-check section nominates `blueman-applet` and `nm-applet` as the
cheapest test apps to launch. **They are now the two filtered items and cannot serve
as the render test.** Use `steam` or `discord` for render, icon, gesture and overflow
checks; keep the applets only as the *exclusion* check described above.

Note the plan's own remark that a menu-only item (`onlyMenu`) was to be exercised via
`blueman-applet` — that gesture still needs a menu-only item to prove it. If neither
Steam nor Discord reports `onlyMenu`, record that path as unproven rather than
claiming it passed.
