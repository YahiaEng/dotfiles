**6. [Rule 1 - Bug, found only after overflow became testable] Popout right-click menu opens then immediately closes**
- **Found during:** Task 3, operator checklist round 6 — right-click on VLC's overflow row (the popout was UNTESTABLE by anyone until this same round's overflow fix made it reachable): "shows the context menu but immediately dismisses it making it impossible to select any action"

Hyprland sees focus leave the grabbed set the instant the menu appears and fires `onCleared -> requestDismiss()`, tearing the popout — and the menu anchored to it — down together

**7. [Rule 1 - Bug, regression introduced by Deviation 6's own fix] Popout right-click menu stopped opening entirely**
- **Found during:** Task 3, operator checklist round 7 — testing Deviation 6's fix (`13961ac2`): "Right click now does not even open the context menu" — worse than the bug Deviation 6 fixed, which at least showed the menu briefly
- **Root cause 1 (coordinator diagnosis by reading, confirmed live before any fix was written):** `barWindow: QsWindow.window` in `TrayCapsule.qml` was written INSIDE `PopoutTrigger { popoutComponent: Component { TrayPopout { ... } } }` — lexically inside the `TrayPopout` object literal that `Component` instantiates. `QsWindow` is an attached property; it resolves against the object literal its syntax is textually written inside, not against whichever `.qml` FILE that syntax happens to live in. **8. [Rule 1 - Bug, residual race exposed by Deviation 7's own fix] Popout right-click menu opened correctly but still closed before a selection could be made**
- **Found during:** Task 3, operator checklist round 8 — re-testing Deviation 7's fix (`992d78c3`): menu appears (YES), positioned sensibly near the chevron (YES), click-outside/left/middle click all unaffected (YES) — but "stays open long enough to pick an action" was NO
- **Root cause (measured before any fix was written, not inferred):** `grep -c HyprlandFocusGrab modules/Bar.qml` returns 0 — the bar window holds no focus grab at all, which is exactly why the inline right-click path has never had any version of this bug. `SectionPopout.qml`'s own `popoutGrab` (`active: pinned`, `onCleared: requestDismiss()`) is real and still fires the instant the menu takes focus, independent of whether `TrayPopout.qml` calls `requestDismiss()` itself. `requestDismiss()` is ASYNCHRONOUS — confirmed directly in `SectionPopout.qml`'s own source: it either starts an exit animation (`exitFade.start()`) or, under reduced motion, emits `dismissFinished()` synchronously; either way the popout's own unmap and grab teardown do not complete on the calling line. Deviation 7's own investigation of removing `requestDismiss()` entirely (a design later overridden by the coordinator before being implemented in code) would not have fixed this either — the popout's own grab still tears itself down independently
- **Fix:** sequence the `display()` call off `SectionPopout.qml`'s own `dismissFinished()` completion signal (which both the animated and reduce-motion branches of `requestDismiss()` already converge on) instead of firing it immediately alongside an incomplete, asynchronous dismiss. By the time `dismissFinished()` fires, the popout window and its grab are both fully torn down, so nothing remains to clear when the menu subsequently takes focus — the identical grab-free end state the inline path has always had. The connection is explicitly ONE-SHOT (self-disconnects on first fire; a permanent connection would re-open the menu on every future dismissal of that popout instance — a latent bug worse than the one being fixed) and made BEFORE `requestDismiss()` is called, not after — required, not stylistic, since the reduce-motion branch emits `dismissFinished()` synchronously inside `requestDismiss()` itself, and a handler connected afterward would permanently miss that emission, silently breaking the menu for anyone running with reduced motion
- **Files modified:** `TrayPopout.qml` only — `TrayCapsule.qml` (the inline path) is diff-verified untouched across this and both prior popout-menu rounds
- **Verification:** full gate suite green, detached restart, 0 log errors/warnings beyond the two pre-existing lines, no recurrence of "null parent window". Explicitly NOT provable by a clean log: a menu that opens and then closes from a focus disturbance produces no log signal at all, which was true for every round of this bug including the two that shipped genuinely broken behaviour behind a fully green gate suite — only a live click, held open long enough to attempt a selection, can settle this
- **Committed in:** `b46fef61`
