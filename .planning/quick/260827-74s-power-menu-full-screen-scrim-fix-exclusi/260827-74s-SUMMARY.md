## Task 1 — the scrim was short by exactly the reserved zone

**Measured, not inferred.** `hyprctl monitors -j` reports
`reserved = [left 0, top 6, right 50, bottom 6]`. With the menu open,
`hyprctl layers -j` put `quickshell-session` at **`0,6 2510x1428`** against a
`2560x1440` monitor. The deficit is the reservation, to the pixel. `grim -g`
region captures of the right and top edges show the edge bar and a 6px top
strip rendering bright and undimmed beside a blurred, scrimmed desktop.

**Cause:** `exclusiveZone: 0`. An explicit non-negative zone **overrides**
`ExclusionMode.Ignore` and places the surface inside every other surface's
reservation. Fixed to `-1`.

**The old comment named the wrong cause and that is the reusable lesson.** It
blamed layer ORDER, declared `Ignore` the fix, and read as settled — so the
defect survived a whole redesign underneath a confident explanation. Layer order
genuinely never was the problem (Overlay level 3 vs the bar's Top level 2). The
comment is rewritten to carry the measurement.

Positive control that a full-span layer surface is reachable on this host:
`hyprshutdown`'s own overlay measured `0,0 2560x1440` in the same session.

## Task 2 — hyprshutdown waits forever, by design, with no timeout

`hyprshutdown` 0.1.1-6 registers exactly `dry-run`, `no-exit`, `top-label`,
`post-cmd`, `verbose`, `no-fork`, `vt`, `help`. **No timeout of any kind.** Its
UI strings are `Shutting down...`, `Waiting for your apps to exit.`,
`Force quit`, and *"You can force quit Hyprland, but that risks losing unsaved
progress."*

Confirmed live under `--dry-run --no-exit --no-fork --verbose` (safe: dry-run
guards the kill path, no-exit guards the compositor exit) — it loops
`Re-closing apps` / `Updated state: apps size 14` indefinitely. It stops only
when the last app exits or the operator clicks Force quit. **That loop is the
hang.** The operator's "staring at arch shutting down" is literally this UI.

**systemd was ruled out by counter-evidence, so a timeout drop-in would have
fixed nothing.** The journal holds two clean power-key poweroffs that bypass
hyprshutdown entirely:

| Date | Power key → `Reached target System Power Off` |
|---|---|
| Aug 22 | 05:19:55.548 → 05:19:57.043 — **1.5s** |
| Aug 24 | 18:31:44.087 → 18:31:45.380 — **1.3s** |

with `app-graphical.slice` removed 75ms into the Aug 24 teardown. The 90s
`DefaultTimeoutStopSec` on every `app-*.scope` is never reached. Notably there
is **no journal record of any power-menu shutdown completing** — consistent with
the machine being cut by hand, which also explains the `~`-suffixed (uncleanly
closed) journal files.

**The wrap was never load-bearing.** Phase 4's own
`04-01-SUMMARY.md` Task 2 records the FIX-01 hang it targeted as **never
reproduced** — "No hang reproduced", "intermittent / not currently reproducible
on demand" — and applied the wrap on a structural
bare-`systemctl`-is-uwsm-incorrect argument, not on evidence. So this change
does not reopen a demonstrated failure; it retires a precaution against an
undemonstrated one.

**Operator decision, made against a stated trade-off.** Offered a bounded grace
(10s), dropping hyprshutdown, or a longer grace (30s), the operator chose to
drop it. Accepted cost, stated before the choice: apps are killed when the
compositor exits rather than asked to close, so unsaved work is likelier lost,
and requirement **QPOWER-04**'s mechanism is retired.

**Escape hatch recorded in the file header, not just here:** if a black-screen
hang ever does appear on this path, `hyprshutdown --vt N` ("Switch to VT N after
Hyprland exits (fixes NVIDIA+SDDM black screen)") is the targeted remedy. It was
never wired up, in any revision of this repo.

### Bare `uwsm stop` does not stall — WR-04 / D-29 answered from the journal

This is the measurement the operator **waived unrun on 2026-07-28**, which is why
`13-03-SUMMARY.md` records Logout as staying wrapped *"by default, not by
evidence"*. The Aug 24 teardown supplies it. Apps live at the time: VSCodium, Zen
and seven kitty windows, `10.2 GiB` peak across `app-graphical.slice`.

| Elapsed | Event |
|---|---|
| `+0ms` | `uwsm[847]: Received SIGTERM, stopping wayland-session-envelope@...` |
| **`+67ms`** | `app-graphical.slice` released |
| `+486ms` | `wayland-wm@hyprland.desktop.service` stopped |
| `+593ms` | `Stopped target Session envelope` |

Clients never held it up. Nothing came near `wayland-wm`'s own 10s
`TimeoutStopSec`, let alone the 90s every `app-*.scope` carries. `uwsm stop`
stops `wayland-wm@*.service` (`uwsm main.py` `stop_wm()`, read directly), and
systemd cascades that to `graphical-session.target` and `app-graphical.slice` —
the same units above.

**Caveat, stated rather than glossed:** that trigger was SIGTERM delivered to
uwsm during a system poweroff, not the `uwsm stop` CLI. Same units, same cascade,
so the durations carry — but this is journal-derived inference, not the literal
stopwatch D-29 specified. Treat WR-04 as **answered by evidence**, not as a gate
that was finally run. Whether that closes MAINT-02 is the operator's call.
