<objective>
Make the News tab self-healing: on a centre-open where the whole-cache TTL is still
fresh, re-attempt ONLY the configured sources that currently have zero cached
headlines, leaving the healthy sources and the whole-cache age untouched.

Purpose: today `refresh(force)` gates on WHOLE-CACHE staleness. A run in which one
source failed while the others succeeded writes a cache that is "fresh" but missing
that source's items, so every later centre-open inside `ttl_minutes` skips the whole
refresh and the failed source reads as a dead feed until the TTL expires. This was
observed end to end: Hacker News took one transient `network error (status 0)` at
21:02, 40 items were written from the other three sources, and every subsequent open
logged `refresh() skipped — cache fresh, N minute(s) old` until the TTL rolled over,
at which point HN fetched 10 items normally. The feed was never broken.

Output: one modified backend file plus a structural gate script. No new UI surface.
</objective>

  <action>
**The design decision this task settles, and why — record it in the file's header.**

The retry set is derived from CACHE CONTENTS, not from `_failedNames`. `_failedNames`
is in-memory only, so after a shell restart the shell no longer knows which sources
failed; the loaded cache still does, implicitly, because a configured enabled source
with zero items in the current cache is exactly a source that failed or came back with
nothing. Deriving from the cache is therefore restart-durable where deriving from
`_failedNames` is not. It also catches a case `_failedNames` structurally cannot: a
source that fetched and parsed cleanly but yielded zero items increments `sourcesOk`
and never enters `_failedNames`, yet is indistinguishable to the operator from a dead
feed. The cost of the broader net is that a source which legitimately publishes nothing
is re-attempted on each centre-open; that is one bounded, idempotent HTTP GET behind
the D-32 centre-open gate, on a list already hard-capped at `maxSources` (8), and it is
cheaper than the alternative of a feed silently reading as dead. State this trade-off in
the header, including the one pathological case: if an operator sets `max_items_total`
below the number of configured sources, round-robin selection gives the tail sources
zero slots and they will be re-attempted on every centre-open — bounded, logged, and
visible rather than silent.

**New run state (declare beside `_failedNames`, above the FileViews).**

Add `property var _okNames: []` — the names of the sources that SUCCEEDED this run
(fetched and parsed without throwing). It is the positive twin of `_failedNames`, and
it is what both the publish gate and the carry-forward now key on. Add
`property int _runSourceCount: 0` — how many sources this run actually attempted, used
only so the log lines cannot let a partial run be mistaken for a whole one.

**Correct the `_failedNames` comment.** It currently claims it is what "the
partial-failure rule in _finishRun() below needs". After this task that is no longer
true — the carry-forward keys on `_okNames`. Rewrite the comment to say what it is now
for: per-run failure reporting and the failed-source log line. Do not leave the old
claim standing.

**New helpers (declare above `_finishRun()`, per the helpers-above-use rule).**

`_sourcesNeedingRetry()` returns the subset of `root.sources` whose `name` appears on
zero items in `root.items`. Build a names array from `root.items` and test membership
with `indexOf` — use an array, NOT a plain object used as a map, because an
operator-authored source name such as `constructor` or `__proto__` collides with
`Object.prototype` and would silently produce a wrong answer; `indexOf` on a list capped
at 8 sources and 200 items has no such hazard, and it matches the `_failedNames.indexOf`
idiom this file already uses.

`_carryForward()` returns the items to carry over from the previously published set. An
item is carried when BOTH hold: its `source` is the name of a currently-configured
enabled source (i.e. it appears in `root.sources`), AND its `source` is NOT in
`_okNames`. The first condition preserves an existing behaviour that must not regress —
a source removed from `news-sources.json` by hand-editing (which `watchChanges: true`
picks up, but which runs no prune) must have its items dropped, exactly as today's
`_failedNames` keying happens to achieve. The second condition is the generalisation:
in a whole run a source is either ok or failed, so items from ok sources come from
`_runBuffer` and items from failed sources are carried — byte-identical to today's
behaviour; in a partial run the sources that were never attempted are also not in
`_okNames`, so their items are carried too, which is precisely what stops a partial run
clobbering the healthy sources.

**`_fetchSource()`.** In the success branch, alongside the existing `sourcesOk`
increment, push `src.name` onto `_okNames`. A source that parses cleanly but yields zero
items still counts as ok here — that stays exactly as it is; success-with-nothing
remains a different state from failure at the run level, and the retry set above is what
now covers it at the cache level. Change nothing else in this function; the
`requestsInFlight` increment must stay BEFORE the shared-transport call for the reason
its own comment gives (the transport's scheme guard can fail synchronously).

**`_finishRun()`.** Four changes, no more:

(a) The publish gate becomes `root._okNames.length > 0` — "did THIS run actually bring
    anything back" — replacing the counter-based gate. This matters because
    `sourcesOk` is now seeded (see refresh() below) and a seeded counter would let a
    wholly-failed partial run take the publish branch.

(b) Replace the `_failedNames`-keyed carry-forward loop with a call to
    `_carryForward()`. Keep a log line of the same character, naming how many items were
    carried and how many sources contributed them, so the behaviour stays observable.

(c) Assign `root.fetchedAtMs = Date.now()` ONLY when this was a whole run, i.e. when
    `root._runSourceCount === root.sources.length`. A partial run did not refresh the
    whole cache; advancing the whole-cache timestamp would both lie in the age readout
    and push the TTL out, indefinitely deferring the full refresh the healthy sources
    still need. Log the skip explicitly when a partial run leaves it alone —
    a silent guard is what makes a wrong answer look plausible. `writeCache()` still runs
    unconditionally inside the publish branch, so a healed partial survives a restart.

(d) Reset `_okNames` to empty alongside the existing `_runBuffer` reset at the end, and
    update the zero-successful-sources log line so it names attempted-vs-configured
    counts instead of implying every configured source was tried.

Leave the round-robin fair-selection block and the single-statement `root.items`
assignment exactly as they are — both carry their own recorded bug-fix rationale.

**`refresh(force)`.** Restructure, preserving guard order and semantics:

1. The `!root.centreOpen` guard stays FIRST and unchanged — D-32 depends on it, and
   every new path in this plan sits behind it.
2. The `requestsInFlight > 0` guard stays second and unchanged — no overlapping runs.
3. Move the zero-valid-sources guard ABOVE the staleness gate. Its log line and effect
   are unchanged; it just now also short-circuits the fresh-cache branch cleanly.
4. Declare a local targets list initialised to `root.sources`. When `force` is falsy and
   the cache is not stale, set targets to `_sourcesNeedingRetry()`. If that is empty,
   log that the cache is fresh, give its age in minutes as today, add that every source
   has headlines so there is nothing to re-attempt, and return. If it is non-empty, log
   that the cache is fresh but name the sources being re-attempted and continue.
5. Seed the counters for the run: set `root.sourcesOk` to
   `root.sources.length - targets.length`. One expression, correct in both shapes — zero
   for a whole run, and for a partial run the number of sources deliberately skipped,
   which were skipped precisely BECAUSE they already have cached headlines, i.e. they
   are known good. This is what keeps `NewsPane.qml`'s "N of M sources unreachable"
   footer honest: M stays the configured source count rather than collapsing to the
   retried subset. Set `root.sourcesFailed` to 0, `root.lastError` to empty,
   `root._runBuffer` and `root._failedNames` and `root._okNames` to empty arrays, and
   `root._runSourceCount` to the targets length.
6. Loop over targets, not over `root.sources`.

**`abort()`.** Reset `_okNames` to an empty array and `_runSourceCount` to 0 alongside
the existing `_runBuffer` reset, so a centre-close mid-run cannot leave a stale positive
record for the next run's carry-forward to read.

**Do not weaken anything.** `maxSources` stays a hard 8 and is not read from JSON;
`maxItemsPerSource`, `maxItemsTotal` and `ttlMs` stay clamped; `maxResponseBytes` stays
a hard 2MB; all three https enforcement points (`_validSources()`, `_parseFeed()`'s
acceptance filter, `_imageOf()`) are untouched. Introduce no timer type of any kind —
the retry may only ever run from a centre-open. Every new property and function goes
ABOVE the two FileView blocks.

When writing header or inline prose, describe the superseded publish gate in words

clean code by matching its own comment, and prose that cannot self-match is cheaper than
