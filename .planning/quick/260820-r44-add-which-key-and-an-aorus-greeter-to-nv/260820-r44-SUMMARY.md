# which-key + greeter

Two operator-requested additions to the nvim config built in 260820-nua.

## What shipped

**which-key** (`lua/plugins/which-key.lua`) — pops up the available next keys
when a Space chord is left half-typed. Pinned to v3; the `helix` preset draws a
bordered panel down the right-hand side. Prefix groups are named (`find`,
`code`, `rename`, `git`) so a partial chord reads as a category. `<leader>?`
shows buffer-local maps.

**Greeter** (`lua/plugins/dashboard.lua`) — snacks.nvim's dashboard module,
showing an AORUS banner, the seven cold-start keys, and the five most recent
files. Layout chosen by the operator from three rendered options.

**Theming** (`colors/rice.lua`) — 18 `WhichKey*` and 11 `SnacksDashboard*`
groups painted explicitly from the palette. Before this, plugin surfaces
inherited from base groups; these are the first painted deliberately.

## Decisions

- **snacks.nvim over alpha-nvim / dashboard-nvim / mini.starter.** None of the
  four is archived, so this was a live choice, not an elimination. snacks is the
  most active, shares an ecosystem with lazy.nvim, and is one dependency instead
  of several.
- **Only the dashboard module is enabled.** `explorer`, `picker` and `notifier`
  are switched off so neo-tree, telescope and gitsigns keep their roles. Research
  explicitly abstained on whether snacks' explorer overlaps awkwardly with
  neo-tree — leaving it off sidesteps the question rather than betting on it.
- **The greeter loads eagerly** (`lazy = false`, `priority = 1000`), per its own
  README. A greeter that lazy-loads has missed the moment it exists for.
- **Icon accents map to ramp slots, not literals.** which-key names groups
  `WhichKeyIconGreen`, `...Red`, `...Azure` and so on, but the palette carries
  roughly four real hues. Each maps to the nearest slot the ramp produced, so
  they follow every theme instead of fighting it.

## Two things caught in flight

**`Lazy! sync` was the wrong verb.** It updated existing plugins as well as
installing the new ones, drifting `lazy.nvim`'s pin backwards to an 8-month-old
commit. Reverted to the previously verified pin and reconciled with
`Lazy! restore`, so the lockfile diff is two additions and no drift. Use
`Lazy! install` or `restore` when adding, never `sync`.

**A probe reported both plugins missing when both were fine.** `require()` under
`nvim -l` failed for which-key and snacks, because `nvim -l` does not run the
plugin loader. Re-probed through lazy's own load state during a real startup:
`snacks.nvim lazy=false loaded=true` with the `Snacks` global live, and
`which-key.nvim` correctly still lazy on `VeryLazy` but resolvable. The
highlight-group half of the first probe was trustworthy because it carried a
positive control (`Normal.fg` non-nil); the require half carried none, which is
exactly why it misled.

## Follow-up: prefix groups corrected (b569afa)

The operator confirmed the greeter renders correctly on light and vantablack,
and that which-key works, then asked for all keymaps to be covered.

An audit found the first spec declared a `<leader>g` group that **nothing is
bound under** — git hunks live on `<leader>h` (`hs`/`hr`/`hp`). The popup was
advertising an empty prefix while leaving the real git group unlabelled. Fixed,
and the three non-leader prefixes actually in use are now named too: `g` (goto),
`]` (next), `[` (previous).

No per-key entries were needed. All **107** global mappings already carry a
`desc` where they are defined, and that is exactly what which-key renders.
Buffer-local maps from the LSP and gitsigns appear once those attach — present
on a real buffer, absent on the greeter, which is correct.

Verified: no startup errors, `preset = helix` in effect, `delay = 300`, both
plugins installed. One probe attempt against which-key's internal tree API
returned nil for every prefix including `<leader>` — that was the probe being
blind against a v3 internal, not a config fault, and it was discarded rather
than reported.

## Optimization pass (379435c)

Operator asked for the `gr` removal plus a wider look for optimizations. What
the audit actually found:

**Removed — `gr` (references).** It was both a binding and a prefix, because
nvim 0.11+ ships `gra`/`gri`/`grn`/`grr`/`grt`/`grx`. Every press stalled
`timeoutlen` (400ms, `options.lua:55`), and it duplicated the built-in `grr`.

**Removed — `K` (hover).** nvim binds this itself on `LspAttach`
(`runtime/lua/vim/lsp.lua:869-871`), guarded by `maparg('K','n') == ''` so it
never clobbers an existing map, and it deletes it again on detach
(`lsp/client.lua:1415-1417`). The hand-rolled version did neither. Both lines
also contradicted the comment directly above them, which claimed the autocmd
only adds what core does not cover.

Verified on a real buffer with clangd attached: `K` resolves to
`vim.lsp.buf.hover()` buffer-locally, `grr`/`grn`/`gra`/`gri` and `]d`/`[d` all
come from core as globals, and `gd` — the positive control — is still ours.
`gd` stays because it genuinely has no default map; it rides the tagfunc.

**Checked and found already optimal — no changes made:**

- *Startup*: ~37ms before, ~38ms after. The largest single cost is nvim's own
  `ftplugin/lua.lua` at 4.7ms, not this config. Not a useful target.
- *Options*: all 20 that `options.lua` sets genuinely differ from nvim's
  defaults. Zero redundant assignments.
- *Lazy-loading*: only `nvim-treesitter` and `snacks.nvim` load eagerly, both
  deliberately and for documented reasons. Everything else is event/cmd/key
  triggered.
- *Plugins*: no orphans — every one of the 14 locked plugins is referenced by a
  spec, and `friendly-snippets` is properly wired into blink's sources.
