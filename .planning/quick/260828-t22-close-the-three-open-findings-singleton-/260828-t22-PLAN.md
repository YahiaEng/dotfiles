# Close the three findings left open by 260828-so7

## What changed the plan before it was written

Two measurements taken up front reordered everything:

1. **`qml-import-check` does NOT validate singleton member names.** Positive
   control: injected `BarRoles.thisRoleDoesNotExist` and the gate still reported
   `0 unresolved across 191 files`. Its own header says why — dotted forms are
   "enum/attached references" and are structurally excluded. So a 75-reference
   popout migration would have had **no static safety net** for a typo'd role.

2. **Quickshell only watches files it has actually loaded.** A comment touch on
   `SystemCapsule.qml` (loaded) produced a reload (`delta=5`, one
   `Configuration Loaded`); the same touch on `UpdatesPopout.qml` (lazily loaded,
   never instantiated this session) produced **zero** log lines.

   **Consequence — a correction I owe:** 260828-so7's commit and SUMMARY cite the
   hot reload as evidence the BarRoles routing loaded cleanly. That file has
   never been loaded, so the reload never exercised it. The static gates were
   real; that one runtime claim was not. It must be corrected, not quietly
   dropped.

Together: for lazily-loaded surfaces, a **static** member-resolution check is the
only verification available. Build it first, then migrate behind it.

## Tasks

### Task 1 — `singleton-prop-check`: a new gate for singleton member resolution

A new gate, not an extension of `qml-import-check` — extending it would
contradict its own documented resolution model (types, not members).

Resolves every `<Singleton>.<member>` reference against the members that
singleton actually declares. Singletons are discovered from `qmldir` manifests
(26 found), never hand-listed.

**Deliberately over-approximates the member set** — it collects `property`,
`readonly property`, `property alias`, `function` and `signal` names from
*anywhere* in the singleton's file, not just its root object. `Colours.qml`
declares its roles inside a nested `JsonAdapter` behind an alias layer; a strict
top-level parse would false-positive on every `Colours.*` reference in the tree.
Over-approximation is the safe direction: the gate catches names that exist
**nowhere** (the typo/removed-role class) and does not police scope.

Prototype already measured: **0 violations tree-wide**, **1** when a bogus role
is injected, back to **0** on restore.

**Done when:** the gate ships with a `--self-test`, poison-tested, and reports 0
against the live tree.

### Task 2 — `TapHandler.PassiveOnly` does not exist (4 sites)

Measured against `/usr/lib/qt6/qml/QtQuick/plugins.qmltypes`: `GesturePolicy`
has exactly four values — `DragThreshold`, `WithinBounds`, `ReleaseWithinBounds`,
`DragWithinBounds`. `PassiveOnly` appears **nowhere in Qt**, so every one of
these assignments fails at runtime and the handler silently keeps its default.

It is a population, not an instance — **all four** `gesturePolicy` lines in the
repo are this same invalid value:
`SliderRow.qml:85`, `ToggleRow.qml:127`, `SelectRow.qml:100`, `StepperRow.qml:84`.

**Action:** remove the invalid assignment at all four sites and correct the
comments, which describe a "PassiveOnly TapHandler [that] observes press/release
without grabbing the point" — a mechanism that was never in effect.

**Deliberately NOT substituting a different enum value.** The rows currently run
on the default and the operator approved that behaviour live in round 5.
Swapping in a real-but-different policy would change approved behaviour on a
surface I cannot exercise from here. Removing the dead line makes the code honest
about what it already does; changing the policy is a separate, testable decision.

**Done when:** no `PassiveOnly` remains, and the log stops emitting
`Unable to assign [undefined] to QQuickTapHandler::GesturePolicy`.

### Task 3 — migrate the nine exempt popouts onto BarRoles

Closes `WINDOWS.md` row 57. Measured scope: **75 `Colours.*` references across 9
files**, using 9 distinct roles.

Seven map to roles that already exist; two need new aliases:

| Colours role | count | BarRoles target |
|---|---|---|
| `onSurfaceVariant` | 25 | `capsuleFg` (existing) |
| `onSurface` | 17 | `popoutFg` (added by so7) |
| `surfaceVariant` | 12 | **new** `popoutSurfaceVariant` |
| `primary` | 11 | `accent` (existing) |
| `error` | 4 | `danger` (existing) |
| `tertiary` | 2 | `warn` (existing) |
| `onPrimary` | 2 | `onAccent` (existing) |
| `surface` | 1 | **new** `popoutSurface` |

The two new roles are **exact aliases**, not the existing `capsule`/`barSurface`
blends — those carry alpha (0.85/0.55) and substituting them would change
appearance. Every mapping must be value-identical so the nine surfaces cannot
look different by construction.

Then shrink `QSD_BAR_COLOUR_ROLE_EXEMPT` from 10 entries to 1 (`BarRoles.qml`
itself, the one legitimate `Colours.*` consumer) and close WINDOWS row 57.

**Done when:** `bar-colour-role-routing` passes with all nine files **scanned**,
`singleton-prop-check` is 0, and the exemption array holds only `BarRoles.qml`.

## Explicitly NOT done here

- **`--with-compositor-reload` is not run.** It performs a live `hyprctl reload`,
  which on this Lua-parser build re-applies `~/.local/state/hypr/overrides.lua`
  and can silently revert operator customisations, and it restarts the shell
  mid-session. That is an operator decision, not mine to take unprompted.
- **`NotifCentre.qml:1092` is not a defect and gets no code change.** The file's
  own comment documents the absent file as the designed path ("falls straight
  through to the bundled glyph"); it is an optional user override. The log line
  is graceful degradation, not a fault. Recorded so it is not re-investigated.
- The nine popouts' *rendered* appearance is not verifiable from here (no input
  injection for layer surfaces). Value-identical mapping is the guarantee; an
  operator checklist is the confirmation.
