# Phase quick-260812-59l Plan 01: BarDrawer vertical drawer host Summary

One new registered QML type — `BarDrawer.qml`, a LazyLoader-gated anchored strip surface — hosts the launcher and settings drawers in vertical orientation, closing GATE-02 row `B.4-DRAWER`'s structural half; `Bar.qml`, the reservation, and the horizontal drawer behaviour are all untouched.

## What shipped

`quickshell/.config/quickshell/modules/bar/BarDrawer.qml` — an ordinary (non-singleton) `PanelWindow` type, registered once in `modules/bar/qmldir`. Public contract, all set by the consuming capsule:

- `drawerId: string` — namespace suffix and diagnostic name.
- `triggerCentre: real` — the trigger cell's scene-space centre along the bar's long axis, published once at expand time (never a live binding).
- `crossExtent: int` — the consumer's `expandedCrossExtent`.
- `cellPitch: int` — the consumer's cell pitch.
- `default property alias cells: drawerGrid.data` — where the consumer's own `Repeater` lands.
- `readonly property bool hovered` — the sole hover relay, mirroring `SectionPopout.qml`'s own `hovered`.

Namespace pattern: `"quickshell-bardrawer-" + drawerId`, e.g. `quickshell-bardrawer-launcher`, `quickshell-bardrawer-settings`. Layer posture copies `SectionPopout.qml` (Overlay layer, `exclusiveZone: 0` as a bare literal, `exclusionMode: ExclusionMode.Ignore`, no keyboard focus, no `HyprlandFocusGrab`); lifecycle discipline (one job, nothing else) copies `HotZone.qml`. Anchoring is the same expression pair `SectionPopout.qml` uses for its vertical branch (`_verticalRightMargin`, `_verticalClampedTop`), inlined here as two properties per the plan's own instruction rather than a third helper property, so BarDrawer and SectionPopout still share one anchoring rule (constraint 8) with no extracted helper (constraint 4).

Both `LauncherCapsule.qml` and `ClockActionsCapsule.qml` mount the SAME type behind their own `LazyLoader { active: vertical && expanded }`, matching `shell.qml`'s own default-property idiom and `HotZone.qml`'s create/destroy shape (D-18-24) — no wl_surface exists while collapsed. Each capsule's existing `reportDrawerHover("strip", …)` entry point is the sole hover relay; no second dwell or grace timer was added (D-18-19).

## The namespace-prefix finding

`_qsd_assert_bar_surface_registry_live` (quickshell-doctor) walks every live bar-family namespace and requires it to match EXACTLY ONE registry row. The existing `SectionPopout` row stores the pattern prefix `quickshell-bar-`, which matches ANY string beginning with that prefix plus at least one character. A drawer namespace of the shape `quickshell-bar-…` would therefore match both the SectionPopout row and a hypothetical drawer row, be counted `unmatched`, and fail the live half the moment a drawer is actually open. This is why the drawer prefix is `quickshell-bardrawer-` — still `quickshell-bar`-shaped for the broad candidate net and still `quickshell-`-shaped for the family-wide blur/`ignore_alpha` layer rules, but resolving to exactly one row.

**Latent defect this uncovered, deliberately NOT fixed here:** `HotZone.qml`'s own namespace `quickshell-bar-hotzone` matches BOTH the `SectionPopout` pattern row (`quickshell-bar-` + `hotzone`) AND its own exact row (`quickshell-bar-hotzone`). If both matched simultaneously the live half would count it `unmatched` (matched=2) and fail — this is dormant today only because the hot zone is transient and is not mapped while the bar is visible (its `LazyLoader` is gated on `barVisibilityState !== "visible"`, so `HotZone` and any drawer are never live at the same moment the doctor could observe both). This belongs on the operator's desk as an open item, not fixed inside this quick task — it predates this plan and this plan's own row addition did not create it, only the act of specifying this plan's namespace surfaced it by comparison.

## What was NOT verified

**Unhedged: no pointer gesture was performed and no visual observation was made.** An agent cannot move the physical pointer on this host — `hyprctl dispatch movecursor` is rejected by Hyprland 0.56.2's Lua dispatch form, and `wtype` is keyboard-only. The leftward-expansion behaviour D-18-11 requires is therefore **claimed by construction and unproven by observation.**

What the operator should look at during the GATE-02 pass:

1. Does the strip appear leftward of the bar column, clear of it — not overlapping or along the 44px column?
2. Is it vertically centred on its trigger cell and clamped inside the screen (does not run off the top or bottom edge when the trigger is near either)?
3. Does the drawer survive the pointer crossing the `Design.spacingXs` gap between the bar column and the floating strip, or does the grace timer expire mid-crossing (closing the drawer before the pointer arrives)?

For (3), the pre-specified remedy if it fails: drop the `Design.spacingXs` term from `_verticalRightMargin` so the strip abuts the bar directly (removing the gap the pointer has to cross), OR lengthen `Design.popoutDismissGraceMs` (the existing grace interval `drawerGraceTimer` already uses). One expression either way — no new machinery, no new timer.

## Residue, named rather than absorbed

The horizontal in-bar strips (`stripHost` in `LauncherCapsule.qml`, `settingsStripHost` in `ClockActionsCapsule.qml`) still exist in both capsule files, because a strip that lives inside the bar window's own `Grid` layout cannot be a separate surface — Option B only replaces the vertical-orientation host, not the horizontal one. Option B's "stop duplicating the strip shape" benefit is therefore realised for the vertical case only: two consumers now share one `BarDrawer` type for vertical orientation, but each still carries its own horizontal-orientation strip markup (unchanged from before this plan).

`MediaConnectivityCapsule.qml`'s sibling audio/connections strips were deliberately NOT migrated to `BarDrawer` — 18-11's Option B names exactly two consumers (launcher, settings), and widening the host to a third consumer here would be scope drift beyond what was specified.
