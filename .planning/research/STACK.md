| Recommended | Alternative | When to Use Alternative |
|---|---|---|

| `hyprctl devices -j` polling / sysfs `FileView.watchChanges` for capslock | Keep `swayosd-libinput-backend.service` running standalone (un-uninstall just that one binary) purely for capslock detection | Only if the sysfs/hyprctl approach is prototyped and found unreliable (e.g. multi-keyboard ambiguity, or the LED node path differs across reboots/USB re-enumeration) — in that case, keeping one small root systemd unit alive is a legitimate fallback, but it means SwayOSD's package technically isn't fully gone (its binary would need to be extracted/vendored, since removing the `swayosd` package removes `/usr/bin/swayosd-libinput-backend` too). ## Stack Patterns by Variant

**Q1 — Notification server: YES, `Quickshell.Services.Notifications` can fully replace swaync as the D-Bus server, not just read from it.**

Verified directly from the installed `quickshell-service-notifications.qmltypes` (HIGH) and cross-checked against `quickshell.org/docs/v0.3.0/types/Quickshell.Services.Notifications/` (webfetch, matches installed version, MEDIUM-verified):

- `NotificationServer` is the server component. It advertises capabilities to D-Bus clients via boolean properties, each independently togglable and all **default to conservative/off** except `bodySupported` (defaults true) and `keepOnReload` (defaults true): `imageSupported`, `actionsSupported`, `actionIconsSupported`, `bodyMarkupSupported`, `bodyImagesSupported`, `bodyHyperlinksSupported`, `inlineReplySupported`, `persistenceSupported`. This means a straight swap needs each of these explicitly turned on to match swaync's current feature set (swaync supports images, actions, markup body — verify per-flag during implementation, not assumed here).
- `trackedNotifications` is a live `ObjectModel` of the current notification set — this is the QML-side data the bar/notification-center UI binds to.
- Each `Notification` object exposes: `id` (uint), `appName`, `appIcon`, `summary`, `body`, `image` (icon/image path, empty string if none), `urgency` (enum: `NotificationUrgency.Enum`), `actions` (`QList<NotificationAction*>`, each with `identifier`/`text`/`invoke()`), `hasActionIcons`, `expireTimeout` (double), `resident`, `transient`, `desktopEntry`, `hasInlineReply` + `inlineReplyPlaceholder` + `sendInlineReply(...)` method, `hints` (`QVariantMap` — the raw D-Bus hint bag, this is where `urgency`/custom hints not otherwise modeled surface), `tracked`/`lastGeneration` (bools that govern reload/replace bookkeeping), and lifecycle methods `expire()`/`dismiss()`, plus a `closed(reason)` signal with a `NotificationCloseReason` enum. This is a complete implementation of the `org.freedesktop.Notifications` spec's notify/close/actions/hints surface — including inline reply, which swaync 0.12.6 does **not** offer at all (swaync has no documented inline-reply support; this would be a net-new capability, not parity).
- **Documented as not explicitly covered** in the fetched docs page: `replaces_id` merge semantics and `expire_timeout` wall-clock handling are not spelled out in prose on the docs page fetched (LOW on this specific sub-point) — but the `id`/`tracked`/`lastGeneration` property triple strongly implies replacement-by-id is handled internally (a notification with a matching `replaces_id` reuses the tracked object rather than spawning a new one). **This is the one sub-question in this research that should be settled by a short throwaway `NotificationServer{}` probe early in the notification-migration phase** (fire two notifications with the same synthetic `replaces_id` via `notify-send -r`, confirm one object updates in place rather than two objects appearing) — same "prove before building" discipline QS-02 already established for this project.
- **What swaync 0.12.6 does that this module does NOT give you for free:** the slide-out **control center UI** (history list, clear-all, do-not-disturb persistence across restarts, the toggle grid, volume/brightness sliders) is swaync's own GTK application code on top of its own D-Bus server — none of that UI ships with Quickshell. `NotificationServer` gives you the data/protocol layer only; the control-center surface, DND state persistence, and toggle-grid wiring all have to be built in QML, reusing the existing anti-drift toggle-grid scripts the Dashboard already shares with swaync per PROJECT.md's Validated list ("quick-toggles executing byte-identical scripts to swaync's grid" — Phase 14). This is exactly in scope per the Active requirements ("swaync → QML notifications — popups plus the slide-out centre, toggle grid and volume/brightness sliders").

**Q2 — Hardware key / OSD path: the volume/brightness path needs no new mechanism at all; only capslock genuinely loses its trigger and needs a specific, verified-viable replacement.**

Verified live on this host (HIGH throughout):

- **Volume/brightness/mic-mute/media-next-prev are already triggered by Hyprland `bind` entries, not by SwayOSD's libinput backend.** `hypr/.config/hypr/config/keybinds.lua:264-281` shows `hl.bind("XF86AudioRaiseVolume", hl.dsp.exec_cmd("swayosd-client --output-volume raise"), { locked = true, repeating = true })` and five siblings — Hyprland itself (the compositor) is what catches these XF86 keysyms, `locked = true` is what makes them fire even while `hyprlock` holds the session lock. Deleting SwayOSD only requires swapping the `exec_cmd` target from `swayosd-client ...` to whatever new Quickshell OSD trigger is chosen (a `hl.dsp.global("quickshell:osd-volume-raise")` call feeding a `Quickshell.Hyprland._GlobalShortcuts.GlobalShortcut`, following the exact `quickshell/.config/quickshell/shortcuts.json` + `keybinds.lua` contract already proven for Super+D/Super+O). **No lock-screen regression** — the `locked = true` flag is a Hyprland property of the bind itself, independent of which program the bind execs.
- **Capslock is the one real gap.** The repo's own prior finding, verbatim in `keybinds.lua:262`: *"Caps-lock OSD is keyless — handled by swayosd-libinput-backend.service"* — i.e., Hyprland's own bind engine cannot fire on Caps_Lock the way it can on XF86 keys (this was already established empirically in Phase 6/OSD-01, not re-litigated here). `swayosd-libinput-backend.service` is confirmed **enabled and actively running** on this host (`systemctl status` shows `Loaded: enabled`, `Active: active (running)`, root-owned, direct evdev capture per its own unit description: *"SwayOSD LibInput backend for listening to certain keys like CapsLock, ScrollLock, VolumeUp, etc."*). Deleting the `swayosd` package removes this binary and this input path outright.
  - **Concrete, verified-viable replacement found:** `hyprctl devices -j` already reports live `"capsLock": true/false` per keyboard on this host's Hyprland 0.56.2 (feature landed upstream in PR #8145, shipped since v0.45.0 — well below this host's version, so no compositor upgrade risk). Separately, and more efficiently, this host's kernel already exposes a capslock LED class node — verified present and readable at `/sys/class/leds/input5::capslock/brightness` (content `0` when off). `Quickshell.Io.FileView` has a genuine `watchChanges` bindable bool property (inotify-backed, confirmed in the installed `quickshell-io.qmltypes`), so a Quickshell OSD surface can watch that sysfs node directly and react the instant the LED toggles — **zero root daemon, zero udev rule, zero polkit policy**, strictly simpler than what SwayOSD needed to do the same job. This should be the default plan; `hyprctl devices -j` polling is the fallback if the sysfs LED path proves to differ across USB re-enumeration/reboots on this specific keyboard (worth a quick empirical check across one reboot before committing, given this host is USB-keyboard-based per the LED path itself: `.../usb1/1-3/1-3:1.0/...`).
  - **What would settle this fully, if not settled by a probe:** boot with the keyboard unplugged/replugged and confirm the `inputN::capslock` numbering is stable or re-discoverable (e.g. via a glob watch rather than a hardcoded `input5` path) — this is a real risk specific to USB HID re-enumeration, not a Bluetooth/built-in keyboard, and was not fully resolved by this research pass.
