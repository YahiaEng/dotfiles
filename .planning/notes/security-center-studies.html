Measured first

Five findings decide what is buildable

Each of these came from a command on this machine, not from inference. Two of them change what the pane must show; one of them changes where the code is allowed to live.

01

None of the scanners are installed — so “absent” is a state, not an error

Every capability this pane would report on is missing today. All four packages are in official extra, so this is a pacman line in install.sh — no AUR helper, no new mechanism. 

clamav      NOT INSTALLED   extra 1.5.3-1   30.65 MiB
arch-audit  NOT INSTALLED   extra 0.2.0-5    1.91 MiB
rkhunter    NOT INSTALLED   extra 1.4.6-4    0.22 MiB
lynis       NOT INSTALLED   extra 3.1.7-1    0.26 MiB
smartmontools 7.5-1 · lm_sensors 3.6.2 · nftables 1.1.6  — present

On a fresh install — the project's whole reproducibility premise — every scanner tile opens absent. A design that only draws clean-or-threat is wrong on day one. Each capability needs a first-class “not installed, install it” state carrying its own download size.

02

A real scan outlives the page that started it

UpdatesPage.qml's own header states the rule that kills the naive build: “a page is destroyed when the user navigates away (Pages.qml:_swapTo destroys before incubating the next), so a page-scoped Process's lifetime is naturally capped.”

Every probe in the shell today is sub-second — checkupdates, paru -Qua. A clamscan over a home directory runs for minutes. A page-scoped Process is killed the instant you navigate away, mid-scan, silently. This is the same class as the standing launcher rule: work that must outlive its surface belongs on a singleton, never on a component-scoped Process.

This is the finding that separates the four plates. The Security Center is the first surface here that needs progress, cancel, and survive-navigation — so “where is a running scan visible from?” is a layout question, not just an architecture one.

03

The host has no firewall running right now

The only ruleset present was created by Docker. Both packet-filter services are disabled and neither front-end is installed. 

systemctl is-enabled nftables  -> disabled
systemctl is-enabled iptables  -> disabled
firewalld / ufw                -> not-found
nft list ruleset               -> table ip nat { chain DOCKER … }  (Docker's own)

This is a genuine finding the pane reports the first time it opens — not a hypothetical used to fill a mockup. Every plate below shows it.

04

SMART needs root; temperatures do not

Device enumeration and sensors are free; the actual health attributes are privileged. Two escalation paths already exist in this repo. 

smartctl --scan       -> ok, 3 devices
smartctl -H /dev/sda  -> Permission denied
smartctl -H /dev/nvme0-> Permission denied
sensors               -> ok  (Tctl +53.9°C · nvme Composite +50.9°C)

polkit-gnome-authentication-agent-1 is already autostarted (autostart.lua:191), so pkexec pops a real GUI prompt. Alternatively smartd.service ships with smartmontools and is currently disabled — enabling it in install.sh puts SMART in the journal with zero runtime privilege in the shell. Three disks to cover: one SATA ST2000DM008 and two WD_BLACK SN850X.

05

The palette has error but no severity ramp

Colours.qml exposes 19 roles and not one of them is a warning or a success. A CVE list needs four steps; an AV verdict needs two more.

And a repeat trap, already paid for once on the screensaver: the roles are property string, so .r/.g/.b are undefined and Qt.rgba(role.r, …) renders pure black at the right alpha. Severity must be derived from the roles that exist — colour-lint rejects hardcoded colours, so a literal ramp is not available even as a shortcut.

One caveat worth stating before you pick: on dracula, surfaceVariant, primaryContainer and secondaryContainer are byte-identical #44475a. There is exactly one container tint above surface, so severity has to read from the foreground and a thin rim — a tinted card back will not separate.

The directions

Four plates, one shared scale

Each plate is authored at true pixels and scaled once, so the numbers on the page are the numbers in the code — and a 760-wide drawer visibly differs from an 800-wide settings page. All four are drawn in first-open state: firewall down, scanners absent, disks readable. That is what you would actually see today.

What it buys

  • Zero new primitives — PageBase, SettingsSection, InfoRow and NavRow already do all of it.
  • One new page, one PageRegistry row, one qmldir line. Nothing else in the shell is touched.
  • The install affordance sits exactly where the missing capability is, with its real download size.
  • Structurally identical to a page that already ships and works, so the failure modes are known.

What it costs

  • No verdict. You must read four sections to learn whether anything is wrong — the one question the pane exists to answer.
  • Walks straight into finding 02: a scan started here dies when you click any other rail item.
  • On a fresh install the top half is three grey “Install” rows, which reads as broken rather than as ready.
  • Severity has nowhere to aggregate, so a critical firewall finding looks the same weight as a disk temperature.

What it buys

  • Answers the question in one line. “1 issue needs attention” is legible before you read anything else.
  • Absent tools stop reading as breakage — they become one low-priority finding among others, with the fix attached.
  • Severity is expressed as ordering, which survives finding 05: no ramp is strictly required for the list to be correct.
  • Collapsing three healthy items into one row keeps a good machine from looking empty.

What it costs

  • Loses the domain map — you can no longer ask “how are my disks?” without filtering.
  • Still a settings page, so finding 02 is unsolved: a running scan is invisible the moment you navigate away.
  • Needs a real merge-and-rank step across four unrelated data sources; that ranking is new logic with no precedent in the repo.
  • The severity ramp is genuinely wanted here even if not required, and it does not exist yet.

What it buys

  • Zero navigation. Posture is one Super+D away, in the surface you already open daily.
  • The bento maps cleanly onto four domains plus a verdict, and reuses DashBento.qml's existing cell language.
  • Glance-legible: dot colour plus one number per cell answers “anything wrong?” without reading.

What it costs

  • Worsens a known defect. The drawer already animates width between tabs because each tab declares its own contentWidth; a fifth width makes the 280px jump worse, not better.
  • Finding 02 at its sharpest — the drawer closes on focus loss, so a minutes-long scan started here is the most fragile placement available.
  • No room for detail. A CVE list, a quarantine table and per-drive SMART attributes cannot live in a 760-wide bento cell, so this needs a settings page anyway.
  • A fifth tab pushes the tab strip toward crowding at the drawer's 760 floor.

What it buys

  • Solves finding 02 by construction. The scan lives on a singleton, so navigating away — or closing settings entirely — cannot kill it.
  • A running scan stays visible from anywhere in the session, which is the only way a minutes-long job is honest about itself.
  • The capsule carries posture at all times, so you get D1's glanceability without a fifth drawer tab or a fifth content width.
  • The page keeps S2's verdict-first ordering and has full width for detail — CVE lists, quarantine, per-drive attributes.

What it costs

  • The most work of the four: a new singleton, a new bar capsule, a new page, plus install.sh and prefs.
  • Touches Bar.qml, which nothing else in this task would otherwise need to.
  • Needs a capsule visibility rule — a permanent security chip on a healthy machine is clutter, so it has to know when to hide.
  • Capsule state is the one thing here that cannot be verified from an agent shell; it needs an operator look.

Recommendation — build H1, in two stages

Stage one is S2: the settings page with the posture header and the ranked findings feed, backed by a SecurityBackend singleton rather than page-scoped processes. That single decision is what makes stage two additive instead of a rewrite — the page reads the singleton, so the capsule can read the same singleton later without the page changing at all.

Stage two is the capsule, once you have seen the page work. It is the half that touches Bar.qml and the half I cannot verify without you, so it should not ride along with the part that is verifiable.

D1 is the one I would not build. It is the most fragile home for a long scan, it has no room for the detail this subject needs, and it makes an existing drawer defect worse — and everything it offers, the capsule offers without a fifth tab.

Before I write QML

Four things only you can decide

  1. Which plate — and do you want it staged?

    My recommendation is H1 built as S2 first. Picking S2 alone is a complete, shippable answer; picking H1 commits to the capsule as well.

  2. Which scanners go into install.sh?

    arch-audit (1.9 MiB) and smartmontools (already present) are cheap and I would default them on. clamav is 30.7 MiB plus a signature database and a daily freshclam — real weight on every fresh install. rkhunter and lynis are optional extras. Say which set, and whether they should be installed by default or offered from the page.

  3. How should SMART get its privilege?

    Enabling smartd.service in install.sh means zero privilege in the shell — the data comes from the journal, and it works on a fresh machine with no prompts. pkexec means a GUI password prompt every time you open the page, using the polkit agent that is already running. I lean smartd; it is the only one that stays true to the reproducibility constraint.

  4. May the page act, or only report?

    “Enable firewall” and “Install clamav” are both privileged, state-changing actions on your live system. I can build them as real buttons, or the page can name the exact command and let you run it. Nothing here decides itself — a security pane that silently changes your firewall is worse than one that tells you to.

What this study is not

Nothing has been installed and no QML has been written. The four packages are still absent, nftables.service is still disabled, and the shell is untouched. The mockups are HTML drawn to the shell's measurements — they are a proposal, not a screenshot of anything running.
