Retiring hyprlock

Whether the lock screen can move into the Quickshell process alongside the bar, the notification centre and the launcher — and if so, what it should look like. Every mockup below is rendered at 2560×1440, this monitor's real geometry, in the live Dracula palette.

Yes

Quickshell can replace hyprlock outright — and Caelestia already did it

Quickshell 0.3.1 ships WlSessionLock and WlSessionLockSurface in Quickshell.Wayland, plus a complete PamContext in Quickshell.Services.Pam. Both /usr/bin/quickshell and /usr/bin/Hyprland carry the ext_session_lock_v1 symbols, so client and compositor agree on the protocol. Caelestia does not use hyprlock at all — it ships its own QML lock at modules/lock/, sixteen files deep, which is what Direction A reproduces.

Why this one

Why this one

A lock screen is looked at far more than it is typed into. This direction optimises for the glance, not the login.

Signature move

Idle → the clock alone. Any keypress → the field rises and the clock shrinks up. Idle again → it all recedes. The surface has two states, not one.

What it costs

A hidden password field is a real usability risk on a machine you hand to someone else. Needs a visible affordance the ghosted mockup does not yet show.

Effort


Least content, most state machine.

Before committing

Three things that are genuinely different about a lock screen

Not generic caution — each of these is specific to putting the lock inside the shell process, and each has bitten this project or Caelestia already.

Hard constraint

A shell restart while locked strands the session

The lock would live in the same process as the bar. The protocol protects the secret: if the lock client dies, ext-session-lock-v1 requires the compositor to keep the session locked and paint a blank surface — the desktop is never exposed. But the unlock UI dies with the process, so recovery is a VT switch, exactly the --vt N escape hatch that came out of the hyprshutdown work. This upgrades an existing house rule — never restart quickshell from the agent shell — from an annoyance into a lockout. Caelestia accepts this same trade.

Known gotcha

Screencopy must be warmed before the lock engages

Caelestia carries a deliberate hack for this: a Loader that instantiates one throwaway ScreencopyView at startup and immediately deactivates itself, with the comment "Force a load of a screencopy so the one in the lock works." The compositor refuses capture once locked, so if the lock is the first screencopy request, the backend is still loading asynchronously and the capture fails. Any direction that blurs the live desktop rather than the wallpaper inherits this. Directions C and D sidestep it — they show the wallpaper, not a screencopy.

Verification gap

No gate on this host can prove a lock screen works

There is no input-injection tool here, and a wrong PAM wiring is not visible to colour-lint, quickshell-doctor or any static check — they would go green over a lock screen that cannot be unlocked. This is the surface where the operator checklist has to carry the verification, the pattern that has now outperformed gate reruns on three consecutive tasks. Minimum: lock, fail once deliberately, succeed, then lock again after a suspend cycle.
