Read this first

Updates already ship. This is a browser.

Settings → Updates has done this since quick task 260826-1n9

modules/settings/pages/UpdatesPage.qml is 347 lines that already run checkupdates and paru -Qua, parse both into package records, show a status line and a last-checked time, offer Update all through the terminal, and support a two-click armed single-package update carrying an explicit partial-upgrade warning. modules/launcher/UpdatesMode.qml shows the same list under Super → System → Updates.

So updates are not the gap. The gap is everything else: searching and browsing what is installed, seeing why a package is on the disk, what depends on it, what it costs in space, and removing it. None of that exists anywhere in the shell today. Each direction below is judged on that, and on what it does with the Updates page that already exists — absorb it, link to it, or leave it alone.

Second thing worth naming: you installed octopi-git, qt-sudo and qtermwidget at 03:50 this morning. Octopi is a Qt package manager, so this panel is competing with something you already reached for a few hours ago. That is useful — it means the direction you pick should be measured against Octopi, and if the panel wins, Octopi and its two dependencies come back off the disk.

Measured on this host, today

Every query is cheap enough to run on open

This is the fact that unlocks the whole design: the complete local database — all 1,420 packages with every field — dumps in a fifth of a second. There is no need for incremental loading, a cache file, or a background daemon. A backend singleton runs one command at first open and holds 1.3 MB in memory.

What it does best

Answers “what is this and why is it here?” for any of 1,420 packages, in the place you already go for system settings. The detail pane is the whole of -Qi, which is more than Octopi shows without a second click.

What it can't do

No bulk selection, no transaction queue. Removing five orphans is five separate confirmations. The Settings window is also modal to your attention — it isn't a thing you leave open while working.

Does it absorb Updates?

Yes — an “Updates 4” chip is one more filter over the same list, and the existing page's actions move onto the detail pane. That would retire UpdatesPage.qml's 347 lines rather than run two package surfaces side by side.

Rough cost

≈ 800 lines

A PackagesBackend singleton, the page, a row component. Closest analog is SecurityPage + SecurityOverview at 548, plus a backend.

What it does best

Turns package state into something you glance at rather than query. The footprint plate in particular answers a question nothing on this machine answers today, and it found a 1.1 GiB font while I was measuring for this study.

What it can't do

It is not a browser and shouldn't pretend to be. No search, no per-package detail, no removal. On its own it does not satisfy the ask — it is a companion to D1 or D4, not a replacement.

Does it absorb Updates?

No. The Pending plate duplicates the Updates page's headline number and should link to it, not re-implement it. Two readers of checkupdates is fine; two owners of the update action is not.

Rough cost

≈ 300 lines

Cheapest real surface here if the backend already exists. SecurityTab.qml is 196 lines over an existing backend.

What it does best

Speed, and near-zero new surface area. “Is X installed, and what version?” goes from opening a terminal to three keystrokes. It also inherits keyboard navigation and dismissal for free.

What it can't do

A launcher row cannot hold -Qi. No sorting by size, no orphan sweep, no comparison, no bulk anything. It answers lookups, not the browsing half of the ask.

Does it absorb Updates?

It sits beside the existing System → Updates entry without touching it. If anything it argues for folding that entry into the same route later.

Rough cost

≈ 180 lines

One mode component plus a router entry. UpdatesMode.qml is 132 lines and does strictly less.

Defect 1 — blind to the AUR

The cell polls checkupdates and nothing else, so pendingUpdatesCount counts repo updates only. Right now it reads 3 while 4 are pending — python-steam does not exist as far as the bar is concerned.

Defect 2 — no look before the leap

Clicking it calls launchUpgrade(), which opens kitty on paru -Syu immediately. There is no way to see what is about to change without starting the transaction. That is what the popout is for.

What already works, and stays

Hidden at zero. Single-flighted, so a slow mirror can't stack probes. 30-minute poll, already configurable. Filled tertiary pill per Athena's own rule. Terminal handoff for the upgrade. None of that changes.

Rough cost

≈ 220 lines

A second Process for paru -Qua, a popout component, and a route into D4. The glyph, poll timer and click action already exist.

Third axis · the one with a safety answer

How anything that writes gets root

Browsing needs no privilege at all — every command in the table above runs as you. Removing or installing does. There are two shapes in this repo already, and they were chosen for different reasons.

ShapePrecedent hereWhat you seeNew attack surface
Terminal handoff UpdatesPage.qml — execDetached([terminal, "-e", "paru", …]) pacman's own prompt, its own confirmation, its own output. You approve the real transaction. None
pkexec helper section_security — hardcoded verb allowlist + polkit action A polkit password dialog, then a spinner. The transaction happens where you can't see it. A new allowlisted verb that runs pacman as root

Terminal handoff, for everything that writes. The Security Center needed pkexec because “enable the firewall” has no meaningful output to watch — it either worked or it didn't. A package transaction is the opposite: the list of what will actually be removed is the whole reason to pause, and pacman already prints it and already asks. Wrapping that in a polkit dialog replaces a good confirmation with a worse one, and adds an allowlist entry that runs pacman as root on arbitrary arguments.

It also means the panel can be built with zero root-side install — no addition to install.sh, no polkit action, nothing in section_security's shape. That is a genuinely smaller thing to get wrong, and it survives a fresh install for free.

Shipped 2026-08-28 · operator-confirmed after three rounds

What shipped

Build D4 Workbench as the main surface — an actual Octopi replacement — with D3, D5 and a rescoped D1 around it, all over one backend. D2 Sentinel is not being built.

I recommended D1-as-a-browser and was overruled on the strength of the real goal: the ask was always a replacement for Octopi, and a Settings page is not that. D4 is a window you leave open and work in, with bulk selection and a removal preview — the two things a Settings page genuinely cannot fake.

That decision then forced a second one. With D4 in the tree, D1 as drawn would have been the same browser in a different frame, which is precisely the redundancy that got the Security Center's two layouts merged in operator round 3. D1 is therefore rescoped to a thin preferences page: package settings plus one button into D4. One browser in the tree, not two.

RoundWhat changed, and why
Build The bar's updates pill was AUR-blind — it polled checkupdates alone and read 3 while 4 were pending. That defect, not the feature request, is what the backend fixed first.
Round 1 Window sized off the screen (Settings' own formula) instead of a literal; ad-hoc unicode glyphs replaced with Material Symbols, all 19 verified against the installed font with an absent control; UpdatesPage.qml retired with its per-package armed update absorbed; Super+P bound.
Round 2 Dismiss-on-click-outside was really dismiss-on-mouse-exit: follow_mouse is 1 here, so Qt's Window.active tracks the pointer. Replaced with HyprlandFocusGrab. Panes made resizable, fonts up a step, columns widened to match, thin scrollbars added.
Round 3 The + route became the word pkg, painted in the accent colour from the first keystroke. Pane resize was measuring in the grip's own moving frame; re-anchored to scene coordinates at press-time. Right pane made resizable too.

Standing constraints, honoured throughout:

  1. One owner for the update action. D4 owns browsing and transactions; the capsule and D3 route into it. UpdatesPage.qml is absorbed by D4 rather than left running beside it.
  2. Terminal handoff for every write. No pkexec verb, no polkit action, no install.sh change. Browsing is unprivileged and stays that way.
  3. Octopi is gone — done 2026-08-28. The removal preview earned its keep on the way out: the obvious -Rs would have taken pacman-contrib with it, and pacman-contrib owns checkupdates.
