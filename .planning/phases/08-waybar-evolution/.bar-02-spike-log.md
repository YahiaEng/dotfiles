## GATE K0-a — actuation-cost probe

**Method:** the owner's existing actuation path is `waybar-visibility.sh reassert` while the bar is
VISIBLE and its computed state is unchanged (a no-op reassert). Per `bar-common.jsonc`, waybar's
`on-sigusr2` action is fixed to `"reload"` — a FULL bar-config reload, not a lighter CSS-only
refresh (confirmed by reading `bar-common.jsonc` directly, lines 16-25). Any owner-driven CSS
change — including a hypothetical jitter offset — has no other actuation path available; it MUST
go through this same SIGUSR2/reload signal. So this probe is mechanism-independent: whatever it
measures here applies to M1 and M2 both, before either is even tried.

Setup: two real tiled windows (`kitty` 0x5612126237f0, `zen` 0x5612113000a0) on the SAME active
workspace (2), confirmed side-by-side (`at=[13,50]/[1288,50]`, `size=[1259,1377]` each, filling the
2560px output minus the bar's reserved 37px top strip).

### Reflow cost — instrument: `hyprctl clients -j` (via `jq`), 30-50ms polling burst across the signal

**Control burst (no signal fired), 10 samples @ 30ms — zero polling noise:**

observed `reserved: [0,37,0,0] -> [0,0,0,0] -> [0,37,0,0]` transition — see raw capture

**Cross-check against `08-03-SUMMARY.md` D3, as the plan instructs:** 08-03's claim ("idle-hide
left the window's `at`/`size` completely unchanged... zone kept") is **not contradicted at the

## GATE K0-b — displacement viability (SKIPPED, per K0-a's fast path)

**K0-b: SKIPPED — not mechanism-unavailable, mechanism-moot (K0-a already disqualifies actuation).**

K0-a fired on both sub-costs, so per the plan's own explicit instruction K0-b is not run this
session. Recording what is and is not known about each candidate mechanism, honestly:

- **M1 — CSS `margin` on `window#waybar`.** NOT independently re-tested this session (no new
  surface/content readback taken). Prior evidence stands as recorded in `08-RESEARCH.md` VERDICT 1
  (HIGH confidence, verified directly against the installed `waybar.5.gz`): CSS margin on
  `window#waybar` does not reposition the layer-shell surface (`Alexays/Waybar#1533`). Whether it
  shifts rendered *content* inside the surface was left open by RESEARCH and remains open here —
  **not resolved by this plan**, because it is moot: even if M1's content readback had shown a
  clean 2px shift, the shift could only ever reach the screen via the same reload-signal actuation
  measured in K0-a above, which already flashes and transiently reflows on its own, independent of
  what the CSS payload says.
- **M2 — CSS `padding` on `window#waybar`.** NOT tested this session, same reasoning as M1: any
  padding-shift CSS would still need the identical SIGUSR2/reload actuation to apply, which K0-a
  already disqualifies before the padding content is even considered.
- **M3 — rewriting bar-config `margin-*` keys + reloading.** Disqualified by design, per three
  citations: (1) rewriting a waybar *config* file at runtime violates this repo's established
  "runtime-only state overrides, never config rewriting" pattern (P7 D-26, 08-CONTEXT Established
  Patterns); (2) a full `reload` resets the bar to config-time visibility, which would resurrect a
  bar the owner had hidden — D-09 kill criterion #3 by definition; (3) recreating the layer-shell
  surface drops/re-adds the exclusive zone — kill criterion #2. **Claim (3) is substantiated with a
  real number, reusing K0-a's exact harness rather than left as an argument:** K0-a's `reassert`
  action IS a bare SIGUSR2/`reload` — the identical signal M3 would also require — and it measured a
  real, reproducible transient reflow (Δy=37px, Δh=37px, confirmed 3/3 runs, see K0-a above). M3's
  kill-#2 prediction is therefore not just argued but directly measured, using data already in this
  log.
- **M4 — `reload_style_on_change`.** Deliberately not enabled/acted on, per the plan's own
  instruction: enabling it means editing `bar-common.jsonc`, which would re-snapshot the
  `waybar-equivalence-check` baseline that 08-08 is also re-snapshotting in this same wave. Noted
  here as a lead for a future phase, not evaluated further.

**K0 (mechanism-viability) is not marked FAIL-mechanism-unavailable** — that framing is reserved
for the case where neither M1 nor M2 displaces anything. Here the situation is different and must
not be conflated: the mechanism's *actuation cost itself* (K0-a) already disqualifies every
CSS-based approach before displacement viability is even asked. This distinction matters for
whoever revisits this: "actuation always twitches/reflows" (this finding) is a different, and in
some ways more fundamental, problem than "no available CSS trick moves content" (the K0-b framing),
and a future phase attacking BAR-02 again needs to solve THIS problem first (a way to update the
bar's CSS with zero flash/reflow) before M1/M2's own displacement question is even worth re-asking.

  DESCOPE"), this alone would force FAIL even setting the flash evidence aside.

**K2 — "it reflows any window."**
- Method/instrument: `hyprctl clients -j` (`at`/`size` per window address) polled at 30-50ms across
