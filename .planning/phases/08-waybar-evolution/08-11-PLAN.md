<planner_corrections>
Two claims in 08-UAT.md were verified FALSE during planning. They are corrected here and
this section overrides the UAT wherever they conflict. Do not "restore" the UAT's version.

**CORRECTION 1 — the palette has no `surface_container` token.**
08-UAT.md's `design_direction` field literally prescribes `alpha(@surface_container, 0.55)`.
That colour name DOES NOT EXIST. The rendered `~/.local/state/theme/waybar.css` defines
exactly 19 `@define-color` names, and all 22 palette JSONs under
`theme-engine/.config/theme-engine/palettes/` carry the same 19-key schema. There is no
`surface_container` in any of them (verified: `grep -rl surface_container palettes/` returns
nothing).

GTK3 discards an ENTIRE stylesheet when it hits one unresolvable `@color` reference — this is
the documented WLOG-01 failure class, already logged as a standing project blocker. Writing
that token would make all four bars render completely unstyled while a naive "the CSS parses"
check still passed.

The 19 names that DO exist, and the ONLY ones theme.css may reference:
primary, on_primary, primary_container, on_primary_container, secondary, on_secondary,
secondary_container, on_secondary_container, tertiary, on_tertiary, surface, on_surface,
surface_variant, on_surface_variant, background, on_background, outline, error, on_error.

The island surface is therefore built from `@surface` (the neutral surface token — semantically
exactly what M3 calls surface_container), NOT from the non-existent name.
<!-- planner-discipline-allow: surface_container -->

**CORRECTION 2 — waybar IS correctly stow-symlinked; the UAT's deployment caveat is a
misdiagnosis.**
08-UAT.md's `note` claims `~/.config/waybar/*` are regular files, not stow symlinks, and that
repo edits will not reach the live bar. This is wrong. `~/.config/waybar` is itself a directory
symlink into the repo (`ls -ld` shows `-> ../dotfiles/waybar/.config/waybar`). The diagnosing
agent ran `ls -la ~/.config/waybar/` with a trailing slash, which FOLLOWS the symlink and lists
the regular files inside it — the classic way to miss a folded stow symlink. Repo→live
propagation was proven during planning with a write probe.

Task 1 keeps this as a cheap, loud assertion (because if it ever DID break, every subsequent
visual check in this phase would be silently meaningless) — but it is a guard, not a repair.
</planner_corrections>

Then create `hypr/.config/hypr/scripts/waybar-design-lint`, a rerunnable gate in the exact
mould of the existing `waybar-equivalence-check` and `theme-doctor` (bash wrapper, python
heredoc for the parsing, TAB-separated OK/FAIL lines, nonzero exit on any FAIL). It must be
executable and it must accept an optional waybar-dir argument defaulting to `~/.config/waybar`.

The gate performs five checks. Each is a hard FAIL, and each exists because a specific
already-observed failure mode slipped past the previous round of green gates.

CHECK A — token resolution (the WLOG-01 killer). Parse every `style-*.css`, `waybar-modules.css`
and `theme.css` under the waybar dir. STRIP CSS COMMENTS FIRST (match the `/* ... */` block form
non-greedily across newlines in python; a naive line-based grep will produce both false
positives from prose and false negatives from multi-line rules). Collect every `@name`
colour reference. Collect every name defined by `@define-color` in `theme.css` AND in the
rendered `~/.local/state/theme/waybar.css`. FAIL on any referenced name that is not in the
defined set, naming the file and the offending token. This is the check that catches the
non-existent surface-container token class before GTK3 silently eats a whole stylesheet.

CHECK B — the alias boundary. Any file OTHER than `theme.css` that references one of the 19
raw matugen token names is a FAIL. This is what keeps palette names in exactly one file; a
role-name-only rule elsewhere is unenforceable by convention alone. Read the 19 names
dynamically from the rendered `waybar.css` — never hardcode the list, or a future palette
change silently un-guards the gate.

CHECK C — transparent window. For each `style-*.css`, the `window#waybar` rule must declare
`background: transparent`. Any other background value on that selector is a FAIL. This is the
single rule that fixes the user's reported "dark bar behind all modules", and it must be
mechanically defended so it cannot regress a third time.

CHECK D — no literal hex. Any `#rrggbb` / `#rgb` literal in any waybar `.css` or `.jsonc`
(comments stripped) is a FAIL. This is a core project constraint (no hardcoded hex anywhere)
and it is CURRENTLY VIOLATED — see Task 2.

CHECK E — no empty glyph fields. Parse every `config-*.jsonc` and `modules.jsonc` (strip `//`
comments before json.loads). For every key matching `format*`, `player-icons`, `status-icons`
recursively: FAIL on any string value that is empty, or that is whitespace-only, or that
contains a run of 2+ consecutive spaces (the exact fingerprint of a glyph that was deleted and
left its separator space behind — this is precisely how cpu/memory/clock/network shipped
iconless). Values that are pure format placeholders with no icon slot (e.g. a bare
`{:%H\n%M}` clock, or a `{}` passthrough) are legitimately glyphless: exempt any value that
contains no icon placeholder AND no leading separator run. Keep the exemption narrow and
comment it.

Run the gate. Checks D and E are EXPECTED TO FAIL on the current tree — that is the point;
it proves the gate has teeth. Do not fix them here; Task 2 does. Record the failing output in
the SUMMARY as the gate's own self-test (the same "prove it fails before trusting it" discipline
08-05 used for theme-doctor's D-17 gate).

**Verification method (MANDATORY — presence is not enough).** This phase already got burned
once: 08-05 found that U+F04FE/U+F04FF are PRESENT in the installed font's cmap but resolve to
the glyphs `md-target` and `md-taxi` — not the game controller the UI-SPEC assumed. A presence

look the codepoint up to get its glyph name. Print a codepoint→name table for every glyph you
intend to ship, put that table in the SUMMARY, and reject any codepoint whose name does not
describe the intended icon. Do not copy a codepoint from a cheat-sheet without running it
through this.

**Reference set — already cmap-verified, reuse verbatim.** `config-vertical.jsonc` holds a
correct glyph set (08-05 fixed it there and only there). Promote these upstream into
modules.jsonc so all four layouts inherit them, rather than leaving three layouts broken:
cpu U+F2DB (fa-microchip), memory U+F0C9 (fa-reorder), temperature format-icons
U+F2CB/U+F2CA/U+F2C9/U+F2C8/U+F2C7 (fa-thermometer scale), pulseaudio format-icons

**Not covered by the reference set — you must pick and NAME-VERIFY these yourself:** clock,
custom/theme, custom/waybar-layout, custom/power. custom/theme and custom/waybar-layout are the
two most-clickable buttons on the bar and currently render as a single space; custom/power

concept-appropriate glyphs, verify each by NAME, and record the table.

**Separator hygiene.** The horizontal formats currently lead with two spaces where a glyph was
deleted (cpu `"  {usage}%"`, memory, clock, network, pulseaudio-muted). Restore the glyph and
leave exactly ONE space between glyph and value. CHECK E of the lint gate enforces this.

**Remove the hardcoded Catppuccin hex.** The `clock.calendar.format` block hardcodes five
literal hex colours (#cba6f7, #cdd6f4, #585b70, #f5c2e7, #1e1e2e — Catppuccin Mocha). This
violates the project's core no-hardcoded-hex constraint and renders a dark-purple-on-dark
calendar tooltip on every light preset. Pango span `foreground=` cannot reference a GTK named

weight and underline markup instead (`<b>` for months/weekdays, plain for days, `<u><b>` for
today). The tooltip then inherits `tooltip label { color: @fg; }` from CSS and is automatically
correct in both light and dark with zero pipeline change. This is not a downgrade — it is
exactly the design rule the redesign is built on (chroma is reserved for state; a calendar
tooltip painting four competing hues is the same rainbow being deleted from the bar). Apply the
identical treatment to `config-vertical.jsonc`, which carries a copy of the same hex block.

security-hardened `mpris.tooltip-format` (WR-03 deliberately excludes attacker-controlled
metadata — leave it exactly as-is).

<task type="auto">
  <name>Task 3: Author theme.css — the semantic alias layer</name>
  <files>waybar/.config/waybar/theme.css</files>
  <action>
Create `waybar/.config/waybar/theme.css`. This becomes the ONLY waybar file permitted to name a
matugen palette token (CHECK B of the lint gate enforces it). Every layout sheet will import it
and speak in role names only.

It must first `@import url("../../.local/state/theme/waybar.css")` (the matugen-rendered 19-token
file), then re-export role aliases via `@define-color`. GTK3 supports colour expressions in
`@define-color` values — `alpha()`, `shade()` and `mix()` are first-class and may take another
`@name` as their first argument. The repo already relies on `alpha(@background, 0.90)` inline,
which proves the parser handles a named colour inside `alpha()`; this task extends the same
construct into a definition. If the parse gate in `theme-doctor` reports any fatal CSS error
after this lands, that construct is the first suspect — but it is expected to work.

Define these roles, and ONLY derive them from the 19 real tokens (re-read CORRECTION 1 —
there is no surface-container token; the neutral island surface is built from `@surface`):

Surfaces — the translucent island. `bar-surface` as `alpha(@surface, 0.55)`: this is the one
neutral surface the whole design rests on, and because it is derived from a token via alpha()
rather than hardcoded, it is automatically correct in light and dark with no branching.
`bar-surface-hover` as `alpha(@surface, 0.78)` for interactive feedback. `seg-surface` as
`alpha(@surface_variant, 0.40)` for the rare segment that genuinely needs to sit proud of the
island (use sparingly — the default is NO fill).

Foreground. `fg` as `@on_surface` (primary text/glyph). `fg-dim` as `@outline` (inactive
workspaces, idle glyphs). `fg-mute` as `alpha(@on_surface, 0.55)` (secondary text such as the
window title).

State — and chroma lives here and NOWHERE else. `accent` as `@primary` and `on-accent` as
`@on_primary` (active workspace, and only the active workspace, plus genuinely-active module
states). `warn` as `@tertiary`. `danger` as `@error` and `on-danger` as `@on_error`.

Geometry is NOT expressible as a GTK named colour, so the radius and size scale cannot live
here. Record it instead as a comment block at the top of this file so there is one documented
source of truth that the layout sheets follow by hand: radius 14px bar / 10px segment / 6px
workspace button; font 13px body, 16px glyph-only module, 18px vertical-column glyph; the
workspace-button min-width floor of 14px.

Add a header comment stating the alias-boundary rule explicitly (palette tokens appear in this
file and nowhere else; every other sheet uses role names), and stating that a role name must
never be added without a corresponding real token behind it.
  </action>
