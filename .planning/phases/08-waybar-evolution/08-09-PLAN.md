<planner_findings>
Four things were verified live on this machine during planning. They are not assumptions; act on them.

**F1 — There is NO backlight device on this host, and bare `brightnessctl` targets a LAN port LED.**
`ls /sys/class/backlight` is **empty**. `brightnessctl -c backlight g` prints `Failed to read any devices of class 'backlight'.` — and **exits 0 anyway**. Worse: `brightnessctl` with no `-c` selects `enp5s0-3::lan`, an Ethernet port LED. A brightness control wired to bare `brightnessctl` on this machine would dim a network port.

Consequence for D-27's brightness slider: swaync's native `backlight` widget requires a `device` string (schema default `intel_backlight`) which is **host-specific** — it would be wrong on this AMD desktop (no device at all) and wrong again on any laptop (`amdgpu_bl0`). Baking a discovered device name into a stow-tracked config is exactly the host-only state CLAUDE.md forbids. **Use swaync's generic `slider` widget backed by class-scoped `brightnessctl -c backlight` instead** — device-agnostic, reproducible on any host, reusing the brightness abstraction the repo already depends on. RESEARCH sanctions this explicitly ("Generic `slider` exists as a fallback if `backlight`'s native sysfs read doesn't suit this machine's hardware"), and UI-SPEC's own component list already names `slider` as an available widget. This is an implementation choice INSIDE locked decision D-27, not a scope reduction: a pointer-draggable brightness control ships. It is inert on a desktop with no panel to dim (correct — there is nothing to control) and functional on any laptop the dotfiles install to.

**Declare this deviation from the outline's literal `backlight` widget key in the SUMMARY, with this evidence.** Do not silently substitute.

**F2 — The active-toggle CSS selector is `button.toggle:checked`, NOT `.active`.**
The configSchema's prose says toggle buttons "receive the .active css class". The installed swaync 0.12.6's own shipped stylesheet (`/etc/xdg/swaync/style.css:472`) says otherwise, with its own comment: `.widget-buttons-grid flowboxchild > button.toggle:checked { /* style given to the active toggle button */ }`. **Styling `.active` alone would produce a toggle that never visually lights up when ON — a stale-looking ON/OFF display, which is precisely the drift class D-28 exists to kill, expressed in CSS.** Style `button.toggle:checked` as the primary selector.

**F3 — The glyphs you need are already cmap-verified, with one trap.**
Direct fontTools cmap + `hmtx` advance-width parse of `/usr/share/fonts/TTF/FiraCodeNerdFont-Regular.ttf` (the Phase 6/7 discipline) was run during planning:

| Codepoint | Glyph name | Present | Advance (÷ `M`) | Use |
|---|---|---|---|---|
| `U+F02B4` | `md-google_controller` | yes | 1.00 | **gaming toggle** |
| `U+F1FC` | `fa-paintbrush` | yes | 1.00 | **theme toggle** (same glyph the Super-key menu's Theme entry already uses) |
| `U+F009B` | `md-bell_off` | yes | 1.00 | **DND toggle** (already live as `dnd-none` in `config-full.jsonc`) |
| `U+F205` | `fa-toggle_on` | yes | 1.00 | **DO NOT USE** — see trap |

**The trap:** Phase 7's Super-key menu uses `U+F205` for its "Gaming mode" entry — but `U+F205` is `fa-toggle_on`, a *toggle switch*, not a gamepad. Inside a grid where every button is a toggle, that glyph is meaningless. Use `U+F02B4` (a real controller) for the gaming toggle. The theme toggle DOES reuse Phase 7's `U+F1FC` — same glyph, same script, same action, so the two surfaces stay visually consistent, which reinforces D-28's anti-drift intent.

You must still re-run the cmap gate yourself (Task 1). Never ship a codepoint you did not personally resolve from the installed font.

**F4 — swaync's own default config ships a live worked `buttons-grid` toggle.**
`/etc/xdg/swaync/config.json` contains a real WiFi toggle using `type: "toggle"` + `command` (reading the `SWAYNC_TOGGLE_STATE` env var swaync injects) + `update-command` (echoing `true`/`false`). It is a near-literal template for D-28's three toggles. Read it before writing yours.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Any application (incl. a browser rendering remote content) → swaync via D-Bus `org.freedesktop.Notifications` | Notification summary, body, and **inline action labels** are fully attacker-influenced strings rendered as markup-capable GTK labels in the panel. This is the only genuinely untrusted input in the plan. |
| `swaync/config.json` `command` / `update-command` strings → shell | swaync executes these through a shell with the session's privileges: `update-command` on every control-centre visibility change, `command` on every click. |
| State files (`~/.cache/gaming-mode`, `~/.local/state/theme/mode`) → `update-command` shell | File contents are read into a shell via command substitution on every panel open. Any local process able to write these files controls that substitution's content. |
| swaync `slider` `$value` → `cmd_setter` shell string | swaync textually substitutes `$value` into a shell command string before exec. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-08-40 | Tampering | State-file content → `update-command` command substitution | medium | mitigate | Every `$(cat ...)` is **quoted** and guarded (`2>/dev/null`, defaulting to the off value), and its result is only ever a right-hand operand of a string comparison — never a command word, never an argument to an invoked script, never `eval`'d. Crafted file content can therefore change what the toggle *displays*, but cannot inject a shell word. Asserted by a `grep -c 'eval'` == 0 criterion and by the quoted-substitution criterion in Task 1. |
| T-08-41 | Tampering / Spoofing | Notification **body** rendered as Pango markup in the panel | medium | mitigate | swaync owns notification escaping; this plan adds **no** widget that interpolates notification content into a shell command or into a markup-enabled label of its own. | T-08-42 | Spoofing | Notification **inline action label** (D-29) | medium | mitigate | The action label is supplied by the notifying app and rendered inside a clickable button.
