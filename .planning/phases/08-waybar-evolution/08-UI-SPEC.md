# Phase 8 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Domain note:** Not a web/component-library UI. This phase spans **five distinct visual/interaction surfaces**, all driven by the same bash/matugen pipeline established in Phases 1–6, plus one brand-new toolkit:

1. **waybar (existing 3 bars)** — OLED-safe luminance trim (BAR-01/D-06) + a behavior-preserving shared-include refactor (D-31/33/34). **No redesign** — this is a styling *trim*, not a new visual identity.
2. **waybar (new 4th layout: vertical/left)** — new JSONC composition + CSS, zero new render target (BAR-03).
3. **eww media popup** — brand-new component, brand-new render target, GTK3-based (BAR-04/D-18..25).
4. **swaync control-center panel** — widget rework: `mpris` removed, `slider`/`volume`/`backlight`/`buttons-grid` added (BAR-05/D-27..30).
5. **Visibility owner behavior** — a new interaction/state-machine layer with a real visual consequence (idle-dim, fullscreen/gaming unmap) but no new CSS surface of its own beyond one owner-written override file.

Every CSS surface below reuses the **same 19-key palette schema** locked in `05-UI-SPEC.md`/`06-UI-SPEC.md` (`primary, on_primary, primary_container, on_primary_container, secondary, on_secondary, secondary_container, on_secondary_container, tertiary, on_tertiary, surface, on_surface, surface_variant, on_surface_variant, background, on_background, outline, error, on_error` — this repo's live `waybar-colors.css`/`swaync-colors.css` templates render exactly these 19 keys, verified by direct read). **eww is the one genuinely new render target this phase adds** — see Color → Rendered-Target Inventory.

BAR-02 (pixel-shift) is explicitly allowed to end in a documented descope (D-09/D-10) — this file specifies the concrete mechanics to *attempt*, not a guaranteed shipped feature.

### Pixel-shift jitter mechanics (BAR-02, D-09 — spike parameters, not a committed feature)

| Parameter | Value | Kill criterion it must respect |
|---|---|---|
| Jitter magnitude | 2px | Must stay imperceptible as a "twitch" (D-09 kill criterion #1) — 2px is at the low end of what's typically sub-perceptible for a screen-edge bar; if the spike shows it's noticeable, **do not increase it — kill the feature**, per D-09's explicit instruction, don't tune around a failed perception test |
| Jitter interval | every 15 minutes | Slow enough that no reasonable viewer correlates two consecutive frames; must never coincide with or be driven by the visibility owner's own signal (D-09 kill criterion #3 — this must NOT become a second bar-mover; if it needs to coordinate with `waybar-visibility.sh` at all beyond "don't jitter while hidden," kill it) |
| Mechanism | `margin-left`/`margin-top` micro-adjustment via the same owner-CSS-file + SIGUSR2-reload pattern already used for idle-dim (reuse, not a new mechanism) | Must not reflow any window (D-09 kill criterion #2) — since idle-dim already proves CSS-only property changes on a mapped `window#waybar` don't reflow tiled windows, jitter should inherit that same safety property; if it doesn't, kill it |

If any kill criterion fires, BAR-02 closes as **descoped with evidence** in `08-VERIFICATION.md` (D-10) — not silently dropped. The standing hypothesis (D-01's auto-hide + D-06's low-luminance styling already remove most of the exposure) should be stated and evaluated explicitly, not assumed.

Exceptions beyond the above: none.

## Interaction Contract

### Visibility owner (BAR-01, D-01..08 — binding on the plan)

- **Two independent hide triggers, OR'd together (D-01):** idle-timeout and fullscreen. Either alone hides the bar; it only returns when **both** clear.
- **Idle-hide path:** CSS-dim, not unmap. The owner script writes `window#waybar.idle-dimmed { opacity: 0.05; }` (or empty, to reveal) to an owner-exclusive file (e.g. `~/.local/state/theme/waybar-visibility.css`, imported by every `style-*.css` **after** the theme import) and sends `SIGUSR2` (configured as `reload` — already the theme-switch signal, reused not repurposed). The surface stays mapped: **exclusive zone is kept** (D-04), no window reflow during normal idle cycles.
- **Fullscreen-hide / gaming-mode-hide path:** true unmap via `SIGUSR1` (configured as a fixed `hide` action, never `toggle` — D-03's explicit kill of the shared-toggle approach). **Exclusive zone is dropped** (D-04) — this is the genuinely-want-the-pixels case.
- **Reveal:** any input clears idle-hide naturally (the idle condition ended). Fullscreen-hide persists and is cleared **only** by the explicit bar-toggle keybind (D-02 — no edge-hover reveal, full stop; this is a hard rejection, not a tunable).
- **Animation (D-07):** **instant, not animated** — documented fallback, evidence-backed (waybar's layer-shell surface has no map/unmap animation primitive; CSS margin does not reposition the real surface; see `08-RESEARCH.md` Verdict 1). Do not build a bespoke animation harness.
- **Overlays are not a visibility intent (D-08):** opening walker, the swaync panel, or any picker never changes bar visibility state, in either direction. If the bar happens to be idle-hidden, it stays that way; opening a menu is itself input, so the idle condition resolves on its own with no special-casing needed.
- **Owner intent model (D-03):** every actor (idle watcher, fullscreen watcher, gaming-mode, keybind) calls one entrypoint with its own name + desired state (`waybar-visibility.sh <source> <hide|show>`); the owner computes the OR-union and only signals waybar when the computed result actually changes.

### Vertical layout (BAR-03, D-11..17)

- Appears on **every** monitor identically (D-15 — no `output` key, no per-monitor config).
- **Not** the default layout (D-16) — becomes a 4th valid value in the existing last-used-layout state file, selected via the same picker used for the other 3.
- Detail that doesn't fit the column (window title, now-playing text) surfaces **only** via native GTK tooltip on hover (D-13) — never a rotated/truncated text label.
- D-17's "full module re-test" gate: every module class used by every layout (including vertical) must resolve to a real named color in the rendered `waybar.css` (rerunnable gate, prefer folding into `theme-doctor`'s existing CSS-parse guard) **plus** a human visual pass on one light and one dark preset.

### Media popup anchoring and lifecycle (BAR-04, D-22/23)

- **Trigger:** the existing `mpris` bar segment's `on-click` action changes from `playerctl play-pause` to **open the media popup** (this is D-22's "rethink" — clicking the segment now opens the media center rather than toggling playback; play/pause moves inside the popup). `on-click-right` (`playerctl next`) and `on-scroll-up/down` (volume ±0.05) are **unchanged** — they don't conflict with the popup opening and remain useful as quick actions without opening it.
- **Anchoring (primary mechanism, D-23):** read `hyprctl cursorpos` at click time, clamp to the active monitor's bounds (`hyprctl monitors -j`), pass as `eww open media-popup --toggle --arg x=$X --arg y=$Y`. This is real, verified-available machinery (not fabricated) and works identically from every layout (horizontal, vertical, hidden-bar), since a hidden bar has no clickable segment anyway (consistent with D-08).
- **Fallback (zero-risk, if the cursor-position approach shows jitter/inaccuracy during implementation):** a fixed `:geometry` anchor near the top-right (mirroring where swaync opens), portable across all layouts with zero coordinate logic.
- **Close semantics:** re-click the trigger (`--toggle`), click-away (`:onlostfocus`), or Esc (`onkeypressed` keyevent) — all three must close the popup.
- **No "nothing playing" placeholder (D-25):** if there's no active player, there is no trigger segment and no popup — nothing to click, nothing to show.

### Notification panel (BAR-05, D-27..30)

- **Parity fix:** `custom/notification` (the bell button) lands in the floating layout (currently missing) and the new vertical layout — this is the literal, minimal parity fix, not a redesign of the bell itself.
- **Interact = inline actions + per-notification dismiss (D-29):** notification action buttons (e.g. a browser notification's "Open") must work from the panel, and each notification must be individually dismissable, not just via "Clear All." This is primarily a verification task against swaync's existing behavior plus styling the action buttons through the palette (already covered under Color above) — not new logic.
- **Toggle grid (D-28, hard constraint):** every toggle's `command` calls the exact existing script (`gaming-mode-toggle.sh`, `theme-switch.sh`, `swaync-client -dn/-df`) and every toggle's `update-command` reads the exact existing state file/query (`~/.cache/gaming-mode`, swaync's own DND state, the theme-engine's current-theme state). **No independently-derived state, no second copy of any toggle's logic** — the swaync `config.json` schema's `type: "toggle"` + `update-command` fields are purpose-built for exactly this call-out-and-read-back shape (live example already shipped in swaync's own default config, the WiFi toggle).
