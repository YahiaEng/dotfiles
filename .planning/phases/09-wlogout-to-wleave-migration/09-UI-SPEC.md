# Phase 9 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

> **Gate requirement (D-14, carried from Phase 6's WLOG-01 lesson):** every dimension below is
> necessary but NOT sufficient. Phase 6 shipped six unstyled wlogout buttons while CSS-parse,
> shellcheck, code-review, and theme-doctor were all green — automated gates only ever proved
> *token resolution*, never *appearance*. This contract does not close until a human has looked
> at a live `grim` screenshot of the rendered wleave capsules (dark preset, light preset, and a
> post-theme-switch reopen) and approved on sight. Do not mark this phase verified on parse/lint
> evidence alone.

**Domain note:** Not a web/component-library UI. This is a single GTK4/`gtk4-layer-shell`/
libadwaita surface (`wleave` 0.7.1) driven by the same bash/matugen theming pipeline as every
other surface in this repo (Phases 5/6/8/10). It replaces `wlogout` (GTK3) 1:1 — same six power
actions, same entry points, same theme-pipeline plumbing pattern — but is a genuine visual
**redesign**, not a port: transparent-window-plus-scrim (the Phase 10 AGS media-popup technique),
six discrete frosted capsules (the Phase 8 athena/floating capsule + rainbow language), and
`mix()`-derived hues (the Phase 8-14 vertical-bar technique). All three borrowed techniques are
proven elsewhere in this exact repo — see file citations throughout.

Two locked decisions (D-22 multi-monitor, D-10 reverse-stagger exit) are **not natively
achievable** on wleave 0.7.1 per `09-RESEARCH.md` Pitfalls 3–4. This contract specifies the
closest achievable alternative for both and requires the deviation to be recorded, not silently
dropped — see **Motion & Interaction Contract** below.

## Spacing Scale

Standard 8-point base scale (unchanged from every prior phase):

| Token | Value |
|-------|-------|
| xs | 4px |
| sm | 8px |
| md | 16px |
| lg | 24px |
| xl | 32px |
| 2xl | 48px |
| 3xl | 64px |

### Per-element application (D-02)

| Element | Value | Token |
|---|---|---|
| Capsule outer visible size | 96×96px | custom component dimension (multiple of both 4 and 8, but not itself a scale token — a deliberate component size, see GTK content-box math below) |
| Inter-capsule gap | 24px | `lg` |
| Corner radius | 24px | `lg` — within D-02's 20–24px range, chosen as the exact top of that range to land on-scale (matches the AGS media-card radius language at the upper end without exceeding it) |
| Hairline border (rest state, D-06) | 1px | stroke width, not a spacing token (same non-grid exception class as every prior phase's border widths — see 08-UI-SPEC "Scope note") |
| Capsule internal padding | 16px | `md` |
| Row-to-scrim vertical center | native — `GtkCenterBox` self-centers; no manual offset | n/a |

**GTK content-box carry-forward (Phase 6 finding #1, re-applied to a NEW location):** `09-RESEARCH.md`
confirms wleave self-sizes its *window* (no port of `wlogout.sh`'s outer-window geometry math is
needed — that whole problem class does not exist on this engine). But GTK's `min-width`/`min-height`
→ content-box-only rule is a general CSS-box-model fact, not a wlogout-specific bug, and it still
governs the **capsule's own visible footprint**: `min-width`/`min-height` set the content box;
padding and border are added on top. To hit the 96px outer target with 16px padding and a 1px
border:

```
CONTENT_BOX = OUTER_TARGET − 2×PADDING − 2×BORDER
            = 96px − 2×16px − 2×1px
            = 62px
```

Set `button { min-width: 62px; min-height: 62px; padding: 16px; border: 1px solid ...; }` — **derive
this value, do not hardcode a different padding/border combination without recomputing it**, exactly
the discipline `wlogout.sh`'s own comment already established for the outer-window case. Confirm the
actual on-screen capsule measures ~96px at the D-14 render check; if it doesn't, the padding/border
inputs — not the formula — are what changed.

**Vertical label centering (Phase 6 finding #2, DIFFERENT mechanism on GTK4 — do not copy blindly):**
`09-RESEARCH.md` Pitfall 1 confirms wleave positions the icon-less glyph label via an `Overlay` at
`yalign = height.unwrap_or(0.9)` — i.e. it defaults to sitting near the **bottom** of the button, not
centered, exactly reproducing Phase 6's visual symptom (glyph crowding the lower border) through a
**JSON config field, not a CSS `margin-bottom`**. Phase 6's `margin-bottom: 16px` trick is GTK3-only
and has no equivalent effect here. Fix: set `"height": 0.5` explicitly on every button object in
`layout.json` (leave `"width"` unset — its 0.5 default already centers horizontally). Treat 0.5 as
a starting value, not a guaranteed-correct one — re-measure at the D-14 render gate and nudge within
~0.45–0.55 if the installed font's glyph metrics sit off-center; this is exactly the kind of
DSL/render mismatch the render-and-look gate exists to catch.

## Typography

This surface has exactly **2 real typographic roles** — deliberately fewer than the standard
3–4-size guideline. wleave's UI is glyph-only (no descriptive body text; D-19 keeps keybind hints
out of the UI entirely; D-18/D-20 rule out any confirmation-dialog copy). Padding in a third
arbitrary size purely to hit a target count would violate this project's own repeated
one-token-per-real-consumer discipline (Phase 6/8 precedent) — so 2 is declared and justified here
rather than inflated.

| Role | Size | Weight | Line Height | Notes |
|------|------|--------|-------------|-------|
| Body | n/a | — | — | No body text on this surface |
| Label (hover/focus action-name reveal, D-08) | 13px | 400 | 1.2 | Matches the repo-wide 13px compact-label convention (Phase 6/8 SwayOSD/waybar tooltip precedent) |
| Heading | n/a | — | — | No heading text on this surface |
| Display (glyph) | 36px | n/a (glyph, not weighted text) | n/a | Scaled from the same visual ratio wlogout used (28px glyph / 72px button ≈ 0.39) applied to the new 96px capsule: 96×0.39 ≈ 37px, rounded to 36px |

**Show-keybinds (D-19):** `"show-keybinds": false` at the top level of `layout.json` — the `l`/`e`/`u`/`h`/`s`/`r` keyboard shortcuts stay functional but are never rendered as text. Do not add a visible key-hint label; this is a locked decision, not an oversight to "fix."

## Color

### Palette schema — reuses the existing 19-key schema, but exercises 4 KEYS NEVER PROVEN in this repo

Same schema as every prior phase (`primary, on_primary, primary_container, on_primary_container,
secondary, on_secondary, secondary_container, on_secondary_container, tertiary, on_tertiary,
surface, on_surface, surface_variant, on_surface_variant, background, on_background, outline,
error, on_error`). **D-03/D-04 require four additional M3 role keys this repo has never rendered
before: `tertiary_container`, `on_tertiary_container`, `error_container`, `on_error_container`.**
`09-RESEARCH.md` Assumption A1 / Pitfall 5 confirms a repo-wide grep found zero prior usage — only
`primary_container`/`secondary_container` and their `on_*` pairs are empirically proven to resolve
today. **Before committing `wleave-colors.css`, run the cheap dry-run RESEARCH.md prescribes:**
add the four new `@define-color` lines to a scratch copy of the template, run `theme-engine`'s
`generate.sh`, and grep the rendered output for a literal unresolved `{{...}}` token or an empty
hex value. Treat this as a required verification step, not an assumption carried into execution
unchecked.

### Six-capsule severity/hue mapping (D-03, D-04, D-05)

Left→right order is the locked severity gradient (D-05). Each capsule pairs a **container** color
(translucent frost fill) with its matching **on_container** color (glyph) — the exact M3 pairing
that avoids the 08-16 light-preset illegibility failure (a colored glyph directly on a neutral
translucent pill measured ~2–3:1 contrast in that phase; never repeat that mistake here).

| # | Action | Severity | Hue source | Frost fill (translucent) | Glyph color | Rest-state border |
|---|--------|----------|------------|---------------------------|-------------|--------------------|
| 1 | lock | least severe | native `primary` | `alpha(primary_container, 0.35)` | `on_primary_container` | `alpha(primary, 0.5)` |
| 2 | logout | | native `secondary` | `alpha(secondary_container, 0.35)` | `on_secondary_container` | `alpha(secondary, 0.5)` |
| 3 | suspend | | native `tertiary` | `alpha(tertiary_container, 0.35)` | `on_tertiary_container` | `alpha(tertiary, 0.5)` |
| 4 | hibernate | | derived `vhue-teal` | `alpha(mix(secondary_container, tertiary_container, 0.5), 0.35)` | `mix(on_secondary_container, on_tertiary_container, 0.5)` | `alpha(mix(secondary, tertiary, 0.5), 0.5)` |
| 5 | reboot | | derived `vhue-purple` | `alpha(mix(primary_container, error_container, 0.4), 0.35)` | `mix(on_primary_container, on_error_container, 0.4)` | `alpha(mix(primary, error, 0.4), 0.5)` |
| 6 | shutdown | most severe | native `error` | `alpha(error_container, 0.35)` | `on_error_container` | `alpha(error, 0.5)` |

**Derived-hue formulas reuse the exact Phase 8-14 `mix()` ratios and naming** (`vhue-purple =
mix(primary, error, 0.4)`, `vhue-teal = mix(secondary, tertiary, 0.5)` — durable finding: GTK CSS
`mix()` works inside `@define-color`, verified via theme-doctor's non-empty-provider check, no
WLOG-01-style discard). **This phase applies `mix()` at the *container* level for the first time**
(Phase 8 mixed base hues for opaque fills; here both the container-tint and the on-color need their
own mix so the frost-fill/glyph contrast pairing holds for the two derived capsules too) — flagged
in `09-RESEARCH.md` Open Question 1 as unverified until rendered. Confirm visually at D-14 that both
derived capsules read with the same contrast quality as the four native ones; if `mix()`-of-mix
composited with the 0.35 frost alpha reads illegibly, the fallback is a manual `alpha()`-only tint
of the derived hue with a manually-chosen `on_*` pairing from the nearest native role — record as a
deviation if taken, don't silently improvise.

### Transparent-window + scrim (D-01, D-07) — the AGS/10-06 technique, reused verbatim

```css
/* Source: 09-RESEARCH.md Pattern 2, widget-tree-verified against wleave@0.7.1 src/app/mod.rs.
   GtkCenterBox and GtkBox share the CSS node name "box" in GTK4 — a bare `box{}` selector
   would ALSO match the nested buttons-row box (09-RESEARCH.md Pitfall 2). The direct-child
   combinator scopes the scrim to ONLY the outer CenterBox. */
window {
    background-color: transparent;   /* D-01 prerequisite, same as ags/style.scss line 44 */
}
window > box {
    background-color: rgba(0, 0, 0, 0.40);   /* D-07 starting point — tune live at D-14 */
}
```

Starting scrim alpha is **0.40** (D-07's stated ~40% starting strength). Tunable range for the D-14
live checkpoint: 0.30–0.50 — must read as a dim, not a near-opaque cover (the desktop should stay
recognizable behind it, matching the AGS media-popup's "gentle blur, not a solid panel" standard).
Re-verify the `window > box` selector actually scopes correctly on first render — this is derived
from source-code widget-tree analysis, not an actual on-screen render, and this phase's entire
premise is that CSS logic without a render check is exactly how WLOG-01 shipped broken.

**Blur strength is out of scope, permanently:** `decoration:blur` is a global Hyprland setting; no
`layerrule` can set a per-surface blur strength (ROADMAP.md, CONTEXT.md both restate this). Do not
attempt to tune "how strong the blur looks" via anything other than the scrim alpha above — that
alpha is the *only* wleave-local lever on how much desktop reads through, exactly as it was for
wlogout.

### 60/30/10 framing

This surface is six independent color islands rather than one dominant/accent pairing, so — same
framing 06-UI-SPEC used for wlogout — the 60/30/10 split describes *screen real estate*, not a
single hue:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | full-screen scrim, `rgba(0,0,0,0.40)` over the transparent window | Backdrop; the desktop remains visible/blurred through it |
| Secondary (30%) | the six capsules' rest-state translucent frost fills (0.35 alpha, per-hue) + 1px hairline borders | Collectively the "surface" layer — always visible, low-saturation until interaction |
| Accent (10%) | the hover/focus-state saturation increase (fill alpha up, border to full opacity + glow, D-08) + the always-present `on_*_container` glyph colors | **Reserved for:** glyph fills and the interaction-state delta only — never applied to the scrim, never used to make a rest-state capsule "pop" above its neighbors |
| Destructive | `error` / `error_container` (shutdown only) | Reserved for the single most-severe action. `reboot`'s derived `vhue-purple` deliberately approaches but does not equal `error` — preserves the severity gradient; no other capsule may borrow `error`/`error_container` |

## Motion & Interaction Contract

Beyond the template's standard sections — this phase's design language is motion-heavy (D-08,
D-10) and includes two decisions research proved are not natively achievable (D-22, D-10's
reverse-stagger half). Both are specified here as pre-authorized fallbacks per CONTEXT.md's own
Claude's-Discretion clause, not open questions for the planner to re-litigate.

### Entrance (D-10)
Staggered pop/slide-in, left→right, ~30–40ms offset per capsule (use 35ms), total under ~350ms
including each capsule's own transition. Each capsule: opacity 0→1 + slight translate-up
(~8–12px) + scale ~0.9→1.0, `cubic-bezier` easing in the same family wlogout already used
(`cubic-bezier(0.55, 0, 0.28, 1.68)` — slight overshoot, "lively" per CONTEXT.md's specifics).
Implement via wleave-native options if 0.7.1 exposes any (verify against the CLI/config surface
enumerated in `09-RESEARCH.md`); otherwise GTK4 CSS `@keyframes`/`animation-*` on the button/label
nodes (WebSearch-confirmed supported in GTK4 CSS per RESEARCH's Secondary sources).

### Hover / keyboard focus (D-08) — must render identically for both
- Frost fill alpha: 0.35 → ~0.55
- Border: reduced-alpha hue → full-opacity hue, optionally with a soft glow (`box-shadow` in the
  same hue, low spread)
- Scale: +5–8% (use 6%)
- Action-name label: fades + slides up into place below the capsule (13px Label role, see
  Typography)

### Dismissal (D-18)
Esc **and** click-away on the scrim — both native/unconditional in wleave 0.7.1 (`09-RESEARCH.md`
confirms click-away is *already* built in via an always-active `GestureClick`, no
`--close-on-lost-focus` flag needed and that flag must stay `false` per D-18/D-20 — it's a
*different*, focus-loss-triggered behavior that would add an unwanted extra dismissal path). No
toggle logic (no pgrep/pkill) — open-only semantics.

### Exit animation — LANDMINE, pre-authorized degradation (D-10 + Pitfall 4)
`09-RESEARCH.md` confirms wleave's `on_option()` calls `window.set_visible(false)` **synchronously,
before** the command-delay elapses — there is no window-visible "closing" interval a GTK CSS
transition could animate, and per-capsule reverse-stagger is very unlikely to be achievable at all
(the whole window vanishes in one call, no per-widget teardown phase). **Target, in priority
order:**
1. A compositor-level exit affordance via `layerrule = animation <style>, match:namespace wleave`
   (Hyprland 0.55.4 confirmed to support the `animation` layerrule keyword) — attempt this first;
   whether it actually fires on wleave's client-initiated hide (vs. only a compositor-initiated
   close) is unconfirmed (`09-RESEARCH.md` Assumption A2) and must be checked live.
2. If (1) doesn't fire or doesn't read as an animation: degrade to a fast whole-window fade.
3. If neither is achievable: ship an abrupt cut and **record the deviation explicitly** in the
   phase summary — do not silently claim D-10 was fully delivered.
**Non-negotiable regardless of which tier is reached:** the power action must fire immediately on
click — no exit-animation attempt may ever delay `sh -c "<action string>"` execution. This is
locked (D-10's own final clause), not a trade-off to weigh against visual polish.

### Multi-monitor — LANDMINE, pre-authorized deviation (D-22 + Pitfall 3)
wleave opens exactly one window on the compositor-chosen (typically focused) output; there is no
per-output targeting API on 0.7.1. D-22's literal spec ("scrim on ALL monitors, capsules on the
focused one") is **not achievable** — ship single-output behavior (scrim + capsules together, one
monitor only; other monitors show nothing) and **record this as a documented deviation**, not a
silent scope cut. Do not attempt a multi-instance-per-output workaround — research explicitly
found that would put a full interactive capsule row on every monitor, a worse UX mismatch against
D-22's intent than simply not dimming the other monitors.

### Render-gate coverage required (D-14, D-15, D-17)
The blocking human visual checkpoint must cover, with `grim` screenshot evidence:
1. Dark preset, cold open
2. Light preset, cold open
3. A live theme switch, then reopen (spawn-per-open means "re-theme" = next open, confirmed
   nothing in `lib/reload.sh` needs a wleave-specific action)
4. Hover/focus state on at least one capsule (proves D-08's tint/border/scale/label-reveal
   together, not just rest state)
5. Live spot-check: lock, suspend, logout actually perform their action (D-17) — shutdown/reboot
   are trusted by command-string byte-parity with the Phase-4-audited strings, not re-executed live
