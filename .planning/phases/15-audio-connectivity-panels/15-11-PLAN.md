<objective>
Close gap **G-15-1**: the wifi scan progress line moves too fast, and pressing Rescan
produces no feedback at all.

Two independent root causes, both proven with live measurement:

**RC1 (too fast).** The indeterminate sweep is an infinite `SequentialAnimation` whose two
legs bind `Motion.emphasizedInDuration` (375ms) and `Motion.emphasizedOutDuration` (187ms)
— MD3 **one-shot enter/exit transition** tokens being used as a continuous **loop period**.
Full cycle 562ms at the current `lively` scale against MD3's ~2000ms reference for an
indeterminate linear indicator. Enabling condition: `motion.json` already carries three
loop-period tokens (`ambient` 1250ms, `blink-slow` 1250ms, `blink-fast` 625ms) but
`Motion.qml` exposes an alias for none of them — `Motion.qml:56`'s `_pairNames` is a fixed
four-entry positional list that never reaches them, and the only reachable loop token is
`borderRotateDuration` (10000ms, far too slow). No correctly-scaled loop period was
reachable from QML at all.

**RC2 (no rescan feedback).** AND-gated, both halves present: (a) `WifiBackend.scanning` is
a LEVEL, not an EDGE — it reads back `wifiDevice.scannerEnabled`, which the panel-lifecycle
`Binding` already forces true whenever the panel is open, and `rescan()` writes
false-then-true synchronously in one JS frame. Measured directly in a qml6 harness: every
UI-bound property is byte-identical before and after the press. (b) The `refreshControl`
glyph carries no pressed/active/busy state whatsoever — a constant-coloured `Text` whose
only affordance is a hover tooltip.

Purpose: make the indicator honest — a readable pace, and a press that says something.

Output: a loop-period token reachable and scale-safe from QML, a synthesised bounded
in-flight edge, a refresh control that acknowledges its own press, and the spec amended so
the fix is not flagged as a deviation.

<design_decisions_resolved>
Three choices this plan makes on the executor's behalf, each with its reason, so they are
not re-litigated mid-execution:

**1. The multiplier is emitted, not re-derived.** To keep a loop period from shrinking
under `reduced`, QML has to know the active multiplier. The rendered `motion.json` carries
`motion_scale` (a name) but not the number. The two rejected alternatives: hardcoding a
scale→multiplier table in `Motion.qml` (duplicates `motion.json`'s own authored `scales`
block and silently drifts the moment that table is retuned — exactly the zero-duplicate-value
failure class this pipeline exists to prevent), and reading the authored `motion.json`
directly from QML (breaks `Motion.qml`'s stated discipline of consuming only the render
target). `lib/motion.sh` already has `$multiplier` in scope at the `jq -n` call that writes
the QML target; emitting it is one line, and it mirrors the two top-level keys
(`motion_scale`, `motion_enabled`) already there.

**2. Only the two `duration:` bindings change on the sweeps — the easings stay.** The defect
is a one-shot *duration* token used as a loop *period*. `emphasizedInEasing`/
`emphasizedOutEasing` are bezier **shapes**, not periods; an accelerate-then-decelerate
sweep is a legitimate and deliberate feel, and `ambient`'s own easing is `linear`, which
would flatten it. Changing the easings would be an unrequested feel change.

**3. `ambientDuration` carries the scale-floor clamp; `borderRotateDuration` deliberately
does not.** These two are asymmetric on purpose and the asymmetry must be written down in
`Motion.qml`'s header: `border-rotate` has to stay in lockstep with Hyprland's own
`borderangle`, which Hyprland scales by the same multiplier, so clamping it would make the
drawer's rim drift out of step with every window border on screen. `ambient` has no
external counterpart and is consumed only by in-shell indicators, so it is free to be
scale-floored — and must be, because a faster indicator under `reduced` is the opposite of
what that preset means.
</design_decisions_resolved>

<scope_fence>
Two adjacent instances of the same token misuse are **deliberately not changed** by this
plan, and the reason is recorded here rather than left as a silent omission:

- `WifiPanel.qml`'s `pendingGlyph` opacity pulse (around :574-595) and its bluetooth
  counterpart bind the same one-shot tokens as an infinite loop period. They are **pulses**,
  not sweeps: a pulse's whole message is "busy", and a fast pulse still reads as busy,
  whereas a sweep's message is "progress at a readable pace", which is what the user
  reported as broken. Changing pulse rhythm is an unrequested feel change on a surface
  nobody complained about.
- Both pulses do inherit the same `reduced`-makes-it-faster inversion. Record that in the
  SUMMARY as a known, named, open item for a future phase — do not fix it here and do not
  leave it undocumented.

The bluetooth **discovery line** IS in scope, and is not scope creep: it is the identical
indeterminate-line idiom, bound to the identical wrong tokens, in the identical shared
indicator grammar. Shipping a corrected wifi line beside an uncorrected bluetooth line
running 4.4x faster would be a visibly inconsistent pair inside one phase.
</scope_fence>
