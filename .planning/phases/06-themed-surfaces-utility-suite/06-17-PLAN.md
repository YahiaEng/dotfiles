  <action>
**WR-01 (`color-picker.sh`, lines 25-32).** The failure branch reads `$ERR_FILE` (hyprpicker's **stderr**) and treats empty stderr as an Esc-cancel (`exit 0`, silent). But hyprpicker never writes diagnostics to stderr — upstream `src/debug/Log.cpp` states "hyprpicker only logs to stdout", so every ERR/CRIT message ("zwlr_screencopy_v1 not supported, can't proceed", "No wayland compositor running!", xkb failures) goes to **stdout**, which the failed command substitution captures into `$HEX` and throws away. Net result: every genuine failure mode takes the silent-cancel path.

Restructure so failure is classified by **stdout content**, not by empty stderr:
  - Capture hyprpicker's stdout into a variable (call it `OUT`) with stderr still redirected to `$ERR_FILE`.
  - On non-zero exit: build the error text from **both** streams (`$ERR_FILE` contents and `$OUT`), passed through the existing `sanitize` function. If the combined, sanitized text is empty, that is the genuine silent Esc-cancel -> `exit 0`. Otherwise `notify-send` the sanitized error with `-i dialog-error -t 6000` and `exit 1`.
  - On success: derive `HEX` from the **last line** of `$OUT` (`tail -n1`) before the existing `tr -d '[:space:]'` strip. This is the secondary half of WR-01: on a compositor that emits WARN lines to stdout during a *successful* pick, those lines would otherwise concatenate into `$HEX` and corrupt the copied value.
  - Add a format guard after the strip: the value must match a six-hex-digit colour with an optional leading `#`; if it does not, `exit 1` rather than copying garbage to the clipboard.

Keep the existing `sanitize` function (head -c 200 + control-char strip) and the existing `trap 'rm -f "$ERR_FILE"' EXIT` exactly as they are — both are correct and are the T-06-18 mitigation.

**WR-02 (`clipboard-wipe.sh`, line 12).** Verified on this machine: `cliphist list` exits **1** with "opening db: please store something first" when nothing has ever been stored — which is also the state left behind by a successful wipe. Under `set -euo pipefail`, the `COUNT=$(cliphist list 2>/dev/null | wc -l | tr -d '[:space:]')` assignment therefore fails and `set -e` kills the script **before the confirm dialog appears**. The existing `2>/dev/null` hides the message but not the exit code.

Fix it so a failed/empty `cliphist list` yields a count of zero instead of aborting: append `|| true` to the pipeline inside the command substitution (pipefail makes the whole pipeline non-zero; `|| true` neutralises that while `wc`'s output is still captured), then default the result with a parameter expansion so an empty capture becomes `0`. The confirm dialog must then render with a count of 0 and the destructive-confirm default-No ordering (`printf 'No\nYes\n'`) unchanged.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| subprocess stderr/stdout (`hyprpicker`, `gpu-screen-recorder`) -> `notify-send` | Untrusted-shaped text from a subprocess crossing into a notification body. Already mitigated by the `sanitize` function (truncate to 200 bytes + strip control chars, T-06-18); WR-01's fix must **preserve** that, because it newly routes **stdout** into the notify path too. |
| `pkill` pattern -> process table | A pattern that is broader than intended is a kill primitive aimed at processes the script does not own. |
| clipboard contents (`cliphist` db) | Plaintext clipboard history, potentially containing secrets. The wipe path is the user's only manual purge control. |
