# Permission Grant Side-by-Side Review (D-16 compensating control)

Phase 13.1, plan 13.1-07. This document is the compensating control the
baseline manifest (`.hypr-baseline/MANIFEST.md`, "Documented coverage
limits (D-16)") committed to: permission grants are read once at Hyprland
startup and are **not** reachable through `hyprctl getoption` — no
per-grant introspection key exists on this installed binary — so the
phase's automated `hypr-equivalence-check` gate structurally cannot cover
them. `.hypr-baseline/uncovered.txt`'s four `permission-grant:` entries
name this document as their compensating check (corrected in this plan
from a stale "plan 13.1-06" pointer to the live "plan 13.1-07" pointer —
13.1-06 ported the animation surface, not permissions; this document is
the actual deliverable).

Because this gate cannot be mechanized, the review below is a **recorded
character-by-character textual comparison**, not a live enforcement test.
It proves *fidelity of translation* (the Lua port says exactly what the
hyprlang original said) — not that permission enforcement itself works
end-to-end. Live enforcement is explicitly out of scope here, unchanged
from `permissions.conf`'s own header: Phase 16 (OVER-04) must perform that
proof itself before depending on this allow list in practice.

a regular-expression alternation, or a directory prefix — confirmed
mechanically below, not just by eye.

### Explicit divergence check

Zero divergences found. For completeness, the check that would have
caught a broadened path: a regex-metacharacter scan
(`[()|*?[\]]`) over all four Lua `binary` values returned no matches —
none of the four paths contains `(`, `)`, `|`, `*`, `?`, `[`, or `]`. This
matters specifically because the vendor-shipped example this port's call
form is modeled on (`/usr/share/hypr/hyprland.lua`, lines 76-78) uses
exactly this kind of alternation (`/usr/(bin|local/bin)/grim`) for the
same class of binary — this port copies the vendor's **call shape only**
(the `hl.permission({...})` table form), never its path style (T-13.1-02).

## Mechanism check (live, via `hypr-lua-harness`)

Run against a nested Lua-booted instance with `config/permissions.lua`
loaded through the real `require()` chain (not a synthetic fixture):

```bash
hypr-lua-harness start
hypr-lua-harness hyprctl configerrors
hypr-lua-harness hyprctl -j getoption ecosystem:enforce_permissions
hypr-lua-harness stop
```

**Registration:** all four `hl.permission({...})` calls and the
`hl.config({ ecosystem = { enforce_permissions = false } })` call
registered with **zero** `configerrors` output — both immediately after
harness start (when the four grants first load) and again after an
explicit `hyprctl reload` mid-session. No `hl.permission: expected
{ binary, type, mode }` diagnostic (the malformed-table error this
build's field validator is confirmed, in 13.1-LUA-FINDINGS.md's
`hl.permission()` calling-convention spike, to raise for a genuinely
malformed grant) appeared for any of the four real grants.

**`ecosystem:enforce_permissions` readback:**

```
{"option": "ecosystem:enforce_permissions", "bool": false, "set": true }
```

Compared against the committed pre-migration baseline
(`.hypr-baseline/options.jsonl`):

```
{"option": "ecosystem:enforce_permissions", "int": 0, "set": true }
```

**Equal, normalized.** `bool: false` and `int: 0` are the same disabled
state — the identical `int`↔`bool` JSON-shape divergence already
established and normalized by `hypr-equivalence-check` in 13.1-02/13.1-03
(the config-manager backend that SET the option determines the JSON
type-key name, not the semantic value). `enforce_permissions` is `false`
under both the hyprlang original and this Lua port — the file ships
inert, exactly as `permissions.conf`'s own header states it does today.

## SHIPS INERT — unchanged from the hyprlang original

`enforce_permissions` is `false` in both the ported Lua file and the
hyprlang original it replaces. None of the four grants are actively
enforced on this build today, under either config format. Per
`permissions.conf`'s own header (carried across verbatim into
`permissions.lua`'s comments): grants are read **once** at compositor
startup, and `hyprctl reload` does **not** apply a change here — a full
Hyprland restart is required. Phase 16 (OVER-04) activates enforcement by
flipping the single `enforce_permissions` value to `true` and restarting
Hyprland; Phase 16 must independently verify that live enforcement itself
works (admits these four clients, denies everyone else) — this review
proves the four grants and the ecosystem option are byte-faithful
translations, not that enforcement functions end-to-end. That live-restart
proof was also explicitly out of scope for the original Phase 11 grant
authoring, for the same reason (this machine's operator session runs as a
child process of the compositor being restarted).

## Conclusion

All four permission grants and the `ecosystem:enforce_permissions` option
are translated with character-level fidelity: no path broadened, no type
or mode changed, no grant added or dropped. This closes the D-16
compensating control the baseline manifest committed to for the one
surface `hypr-equivalence-check` structurally cannot introspect.
