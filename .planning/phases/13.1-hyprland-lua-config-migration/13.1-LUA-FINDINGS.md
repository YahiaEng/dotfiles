## require() root behaviour (RESEARCH Assumption A1 — now VERIFIED, not cited)

**Claim tested:** Hyprland's `require()` prefixes every module path with the Hyprland config root (`$XDG_CONFIG_HOME/hypr`), and that root follows `XDG_CONFIG_HOME`, not a hardcoded `~/.config/hypr`.

**Command:**
```bash
ROOT="$(mktemp -d)"
mkdir -p "$ROOT/hypr/state" "$ROOT/outside"
cat > "$ROOT/outside/hyprland-tokens.lua" <<'EOF'
return { gaps_in = 42, colors = { outline = "rgba(6272a4ff)" } }
EOF
ln -s "$ROOT/outside/hyprland-tokens.lua" "$ROOT/hypr/state/tokens.lua"
cat > "$ROOT/hypr/hyprland.lua" <<'EOF'
local ok, tokens = pcall(require, "state.tokens")
if not ok or type(tokens) ~= "table" then tokens = {} end
hl.config({
    general = {
        gaps_in = tokens.gaps_in or 5,
        col = { inactive_border = tokens.colors and tokens.colors.outline or "rgba(ffffffff)" },
    },
})
EOF
XDG_CONFIG_HOME="$ROOT" Hyprland > "$ROOT/nested.log" 2>&1 &
# ... poll hyprctl instances -j for the new PID ...
hyprctl -i <signature> -j getoption general:gaps_in
hyprctl -i <signature> -j getoption general:col.inactive_border
```

**Output:**
```
{"option": "general:gaps_in", "css": "42 42 42 42", "set": true }
{"option": "general:col.inactive_border", "gradient": "ff6272a4 0deg", "set": true }
```

**Verdict:** CONFIRMED. `require()`'s root follows `XDG_CONFIG_HOME` (the config root actually used is `$XDG_CONFIG_HOME/hypr`, not a hardcoded `~/.config/hypr`), and `require("state.tokens")` resolves through a RELATIVE-outside symlink (`$ROOT/hypr/state/tokens.lua` → `$ROOT/outside/hyprland-tokens.lua`, a file structurally outside the config root) to a real file living outside the config tree. This is the exact mechanism `stow.sh`'s `~/.config/hypr/state/tokens.lua` → `~/.local/state/theme/hyprland-tokens.lua` symlink relies on — proven, not assumed.

## New finding: `hyprctl getoption` JSON key-name/type differs between hyprlang and Lua for the SAME semantic value

**Not anticipated by CONTEXT.md/RESEARCH.md — found live during the end-to-end proof above.** Three of the seven `general:` keys report a DIFFERENT top-level JSON key name/type when the same value is set via the Lua config manager instead of the hyprlang parser, even though the underlying value is semantically identical:

| Key | hyprlang (baseline) | Lua (nested, this plan) | Semantically equal? |
|---|---|---|---|
| `general:gaps_in` / `gaps_out` | `"custom": "5 5 5 5"` | `"css": "5 5 5 5"` | Yes — value string identical, only the JSON field NAME differs (`custom` vs `css`) |
| `general:col.active_border` / `col.inactive_border` | `"custom": "ffff79c6 ..."` | `"gradient": "ffff79c6 ..."` | Yes — value string identical, only the JSON field NAME differs |
| `general:allow_tearing` | `"int": 0` | `"bool": false` | Yes — `0` and `false` are the same disabled state, but the JSON field NAME **and type** both differ (int vs bool) |
| `general:border_size` | `"int": 3` | `"int": 3` | Identical, no divergence at all |
| `general:layout` | `"str": "dwindle"` | `"str": "dwindle"` | Identical, no divergence at all |

**Why it happens:** the two config-manager backends (hyprlang parser vs the Lua config manager) apparently serialize `hyprctl getoption`'s JSON differently for CSS-shorthand (gap/CSSGapData), gradient, and boolean-typed options — a Lua `true`/`false` literal produces a genuine JSON boolean field, where hyprlang's own `0`/`1` int convention for the same conceptual boolean produces an int field. This is inherent to which parser SET the option, not a bug in either config.

**Implication for the full equivalence gate (owned by a later plan, likely the cutover plan):** `hypr-equivalence-check`'s current `options.jsonl` diff is a byte-exact `diff -u` over each `hyprctl -j getoption` line — that mechanism WILL report a spurious divergence for every boolean-typed and CSS-shorthand-typed option once the full config is ported, even though nothing is actually broken. The gate's current all-or-nothing exact-match posture (D-10) will need either (a) a semantic-equality comparison layer for these known representation-only fields, or (b) each such divergence individually recorded as intended and reasoned, exactly as D-10 already anticipates for the general case ("every divergence individually recorded as intended and reasoned"). This finding is handed off, not fixed here — this plan's own narrower verification (the table above) used semantic-value comparison directly, which is why Task 1's acceptance criteria are satisfied despite these three representation differences.

**RESOLVED in plan 13.1-03 Task 3** (authorized scope addition, human decision
at the 13.1-02 checkpoint): `hypr-equivalence-check`'s `options.jsonl`
comparison was changed to option (a) above — a normalized `(option,
normalized_value)` comparison discarding the type-key name and folding
`bool`<->`int`. See the "13.1-03 Task 3: Equivalence-gate normalization"
section below for the implementation evidence, and `COVERAGE.md`'s
"Documented gate limits" section for the named assumption this rests on
and the (separate, more severe, NOT normalized) `binds.json` finding this
same task surfaced.

## Rollback procedure (verified)

**Activate** (repo-side rename + redeploy + a compositor start):
```bash
mv hypr/.config/hypr/hyprland.lua.disabled hypr/.config/hypr/hyprland.lua
./stow.sh
# then a real compositor start (next login, or an explicit restart)
```
Renaming the REPO-SIDE file (not only the deployed symlink) is what makes this survive a `stow.sh` re-run — `stow.sh` restows package contents by name, so a rename purely of the deployed `~/.config/hypr/` symlink would be silently reverted back to `hyprland.lua.disabled` the next time `stow.sh` runs, while a repo-side rename is what `stow.sh` actually re-deploys.

**Deactivate** (exact inverse):
```bash
mv hypr/.config/hypr/hyprland.lua hypr/.config/hypr/hyprland.lua.disabled
./stow.sh
# then a real compositor start
```

Both directions verified this plan via the nested-instance equivalent (`XDG_CONFIG_HOME`-scoped throwaway roots with/without a `hyprland.lua` present) — see "Format-selection determinism" and "Rollback: hyprland.lua absent" above. Neither direction was exercised against the LIVE session (D-09/D-12: the legacy tree must stay untouched and bootable for the whole phase); this procedure is recorded as the verified COMMANDS, not as something actually run against `~/.config/hypr/` this plan.

## The field-validator discovery (corrects 13.1-02's "unknown keys are
tolerated without complaint" characterization for `hl.window_rule` /
`hl.layer_rule` / `hl.permission`)

13.1-02's `getoption` finding left an open worry: does this Lua config
manager silently swallow unknown table keys (the T-13.1-10 silent-no-op
failure mode), the same way an unset hyprlang variable would just not take
effect? Tested directly with a deliberately bogus field name:

**Command:**
```lua
hl.window_rule({
    name = "spike-control-bogus",
    match = { class = "^(spike-bogus-window)$" },
    totally_bogus_property_xyz_control = true,
})
```
```bash
hypr-lua-harness hyprctl reload
hypr-lua-harness hyprctl configerrors
```
**Output:**
```
/tmp/.../hyprland.lua:84: hl.window_rule: unknown field 'totally_bogus_property_xyz_control'
```

**Verdict:** CONFIRMED — `hl.window_rule`, `hl.layer_rule` and `hl.permission`
all validate their table argument's field names against a known schema at
config-load time and report a precise `configerrors` diagnostic
(`<file>:<line>: hl.<fn>: unknown field '<name>'`) for any unrecognised key.
This is **materially better** than the silent-no-op scenario RESEARCH.md's
A3 worried about, and is the mechanism every VERIFIED verdict below relies
on: pair the real candidate key with a `<key>xyz` misspelling on a sibling
rule in the same reload, and the presence/absence of an `unknown field`
line for each is the live evidence.

## Harness gotcha discovered this task: the entry point is copied, not
## symlinked

`hypr-lua-harness start` copies `hyprland.lua.disabled` into the
throwaway root as a static file (`grep -vx ... > $ROOT/hypr/hyprland.lua`)
at **start time**, whereas every other file under `~/.config/hypr/`
(including everything `require()`d, e.g. `config/keybinds.lua`) is
**symlinked** into the throwaway root. Consequence: editing
`hyprland.lua.disabled` and running `hyprctl reload` against an
**already-running** harness instance is a silent no-op — the reload
re-executes the STALE copy captured at `start` time, not the edited file.
Editing a `require()`d module (e.g. `config/keybinds.lua`) and reloading
DOES pick up the change immediately, because that file is reached through
the symlink. First diagnosed when a full options.jsonl readback showed
`set:false` and default values for every key this task added — not a
Lua/API problem at all, just a stale harness copy. Fix: `hypr-lua-harness
stop && hypr-lua-harness start` after any edit to `hyprland.lua.disabled`
itself (not needed for edits to any `require()`d `config/*.lua` module).
This is a durable operational finding for every remaining plan in this
phase that edits `hyprland.lua.disabled` directly (13.1-06 and later).
