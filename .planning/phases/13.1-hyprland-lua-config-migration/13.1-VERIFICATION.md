### Gap 2 Closure — CR-01, `stow.sh` `~/Pictures` fold bug

**Independently reproduced, not taken on trust:**

I ran the same class of proof the executor claimed, from scratch, using `git archive HEAD` (commit `9d57343`) into a throwaway `$HOME`:

1. **With the fix (real `stow.sh`, line 181):** ran the full script against a fresh throwaway `$HOME` (no pre-existing `~/Pictures`). Result: `$HOME/Pictures` is a **real directory** (`file` confirms "directory", not a symlink); `$HOME/Pictures/Wallpapers` and `$HOME/Pictures/Screenshots` are both real directories; only individual theme subdirectories (`anime`, `catppuccin`) and `current.jpg` are symlinked into the repo, exactly the intended per-leaf-entry stow behavior. Script exited 0.
2. **Without the fix (same script, line 181 deleted to reproduce the pre-fix state):** ran again against a second fresh throwaway `$HOME`. Result: `$HOME/Pictures` folds into a **single symlink** pointing at `dotfiles/wallpapers/Pictures` — reproducing the exact bug CR-01 described, confirming the fix is both present and load-bearing (not a no-op change).

This closes the gap. `stow.sh` line 181 (`mkdir -p "$HOME/Pictures/Wallpapers" "$HOME/Pictures/Screenshots"`) runs before the `PACKAGES` restow loop at line 183, mirroring the pre-create idiom already used for `~/.config/hypr` (line 116) and `~/.local` (line 143).

**One accuracy note on the fix's own commentary (not a functional gap):** the fix's audit-note comment (lines 168-180) states "every OTHER package in the PACKAGES array ships exclusively under `~/.config/<pkg>/...` or `~/.local/<pkg>/...`" and concludes `wallpapers` is "the ONLY package whose shipped tree roots at something other than .config/ or .local/ directly under $HOME." This is not quite accurate: `zshell/.zshrc` also ships a top-level entry directly under `$HOME` (`zshell/.zshrc` → `$HOME/.zshrc`), outside `.config`/`.local`. However, this does **not** represent an unfixed instance of the same bug class: the fold bug is specifically about a *directory* getting symlinked whole when its parent doesn't yet exist; `.zshrc` is already a leaf file, so there is no directory to fold — stow either symlinks the single file directly (target absent) or conflicts loudly (target present as a real file), neither of which silently redirects writes into the repo tree the way a directory fold does. I verified this by including `zshell` in both throwaway-`$HOME` reproduction runs above — `$HOME/.zshrc` came through as a normal file-level symlink in both cases, with no fold behavior. This is a minor overstatement in an internal comment, not a functional or reproducibility defect, and does not block the phase goal.
