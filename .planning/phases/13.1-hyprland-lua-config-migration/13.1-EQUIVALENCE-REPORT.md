## Curve-ordering fix applied before this run (operator decision)

Before this task's gate run, an operator decision closed a genuine
nondeterminism found during Task 3 diagnostic work by a prior executor
session: `config/animations.lua`'s bezier-curve registration used a bare
`pairs()` loop over `tokens.motion.curves`, and Lua 5.5 randomizes its
string-hash seed **per process** — proven live this session by running 5
separate `lua` processes over the real
`~/.local/state/theme/hyprland-tokens.lua` and observing 5 different
`pairs()` orderings:

```
run 1: emphasized-accelerate,legacy-decelerate,legacy-accelerate,css-linear,standard-accelerate,standard-decelerate,emphasized-decelerate,standard,linear,legacy
run 2: standard-decelerate,legacy-accelerate,legacy,emphasized-decelerate,standard-accelerate,css-linear,linear,legacy-decelerate,standard,emphasized-accelerate
run 3: standard,legacy-decelerate,emphasized-decelerate,legacy-accelerate,css-linear,linear,standard-decelerate,legacy,standard-accelerate,emphasized-accelerate
run 4: standard,standard-accelerate,legacy,standard-decelerate,linear,emphasized-decelerate,emphasized-accelerate,css-linear,legacy-accelerate,legacy-decelerate
run 5: standard,linear,emphasized-accelerate,standard-decelerate,legacy-decelerate,legacy-accelerate,emphasized-decelerate,css-linear,standard-accelerate,legacy
```

This disproves the prior agent's "deterministic, not flapping" claim — that
test used 3 `hyprctl` calls plus a reload inside the SAME running
compositor process (same Lua hash seed throughout), which cannot observe
per-process randomization. **Fix applied and committed (`d6b956e`):**

1. `config/animations.lua` now collects `tokens.motion.curves`' keys into a
   table and `table.sort()`s them before iterating — proven stable across 5
   separate fresh `lua` processes post-fix (identical output every time:
   `css-linear,emphasized-accelerate,emphasized-decelerate,legacy,legacy-accelerate,legacy-decelerate,linear,standard,standard-accelerate,standard-decelerate`).
2. `hypr-equivalence-check`'s `animations.json` comparison now treats the
   curve array (`data[1]`) as a SET keyed on `(name, X0, Y0, X1, Y1)` —
   order carries no compositor-observable meaning, since Hyprland resolves
   a leaf's `bezier = "motion-X"` reference by name, never by array index.
   The animation LEAF array (`data[0]`, 35 records) stays byte-exact
   positional, unchanged.

**Sorted registration alone does NOT make the gate pass** — confirmed
live: after the sort fix, `hyprctl -j animations`'s own curve order is
still not alphabetical (`['motion-emphasized-accelerate', 'motion-standard',

## Individually reasoned divergences

The gate printed exactly 2 divergences. Both get an entry.

### 1. `bindm mouse:272` (`movewindow`) — field `mouse`

- **Baseline value:** `true`
- **Live value:** `false`
- **Reason:** the vendor-example shape (`/usr/share/hypr/hyprland.lua`
  lines 290-291) is used verbatim for the `movewindow` `bindm` port, but
  `HL.BindOptions` does not list `mouse` as a member and `hl.bind`'s opts
  table has no field validator for it — this is a `hyprctl -j binds`
  serialization gap for Lua-registered mouse binds, documented since
  `13.1-04` and left deliberately **un-loosened** (not carved out like the
  `keycode` gap) because whether it has any runtime effect is NOT
  MECHANICALLY VERIFIABLE with tooling available in this environment (no
  evdev/uinput mouse-button injection tool). Compensating check: physical
  mouse-drag confirmation, listed under Criterion-adjacent manual checks
  below.

### 2. `bindm mouse:273` (`resizewindow`) — field `mouse`

- **Baseline value:** `true`
- **Live value:** `false`
- **Reason:** identical to entry 1 above, same known gap, same bind class
  (the two `bindm` ports registered in `keybinds.lua`).

Every other structural field on all 80 binds matches exactly (verified by
`_compare_binds_structural`'s own count and per-field checks — zero other
`!`-prefixed lines in the output above). `animations.json` and
