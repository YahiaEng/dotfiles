<objective>
Load the plugin declaratively from the repo, ship its config surface with shake-to-find off and all three modes switchable, and move the cursor-theme pin — after settling a live-verified conflict between what D-32 says to do and what the installed theme can actually do.

This plan is the runtime half of AMB-02. 17-04 made the plugin *installable* without ever failing an install; this makes it *configured*, from inside the repo, where the cut sweep can see it. The guarded Lua module resolves the username-scoped hyprpm artifact path at runtime (D-35), checks `hl.get_loaded_plugins()` before loading because a double load is proven to time out the IPC, wraps the load in `pcall` so nothing about a missing plugin can reach the compositor's startup path, and applies the `dynamic_cursors` block behind upstream's mandatory guard with shake-to-find disabled (D-36) and all three `mode` values trivially switchable for the operator to judge at a blocking render gate (D-37).

Purpose: `mode` is read once at plugin load and is provably not runtime-switchable — setting it via `eval` updates the stored value while the plugin keeps rendering the old one, and toggling `enabled` off and on does not re-initialise it. So the three modes genuinely cannot be compared live; the only honest way to choose is to ship them switchable and let a human look once. That is D-37, and standing constraint #1 requires the gate regardless.

Output: one new guarded config module, one require line in the compositor's load-bearing entry point (harness-tested before it ever touches the live session), the cursor-theme pin applied across every verified site, and a repo-wide sweep proving no site was left behind.

**Precedence note — this plan corrects both CONTEXT.md and RESEARCH.md, on evidence gathered live during planning.**

RESEARCH.md's Pitfall 6 corrected CONTEXT.md's D-32 by finding a *third* cursor-theme site at `env.lua:9` that D-32 never named. That correction was right and is carried forward. It was also incomplete in two ways, both verified live against the filesystem and the package database during this planning pass:

1. **There are five sites, not three.** `uwsm/.config/uwsm/env` line 16 exports `XCURSOR_THEME=Bibata-Modern-Classic` independently, and `thunar/.config/xfce4/xfconf/xfce-perchannel-xml/xsettings.xml` lines 6 and 10 set `CursorThemeName` twice. Neither is named by CONTEXT.md, RESEARCH.md or PATTERNS.md. Site 4 matters most: `env.lua`'s own header comment says most env vars are now managed by UWSM, and `uwsm/.config/uwsm/env` is the shared session environment exported *before* Hyprland starts — so fixing only `env.lua:9` would have left the old value still exported at the session level, which is the same split-brain Pitfall 6 exists to prevent, one layer down. Site 5 is currently inert (`xfsettingsd` is verified not running) but is still committed repo state naming a cursor theme.

2. **The literal swap that CONTEXT.md, RESEARCH.md and PATTERNS.md all describe would break the cursor rather than change it.** `rose-pine-hyprcursor` installs `/usr/share/icons/rose-pine-hyprcursor/manifest.hl` plus `hyprcursors/*.hlc` and **no `cursors/` directory and no `index.theme`** — it is a hyprcursor-format theme and is completely invisible to XCursor and to GTK's `gtk-cursor-theme-name`. `Bibata-Modern-Classic` is the mirror image: 148 XCursor bitmaps under `cursors/`, no `manifest.hl`. Writing `rose-pine-hyprcursor` into `XCURSOR_THEME` and `gtk-cursor-theme-name` would therefore name a theme those consumers cannot find, and every GTK app and XWayland client would silently fall back to the stock pointer. That is precisely the failure this repo already shipped once with `adw-gtk3-dark` and recorded in CLAUDE.md as a root-cause finding.

D-32 is a locked user decision and is not being overridden here. But its literal instruction — change `generate.sh:166,171` and the `XCURSOR_THEME` export to `rose-pine-hyprcursor` — cannot deliver its own intent, and the planner has no authority to quietly pick a different one. So the fork goes to a `checkpoint:decision` with a recommendation, exactly as this phase already handles RESEARCH open question 2. CONTEXT.md's own method note applies with force: *"treat every option in this document as needing binary-level confirmation before it is built on."*

**Do NOT carry forward the claim that a hyprcursor theme is a prerequisite for the plugin.** CONTEXT.md specifics #6 records it as a false lead the user personally disproved — the plugin deforms plain XCursor bitmaps fine, and has been doing so on Bibata all along. `rose-pine-hyprcursor` was installed during that false lead and then deliberately kept as a preference, which is D-32. Resolve the artifact path at runtime, never as a literal. Read the username from `os.getenv("USER")` with `os.getenv("LOGNAME")` as the fallback, and build the path as the fixed prefix `/var/cache/hyprpm/`, then the username, then the fixed suffix `/dynamic-cursors/dynamic-cursors.so`. A literal path would not reproduce on another machine or another user, which the project's reproducibility constraint forbids. Before interpolating the username into the path, validate it against a restrictive pattern of alphanumerics, dot, underscore and hyphen only, and skip the load entirely if it does not match — see `<threat_model>` T-17-13. If the name is unset or fails validation, do nothing and let the compositor start normally.

Guard the load with an idempotency check: iterate `hl.get_loaded_plugins()` looking for the plugin name `dynamic-cursors`, and only call load when it is absent. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Environment (`USER` / `LOGNAME`) -> constructed filesystem path -> `hl.plugin.load` -> code executing inside the compositor process | An environment variable participates in choosing which shared object gets loaded into the process that owns the entire session. This is the highest-consequence boundary in the plan. |
| Root-owned `/var/cache/hyprpm/<user>/dynamic-cursors/dynamic-cursors.so` -> compositor address space | Third-party code, compiled from a remote repository by hyprpm, executing with compositor privileges. The build side of this boundary is 17-04's; the load side is this plan's. |
| Repo config -> `hyprland.lua` -> whether the session starts at all | Availability boundary. The file's own header states that if it is wrong the machine does not boot, and that no hyprlang fallback path exists any more. |
| Pinned cursor-theme name -> XCursor / hyprcursor theme resolution -> whether a pointer renders | A name that does not resolve produces a silent fallback, not an error. Failure is invisible by construction. |
