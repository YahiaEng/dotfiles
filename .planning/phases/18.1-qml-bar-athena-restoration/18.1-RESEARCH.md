## Summary

This phase is a styling-and-interaction retrofit onto an already-complete, already-passing-review QML module set — not a rebuild. Every one of the design spec's load-bearing factual claims was independently re-verified this session by reading the actual source files and, in three cases, running a live check on this host; the picture that emerges is **more precise and, in one place, materially different** from the design spec's own inference chain, in ways the planner needs to know before writing tasks.

The `BarRoles` colour table (D-04/D-05) is CONFIRMED byte-exact against `waybar/.config/waybar/theme.scss` — every one of the twelve roles and every `alpha()` value matches exactly, with no corrections needed. The codebase already has an established idiom for expressing an alpha-modulated `Colours.*` role in QML (`Qt.rgba(Colours.X.r, Colours.X.g, Colours.X.b, N)`, used identically in three existing files), so `BarRoles.qml` has a proven pattern to follow, not a new one to invent.

The workspace-glyph diagnosis (D-11) resolves to a **different root cause than the design spec inferred**. Live evidence (a `hyprctl clients -j` read against this session, plus a raw-byte read of `WorkspaceCapsule.qml`) shows: (1) there is no appId/class mismatch — Hyprland reports `class: "zen"` exactly matching the map key; (2) the code already assigns `"FiraCode Nerd Font"` (not `"Material Symbols Rounded"`) to every matched glyph cell; (3) the actual defect is that 7 of the 12 `appGlyphMap` entries (`firefox`, `zen`, `discord`, `spotify`, `net.lutris.Lutris`, `steam`, `thunar`) carry a **literal empty-string glyph** in source — confirmed by reading the raw UTF-8 bytes of the array. This is a data-completeness bug, not a font or appId bug, and this document supplies the exact Athena codepoints (verified present in the installed FiraCode Nerd Font's cmap via `fontTools`) needed to fill them in.

The `BarReveal`/`PopoutController` hover-integration risk (D-18) is real but narrower than "two hover systems colliding": `Bar.qml`'s own `HoverHandler` already spans the whole bar content area and already reports into `BarReveal.reportHover("bar", …)`, so a drawer expanding *inside* the bar's own window is already covered by the bar's existing re-hide protection with zero new wiring. The one genuine, evidenced gap is a **pre-existing, currently-dead latch**: `PopoutController.barSettled` is declared, documented as "the input 18-16's reveal owner drives," and never written anywhere in the repo — grep-confirmed. The drawer hover-reveal mechanism should not repeat this mistake; it should gate its own dwell timer on `Bar.qml`'s already-exposed `barTransitionRunning`/`barRendered` properties, and its own collapse-grace timer should reuse the existing `Design.popoutDismissGraceMs` (200ms) token rather than invent a third duration — the codebase already documents the exact ratio principle needed (`barReHideGraceMs` is deliberately 3× `popoutDismissGraceMs`).

The `TrayCapsule` consumer sweep (D-15) found exactly **four** code-level references (not counting the file itself) — `qmldir`, one `componentFor()` branch plus one `Component` block in `Bar.qml`, and one capsule entry in `BarEntryModel.qml` — and no references anywhere else in `contract.json`-equivalents, doctor scripts, or test fixtures. The sweep is complete and low-risk.

**Primary recommendation:** build `BarRoles.qml` first (it is a pure additive singleton with a mechanical source-of-truth), fix the `appGlyphMap` empty-string data bug as an isolated, independently-verifiable change before touching the numeral→state-glyph swap, and implement drawer hover-reveal as a small **local** dwell/grace mechanism per capsule (not an extension of `PopoutController`'s six-section allowlist, which is architecturally a different kind of surface) that reads `Bar.qml`'s existing settledness signals rather than reinventing — or worse, silently repeating — the currently-dead `barSettled` latch.

### Pattern 1: Alpha-modulated colour role (BarRoles.qml)

**What:** Express `alpha(<Colours role>, N)` in QML, the equivalent of Athena's SCSS `alpha(@token, N)` function.
**When to use:** Every `BarRoles` row that carries an `alpha()` value in D-04 (`barSurface`, `barSurfaceHover`, `capsule`, `capsuleHover`, `capsuleTrack`).
**Verified codebase idiom** — this exact pattern (not a new one) is already used identically in three existing files:
```qml
// Source: quickshell/.config/quickshell/modules/dashboard/PanelDialog.qml:168
color: Qt.rgba(panelWindow.surfaceBase.r, panelWindow.surfaceBase.g, panelWindow.surfaceBase.b, panelWindow.panelSurfaceOpacity)

// Source: quickshell/.config/quickshell/modules/Dashboard.qml:367
color: Qt.rgba(dashboardWindow.surfaceBase.r, dashboardWindow.surfaceBase.g, dashboardWindow.surfaceBase.b, dashboardWindow.drawerSurfaceOpacity)

// Source: quickshell/.config/quickshell/modules/Overview.qml:974
color: Qt.rgba(overviewWindow.catchBase.r, overviewWindow.catchBase.g, overviewWindow.catchBase.b, overviewWindow.catchScrimOpacity)
```
Applied to `BarRoles.qml`, the equivalent for `barSurface = alpha(surface, 0.55)` (theme.scss:56) is:
```qml
readonly property color barSurface: Qt.rgba(Colours.surface.r, Colours.surface.g, Colours.surface.b, 0.55)
readonly property color barSurfaceHover: Qt.rgba(Colours.surface.r, Colours.surface.g, Colours.surface.b, 0.78)
readonly property color capsule: Qt.rgba(Colours.surfaceVariant.r, Colours.surfaceVariant.g, Colours.surfaceVariant.b, 0.85)
readonly property color capsuleHover: Qt.rgba(Colours.surfaceVariant.r, Colours.surfaceVariant.g, Colours.surfaceVariant.b, 0.95)
readonly property color capsuleTrack: Qt.rgba(Colours.outline.r, Colours.outline.g, Colours.outline.b, 0.5)
// Non-alpha rows are direct aliases, no Qt.rgba needed:
readonly property color capsuleFg: Colours.onSurfaceVariant
readonly property color accent: Colours.primary
readonly property color onAccent: Colours.onPrimary
readonly property color warn: Colours.tertiary
readonly property color danger: Colours.error

readonly property color fillClock: Colours.secondary
readonly property color fillClockFg: Colours.onSecondary
```

All twelve `Colours.*` source properties referenced above (`primary`, `onPrimary`, `secondary`, `onSecondary`, `tertiary`, `onTertiary`, `error`, `onError`, `surface`, `surfaceVariant`, `onSurfaceVariant`, `outline`) were individually confirmed to exist as `readonly property alias` entries in `quickshell/.config/quickshell/modules/Colours.qml` (lines 148–166) — no role needs to be invented or approximated.

### Pattern 3: Bounded, non-interpolated appId matching (already correct, keep as-is)

**What:** `WorkspaceCapsule.glyphFor(appId)` resolves a live Hyprland `appId` string to a glyph via four bounded comparison stages against a 12-entry repo-literal array, never compiling or interpolating the untrusted string.
**Verified live this session** — no change needed to this mechanism, only to the data it looks up:
```qml
// Source: quickshell/.config/quickshell/modules/bar/WorkspaceCapsule.qml:133-157
function glyphFor(appId) {
    if (!appId || typeof appId !== "string" || appId.trim() === "")
        return { text: workspaceCapsule.appGlyphFallback, family: Design.symbolFontFamily };
    var map = workspaceCapsule.appGlyphMap;
    var i;
    for (i = 0; i < map.length; i++) {
        if (map[i].appId === appId)
            return { text: map[i].glyph, family: workspaceCapsule.appGlyphFontFamily };
    }
    // ...case-insensitive exact, then case-insensitive containment...
    return { text: workspaceCapsule.appGlyphFallback, family: Design.symbolFontFamily };
}
```
`workspaceCapsule.appGlyphFontFamily` is already `"FiraCode Nerd Font"` (`WorkspaceCapsule.qml:62`), NOT `Design.symbolFontFamily` (`"Material Symbols Rounded"`, `Design.qml:103`) — the font-family switch D-09 asks for is **already done** for every matched glyph cell. `Design.symbolFontFamily` is only reached on the fallback path (empty/unmatched appId). See Pitfall 2 for what is actually broken.

### Anti-Patterns to Avoid

- **Re-diagnosing D-11 as an appId/class problem and "fixing" the lookup logic.** Live evidence (below, Pitfall 2) rules this out for the currently-open apps; do not touch `glyphFor()`'s matching stages.
- **Extending `PopoutController`'s six-section allowlist (`"audio", "wifi", "bluetooth", "clock", "resources", "media"`) to include `"launcher"`/`"settings"`.** That allowlist drives `SectionPopout` — a separate anchored surface with its own `PopupWindow`-like lifecycle (create/destroy per open). The apps/settings drawers are inline strips that already live inside the bar's own window (`Item { id: stripHost }` inside `LauncherCapsule`/`ClockActionsCapsule`). Conflating the two would change the drawers' rendering model, not just their trigger — out of scope per the design spec's explicit "only the trigger changes" (D-16).
- **Inventing a third grace-timer duration for drawer collapse.** The codebase already documents the governing ratio (`Design.qml:230-234`: `barReHideGraceMs` is deliberately 3× `popoutDismissGraceMs` "because re-hiding the WHOLE bar is the more consequential event"). Reuse `Design.popoutDismissGraceMs` (200ms) for the drawer's own collapse grace, not a new literal.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Alpha-modulated colour in QML | A custom colour-blend helper function | `Qt.rgba(Colours.X.r, Colours.X.g, Colours.X.b, N)` | Already the repo's own idiom in 3 files (`PanelDialog.qml:168`, `Dashboard.qml:367`, `Overview.qml:974`); a new helper would be a second, inconsistent way to do the same thing. |
| Drawer hover dwell/grace timing | A copy-pasted clone of `PopoutController`'s `dwellTimer`/`graceTimer` block wired into its `sections` allowlist | A small local mechanism per drawer capsule, reusing `Design.popoutDwellMs`/`Design.popoutDismissGraceMs` tokens directly | `PopoutController` is architecturally scoped to the `SectionPopout` family (separate anchored windows); reusing its *tokens* is correct, reusing its *allowlist/state machine* conflates two different surface types. |
| Workspace click dispatch (QBAR-03) | Any change to `activateWorkspace()`/`Hyprland.dispatch()` | Leave `WorkspaceCapsule.qml:200-212` untouched | This phase is colour/glyph/interaction-only; QBAR-03 is a passing, unrelated requirement already implemented with a documented validate-before-interpolate discipline. Touching it risks a regression with zero benefit to GATE-02. |

### Pitfall 4: `PopoutController.barSettled` is a documented-but-dead latch — don't copy it uncritically

**Why it happens:** `BarReveal`/`HotZone` (Plan 18-16) and `PopoutController`'s hover half (Plan 18-13) were built in different plans/waves, and the wiring between them — `Bar.qml` (or `BarReveal`) writing `PopoutController.barSettled = !barTransitionRunning` — was never added.
**How to avoid:** Do not simply copy `PopoutController`'s `barSettled`/`previewArmed` pattern into the new drawer mechanism verbatim (that would create a second dead latch). **Warning signs:** a drawer that visibly expands while the bar itself is still mid-slide-in from a hot-zone reveal.
