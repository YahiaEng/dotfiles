  <action>
    Work one defect at a time, in the order the harness caught them — the steps
    short-circuit on the first failure, so a later step's health is unknown until
    an earlier one passes. Fixing several at once and re-running loses the
    attribution that makes each fix verifiable.

    For each defect, follow this cycle:

    1. Read the failing step's numbered log and identify the actual failing line —
       not the step name, the line. A failing package install names a package; a
       failing stow names a conflicting path; a failing checklist names a surface
       and a class; a failing symlink sweep names a link and its unresolved target.
    2. Determine whether the defect is in the repository or in the harness. A
       repository defect means a fresh machine genuinely cannot reproduce the
       desktop and the repository must change. A harness defect means the gate is
       wrong about a healthy system. Both get fixed; conflating them does not.
    3. Fix the root cause in the owning file. Do not fix it by weakening the gate:
       an allowlist entry, a removed step, a reverted-to-informational step or a
       lowered threshold are all ways of making the symptom disappear without
       fixing anything, and every one of them is prohibited by this plan.
    4. Commit the fix with a message naming the step that caught it and the
       failing line's substance.
    5. Push to `origin/main`. This is an ordered, mandatory step — the harness does
       a shallow clone from the remote, so the fix does not exist as far as the
       next run is concerned until it is pushed. Verify with `git show
       origin/main:<path>` that the remote actually carries the change.
    6. Re-run `verify/container-run.sh` in the background and poll.
    7. Record the new step ledger. Compare against the previous iteration: the
       fixed step should now pass and the run should reach at least one step
       further. A step that fails identically after a push means the fix did not
       address the root cause — go back to step 1 rather than trying a second fix
       on top.

    Continue until `summary.log` records `overall=PASS` and the harness exits 0.

    Bound the loop at four iterations. If the fourth iteration has not reached
    green, stop and take the decision checkpoint at the end of this plan rather
    than continuing to iterate — four rounds without convergence means the failure
    is not what it appears to be, and burning further container runs on the same
    hypothesis is the wrong move.

    If a defect's correct fix would restructure `install.sh` substantially, or
    would change a decision recorded in the phase context, stop and take the
    checkpoint rather than deciding unilaterally.

    Record every iteration in `.planning/phases/22-fresh-install-proof/22-DEFECTS.md`
    as it happens, not reconstructed at the end: iteration number, step that failed,
    the actual failing line, whether it was a repository or harness defect, the fix,
    the commit SHA, and the resulting step ledger.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| defect pressure → gate strength | The strongest force acting on a gate during a fix loop is the temptation to make the gate stop complaining. This is the boundary this plan defends. |
