<context>
Everything below was measured directly during the 22-01 baseline run
(`run-20260816T191755Z`) and verified by the orchestrator. None of it is inferred.

**Defect 1 — the timeout does not bound the run.**
`verify/container-run.sh:241` wraps a foreground, attached `podman run --rm` in
`timeout --kill-after=30 "$CONTAINER_TIMEOUT"`. The comment at `:235` claims this
"catches ALL hangs (including future ones not yet anticipated)". Under rootless
podman that claim is false: the signal reaches the `podman run` CLI client, which
detaches, while the container itself is owned by a separate `conmon` process and
keeps running. Measured: the host script exited and wrote
`step=container-run status=timeout after=3600s` + `overall=FAIL`, and `podman ps -a`
/ `podman top` / `podman inspect` confirmed container `197980ef926b` still
`running=true` with `paru` still building several minutes later. The container ran
on to its own genuine failure and appended `step=install status=fail` +
a SECOND `overall=FAIL` to the same `summary.log`, through the `/logs:Z` bind
mount. The verdict logic at `:268` guards with `grep -q '^overall='` before
appending, so it cannot defend against a writer that appends *after* it has run.

**Defect 2 — the budget is undersized.**
The run was killed at 3600s with genuine forward progress remaining (log still
growing; paru actively compressing `colloid-nord-icon-theme-git`). This was a
cold-cache first run with no shared pacman/AUR cache.

**Defect 3 — `limine-dracut-support` blocks `--core-only`.**
`install.sh:324`, in the `AUR_PKGS` array commented "core — always installed".
Introduced by `95bb86a` on 2026-03-14 — five months before this milestone and
unrelated to the five deletions. Its build downloads a 333.7 MB
`graalvm-community-jdk-25i1` tarball and builds under Gradle 9.7.0, failing in the
`archlinux/archlinux:latest` image with
`Cannot find module 'gradle-public-api-legacy' in distribution directory '/usr/share/java/gradle'`.
The host has `limine-dracut-support 1.37.1-1` installed successfully, so this is a
container-image toolchain problem, not a broken package.

Operator decision on defect 3 (recorded at the 22-01 checkpoint): move it and its
neighbour `kernel-modules-hook` out of the core set into a host-only group skipped
under `--core-only`. Rationale: `install.sh:816` already skips
`kernel-module-verify` under `--core-only` on the stated grounds that "no hardware
section ran, so there is no kernel/driver work to check" — the package scope was
simply never brought in line with that verification scope. The container has no
bootloader and never proved boot.
</context>

  <files>verify/container-run.sh</files>

  <action>
    Replace the attached-and-hope mechanism with a detached run whose container ID
    the harness owns and can definitively stop.

    Required properties — all of them, not a subset:

    1. Start detached with an explicit, harness-known identity: `podman run -d`
       capturing the container ID (or `--cidfile`). Keep `-v "$LOG_DIR:/logs:Z"`
       and the same image and command. Drop `--rm` from the run itself if it
       prevents inspecting the exit code after the fact; remove the container
       explicitly instead, so cleanup stays deterministic.
    2. Wait for completion with a bounded wait, not a sleep loop that assumes a
       rate. `podman wait --condition=exited` with an outer bound is acceptable;
       so is polling `podman inspect` state on an interval. Whatever you choose,
       the harness must be able to distinguish "exited on its own" from "we hit
       the budget".
    3. On budget expiry, actively stop it: `podman stop --time=30 "$CID"`, then
       `podman kill "$CID"` if it survives, then verify by re-inspecting that it
       is no longer running. Only after that verification may the harness write
       its timeout verdict. This is the whole point of the task — a stop that is
       issued but not confirmed reproduces the original defect in a new costume.
    4. Guarantee `summary.log` cannot receive a second `overall=` line. Because
       the container is confirmed stopped before the verdict is written, the
       late-append race is closed at the source. Additionally make the verdict
       write defensive: if an `overall=` line is somehow already present when the
       harness goes to write its own, record the conflict explicitly rather than
       appending a duplicate.
    5. Preserve the existing exit-code contract. Downstream logic keys on rc 124
       and 137 for timeout; if your mechanism no longer produces those, set
       `IN_CONTAINER_RC` explicitly so `CONTAINER_TIMED_OUT` and the
       `step=container-run status=timeout after=Ns` line still behave identically.
    6. Ensure the container is cleaned up on every exit path — normal completion,
       timeout, and the script being interrupted. A trap is appropriate.

    Then raise `CONTAINER_TIMEOUT` (`:47`). Set it from the measured evidence, and
    write the arithmetic into the comment: the baseline consumed 3600s without
    finishing while carrying the 333.7 MB GraalVM download and Gradle build that
    Task 1 has now removed from the critical path. Choose a value with genuine
    headroom over the remaining work rather than a round number, keep it
    overridable via the existing `${CONTAINER_TIMEOUT:-N}` env form, and state in
    the comment what evidence the number came from.

    Finally, correct the falsified claim: amend the comment at `:235` so it no
    longer asserts the outer wrapper "catches ALL hangs", and note what the
    baseline measured.
  </action>
