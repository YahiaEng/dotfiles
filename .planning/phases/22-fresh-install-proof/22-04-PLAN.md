<objective>
Turn the container tier from a three-gate harness into a five-gate one, and make
`theme-doctor` block inside it against a committed, source-justified allowlist.

Purpose: at the last green run `theme-doctor` was 20 passed / 3 failed and all
three failures were genuinely session-dependent. Today `theme-doctor` runs 578
checks, the overwhelming majority of them file and lint checks that pass fine
headless — so leaving it informational discards roughly 575 checks of coverage
inside the one environment that actually proves reproduction. At the same time
SC-2 asks whether any retired package, config, symlink or contract entry survives
in the REPRODUCED system, which the developer host cannot answer because it still
has the old packages installed. Running the retirement checklist and the new
symlink checker inside the container is what makes that question answerable.

Output: a committed allowlist next to the harness, three new or converted blocking
steps in `container-run.sh`, and one run of the modified harness to establish that
the harness change itself is sound before any defect is attributed to the
repository.
</objective>

    Format: pipe-delimited, one record per line. Lines beginning with `#` and blank
    lines are ignored. Four columns, all mandatory:

    `match_prefix` — the byte-exact leading substring of a `theme-doctor` `[FAIL]`
    line's description, taken from the copied baseline log after stripping the
    two-space indent and the `[FAIL] ` tag. A prefix rather than a whole-line match
    because several descriptions embed runtime values — a mode marker, an observed
    value, a resolved theme name — that differ between runs; anchoring on the stable
    leading text is what makes the entry survive. Keep the prefix as long as the
    stable text allows; a short prefix over-matches and silently admits unrelated
    failures.

    `reason_class` — exactly one of four tokens and nothing else:
    `no-session-bus`, `no-compositor`, `no-display`, `no-user-session`. These are
    the four structural reasons D-22-09 admits. A failure that fits none of them is
    a defect, not an exemption, and must be left off this file so the gate reports
    it.

    `source_ref` — where the reason was read from: a `theme-doctor` file:line, or
    the file:line of the folded checker the failure came from. Not "obviously
    session-dependent" — a reference a future reader can open.

    `reason` — a non-empty sentence saying what the check does and why a container
    with no session cannot satisfy it.

    Write a header comment block explaining the format, the four permitted
    `reason_class` tokens, the derivation rule (measured from a real run, then
    justified at source level, never fitted to whatever went red), and the
    fail-closed rule the harness applies to a malformed file.

    Then work the inventory one row at a time. For each recorded `[FAIL]`:
      - Locate its producing check in `theme-doctor`.
      - Decide whether it carries one of the four structural reasons. If it does,
        write the entry with a real `source_ref`. If it does NOT, leave it off the
        file and record it in the plan's summary as a defect for plan 22-05 to
        close.
      - Fill in the corresponding "structural reason" cell in `22-BASELINE.md`'s
        inventory table, which plan 22-01 deliberately left blank, so the derivation
        is traceable end to end.

    Sanity checks on the finished file, all of which must hold: no entry has an
    empty or whitespace-only `match_prefix`; no `match_prefix` is shorter than 12

    `reason_class` is one of the four tokens; every `reason` is non-empty; and every
    `match_prefix` byte-matches at least one recorded failure in the copied baseline
    log. An entry matching nothing is dead data and must be removed rather than left
    hopefully in place.

    Do not add an entry speculatively for a failure the baseline did not produce.
  </action>
