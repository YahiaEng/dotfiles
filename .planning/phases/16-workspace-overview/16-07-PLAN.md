<objective>
Make the whole surface reachable from the keyboard: arrows between the eleven
tiles, Enter to descend into a tile's windows, Enter again to focus one, and
Shift+1..0 to move the selected window to a workspace.

**This is recorded scope widening, deliberately, and verification should read it
that way rather than as drift.** The phase criteria require only a keybind to
open, a mouse click to focus and a mouse drag to move — everything past
Esc-to-dismiss is capability beyond their literal text. The operator overrode the
recommendation (which was Esc plus number keys only) and authorised a pre-agreed
fallback in the same breath, which is the third recorded override in this
project's history and the pattern this repo names as the one to repeat.

Two levels exist because one does not work. Tile-level selection alone cannot move
a window you can see unless it happens to be the active one, so `Shift+number`
would mean nothing; a single flat field of windows was rejected because crossing
tile boundaries gets ambiguous when layouts differ and because an empty workspace
has no window to land on. The fixed grid is what makes tile-level arrow movement
completely predictable in the first place.

There is one hard boundary. Keyboard navigation must not drift into
type-to-search: no text field, no filter, no search input. That exclusion exists
to avoid a second "type to find a thing" surface competing with the launcher, and
it is a boundary rather than a preference.

Purpose: OVER-02 and OVER-03 gain keyboard parity with the pointer, so nothing has
to be learned twice.
Output: two-level selection, a mode indicator, and a render gate empowered to take
the pre-agreed fallback without a new decision.
</objective>

<assumption_delta_decision>
**Signal:** `pluralization` on *another* ("Dragging a window thumbnail onto
**another** workspace tile moves that window there") and on *fallback*
("…either stays inside it or ships the documented **fallback** instead").

**The noun that is now primary.** The primary key for every operation in this
phase is **(window identity, workspace-target token)** — `HyprlandToplevel.address`
paired with a workspace token that is either an integer `1..10` or the literal
`special:magic`. "The focused window on the current workspace" is demoted to one
*instance* of that pair.

**Decision: `promote`.** This plan is where the promotion explains a design choice
that would otherwise look arbitrary: why two selection levels rather than one. A
single level could only ever address a *workspace*, which is the old singular
model — and under it `Shift+number` has nothing to act on except the active
window, which is precisely the fallback this plan forbids ("Shift plus a number
with no window selected does nothing at all"). Window-level selection exists so
the keyboard can name the same `(window, workspace)` pair the drag names. The
proof that the promotion holds is that `Shift+1..0` calls the *same* guarded move
function the drop handler calls — one mechanism, two input paths, rather than a
keyboard-specific move that quietly reintroduces "the active window".

**Second signal — render mode.** Decision: `promote`, unchanged. This plan adds a
selection outline to `WindowThumbnail` — the general representation — rather than
to a live-capture-specific wrapper, which is why keyboard navigation works
unchanged over thumbnails in any of the three capture states, including a grid
where every capture failed. UI-SPEC's E7 `error` row ("a user can navigate and
focus a workspace whose thumbnails are entirely blank") is satisfied structurally
by that placement rather than by a special case.

**Accepted debt: none in this plan.** Plan 16-04's single-capture-path gate and
this plan's single-dispatch-call-site criterion together keep both promotions from
silently reverting.
</assumption_delta_decision>
