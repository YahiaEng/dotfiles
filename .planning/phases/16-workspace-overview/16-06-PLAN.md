<objective>
Close OVER-03: pick a window up out of one tile and drop it into another, and the
window is there.

The grammar this is designed against is two verbs learnable in one use — **drag
organises, click navigates**. Click already means "focus that workspace and
close", which frees drop to mean something else entirely: the window moves, the
compositor's focused workspace does not jump, and the overview stays open so
moving three windows costs one summon rather than three.

Three constraints shape the implementation and none of them is negotiable here.
The thing that follows the cursor is a still snapshot, not the live view, because
a drag is this phase's load peak — every other tile still capturing, a full-screen
blur, a highlight animating — and that is the wrong moment to start moving a video
feed across the screen at 165Hz. The drop target lights using the lit-tile
treatment the shell already teaches, not a second idiom minted for drags. And
there is no landing preview: the compositor's tiling decides the real layout on
arrival, so a predicted position would be a guess that misleads worse than
showing nothing.

The dispatch itself is the one genuinely unverified mechanism in this phase, which
is why plan 16-01 spiked it and a human locked the answer. This plan implements
that recorded decision verbatim rather than re-deriving it.

Purpose: OVER-03 becomes true, with the drop target visibly highlighted while the
drag is in flight.
Output: a drag ghost, a drop-target highlight, a guarded move dispatch, and a
human-approved feel.
</objective>

<assumption_delta_decision>
**Signal:** `pluralization` on *another* ("Dragging a window thumbnail onto
**another** workspace tile moves that window there") and on *fallback*
("…either stays inside it or ships the documented **fallback** instead").

**The noun that is now primary.** The primary key for every operation in this
phase is **(window identity, workspace-target token)** — `HyprlandToplevel.address`
paired with a workspace token that is either an integer `1..10` or the literal
`special:magic`. "The focused window on the current workspace" is demoted to one
*instance* of that pair.

**Decision: `promote`.** This plan is the one where the promotion is load-bearing
rather than tidy. A drag is by definition an operation on a window that is not
focused, targeting a workspace that is not current — the old singular model cannot
express it at all, which is exactly why plan 16-01 had to establish whether the
compositor's dispatcher supports the promoted form before anything was built on
it. The scratchpad is the visible dividend: it is a drop target and a drag source
with no branch anywhere in this plan, so drag-out — a capability no keybind on this
host offers — falls out for free. Under an add-alongside model it would have needed
its own path, and would almost certainly have shipped one-directional.

**Second signal — render mode.** Decision: `promote`, and the drag is its third
consumer. `DragGhost` renders a still frame taken from the same `WindowThumbnail`
representation the grid uses, and falls back to that thumbnail's own pending or
failed chrome when there is no frame to take. It is not a fourth way to draw a
window; it is the general representation with a different capture mode and a
different transform. That is what makes "dragging a window whose preview never
arrived" a two-line fallback rather than a designed-from-scratch state.

**Accepted debt: none in this plan.** Plan 16-04's single-capture-path gate keeps
both promotions honest — `DragGhost` grabs its frame through the existing
thumbnail rather than instantiating a second capture view, and that gate is what
would catch it if a future edit did otherwise.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| QML string construction → Hyprland Lua evaluator | The move dispatch is a string the compositor evaluates as Lua source; anything interpolated into it crosses into an evaluator |
| client-controlled window metadata → dispatch argument | Window titles and appIds are set by the application and are attacker-influenceable on any machine that opens untrusted content |
| dragged frame → in-memory image | A still frame of a window's content is held for the duration of the drag |
| drag gesture → compositor state mutation | A pointer gesture on a shell surface reparents a real window |
