<objective>
Settle, against the installed binaries, the four mechanisms this phase depends on
and that nothing in the repo or on the web currently proves. Nothing is built
here; the output is a recorded verdict per mechanism plus the exact working
strings later plans consume.

The headline is OVER-03's dispatch mechanism. This repo cut over to the Hyprland
**Lua** config in Phase 13.1, so `Hyprland.dispatch()` must send a Lua-expression
string (`hl.dsp.window.move({...})`), not the classic comma-separated
`movetoworkspacesilent N,address:0x...` form. Whether that Lua table accepts a
window/address selector to target a **non-focused** window is unverified in this
repo, in `/usr/share/hypr/stubs/hl.meta.lua`, and on the web (16-RESEARCH.md Q3,
Open Question 1). D-16-13 requires the move be **silent** — the compositor's
focused workspace must not jump — so a focus-then-move workaround would
contradict a locked decision and needs an explicit human decision, not a
planner's guess.

Three further mechanisms are settled here because standing constraint 2 (verify
options against the installed binary) applies to each and each would otherwise be
discovered mid-build: the keyboard focus posture D-16-16 needs, Qt's drag API
inside a layer-shell surface, and whether screencopy succeeds for a window parked
on an inactive workspace (D-16-01 renders all ten slots regardless).

Purpose: no later plan in this phase writes an unverified call signature into
production QML. This repo's own T-13.1-10 convention — never infer a dispatcher
argument shape from anything but a live test — is the rule being applied.
Output: `16-SPIKE-FINDINGS.md` with four VERDICT records, and a human decision
locking OVER-03's move mechanism.
</objective>

<assumption_delta_decision>
**Signal:** `pluralization` on *another* ("Dragging a window thumbnail onto
**another** workspace tile moves that window there") and on *fallback*
("…either stays inside it or ships the documented **fallback** instead").

**The noun that is now primary.** Before this phase the shell had no identity for
an individual window at all, and "workspace" only ever meant *the one you are on*
(`hl.dsp.focus({ workspace = N })` acts on the current view;
`hl.dsp.window.move({ workspace = N })` acts on the focused window). This phase
makes both plural and addressable: the primary key for every operation here is
**(window identity, workspace-target token)** — `HyprlandToplevel.address` paired
with a workspace token that is either an integer `1..10` or the literal
`special:magic`.

**Decision: `promote`.** The addressed pair becomes primary and "the focused
window on the current workspace" is demoted to one *instance* of it — not kept as
the primary with addressing bolted alongside. The concrete payoff is D-16-05's
scratchpad: under the promoted model `special:magic` is an ordinary member of the
workspace-target set, so drag-in and drag-out are the same code path as any
numbered tile; under an add-alongside model it would be a permanent special case
that no keybind covers today. This is also exactly why Task 1 above is a blocker
rather than a footnote — a dispatcher that can only act on the focused window
would mean the promotion is not actually available, and that is a fact to
establish before ten layers are built on it.

**Second signal — render mode.** The OVER-04 fallback introduces live-capture and
snapshot-capture as two ways to draw the same thing. Decision: `promote` as well —
`WindowThumbnail` (created in plan 16-03) is the general representation and
carries the capture mode as a variant; `live: true` is one variant, not the
primary with snapshot bolted on. D-16-11 bakes exactly one mode into the shipped
build, but the *representation* stays general, which is what makes D-16-07's
ladder a property change rather than a second renderer. The drag ghost
(D-16-12's `captureFrame()` still) is a third consumer of the same path.

**Suggested invariant test (not required by this plan):** a `quickshell-doctor`
source check asserting `ScreencopyView` is instantiated in exactly one file. It
goes red the instant a future phase reintroduces a second, singular capture path.
Plan 16-04 is the natural home for it.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client windows → capture harness | Pixel content of arbitrary windows — possibly a password manager or a private message — crosses into a throwaway surface during the inactive-workspace spike |
