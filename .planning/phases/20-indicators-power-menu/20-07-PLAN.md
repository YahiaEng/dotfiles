> dependency changed by this revision.

**Detector 1 — package manager busy.** `pgrep -x pacman`, `pgrep -x paru`, `pgrep -x yay`, each a
fixed literal command array. `-x` matches the exact process name, so a process merely named
similarly does not false-positive, and a genuinely-running pacman — even one blocked waiting on a
lock — true-positives correctly. Measured cost is 0.016s wall, negligible for a low-frequency
poll. Do NOT use `/var/lib/pacman/db.lck`: D-20-27 rejected lockfile detection explicitly because
a stale lock from a crashed pacman would warn on every shutdown forever, and a warning that always
fires is one you stop reading. Record that rejection and its reason in a source comment.

**Detector 2 — active downloads.** A cheap `find` over the user's Downloads directory for recent
`.part` / `.crdownload` files, or a Downloads-folder mtime check. This is end-4's own second
check and is deliberately a heuristic; record it as a heuristic in its own comment rather than
implying certainty. Verified at rest on this host: the directory exists and the glob returns empty
with no false positive.

**Detector 3 — toplevel count against a window-class deny-list.** Enumerate toplevels via
`hyprctl` and count those whose class appears in a configured deny-list. Record HONESTLY in the
source comment, in D-20-27's own words, that this is a hand-maintained list and not a detector —
it warns about what it was told to warn about — and that it is the bounded stand-in for the
unkillable-client hazard, which is characterised by LEDGER-02 (see
`20-LEDGER-02-RECORD.md`), not by this list. The initial deny-list contents are Claude's
discretion; choose a small, defensible starting set of classes that genuinely resist a clean
close on this desktop, declare it as a single named property so it is editable in one place, and
state in the comment that additions are expected and that an empty list is a valid, warning-free
configuration.

**Polling discipline.** One low-frequency `Timer` whose `running` is bound to the power menu being
VISIBLE. Nothing runs while the menu is dismissed — this is the standing zero-idle rule, and
D-20-30 restates it for this surface specifically. Run the detectors once immediately on open so
the first result does not wait a full interval, then on each tick. Guard each round with the
single-flight discipline `BrightnessBackend.qml` already establishes: if the previous round's
`Process` has not exited, SKIP this tick rather than queueing it, so rounds never overlap or
accumulate. A detector whose `Process` fails to start or exits non-zero for a reason other than
"no match" reports nothing (false) — it never surfaces an error state.

Every `Process.command` is a fixed literal array. Nothing from a detector's own output is
interpolated into a further command; the only value that ever leaves a detector is a boolean and,
for detector 3, an integer count.
