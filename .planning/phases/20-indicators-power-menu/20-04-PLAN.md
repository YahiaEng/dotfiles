<assumption_delta_decision>
**Signal:** `chosen` + `pluralization`. `Toast.qml` currently hardcodes three constants — its
anchor edge (`anchors.top: true`), its layer namespace (`"quickshell-notif-toast"`) and its
dismiss interval (`Design.notifToastDurationMs`) — because it has had exactly one consumer since
Phase 19. This phase introduces a second consumer with different values for all three. Three
constants become parameters, and "the toast" becomes "a toast".

**Noun now primary:** a *transient-notice frame*, parameterised by (edge, namespace, dismiss
interval, interactive), of which the do-not-disturb toast is one instance.

**Decision: `promote`.** `Toast.qml` becomes the generic frame; the DND toast is demoted to one
instance whose values happen to be the defaults. This is not add-alongside — no second frame
type is created, no `OsdToast.qml` fork exists, and the DND toast's own site in `shell.qml` is
not edited at all. Rationale: adding alongside would mean two frames to keep visually reconciled
on every chrome change, which is exactly the outcome `Toast.qml`'s own header was written to
prevent ("Phase 20's OSD indicators reuse it for a value readout").

**Invariant this encodes:** every property the OSD instance overrides defaults to the DND
toast's current literal, so the DND toast's rendered behaviour is byte-identical before and
after. Task 1's acceptance criteria assert this mechanically (the DND `Toast` block in
`shell.qml` is untouched by the diff).
</assumption_delta_decision>
