## Explicit planner assumption (RESEARCH.md Open Question 1)

`BrightnessBackend.qml` exposes only a relative adjust verb. The two candidate resolutions were
(a) add a small absolute-set capability, or (b) accept a slider that snaps to the existing step
increments.

**Chosen: (a), an absolute setter.** Reason: 19-UI-SPEC.md pins the centre's brightness slider to
drag-to-any-position with geometry identical to the volume and mic sliders, and (b) cannot honour
that contract — it would produce a handle that visibly jumps and lags the pointer. This is a
named deviation from D-19-20's literal "as-is" wording, made on the UI contract's authority
rather than on convenience, and it is confined to one new guarded function beside the existing
one. The existing relative verb is left untouched so the bar's scroll-to-adjust path carries no
risk from this change.
</planner_assumptions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| session D-Bus → history store | Sender-controlled notification fields are serialised to a JSON file on disk and re-read at startup, where they are rendered again. |
| filesystem → shell process | The state file's contents are parsed at startup and drive UI rendering; a malformed or hostile file reaches the parser before any UI exists. |
| shell process → domain backends | `ToggleState` becomes the single write path into the audio, network and bluetooth backends for toggle actions. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-19-16 | Tampering | history store round-trip | high | mitigate | Sender-controlled fields are re-rendered after a disk round-trip, so the plain-text format pins added in plans 19-01 and 19-04 must hold on the reload path too — the same card component renders both live and reloaded notifications, so there is one rendering path and one set of pins, not two. |
| T-19-17 | Denial of Service | malformed or hostile state file | medium | mitigate | A history file that fails to parse degrades to an empty list rather than a crash, per the UI-SPEC's own N3 error resolution. The item cap bounds the file's growth so it cannot become unboundedly large through ordinary use. |
| T-19-18 | Tampering | do-not-disturb persistence | medium | mitigate | The tile is truth-driven: it renders the value that was actually read back, never an optimistic local guess, so a failed write is visually silent rather than showing a state the system is not in. This is the N7 error backstop above and must be confirmed against the real implementation, not assumed. |
| T-19-19 | Elevation of Privilege | `BrightnessBackend` absolute setter | medium | mitigate | The new setter is guarded by the same device-presence probe as the existing adjust path and passes its value as a bounded argument to the same tooling the relative path already uses — no new external command surface is introduced. |
| T-19-20 | Spoofing | suppression bypass | medium | accept | Any session process can send a notification, and suppression is a user-experience control rather than a security boundary; a sender cannot bypass it, but nothing prevents a sender from marking a notification critical. D-19-11's height clamp with no critical exemption is the anti-abuse control and is already in place from plan 19-04. |
| T-19-SC | Tampering | package installs | low | accept | This plan installs no package. |
