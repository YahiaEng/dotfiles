# Phase 21 — UI Design Contract

> Visual and interaction contract for the AGS-media-card fold-in and the
> resulting `contract.json` close. Generated by gsd-ui-researcher, verified
> by gsd-ui-checker. This is a Quickshell/QML desktop-shell surface, not a
> web app — there is no shadcn/Tailwind/npm stack in this repo. The design
> system is this repo's own token pipeline: `Colours.qml` / `Motion.qml`
> singletons reading matugen-rendered `~/.local/state/theme/{palette,
> motion}.json`, plus `modules/dashboard/Design.qml` (spacing/type/icon
> constants) and `modules/bar/BarRoles.qml` (bar-specific colour roles
> blended from `Colours.*`). This document does not re-decide anything
> `21-CONTEXT.md` already locked (D-21-00..27) — it restates those decisions
> in implementable token/geometry terms, resolves the two things CONTEXT.md
> explicitly left for this UI phase to render (D-21-10's per-player-volume
> ×dedup interaction, D-21-26/27's exact tint values), and specifies the
> required `14-UI-SPEC.md` amendment verbatim (D-21-04).
>
> **No interactive question round was run for this document.** Every open
> visual call below is resolved with a stated recommendation and rationale,
> rendered as ASCII where the operator's standing preference (`show, don't
> describe`) applies — final pixel judgment happens at D-21-20's blocking
> combined render gate, which is where the operator actually looks at this.

## Appendix: Resolved Design — Cava Lifecycle, Visualiser Geometry, Per-Player Volume, DND Tint

These are the specific renderings this phase's own `21-CONTEXT.md` requires ("render that interaction... before implementing", D-21-10) plus the two remaining Claude's-Discretion visual calls (D-21-06 linger duration, D-21-27 tint strength). Everything else visual in this appendix (bar count, cookie shape, accent colour, refcount+linger *mechanism*) is already locked in CONTEXT.md and is restated here only as implementable geometry, not re-decided.

### Cava claim condition (new resolution — not explicitly stated in CONTEXT.md)

D-21-06 locks *refcount + linger* as the ownership mechanism but does not state exactly when a surface "claims" the process. Resolved here: a surface claims cava when **both** (a) it is visible (Media tab is the active dashboard tab AND the dashboard is open; OR the bar's media popout is open) **and** (b) `mediaBackend.playing === true`. Pausing releases the claim (engages the linger) even if the surface stays open — this keeps the zero-idle rule honest for the common "left the dashboard open on Media, paused the track" case, and it costs nothing extra: the ring's paused-state visual is identical to its no-player visual (the static silhouette), so there is no user-visible loss from not running cava while paused.

```
surface visible? ──┐
                    ├─AND──► claim cava (refcount++)
playing == true? ───┘

release (refcount--) on: surface hidden, OR playing becomes false
refcount reaches 0 ──► start Design.cavaLingerMs timer
timer fires with refcount still 0 ──► kill cava process
refcount becomes >0 before timer fires ──► cancel timer, process stays alive (no re-spawn, no 350ms cost)
```

**Linger duration (Claude's discretion, D-21-06):** recommend **5000ms (5s)**, as a new named constant `Design.cavaLingerMs` (not reusing the bar's sub-second `barDrawerGraceMs`/`popoutDismissGraceMs` family — those govern hover-dismiss grace at a completely different scale/purpose; this is a process-lifecycle decision). Rationale: long enough to survive a quick popout-close-then-dashboard-open flow or a brief pause/resume without re-paying the measured ~350ms cold start; short enough to still read as "a few seconds" per D-21-06's own wording and to matter for the zero-idle budget. **Must be reachable by changing this single constant to a very large value (or a dedicated `Design.cavaAlwaysOn: bool` bypass) if the operator's reserved revisit lands on always-on** — do not restructure the refcount to satisfy that reversal.

### Visualiser Geometry (Claude's discretion, D-21-01/D-21-03)

60 bars (locked, D-21-03), arranged as a `Repeater` of `ShapePath` line segments replacing the single dashed `PathAngleArc` at `MediaTab.qml:525-551` — one straight radial segment per bar, matching Caelestia's "clock hand" construction rather than an arc:

| Property | Recommended value | Rationale |
|----------|---------------------|-----------|
| Inner radius (segment start) | `root.ringRadius` (existing constant, unchanged) | Bars start exactly where today's dashed ring sits — preserves the silence-state footprint pixel-for-pixel |
| Max outer radius (full amplitude) | `root.ringRadius + 14` | Fits inside the existing `artSize`/`artColumn` layout budget without resizing anything else this phase touches |
| Minimum sliver length at silence | `3px` | Matches the existing `dashPattern: [1, 3]` dash length at `ringStrokeWidth: 3` — this is the exact property the silence-state argument (§ round-3 preservation) depends on |
| Bar stroke width | `2px` | Slightly thinner than the old single stroke (3px) since 60 moving bars read denser than 56 static dashes at the same width; render-gate-adjustable |
| Cap style | `ShapePath.RoundCap` | Matches the existing ring exactly |
| Angular slot | `360° / 60 = 6°` per bar | Fixed by the locked bar count |
| Colour | `Colours.outline` at silence, animates to `Colours.primary` when `amplitude > 0` via the existing `Behavior on strokeColor` pattern already present at `MediaTab.qml:560-567` (`Motion.standardDuration`/`standardEasing`) | Reuses the file's own existing colour-transition idiom, no new motion token |

### Per-Player Volume + Dedup Resolution (required by D-21-10, rendered here)

**Where the controls live:** the existing bottom-of-tab `volumeRow` (`MediaTab.qml:1282`, `Slider` bound to `mediaBackend.setVolume`) **stays wired to the active player only** — this is the parity baseline (QMEDIA-01) and needs no change. The **new** per-player capability lives inside the player-switcher dropdown itself (`playerMenu`/`menuColumn`, `MediaTab.qml:824-899`): each row gains an inline mini-slider, so a background (non-selected) player's volume is reachable without switching to it first — discoverable exactly where the player's identity already lives, not as a second detached control surface.

```
┌──────────────────────────────────┐
│  🎧  Firefox            ⌄        │   ← selector pill (existing, unchanged)
└──────────────────────────────────┘
   ┌──────────────────────────────────────┐
   │ ✓  Firefox        ▬▬▬▬▬▭▭  72%       │   ← active row: checkmark, label,
   │    Spotify         ▬▬▬▬▬▬▬ 100%      │      mini-slider, % (Label role)
   │    VLC              (no volume)      │   ← volumeSupported:false → slider
   └──────────────────────────────────────┘      omitted entirely, label-only
```

- Mini-slider width: **56px** (spacing-scale exception, see § Spacing Scale).
- Dragging the mini-slider must not select that row's player — it needs its own `MouseArea`/drag surface separate from the row's existing select-on-click `MouseArea` (`MediaTab.qml:887-895`), i.e. the slider consumes its own pointer events and does not propagate to the row click handler.
- Label elide width shrinks to make room: existing formula `menuColumn.width - spacingSm*2 - (fontLabel+4) - spacingXs` (checkmark column) needs a further `- 56 (slider) - spacingSm (gap) - ~28 (% readout)` subtracted when the row has a slider.
- Backend needs one new function, scoped by player id rather than acting on the active player: `mediaBackend.setVolumeForPlayer(playerId, fraction)` — the existing `setVolume(fraction)` (`MediaBackend.qml:355`) stays for the bottom `volumeRow`'s active-player-only path; the new function is the same clamped-write pattern applied to the matching entry in `Mpris.players.values` instead of `activePlayer`.
- Menu width: currently `width: selectorPill.width` (`MediaTab.qml:834`), which is only wide enough for a label. **Widen the dropdown when any row needs a slider** — recommend `width: Math.max(selectorPill.width, root.artSize * 1.3)` so the slider has room without the label losing all its budget; adjustable at render gate.

**Dedup interaction (the required resolution):** D-21-09's collapsing is a **display-list-only** operation. When two `Mpris.players.values` entries are recognised as the same perceptual source (title-substring or position/length proximity match), the dedup heuristic picks one canonical entry to appear in `players` (the switcher's model) and drops the other from that list — it does not merge two live volume-capable objects into one control. The surviving canonical entry's own `.volume`/`.volumeSupported` are what the row's mini-slider (and, if it's the active player, the bottom `volumeRow`) read and write, via the same `setVolumeForPlayer`/`setVolume` calls as any other row. **No fan-out, no dual-write:** a collapsed row's volume control behaves exactly like any single player's — it is only the *display* that is collapsed, never the underlying MPRIS object being controlled.
