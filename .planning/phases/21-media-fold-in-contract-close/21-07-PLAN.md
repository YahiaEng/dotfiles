Port the duplicate-source collapsing heuristic into the backend's player projection.

The problem, concretely: with some browsers one track appears twice in the switcher — once
from the browser process and once from the site's embedded player. Both reference shells
collapse these; neither this repo's backend nor the retiring card does. A switcher that
shows one song twice undermines the premise that the tab is a credible replacement.

Match two entries as the same perceptual source when EITHER holds:
- one entry's track title contains the other's as a substring (check both directions, and
  normalise case and surrounding whitespace before comparing); or
- their playback positions and their track lengths are each within a small proximity
  window of one another.

Pick one canonical entry per matched group and drop the others from the projection. Prefer
the entry that reports volume support when the group is mixed, so the surviving row keeps
its control; break remaining ties deterministically (a stable ordering, not whichever the
model happened to yield first) so the same pair collapses the same way across restarts.

Collapse INSIDE the loop that builds the projection array, before the array is returned —
not as a filter applied to a finished array. The active-player resolution and the
player-selection function both walk the live model directly, so a post-hoc filter would let
the selection point at an entry the switcher never displays.

**Dedup is display-list-only.** The heuristic picks one canonical entry to appear and drops
the other from the list. It does NOT merge two live objects into one control. The surviving
entry's own volume and volume-support flag are what its row reads and writes, through the
same calls any other row uses. No fan-out, no dual-write: a collapsed row's volume control
behaves exactly like any single player's — only the display is collapsed, never the
underlying object being controlled.

Guard the other direction too. Collapsing two views of one source is the goal; collapsing
two genuinely different players makes the switcher lie about what is running. Keep the
proximity window tight enough that two different tracks at coincidentally similar positions
stay separate, and cover that case in the tests.

Write the tests first, from the behaviour block above, then implement until they pass.
