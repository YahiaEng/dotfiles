<objective>
Close the one diagnosed Phase 05 gap (UAT Test 4 / review WR-04): the theme switcher fires an error toast on every Esc-cancel. Root cause (debug session, source-verified against walker v2.16.2): the WR-04 fix in commit eac9263 assumed walker signals user-cancel as exit 0 + empty output, but walker 2.16.2 exits 130 with no output on Esc / click-outside / Return-on-empty. Under `set -euo pipefail`, the `if ! SELECTED=$(… | walker --dmenu …)` branch keys the toast on ANY nonzero exit, so every cancel takes the failure path and the `[[ -z "$SELECTED" ]] && exit 0` cancel check is unreachable.

Fix: capture the pipeline exit code set-e-safely (`… ) || rc=$?`) and branch three ways — rc==130 → silent exit 0 (cancel); other nonzero → notify-send error + exit 1 (WR-04 intent preserved for 127/1/crash); rc==0 → fall through to the existing defensive empty-output check and selection mapping (unchanged).

Scope also covers the second in-scope script found by the repo grep the debug session requested: `waybar-switch.sh` carries the identical `set -euo pipefail` + `walker --dmenu` trap (its `[[ -z "$SELECTED" ]] && exit 0` on line 22 is dead code under `set -e`, and hard failures are silently swallowed with no toast). It gets the same three-way branch. `powermenu.sh` also pipes into `walker --dmenu` but is intentionally OUT OF SCOPE: it has no `set -e`, so its command substitution does not abort and its empty-output cancel check already works correctly.

Purpose: restore the "Esc closes silently" UX contract across every walker dmenu picker while keeping genuine hard failures loud.
Output: two corrected picker scripts and one committed hermetic exit-code checker.

Ref: .planning/debug/theme-switch-esc-cancel-error-toast.md (root cause + suggested direction).
</objective>
