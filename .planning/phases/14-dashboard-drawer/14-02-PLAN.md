  <name>Task 1: Package-legitimacy gate — `ttf-material-symbols-variable-git` (T-14-SC)</name>
  <what-built>
    Nothing yet — this gate runs BEFORE anything is installed or edited, and it is the
    prohibition "no install of the `[SUS]`-flagged font package before its human
    legitimacy checkpoint passes" made operational.

    14-RESEARCH.md's Package Legitimacy Audit could not verify this package. The AUR
    web page returned an anti-bot challenge (Anubis) when the researcher fetched it,
    so votes, popularity, maintainer identity, last-updated date and PKGBUILD contents
    were all unconfirmed. The package's existence and version
    (`4.0.0.r119.gc51274e9-1`) came from a single WebSearch result and is marked
    `[ASSUMED]`. The verdict recorded was `[SUS — unverified]`.

    `gsd-tools query package-legitimacy check` supports npm, PyPI and crates only —
    it rejected `--ecosystem aur`. There is no automated check to fall back on, which
    is exactly why this is a human gate and why it is never auto-approvable regardless
    of `workflow.auto_advance`.

    What rides on it: D-28 makes Material Symbols Rounded the icon system for the
    whole QML family from this phase onward — the drawer, then Phase 15's audio and
    connectivity panels, then Phase 16's workspace overview. This is a `costly`
    reversibility call (see Task 2's `<reversibility>` block): swapping the icon system
    later re-opens every render gate that ever approved a surface built with it.
  </what-built>
  <how-to-verify>
    Open `https://aur.archlinux.org/packages/ttf-material-symbols-variable-git` in a
    browser (a real browser, not a fetch — the anti-bot challenge is what defeated the
    research session) and read these five things:

    1. **Votes and popularity.** A font packaging that the reference shells
       (end-4/dots-hyprland, Caelestia) genuinely use should have non-trivial votes.
       A near-zero vote count on a package claiming to wrap a Google font is the
       slopsquat shape.
    2. **Maintainer and last-updated date.** An orphaned package, or one untouched for
       years, is the "abandoned" half of the `[SUS]` verdict.
    3. **Out-of-date flag.** Whether one is set, and whether it has been ignored.
    4. **The PKGBUILD `source=` line** (click "View PKGBUILD"). It must point at
       Google's own Material Symbols repository or at the thin
       `github.com/Shiphan/ttf-material-symbols-variable` wrapper that pulls it. A
       source URL pointing anywhere else — a personal file host, a shortened URL, a
       repo with no visible relationship to Google's font — is a reject.
    5. **The `package()` function.** It should do nothing but install `.ttf` files
       into `/usr/share/fonts/`. Any `curl`, `chmod +x`, systemd unit, hook, or write
       outside `/usr/share/fonts` in a *font* package is a reject.

    Then pick one:

    - **`approve-aur`** — the page checks out. This is the recommended outcome and the
      consistent one: every other font in this repo is package-installed
      (`ttf-firacode-nerd`, `noto-fonts`, and the rest), none is vendored, and
      `install.sh`'s existing hard-fail `verify_packages` loop already covers AUR
      entries like `walker` and `elephant` with no extra machinery. The repo also has
      precedent for exactly this gate: the icon-theme block (D-16) and the game-center
      block (D-33) both carry "human package-legitimacy checkpoint approved" comments
      from prior phases.
      *Cost of approving:* an unpinned `-git` AUR package whose PKGBUILD can change
      under you between installs, verified by presence only. That is the same exposure
      this repo already accepts for `walker`, `elephant` and eight `elephant-*`
      providers — not a new class of risk.

    - **`vendor-ttf`** — the page does not check out (low votes, orphaned, wrong
      source, or a `package()` doing more than installing fonts). Fall back to
      vendoring the variable TTF directly from Google's official Material Symbols
      repository into the repo, dropping the AUR dependency entirely.
      *Cost of vendoring:* a binary asset in git, manual update discipline forever, and
      a new stow package plus a fontconfig path to get right — real work, and it
      changes Task 2's shape substantially. But it removes the entire AUR/PKGBUILD
      trust surface, which is the correct trade if the page looks wrong.
      *Recommended only if the page actually looks wrong* — vendoring pre-emptively
      buys nothing here and breaks this repo's uniform "fonts are packages" convention.

    - **`reject`** — the package looks actively compromised (a source URL to somewhere
      unrelated, an executable payload, a maintainer takeover pattern). Halt the plan
      and escalate; do not proceed to Task 2 in any form.

    **Stay at the terminal after approving.** Task 2 installs the package with the
    session's AUR helper immediately afterwards and that prompts for a sudo password.
    Phase 11 lost a whole executor session to exactly this (recorded in STATE.md's
    Blockers: "sudo pacman -S requires an interactive password; no operator responded").
  </how-to-verify>
  <resume-signal>Reply with exactly one of: `approve-aur`, `vendor-ttf`, or `reject`. If `vendor-ttf` or `reject`, describe what on the AUR page decided it — that observation is what gets recorded in the SUMMARY, replacing the research session's unverified `[SUS]` verdict.</resume-signal>
