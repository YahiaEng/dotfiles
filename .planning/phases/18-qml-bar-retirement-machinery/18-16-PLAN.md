## `bar-visibility.sh` still owns visibility. This plan owns nothing of it.

The owner computes a base state — visible, idle-hidden, hard-hidden — from per-source intent files
under an OR-union, and 18-15 pushes that state into the shell. That is the only writer. **Nothing in
this plan writes an intent file, invokes the owner script, or sends the owner a message.**

Reveal is a **transient presentation-layer override**, and 18-15 did not leave this plan to invent
the seam — it declared one. `Bar.qml` carries `property bool revealOverride`, initialised false,
commented in 18-15's own source as this plan's seam, and folded into its `barRendered` derivation
alongside the visibility state. **This plan's whole composition is binding that one property to
`BarReveal.revealActive`.** Three properties make it not a second source of truth, and each is
inherited or asserted rather than argued:

- **It cannot write.** `BarReveal` is a pure function of live pointer and modifier state. It holds no
  file handle, spawns no subprocess and declares no IPC endpoint. The arrow points owner → shell and
  never back, so the two cannot disagree about a value only one of them produces.
- **It cannot outlive what it decorates.** Reveal is observable only while the base state is hidden.
  When the owner flips the base to visible, `barRendered` is already true and the override adds
  nothing; when it flips back to hidden the hot zone is rebuilt from scratch with no carried-over
  hover state. There is no stale-reveal state to desync from.
- **It cannot move the reserved zone, structurally.** 18-15 derived `zoneReserved` from the
  visibility state alone and **deliberately excluded `revealOverride` from that expression**, with a
  gate of its own asserting the exclusion. There is no code path from a reveal to `exclusiveZone`, so
  a revealed bar over a fullscreen window draws without re-reserving space and cannot reflow the game
  the user is playing. This plan asserts the property it inherits — the reserved array byte-identical
  revealed and unrevealed, in Task 1 and again in Task 3 — rather than re-implementing the guarantee.

The desync class the owner's own header records as having been deleted from this repo **twice** is
the class where two writers disagree about one state. There is one writer here, and the second
participant is structurally incapable of writing.

## The finding that reshapes the hover half

`hypridle.conf`'s bar listener declares the idle intent on a 120s timeout and clears it `on-resume`.
Its comment block states — and this is load-bearing, not decoration — that `on-resume` fires on any
keypress or pointer movement, so idle-hide clears on any input with no extra machinery. **The very
pointer motion that would reach the hot zone clears the idle intent first.** Hover reveal is
therefore unreachable in the idle-hidden state, and its only reachable function is under fullscreen,
gaming mode and the explicit keybind — the hard-hidden state, where D-18-23 deliberately releases
the reserved zone so windows reflow into those pixels.

That is exactly where a 4px input-owning strip has a real cost, and the plan does not design around
it by pretending otherwise. The strip is bounded in depth, bounded in lifetime, carries no
click-accepting handler so a swallowed click does nothing rather than something wrong, and the
residual is named in the threat register at `T-18-16-01` with a live human check rather than an
argument. The hot zone is still armed in **both** hidden states — the binding is on hidden-ness, not
on which driver caused it, so no assumption about 18-15 exposing the driver is taken — and in the
idle-hidden state it sits inside space the reserved zone keeps empty, where it takes input from
nothing.

That same comment block ends by asserting that no edge-hover reveal exists in this design and
forbidding one from ever being added. QBAR-08 overrides it — and **18-15 already owns that
correction**, making it in the same wave it repoints the two intent lines beneath it. This plan does
not touch `hypridle.conf` and does not duplicate the edit; Task 3 verifies it landed, because two
plans editing one comment is how a file ends up arguing with itself. What this plan owns is the
consequence nobody had drawn from that listener: the reachability finding above.

## The held-modifier question, and what is actually unverified

RESEARCH's Open Question 2 and assumption A2 record that no held-modifier signal was found in the
scanned API surface, and recommend budgeting a probe before assuming a pure-QML solution. That
recommendation is honoured — and the scan turns out to have been incomplete rather than wrong.

The installed Hyprland global-shortcut type on this build declares a **readonly `pressed` boolean
with a change notification** and a **`released` signal**, alongside `pressed`. A held state and a
release edge both exist on the QML side. What remains genuinely unverified is the **compositor
half**, and it is the half that can actually fail:

- whether Hyprland delivers a release edge for a bind on the Super key itself, or only an activate;
- whether adding a press-side bind on that key collides with the shipped `SUPER + SUPER_L` release
  bind at `keybinds.lua:86` that opens walker's main menu on a bare Super tap — D-01's three-way
  split, proven live by keypress in 07-04 and in daily use since.

`keybind-doctor` **cannot** catch that second one. Its shadow check compares
`(modmask, key, keycode, release)` tuples, and a press bind and a release bind on the same key are
two different tuples — the check passes while the compositor's own precedence does whatever it does.
Only a live keypress settles it, which is why Task 2 takes one, in the nested `hypr-lua-harness`
instance the 13.1 port already used for exactly this class of question rather than against the live
session.

Two candidate mechanisms, both Hyprland binds — D-18-29's precedent is that the bind lives in
`keybinds.lua`, and both branches honour it:

- **Branch A**, preferred: one bind dispatching the global-shortcut identifier, consumed in-process
  by a shortcut declaration whose press and release edges drive the reveal directly. Zero
  subprocesses, zero fork latency on a gesture that must feel instant.
- **Branch B**, the fallback the prompt names and the expected outcome if Hyprland delivers no
  release edge: a press bind and a paired release bind — the `release` option idiom already proven
  at `keybinds.lua:86` — each dispatching a command into the shell.

D-18-29 kept `Super+Shift+B` out of a QML shortcut because a shortcut cannot resurrect a bar whose
process is gone. **That reasoning does not extend to reveal**: there is nothing to reveal when the
shell is dead, so Branch A carries none of the cost D-18-29 was avoiding. This is stated so Branch A
does not read as a violation of a decision it is not in scope of.

Task 2 records which branch was confirmed, which was rejected, and the evidence, in the file that
implements it. And it carries a stop condition: if neither branch can be added without breaking the
Super-tap path, the task reverts and reports rather than substituting a different chord — QBAR-08
names Super specifically.
