<objective>
Run GATE-02's blocking final pass: judge the shipped Quickshell bar against UI-SPEC's five
aesthetic criteria (calibrated on athena) and six capability criteria (audited against
`config-full`, `config-floating` and `config-vertical`), live, on the running bar — and produce a
record that either authorises 18-20's waybar deletion commit or blocks it.

Purpose: this is the last decision point before an irreversible commit. 18-20 deletes
`config-athena.jsonc`, `config-full.jsonc`, `config-floating.jsonc`, `config-vertical.jsonc`,
`modules.jsonc`, `bar-common.jsonc` and `waybar-equivalence-check` — the only tool in this repo
that resolves waybar's first-defined-wins `include` chain correctly — in a single commit. After
that commit, a capability nobody checked for here cannot be re-derived. REQUIREMENTS.md § Out of
Scope records this consequence knowingly: pixel-for-pixel ports are ruled out, so the old-versus-new
equivalence-check shape is unavailable and this human gate carries the load alone.

Three properties shape the whole plan:

1. **It is observed, not read.** UI-SPEC's own pass bar is that a criterion counts only when
   confirmed live — clicked, scrolled, toggled, actually theme-switched. "Looks right in the source"
   never counts. D-18-31 cites the precedent: this repo has shipped visibly broken surfaces through
   fully green automated gates three times (Phase 6, Phase 8's bar, Phase 16's two false passes). An
   automated tally is the evidence this gate exists to distrust, so every automated check in this
   plan checks the *record's* shape and the *build's* identity — never the bar's appearance.
2. **The two baselines stay split (D-18-32).** Athena is the aesthetic reference; the three other
   layouts are a named-capability audit. They are two blocks with two baseline columns, because
   D-18-32 deliberately declined to ask one look to do both jobs. The audit half is walked off
   `18-BEHAVIOUR-BASELINE.md`'s `## GATE-02 Criterion B Index`, which 18-02 built for exactly this
   consumer.
3. **A failure is a stop with a loop, not a note.** Any single `FAIL` writes `RETIRE-02 BLOCKED`
   into the record, and 18-20's precondition reads that section. This plan judges; it never fixes.
   The remedy lands in the owning plan's file, and this plan's tasks 2 and 3 re-run as the next
   iteration — re-observing all fifteen rows, because a fix to one shared surface can regress
   another.

Output: one artifact — `18-GATE-02-RECORD.md`.

## Why this is a `<human-check>` and not a `checkpoint:human-verify` task

`workflow.human_verify_mode` is `end-of-phase` on this project, so this phase's plans carry human
gates as `<verify><human-check>` blocks inside `type="auto"` tasks rather than as
`checkpoint:human-verify` tasks — all sixteen preceding plans in this phase are shaped that way,
including the D-18-31 checkpoints in 18-09, 18-11 and 18-12. The gate's substance is unchanged: the
executor cannot self-certify any of the fifteen rows, task 2 cannot complete without a human having
performed the gestures, and task 3 fails closed on an incomplete sheet. Recorded here so the shape
reads as configuration compliance rather than as a downgrade of D-18-31's blocking pass.

## Explicitly NOT in this plan

Each is owned by a named plan, listed so the executor does not build ahead or double-work:

- **Fixing anything.** A failing criterion is remedied in the file that owns it — `WorkspaceCapsule.qml`
  (18-09) for both workspace findings, `modules/bar/` and the drawer host (18-11) for D-18-11, and so on.
  This plan writes no QML, no script and no doctor check.
- **The deletion itself** — 18-20 (RETIRE-02), which reads this record's authorisation section as its
  own precondition and runs `retirement-check waybar` before and after.
- **The during-phase checkpoints** D-18-31 also mandates — already discharged inside the build plans
  as their own `<human-check>` blocks. Their verdicts are context here, never a substitute (see the
  adjacency contract in `must_haves`).
- **GATE-01's enumeration** (18-02, wave 1), **GATE-03's structural checks and QBAR-12's zone
  stability** (18-17), **GATE-04's hex lint** (18-03), and **QBAR-11's soak with LEDGER-03's frame-rate
  measurement** (18-18). All three dependencies are inputs to this pass, not work it repeats: a green
  18-17 and a green 18-18 are preconditions for sitting down, because judging aesthetics on a build
  whose reserved zone is unstable or whose RSS is climbing wastes the one human pass this phase gets.
