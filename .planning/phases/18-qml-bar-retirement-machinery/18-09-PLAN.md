<objective>
Fill 18-05's `WorkspaceCapsule` slot with QBAR-03: live per-app window icons in athena's
`{icon} {windows}` shape, fixed-extent slots that never move as windows come and go, `+N`
overflow in both orientations, and click-to-switch that actually switches.

Purpose: QBAR-03's requirement text says click-to-switch "restores the capability dead under
waybar 0.15.0's compiled-in dispatch." That word — *restores* — is the whole plan. The retired
bar already has a workspace module with a configured click action; it is present, it is
clickable, and it does nothing. Any acceptance criterion this plan writes that a
present-and-configured handler could satisfy is a criterion the broken thing already passes. So
the close condition here is behavioural and live: click an indicator, watch the desktop change.

Three things land, in this order:

1. **A tracer that proves the whole path on one slot.** Hyprland's live workspace model → one
   window's app id → the glyph map → a rendered cell → a click → a dispatch → the compositor
   actually switching. Every layer this capsule will ever touch, wired once, end to end. If the
   dispatch expression is wrong or the glyph font does not resolve, that is discovered after one
   commit rather than after the whole capsule is built on top of it.
2. **The full fixed-extent slot set.** D-18-12's guarantee is not "the slots look tidy", it is
   "nothing below the workspaces ever moves as windows open and close." That is delivered
   structurally — a constant number of reserved icon cells per slot, so the geometry is a
   function of the tokens and not of what happens to be running.
3. **The vertical form.** The same slots re-stacked into `Design.barColumnWidth`, with the same
   capacity and the same `+N` rule, because UI-SPEC is explicit that the two orientations must
   behave identically rather than the horizontal one being an unlimited-width special case that
   newly caps when rotated.

Output: one file — `modules/bar/WorkspaceCapsule.qml` — filled in.

**Explicitly NOT in this plan.** No new type and no `qmldir` line: `WorkspaceCapsule` was
registered by 18-05 and that manifest is frozen for this wave. No `Bar.qml`, `BarEntryModel.qml`
or `shell.qml` edit; no new backend and no gate widening (the entry list declares no backend for
`workspaces` because `Quickshell.Hyprland` is ungated and already mounted). No new `Design.qml`
token — see the note in Task 1 on why this capsule's three constants stay local, which also
happens to be what keeps all four wave-3 plans off a shared file. No popout: workspaces is not
one of D-18-16's six popout sections. No drag-to-move-window between workspaces — that is
`Overview.qml`'s job and Phase 16 shipped it. No scroll-to-switch — see the explicit finding
below.

**Scroll-to-switch: a named cut, not a silent one.** 18-02's GATE-01 enumeration found that
`config-floating` binds scroll on its workspaces module to next/previous workspace, and that
capability has no owning plan in this phase. This capsule does **not** implement it. Two reasons,
both routing rather than difficulty: QBAR-03's requirement text is click-only, and every scroll
gesture in this phase is QBAR-04's, owned by 18-12 — putting a wheel handler here would give two
plans partial ownership of scroll behaviour on the same bar. The capability is also **not lost by
retiring the bar**: `keybinds.lua` already binds Super plus mouse wheel, globally, to the
identical next/previous workspace expressions, so the only thing that disappears is
scroll-over-the-bar-without-holding-Super. 18-19's GATE-02 criterion B must judge whether that
difference is a loss; if it rules that it is, the remedy is a wheel handler on this capsule
dispatching the same two expressions, and 18-12 is its home. This paragraph exists so that
judgment is made on the record instead of by omission.
