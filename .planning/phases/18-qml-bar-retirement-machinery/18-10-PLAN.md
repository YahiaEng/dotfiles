<objective>
Fill 18-05's `tray` slot: the first `Quickshell.Services.SystemTray` + `Quickshell.DBusMenu` /
`QsMenuOpener` consumer in this repo, and the phase's largest genuinely untrusted input
surface.

Purpose: QBAR-05 is two claims, and the second one is where this kind of work usually fails.
"The system tray shows running tray applications" is straightforward — iterate a model, render
an icon. "**and their menus open on click**" runs through a D-Bus menu protocol whose leaf
activation call this phase's research could NOT confirm from the installed type information.
The observable failure that guards against is specific and quiet: a menu that renders every
row correctly, with the right labels, separators and check marks, and does absolutely nothing
when a row is clicked. No error, no log line, no visual difference from a working menu. That
failure survives every static check in this repo. So this plan's acceptance criterion for
activation is a live click on a real application's real menu row producing the real effect —
never a source assertion, and never a method name written down as though it had been verified.

Three things land, in the order that de-risks the unknown earliest:

1. **The icons, end to end.** One thin path — `SystemTray.items` → `Repeater` → `IconImage`
   → 18-05's `BarCapsule` chrome → a real icon visible in the running bar — plus left-click
   activation and the `"apps"` placeholder for an unresolved pixmap. This is the tracer: it
   proves the whole novel service chain on one real application before any menu work exists.
2. **The menu, including the open question.** `QsMenuOpener` over the item's `DBusMenuHandle`,
   rendered in an inline `PopupWindow` anchored per orientation and styled to UI-SPEC — and
   the leaf-activation call resolved by experiment, with the answer and the evidence recorded
   in the SUMMARY so no later plan has to rediscover it.
3. **The bounds and the hardening.** `trayMaxExtent` appended to `Design.qml`, internal scroll
   past it, and the machine-checkable gates that keep every third-party string inert.

Output: `modules/bar/TrayCapsule.qml` filled, one new `Design.qml` token, and a recorded,
evidence-backed answer to the phase's own Open Question 1.

**Explicitly NOT in this plan** (named so the executor does not helpfully build ahead):
- **No edit to `Bar.qml`, `BarEntryModel.qml`, `shell.qml`, or `modules/bar/qmldir`.** All four
  are frozen for wave 3 by 18-05. `TrayCapsule` is already registered, already instantiated,
  already zoned and already handed all five backend handles. If this plan appears to need an
  edit to any of them, that is an 18-05 scope correction and the executor must stop and say so,
  not edit in place — a wave-3 edit to a frozen file serialises 18-08, 18-09 and 18-11 on a
  merge conflict.
- **No tray tooltip.** UI-SPEC E5 long-text is explicit that tray icons carry no text, and the
  only tray string it specifies a treatment for is the menu row. This repo has no bar-tooltip
  component, and the hover contract that would govern one — the dwell gate, the reveal-settled
  suppression latch, the one-open-at-a-time rule — is 18-13's, which 18-05 already forbade
  stubbing early. Recorded as a named carry-forward to 18-13, not a silent drop. It also means
  `title`, `tooltipTitle` and `tooltipDescription` never reach the screen at all in this phase,
  which is the strongest available mitigation for three of the four untrusted strings.
- **No `SectionPopout.qml` and no reuse of it.** The tray menu is a native-menu list, not a
  section popout; UI-SPEC styles it deliberately lighter (radius 12, not `popoutCornerRadius`).
  18-13 owns the popout frame and lands two waves later.
- **No scroll-to-adjust on tray items.** `StatusNotifierItem.scroll(delta, horizontal)` exists
  and is deliberately unwired: QBAR-04's scroll surfaces are audio and brightness (18-12), and
  the tray's own long axis uses the wheel for its bounded internal scroll instead. Wiring both
  to one wheel would make the tray's overflow scroll and a tray app's volume fight each other.
- **No tray entry in the settings drawer, no tray popout, no per-app allowlist.**

Verified against the installed `quickshell 0.3.0-2` on this host during planning, by reading
the `.qmltypes` files directly. Do not re-derive from memory and do not substitute a

**`Quickshell.Services.SystemTray`** — `SystemTray` is a singleton exposing one readonly
property, `items`, an `UntypedObjectModel` of `SystemTrayItem`. Each item
(`qs::service::sni::StatusNotifierItem`, exported as `SystemTrayItem`) is READONLY throughout
and exposes: `id`, `title`, `status` (`Status.Passive` | `Status.Active` |
`Status.NeedsAttention`), `category` (`Category.Hardware` | `SystemServices` |
`ApplicationStatus` | `Communications`), `icon` (a `QString` source, hand it straight to an
image source — do not parse it), `tooltipTitle`, `tooltipDescription`, `hasMenu` (bool),
`menu` (a `DBusMenuHandle` pointer, notified by `hasMenuChanged`), and `onlyMenu` (bool —
the item declaring that it has no activation action and a primary click should open its menu
instead). Methods: `activate()`, `secondaryActivate()`, `scroll(delta, horizontal)`, and
`display(parentWindow, relativeX, relativeY)`. Signal `ready`.

**`Quickshell.DBusMenu`** — `DBusMenuHandle` (C++ `qs::dbus::dbusmenu::DBusMenu`) exposes one
readonly `menu` property of type `DBusMenuItem`. `DBusMenuItem` has prototype `QsMenuEntry`
and adds `menuHandle`, a `layoutUpdated` signal, and the methods `sendOpened`, `sendClosed`,
`sendTriggered` and `updateLayout`.

**`Quickshell` core menu types** — `QsMenuOpener` has a writable `menu` property
(`QsMenuHandle`) and a readonly `children` property (`UntypedObjectModel`). `QsMenuEntry`
exposes readonly `isSeparator`, `enabled`, `text`, `icon`, `buttonType`
(`QsMenuButtonType.None` | `CheckBox` | `RadioButton`), `checkState` (a `Qt::CheckState`) and
`hasChildren`; signals `triggered`, `opened`, `closed`; and ONE method, `display(parentWindow,
relativeX, relativeY)`. `QsMenuAnchor` also exists (`menu`, `anchor`, `visible`, `open()`,
`close()`) and is NOT used here — it anchors a menu Quickshell renders, which cannot carry
UI-SPEC's styling contract.

> **The one thing that is NOT verified.** Nothing in the scanned type information confirms
> which call activates a leaf entry from QML. `QsMenuEntry` has a `triggered` SIGNAL and a
> `display()` method that reads as a submenu opener. The concrete `DBusMenuItem` subtype adds a
> `sendTriggered` method — that is an EXISTENCE fact read off the type file during planning, and
> it is NOT a semantics fact: nothing confirms that calling it on a leaf row is the intended
> activation path, that `QsMenuOpener.children` hands QML objects on which it is invokable, or
> that it is preferred over connecting to `triggered`. Task 2 resolves this by clicking a real
> row in a real application's menu and observing the real effect. Do not shortcut it.

**`Quickshell.Widgets`** — ships with the installed package and is registered in its own
`qmldir` (`IconImage 0.0 IconImage.qml`). **Not imported anywhere in this repo today; this plan
is its first consumer.** `IconImage` is an `Item` whose own documentation names "System tray
icons" as an intended use. It exposes `source` (aliased to a backing `Image.source`),
`asynchronous`, `status` (aliased to `Image.status`, so the `Image.Null` / `Image.Ready` /
`Image.Loading` / `Image.Error` values apply), `mipmap`, `backer`, `implicitSize` and a readonly
`actualSize`. It forces a 1:1 aspect ratio by padding, which is why it is the right type for a
uniform-cell tray and a raw `Image` is not.

**`PopupWindow`** (`Quickshell._Window/PopupWindow`, reachable from plain `import Quickshell`;
C++ `ProxyPopupWindow`, prototype `ProxyWindowBase`, default property `data`) — exposes
`parentWindow`, `relativeX`, `relativeY`, a readonly constant `anchor` (a `PopupAnchor`),
`grabFocus`, and a `reposition()` method, on top of `ProxyWindowBase`'s `visible`, `implicitWidth`,
`implicitHeight` and `color`. `PopupAnchor` exposes `window`, `item`, `rect`, `margins`, `edges`,
`gravity` and `adjustment`. `Edges` is `Quickshell/Edges` with members `None`, `Top`, `Left`,
`Right`, `Bottom`. `PopupAdjustment` is `Quickshell/PopupAdjustment` with members beginning
`None`, `SlideX`, `SlideY`. A `PopupWindow` is declared INLINE as a child object; it does not
need — and must not get — a `qmldir` registration, which is what keeps this plan off 18-05's
frozen manifest.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Third-party application → session D-Bus (`org.kde.StatusNotifierWatcher`) → QML shell | **The phase's largest genuinely untrusted input surface.** Every tray item's `id`, `title`, `status`, `category`, `icon`, `tooltipTitle` and `tooltipDescription` is authored by an arbitrary application the user happens to be running. Any process on this user's session bus can register an item; the shell has no way to attest who did. 18-05's T-18-05-04 explicitly deferred this assessment to this plan; this is it. |
| Third-party application → `com.canonical.dbusmenu` → `DBusMenuHandle` → `QsMenuOpener` → QML | The menu's entire structure and every row label, icon, enabled flag, check state and nesting depth is application-supplied. `QsMenuEntry.text` is the ONLY third-party string this plan renders on screen — the three item-level strings never reach a rendered element, because no tooltip is built this phase. |
| QML shell → wlr-layer-shell / xdg-popup (the inline `PopupWindow`) | A new on-screen surface this plan creates, parented to the bar. It reserves nothing (`exclusiveZone` is not set on a `PopupWindow`) and it takes focus only while deliberately opened. |
| QML shell → the tray application (`activate()` / `secondaryActivate()` / the menu activation call) | Outbound, over the same D-Bus session the item registered on. The shell sends no application-supplied data back — the calls carry no arguments derived from any tray-supplied string. |

No network listener, no credential handling, no privilege boundary and no filesystem write exists
in this plan's scope. `Design.qml` is the only file written outside the capsule, and it gains one
integer literal.
