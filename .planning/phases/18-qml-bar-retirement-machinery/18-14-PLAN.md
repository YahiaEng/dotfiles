<objective>
Fill the five remaining D-18-16 popout bodies into the frame 18-13 built and proved on audio, and
prove that filling them needed no change to that frame.

18-13 shipped `SectionPopout.qml`, `PopoutController.qml`, `PopoutTrigger.qml` and the whole hover
contract — the suppression latch, the 400ms dwell, the 200ms combined-region grace, click-to-pin,
one-open-at-a-time through one guarded summon path — and declared all six section ids from its first
commit while shipping exactly one body. This plan ships the other five: **wifi, bluetooth,
clock→calendar, cpu/ram/disk→resources and now-playing→media** (D-18-16).

Each body is a **compact summary plus primary quick actions at glance scope**, with an "Open in
dashboard" wayfinding link at the foot. The dashboard drawer keeps its full four-tab role and the
panel family keeps its unbounded lists (D-18-17). **No shipped v3.0 surface is thinned by this
plan** — the proof is the diff: nothing under `modules/dashboard/` changes except two appended
`Design.qml` tokens and two strictly-additive readiness registers.

Three things this plan delivers, in order:

1. **The readiness answer, then the two bodies that depend on it.** The phase's standing question —
   does each backend expose a not-yet-resolved signal distinguishable from resolved-empty? — is
   answered per section against the real files before any body is written, because a wrong answer
   invalidates the body built on top of it. Wifi and bluetooth are the two where the answer requires
   building something, so they are built first and the audit is committed with them.
2. **The two bodies that need nothing new.** Clock is pure date arithmetic with no asynchronous
   source anywhere in it; resources reads a three-value register the shipped sampler has published
   since Phase 14. Neither needs a signal added, and saying so is part of the audit's value.
3. **The media body and the six-section close.** The last body, the last trigger, one bounded
   retrofit so all six bodies read one list cap, and the end-to-end proof that six ids open six
   different popouts one at a time.

**Named seams into files this plan does not own.** Every one is additive and named here rather than
taken silently:

- `quickshell/.config/quickshell/modules/bar/qmldir` — **owner 18-05**. Five type declarations
  appended, each in the commit that creates its type, per the manifest's own standing rule. The
  manifest disables directory-scanner synthesis for its directory, so an unregistered type is
  unresolvable **with no load error** — this is not optional and there is no alternative.
- `quickshell/.config/quickshell/modules/dashboard/WifiBackend.qml` and `BluetoothBackend.qml` —
  **owner 15-03**. One read-only readiness register each, plus one one-shot deadline on the
  bluetooth side. Strictly additive: no existing line changes, no existing consumer's behaviour
  changes, and neither backend's lifecycle gate is touched.
- `quickshell/.config/quickshell/modules/bar/MediaConnectivityCapsule.qml` and `SystemCapsule.qml` —
  **owner 18-08**. Entries wrapped in triggers. 18-08's own verify gate names the popout plans as
  the owners of hover/popout additions to those files.
- `quickshell/.config/quickshell/modules/bar/ClockActionsCapsule.qml` — **owner 18-11**. The clock
  cell wrapped in a trigger; the other five action cells untouched.
- `quickshell/.config/quickshell/modules/bar/AudioPopout.qml` — **owner 18-13**. Exactly one line:
  its list cap literal replaced by the shared token, so six bodies read one number.

**Explicitly NOT in this plan** (named so the executor does not helpfully build ahead):

- **No frame change.** `SectionPopout.qml`, `PopoutController.qml` and `PopoutTrigger.qml` are not
  edited by any task. If a body appears to need a frame change, that is a finding to record and
  raise, not an edit to make — the whole point of 18-13 shipping one body was to leave a frame this
  plan could consume unchanged, and consuming it unchanged is the test of whether that worked.
- **No `Bar.qml` and no `shell.qml` edit.** The wayfinding path is complete: 18-05 declared both
  summon seams and wired the shell side, 18-13 built the relay. Both halves already exist; this plan
  is a caller, not a builder.
- **No scan and no discovery.** Neither backend's lifecycle gate is widened, no scan flag is
  written, and no discovery wrapper is called from anywhere under `modules/bar/`. D-15-15 and
  D-15-18 forbid permanent scanning; 18-05 left both gates alone on purpose and said so in shipped
  source; 18-08 did not reopen it. A popout that opens after a 400ms hover is not a request to
  sweep the radio.
- **No passphrase prompt and no pairing flow.** A wifi connect that needs secrets shows its already-
  mapped reason and stops; pairing an unpaired device is not offered at all. Both belong to the
  panels, and the foot link is how you get there.
- **No second clock and no second sampler.** The calendar reads a date handed down from the clock
  capsule's existing time source; the resource rows read the sampler already running. This plan adds
  exactly one timing object in total, one-shot, and it stops.
- **No shared calendar type and no `DashboardTab.qml` edit.** The compact month grid carries its own
  copy of the date arithmetic; extracting it into one shared type would mean editing a shipped v3.0
  surface mid-phase for a refactor with no user-visible benefit. The duplication is accepted, named
  in the file's own header, and carries a review obligation.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Over-the-air SSIDs → `WifiBackend` → the wifi popout body | Network names are broadcast by whoever is in radio range and are entirely attacker-chosen. The glance body renders the connected network's name and up to three saved network names. |
| BlueZ device names → `BluetoothBackend` → the bluetooth popout body | A device's advertised name is chosen by that device. The glance body renders up to three of them. |
| MPRIS metadata (title, artist) → `MediaBackend` → the media popout body | Any local application that registers on the MPRIS bus writes these strings. The glance body renders the full uncapped title and the artist. |
| MPRIS art URL → `MediaBackend`'s resolver → `artPath` → the media popout's image | The one path in this plan that reaches an image decoder. The popout consumes the **already-resolved** path property and never the raw URL, so the resolution boundary stays where `MediaBackend` and `MediaTab.qml` already put it; the popout is a second renderer of a value the shipped Media tab renders today. |
| Both radios → the popout bodies | The one boundary this plan deliberately does **not** cross. No body writes a lifecycle gate, a scan flag or a discovery property, so nothing in `modules/bar/` can cause the machine to transmit. |

No network listener, no credential handling, no privilege boundary, no filesystem write and no
subprocess launch exists anywhere in this plan's scope. `WifiBackend`'s connect path is invoked with
the panel's own existing call shape and no secret is ever entered, held or rendered by any file here.
