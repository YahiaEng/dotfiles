<waybar_coexistence>
## waybar Coexistence — stated exactly, not left implicit

waybar and the QML bar both exist from wave 1 until 18-20 deletes waybar. This plan makes a
deliberate, recorded choice about the four intervening waves.

**waybar's visibility control is dropped here.** From this plan's commit the owner actuates
the QML bar only. waybar is left permanently `visible` and un-dimmed until RETIRE-02 removes
it whole.

**Why that is safe.** waybar is deleted fourteen plans later. During the window it merely
stops auto-hiding — a visible, non-destructive, self-correcting degradation, on a bar the
user is already living with as a duplicate strip above the new one (18-01 recorded the
co-existing 92px reservation as expected, not a defect). Nothing is lost that is not about to
be deleted anyway.

**Why the alternative is worse.** Dual actuation would mean keeping the CSS-dim machinery
alive precisely so waybar's `hidden-idle` could still work — which is the exact code this
plan exists to delete — and it would put one owner in charge of two actuation targets with
two different state vocabularies and two different failure modes. That is a weaker version of
the multi-writer class the single-owner design exists to prevent, adopted voluntarily, for a
component scheduled for deletion.

**The three cutover hygiene actions this creates**, all one-shot, all in Task 3:

1. `~/.local/state/theme/waybar-visibility.css` loses its only writer. It must be truncated
   to empty once at cutover and must **not** be deleted. waybar's four `style-*.scss` files
   each `@import` it, and an unresolvable `@import` makes GTK3 discard the whole stylesheet —
   the exact failure `stow.sh`'s own seed comment already documents. If the file were left
   holding a dim rule with no writer to clear it, waybar would sit at 5% opacity permanently
   for four waves. The file, its `contract.json` entry, the `stow.sh` seed and the four
   `@import`s are deleted together by 18-20.
2. waybar is sent one signal at cutover — its configured `reload` action, which per its own
   documented behaviour resets the bar to its config-time visibility — so it cannot be
   stranded hidden by whatever state it happened to be in when the owner stopped driving it.
   `reload.sh` already sends that same signal on every theme switch, so waybar's visibility
   keeps being reasserted for free through the rest of the phase.
3. The old intent directory is removed rather than left behind. The owner's directory is
   renamed with the script, so the old one becomes an orphan holding plausible-looking
   authoritative state that reports the wrong thing to anyone who finds it — the same trap
   this repo has already been caught by once with a stale theme-state file.
</waybar_coexistence>
