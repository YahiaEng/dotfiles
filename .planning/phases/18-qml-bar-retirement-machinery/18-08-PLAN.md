<objective>
Fill the two readout capsules 18-05 pre-declared — `[system]` (cpu / ram / disk / updates) and
`[media + connectivity]` (media / audio / network / bluetooth / battery) — against the backends
that already exist, and repoint `MediaBackend.qml` off its shell-script poll loop onto the
native MPRIS singleton. Then write down, per backend and with real numbers, what 18-05's three
widened gates now cost every second of every session.

Purpose: QBAR-06 is the requirement that makes the bar worth having. Everything before it is
structure — a window that reserves space, a chrome that draws pills, an entry list that
survives an orientation flip. This is the plan where the bar starts telling the user something.
Four things land together because they are the same thing seen from four sides:

1. **The `[system]` capsule.** cpu, ram and disk come straight off the one `SystemResources`
   instance the shell already mounts, through the handle `BarCapsule` already carries. Updates
   is the one member with no existing backend, and it is built here as a deliberately
   long-interval local reader rather than inherited at the retired bar's 15-second cadence.
2. **The `[media + connectivity]` capsule.** audio, network and bluetooth come off the three
   panel backends; battery comes off native `UPower` and renders nothing on this host; media
   comes off the backend task 3 repoints. This capsule carries the only unbounded string on the
   entire bar surface, and it is the only place in this phase where third-party D-Bus text
   reaches a rendered element before the tray lands in 18-10.
3. **The `MediaBackend` repoint (D-18-05).** This is a behaviour change, not a refactor. It
   trades a 1 Hz shell reader forking roughly ten processes a second for reactive signals from a
   singleton already inside the running binary. What changes observably is stated and verified
   in task 3 rather than left for someone to notice.
4. **The liveness charge.** 18-05 widened three gates so this capsule has live data. That made
   three backends permanently on for the first time in this repo's history, on the first surface
   that has no dismissed state to fall back to. This plan measures that, names it per backend,
   and hands 18-18 a brief specific enough to diff against.

Output: two filled capsule components, one repointed backend, one appended `Design` token, and
one measurement artifact.

Also not this plan's: any edit to `Bar.qml`, `modules/bar/qmldir`, `BarEntryModel.qml` or
`shell.qml`. All four are frozen for wave 3 by 18-05. This plan needs none of them, which is the
freeze working as designed.

## One shared-file overlap this plan takes deliberately, flagged rather than hidden

18-05's freeze covers `Bar.qml`, `modules/bar/qmldir`, `BarEntryModel.qml` and `shell.qml`. This
plan touches none of them — the pre-declared slot contract holds exactly as designed, and the
four backend handles `BarCapsule` carries are sufficient for both capsules.

It does, however, touch **`modules/dashboard/Design.qml`**, for a single append:
`mediaTitleMaxChars` (30). 18-05 Task 1 set the standing rule for this phase explicitly — "each
plan appends the tokens it actually reads" — and named `mediaTitleMaxChars` as belonging to the
later plan that consumes it. That is this plan.

**The overlap:** 18-10 will need `trayMaxExtent` and 18-11 may need others, by the same rule.
Three wave-3 plans appending to one file is a `files_modified` collision the wave-2 freeze did
not cover, because `Design.qml` is a wave-2 file that stayed open on purpose.

**This is low-risk but it is not zero-risk, and it is the orchestrator's call, not the
executor's.** The appends land in different regions of a file whose every entry is an
independent one-line `readonly property`, so a textual conflict is unlikely and a semantic
conflict is impossible. If the orchestrator prefers zero overlap, the clean resolution is to
move all remaining UI-SPEC token appends into 18-05 as a scope correction; the alternative is to
serialise the `Design.qml`-touching wave-3 plans. Either is fine. What is not fine is
discovering the overlap during a merge, which is why it is written here.
</wave_conflict_notice>
