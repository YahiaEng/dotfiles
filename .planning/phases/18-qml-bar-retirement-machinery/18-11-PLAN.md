## Scope correction required — raised, not taken

**What this plan found.** D-18-11 requires that in vertical orientation the drawers expand
**inward, horizontally** — "a floating strip growing leftward over the desktop." Neither drawer
can deliver that from a capsule file, because 18-05's `Bar.qml` pins the vertical window's
extent to `Design.barColumnWidth` (44) and a wlr-layer-shell surface does not render outside its
own buffer. An expanded 8-cell strip needs roughly 260px on that axis. The three ways out all
touch a file 18-05 froze for wave 3, so this plan **does not take the edit** and raises it
instead, per the wave-3 file freeze.

This is not a capability reduction and must not be recorded as one. The direction is implemented,
`expandedCrossExtent` is published by both capsules, and whichever option below is chosen
consumes a contract that already exists in the shipped files.

**Option A — widen the bar window in vertical (`Bar.qml` only).** Make the vertical
`implicitWidth` `Math.max(Design.barColumnWidth, <the largest published expandedCrossExtent>)`,
re-anchor the three zone containers to the parent's right edge in vertical instead of centring
them on the cross axis (otherwise the un-expanded capsules re-centre and the whole column
visibly jumps left when a drawer opens), and add an input mask so the widened transparent region
does not swallow clicks over the desktop. `exclusiveZone` stays the existing fixed expression, so
QBAR-12's byte-identical reservation is unaffected. Cost: three related changes to the single
most load-bearing file in the phase, and a new input-mask concern with no precedent in this repo.

**Option B — one new registered type, `modules/bar/BarDrawer.qml` (recommended).** A
`LazyLoader`-gated anchored strip surface, created and destroyed with the expanded state so it
costs nothing while collapsed — the same shape D-18-24 already blesses for the hot zone. One new
line in `modules/bar/qmldir`, one new file, no change to `Bar.qml`, no change to the reservation,
no input-mask problem, and both drawers stop duplicating the strip shape across two files.
`18-UI-SPEC.md`'s own popout anchoring rule already ties the vertical direction to D-18-11's
drawer direction, so this type and 18-13's `SectionPopout.qml` would share one anchoring rule
rather than growing two. Cost: a third bespoke frame in a repo whose panel family forbids them —
which means 18-17's GATE-03 namespace checks must cover it, exactly as they already must cover
`SectionPopout.qml` and `HotZone.qml`.

**Recommendation: Option B**, taken as an 18-05 scope correction that registers `BarDrawer` in
the frozen manifest and hands both drawer capsules a shared host. Option A concentrates risk in
the one file every later plan depends on, and its input-mask term is genuinely novel here.

**If neither is taken before 18-19:** the horizontal drawers ship complete and GATE-02 A.5
passes; the vertical drawers expand along the column instead of leftward, which contradicts
D-18-11's stated reason for choosing leftward, and 18-19's blocking pass must record that
explicitly rather than waving it through. Do not let that become the silent default.
</scope_correction_required>
