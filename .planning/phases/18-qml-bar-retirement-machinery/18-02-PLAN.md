<objective>
Read every behaviour of the live waybar off the implementation while it still exists, and
write it down as acceptance criteria a human can execute against the replacement — plus the
standing discipline that makes this a mandatory opening task for the three retirement phases
that follow.

Purpose: this is the phase's one irreversible read. `18-20` (RETIRE-02) deletes
`config-athena.jsonc`, `config-full.jsonc`, `config-floating.jsonc`, `config-vertical.jsonc`,
`modules.jsonc`, `bar-common.jsonc` **and** `waybar-equivalence-check` — the only tool in this
repo that resolves waybar's `include` chain correctly — eight waves from now, in a single
commit. After that commit there is no way to discover a behaviour that was not written down
here. Everything else in this phase can be redone; this cannot.

Three things follow from that, and they shape the whole plan:

1. **The derivation must be mechanical.** waybar 0.15.0's `include` is first-defined-wins,
   whole-key, depth-first. A layout can silently override one nested key of a `modules.jsonc`
   default without restating the object, and hand-reading the `.jsonc` files will miss it.
   `waybar-equivalence-check --resolve` already implements that algorithm and is verified
   working today. Use it, and commit its output so the derivation survives the deletion.
2. **The output must be checkable, not descriptive.** This document is graded by 18-19's
   GATE-02 criterion-B pass, run live with the new bar on screen. A row that records a config
   key is unusable there. A row that says what a user does and what they then see is the
   deliverable.
3. **It must be complete by construction, not by effort.** Completeness is asserted as an
   empty unaccounted-key set across all four resolved layouts — not as a claim that the
   enumeration felt thorough.

Output: `18-BEHAVIOUR-BASELINE.md`, four committed resolved-config snapshots, and one Notes
bullet on each of Phases 19, 20 and 21 in `ROADMAP.md`.

Explicitly NOT in this plan (each owned by a named later plan, listed so the executor does not
build ahead): judging the new bar against these criteria (18-19, GATE-02's blocking pass —
this plan writes the ruler, it does not measure with it); deleting anything (18-20); the
generic `retirement-check` script (18-06); any QML, any `Design.qml` token, any doctor check.
This plan writes documentation and edits `ROADMAP.md`. It touches no code and no waybar file.
</objective>

`## Criterion Grammar` — the rules every row in this document obeys, written so a second author
would produce the same rows:
- ID namespace `WB-<LAYOUT>-<NN>` with LAYOUT one of ATH, FULL, FLOAT, VERT, or ALL for a row
  shared by every layout that references the module. IDs are stable and cited by 18-19 and
  18-20, so a row is never renumbered once written — a superseded row is struck with its ID
  retained.
- Row shape: a table with columns ID, Zone·Index, Module, Checkable criterion, Layouts,
  GATE-02 B. The criterion column is a gesture-and-observation sentence — what a human does and
  what they then observe. A restatement of a config key is not a criterion. Where a behaviour
  has no gesture (a polling interval, a tooltip format), express it as a timing or hover
  observation the human can still take.
- The merge rule: two layouts collapse into one row if and only if their entries for that module
  are byte-identical across the resolved snapshots, compared with `jq -S`. Any difference in any
  resolved key yields separate rows, and the separated rows' text names the differing key.
  Comparison is always against the resolved snapshots, never the raw `.jsonc`, because
  first-defined-wins `include` lets a layout override one nested key without restating the
  object.
- The ordering rule: layout in the fixed sequence athena, full, floating, vertical, shared; then
  zone in the fixed sequence left, center, right; then the entry's index in that zone array as
  it appears in the resolved snapshot; then the group's own `modules` array index for entries
  inside a group. Every tiebreak resolves to a source-declared index, so the row order is
  reproducible.
- The dead-definition rule: a module present in a layout's resolved snapshot but referenced by
  zero zone arrays and zero group `modules` arrays never enters a criteria table — it goes to
  `## Dead Definitions`. A module referenced by a zone but absent from the resolved snapshot is
  a hard stop: it means the resolution is wrong and every derived criterion is untrustworthy.
- The absence rule: an empty zone array is written down as a stated absence for that layout, not
  left out; a group with a single member still earns a criterion, because a one-member drawer
  still has a transition duration and a direction.
