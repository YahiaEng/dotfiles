Create `hypr/.config/hypr/scripts/cheat-sheet-parser.sh` (executable bit set in git). It is a LIBRARY, sourced by both surfaces — it exposes a function (e.g. `cheat_sheet_parse_binds`) and does nothing when sourced.

The function parses `~/.config/hypr/config/keybinds.conf` on every call (D-31 — live, never cached) and emits structured records the callers can format. For each bind line, extract:
  - the bind TYPE (`bind` / `binde` / `bindl` / `bindel` / `bindm` / `bindr`)
  - the MODMASK and KEY, resolving `$mainMod` to its literal value (`SUPER`) by reading the `$mainMod = …` line from the file itself rather than hardcoding it — the same discipline `keybind-doctor` uses
  - the trailing `# description` text
  - the enclosing `# ── Section ──` banner (the section the bind falls under)

After 07-02's backfill this should not occur, but the parser must not depend on that; a bind added later by a future phase might arrive without one, and the cheat-sheet should degrade, not break.

**SECURITY — this is the load-bearing constraint of this plan.** The parser reads a config file. It must treat every parsed field as display-only text:
  - NEVER `eval` a parsed line.
  - NEVER `source` `keybinds.conf` (it is not a shell script, and sourcing it to "resolve the variables" would execute arbitrary content — resolve `$mainMod` by string substitution, not by shell evaluation).
  - NEVER use command substitution or unquoted expansion on parsed content.
  - Emit every field with `printf '%s'`, quoted.
This is the V5 / ASVS L1 input-validation control RESEARCH.md's Security Domain names, and it is the same discipline `theme-doctor` already follows (it only ever reads and reports, never executes parsed config content).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `keybinds.conf` (config file content) → `cheat-sheet-parser.sh` | **This is the phase's primary input-validation surface.** A shell script parses a config file's content on every open. If it executed rather than displayed that content, any line in `keybinds.conf` — including one introduced by a bad merge, a compromised dotfiles sync, or a careless copy-paste — would achieve arbitrary code execution as the user. |
| parsed bind data → two rendering surfaces | Both surfaces render text derived from the config file. Neither may execute it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-03 | Elevation of Privilege | `cheat-sheet-parser.sh` parsing `keybinds.conf` | high | mitigate | Display-only discipline, enforced three ways: (a) grep-asserted absence of `eval`, `source` of the config, and command substitution on parsed content; (b) `$mainMod` resolved by STRING SUBSTITUTION, never by sourcing the file — sourcing it "to resolve the variables" is the obvious wrong turn and is explicitly forbidden; (c) a behavioural test that feeds the parser a hostile line with an embedded command-substitution payload and asserts the payload is displayed as literal text and its sentinel file is NOT created. This is the V5 / ASVS L1 control RESEARCH.md's Security Domain names. |
| T-07-26 | Elevation of Privilege | the walker surface executing a selected bind's dispatcher | medium | mitigate | The cheat-sheet is a REFERENCE, not a launcher. Selecting a row does not execute the bind's dispatcher — asserted by an acceptance criterion. Executing a dispatcher string parsed out of a config file would reintroduce T-07-03 through the back door. |
| T-07-27 | Tampering | the two surfaces silently diverging | low | mitigate | One shared parser, sourced by both, asserted by grep (neither surface may contain its own extraction regex) AND by measurement (both surfaces must report an identical row count). D-29 mandates the shared parser for exactly this reason. |
| T-07-28 | Information Disclosure | the cheat-sheet displaying the contents of keybind commands | low | accept | The cheat-sheet renders the DESCRIPTION comments, not the dispatcher command strings, so it does not surface anything the user did not write as user-facing copy. And `keybinds.conf` is the user's own version-controlled file on a single-user desktop — it contains no secrets. |
</threat_model>
