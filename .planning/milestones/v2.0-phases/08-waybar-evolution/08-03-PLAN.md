<objective>
Deliver the two halves of BAR-01 that are pure waybar-side work: the D-06 OLED luminance trim, and the D-03 single visibility owner with its D-04 trigger-dependent exclusive-zone behaviour. Plan 08-04 then wires the four actors (idle, fullscreen, gaming, keybind) into this owner.

Purpose: today four actors want to move the bar and they all send `SIGUSR1`, whose default action is **toggle**. A toggle shared by four senders desyncs the moment two of them disagree — idle hides the bar, gaming-mode toggles it, the bar comes back mid-game. That is the exact bug class this repo has already deleted twice. D-03 kills it structurally: waybar's `on-sigusr1` is reconfigured to a *fixed* `hide` action, and one owner script computes the resulting state from declared intents.

Output: a trimmed, translucent bar; `waybar-visibility.sh`; the signal-action config; and the reload-fan-out integration that keeps the two signal owners from fighting.
</objective>

**B — write `hypr/.config/hypr/scripts/waybar-visibility.sh`.** This is the sole owner of waybar's visibility. Follow `gaming-mode-toggle.sh`'s house conventions exactly: `#!/usr/bin/env bash`, boxed header comment stating the hard constraint, `set -euo pipefail`, tunable constants at the top, atomic tmp+mv state writes, `2>/dev/null || true` on every external call. **It is silent — no `notify-send` anywhere** (UI-SPEC: the bar appearing/disappearing IS the feedback).

Tunable constants at the top of the file (Claude's discretion per D-05 / the CONTEXT discretion list): the idle-dim opacity value (`0.05` per UI-SPEC) as a named constant. The idle *timeout* itself is a hypridle concern and lives in `hypridle.conf` (plan 08-04) — do not duplicate it here.

CLI contract (four verbs):
  - `waybar-visibility.sh <source> <hide|show>` — a source declares its intent. `<source>` is validated against a strict allowlist: `idle`, `fullscreen`, `gaming`. Any other value exits nonzero with an error on stderr. **This validation is load-bearing security, not hygiene** — `<source>` becomes part of a filename under `~/.cache/waybar-visibility.d/`, so an unvalidated `../../…` would write outside the intent directory.
  - `waybar-visibility.sh keybind toggle` — the explicit bar-toggle bind (D-02). See the override model below.
  - `waybar-visibility.sh reassert` — recompute from the existing intent files and re-signal waybar, changing no source's declared intent. Idempotent. This is what `reload.sh` calls after a theme reload.
  - `waybar-visibility.sh status` — print the computed state (`visible` / `hidden-idle` / `hidden-hard`) and exit 0. Mirrors `gaming-mode-toggle.sh`'s `status` arg contract.

State model:
  - Per-source intent files: `~/.cache/waybar-visibility.d/<source>` containing `hide` or `show`. One file per source, each written with the atomic tmp+mv idiom copied from `gaming-mode-toggle.sh` — the sources write concurrently (a fullscreen event and an idle timeout can land in the same instant), so a torn read is a real possibility, not a theoretical one.
  - A missing intent file means `show` (the default, safe state — a bar you can see).
  - Keybind override file: `~/.cache/waybar-visibility.d/.override` containing `show` or `hide`, plus the base-union value that was in effect when the override was set.

Computation (D-01 + D-02):
  1. `base_union` = `hide` if ANY of {idle, fullscreen, gaming} declared `hide`, else `show`. This is D-01's "hides on either trigger; returns when both clear," generalised to three sources.
  2. If an override exists AND the base_union has NOT changed since the override was set → the override wins. If the base_union HAS changed, the override is stale and is cleared. This gives exactly D-02's behaviour: a fullscreen-hidden bar stays hidden until you press the keybind (base stays `hide`, override forces `show`); when you leave fullscreen the base flips, the override auto-clears, and normal behaviour resumes. An override must never outlive the condition it was overriding.
  3. `keybind toggle` sets the override to the opposite of the currently computed state, recording the base_union at that moment.

Actuation (D-04 — this is the trigger-dependent half, and it is the reason the owner tracks *why* it is hiding, not just *whether*):
  - **Computed `visible`** → truncate `~/.local/state/theme/waybar-visibility.css` to empty, then `pkill -SIGUSR2 waybar` (the `reload` action, which both re-reads the now-empty CSS and — per `waybar(5)` — resets the bar to its config-time visibility, i.e. mapped). One signal does both jobs.
  - **Computed `hidden` and the ONLY hiding source is `idle`** → write the dim rule into `waybar-visibility.css` (an unqualified `window#waybar` opacity rule — see Task 1's UI-SPEC deviation note), then `pkill -SIGUSR2 waybar`. **The surface stays mapped, so the exclusive zone is KEPT** — no tiled window reflows every couple of minutes during normal work. This is D-04's idle case and it is the whole reason idle-hide is not a real hide.
  - **Computed `hidden` and `fullscreen` or `gaming` is among the hiding sources** → truncate the CSS to empty (so a later reveal isn't also dimmed), then `pkill -SIGUSR1 waybar` (the fixed `hide` action → true unmap → **exclusive zone DROPPED**). This is D-04's "you genuinely want the pixels" case.
  - Only signal when the computed actuation differs from the last actuated state (track it in `~/.cache/waybar-visibility.d/.actuated`). Redundant signals are harmless but noisy, and the fullscreen event stream is documented as firing multiple times per transition.

**⚠ RESEARCH Open Question 1 — verify before trusting the split.** The claim "SIGUSR1-hide drops the exclusive zone" is derived from sway-bar's documented mode semantics, which `waybar(5)` says it mirrors — but it was NOT confirmed by a live test. Verify it now, empirically, before building anything on top of it: open a tiled window, record `hyprctl clients -j | jq '.[0].at, .[0].size'`, send `pkill -SIGUSR1 waybar`, record again. If the window reflowed, the zone was dropped (the assumption holds). Then repeat with the CSS-dim path and confirm the window does NOT reflow. Record both results in the SUMMARY. **If SIGUSR1-hide turns out to KEEP the zone**, the D-04 split is unachievable via this mechanism and you must stop and report rather than inventing a second hide mechanism.

**D-07 (animation): the answer is instant, and it is already decided.** RESEARCH Verdict 1 proves against the installed `waybar.5.gz` that no transition/animation/easing option exists anywhere in the bar config schema, that `show`/`hide` are binary map/unmap operations on a layer-shell surface with no animatable intermediate, and that CSS `margin` on `window#waybar` does not reposition the real surface (Alexays/Waybar#1533). **Do NOT build a bespoke animation harness** — no custom GTK widget, no frame-timer loop, no fake-surface interpolation (D-07 forbids this by name, and it is Pitfall 3). You MAY, at zero cost, add a `transition: opacity 0.3s ease;` rule to `window#waybar` and note in the SUMMARY whether the idle-dim path visibly animated — the CSS-dim path keeps the widget mapped, so GTK *might* animate it. Either answer is acceptable; instant is the committed behaviour regardless. Do not make this an acceptance criterion.

**D-08:** there is no overlay actor. Walker, the swaync panel, and pickers never call this script, in either direction. Do not add a fifth source.

**C — integrate with the theme reload fan-out.** `theme-engine/lib/reload.sh` opens by claiming exclusive ownership of `pkill -SIGUSR*` repo-wide, and it sends `pkill -SIGUSR2 waybar` on every theme switch. With `on-sigusr2` configured as `reload`, that signal now also **resets the bar to visible** — meaning a theme switch would resurrect a bar the owner had hidden, and the owner's `.actuated` state would silently desync.

Fix both halves:
  - Amend `reload.sh`'s header comment so its ownership claim is scoped truthfully: it owns the **theme-reload fan-out**; `waybar-visibility.sh` owns the **visibility signals**. Two owners, two disjoint concerns, both idempotent. (This is a comment/doc correction — the alternative reading, that no other file may ever signal waybar, is already false today: `gaming-mode-toggle.sh` has been sending `pkill -SIGUSR1 waybar` since Phase 7.)
  - Immediately after `reload.sh`'s `pkill -SIGUSR2 waybar` line, add a best-effort call to `~/.config/hypr/scripts/waybar-visibility.sh reassert` (guarded `2>/dev/null || true`, per the house idiom, and placed inside the existing no-graphical-session early-return so it cannot run headless). This re-applies the owner's computed state after the reload has reset it.
  </action>
