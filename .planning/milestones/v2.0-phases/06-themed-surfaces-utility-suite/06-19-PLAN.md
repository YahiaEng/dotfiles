<objective>
Add a real GTK CSS-parse regression guard to `theme-doctor`.

**Why this exists.** The WLOG-01 blocker (plan 06-16) survived **four** verification rounds because every round only grep-checked that the `@import` line was textually present. A stylesheet that GTK discards **in its entirety** still passes a grep. Nothing in this repo has ever run a stylesheet through an actual CSS parser. That is the hole this plan closes — permanently, in the project's own rerunnable health check.

**The load-bearing signal is an empty provider, not a parse error.** Empirically confirmed on this machine (GTK 3.24.52): a single invalid pseudo-class makes `Gtk.CssProvider.to_string()` return **0 bytes** — the whole sheet is thrown away. A parse-error-only check is strictly weaker and can miss this. The guard must assert **parses AND yields a non-empty provider**.

Purpose: make the failure mode that produced this blocker permanently detectable by a rerunnable check.
Output: a `theme-doctor` that would have caught CR-01 on day one, proven by a synthetic regression.
</objective>

<prerequisite_findings>
Established empirically by the orchestrator on this machine. Do not re-derive them; do re-verify if a check behaves unexpectedly.

1. **`python-gobject` 3.56.3-1 is already installed AND already listed in `install.sh` PACMAN_PKGS (line ~135).** No new dependency is needed. Task 2 asserts this rather than assuming it.
2. **`Gtk.CssProvider` works fully headless.** Verified by running the probe with `WAYLAND_DISPLAY`, `DISPLAY` and `XDG_SESSION_TYPE` unset — the provider loaded to 15347 bytes. Do **not** call `Gtk.init()`; `CssProvider` needs no display, and calling `init()` would break the container gate.
3. **The guard must parse DEPLOYED paths (`$HOME/.config/...`), never the repo copies.** The stow files import the palette by relative path (`../../.local/state/theme/<name>.css`), which only resolves from the deployed location. Parsing the repo copy produces a spurious `Failed to import` error and an empty provider — a false failure.
4. **GTK3 and GTK4 cannot be loaded in the same Python process** (`gi.require_version` conflict). The guard needs **two** separate `python3` invocations: one for the GTK3 surfaces, one for the GTK4 surfaces.
5. **Fatal vs. non-fatal is distinguishable by GError code.** On GTK3, a real syntax error is domain `gtk-css-provider-error-quark` **code 1** and empties the provider; a deprecation is the same domain **code 4** and the provider is retained. `waybar/style-floating.css` emits exactly one code-4 deprecation today (IN-02, the unitless `border-radius: 10` — an Info item explicitly **deferred**, out of scope). The guard must therefore **not** fail on code 4, or it would false-fail on a sheet that is fine.
6. **Current live state of the surfaces** (post-06-16 for wlogout): all GTK3 and GTK4 sheets parse to non-empty providers with zero fatal errors, EXCEPT `~/.config/swayosd/style.css`, which **does not exist** on this machine — the `swayosd` stow package is listed in `stow.sh` PACKAGES but has not been re-stowed here. That is host drift, not a code defect (a fresh `install.sh` + `stow.sh` run creates it), so the guard must **SKIP** an absent deployed sheet with a clear message, not FAIL.
</prerequisite_findings>

**What the guard asserts, per stylesheet.** A sheet PASSES only if all three hold:
  1. `Gtk.CssProvider().load_from_path(path)` raises no exception;
  2. it emits no **fatal** `parsing-error` — where fatal means any error that is NOT a deprecation (GTK3: domain `gtk-css-provider-error-quark` code `4`; GTK4: domain `gtk-css-parser-warning-quark`, any code). A deprecation is reported as a note but does not fail;
  3. `provider.to_string()` is **non-empty**. This is the load-bearing assertion — an empty provider is the exact signature of a stylesheet GTK discarded in full, and it is the signal a parse-error-only check would miss. Do not drop it in favour of "no errors".

**Which stylesheets.** Use the DEPLOYED paths under `$HOME/.config`, never the repo copies (prerequisite finding 3).

GTK **3** surfaces:
  - `$HOME/.config/wlogout/style.css`
  - `$HOME/.config/waybar/style-full.css`
  - `$HOME/.config/waybar/style-minimal.css`
  - `$HOME/.config/waybar/style-floating.css`
  - `$HOME/.config/gtk-3.0/gtk.css`
  - `$HOME/.config/swaync/style.css`

GTK **4** surfaces:
  - `$HOME/.config/gtk-4.0/gtk.css`
  - `$HOME/.config/swayosd/style.css`   (swayosd 0.3.1 links libgtk-4 — use the GTK4 binding for it, not GTK3)
  - `$HOME/.config/walker/themes/rice/style.css`

**Structure.** Two separate `python3` invocations are required — GTK3 and GTK4 cannot coexist in one process (prerequisite finding 4). Write one small parametrised probe taking the GTK major version as its first argument and the stylesheet paths as the remaining argv, then call it twice. Pass paths as **argv**, never by interpolating them into a shell-quoted Python string — the paths are constants here, but argv-passing is the correct habit and removes the injection surface entirely.

Have the probe print one machine-readable line per sheet that bash can turn into a `check` call — a status token (`PASS` / `FAIL` / `SKIP`), the sheet's identifying path fragment, and a short reason (provider byte count on pass; the fatal error message, or a "provider is EMPTY — stylesheet discarded" note, on fail). Then loop over the probe's output in bash and call `check "<desc>" "0"` or `check "<desc>" "1"` accordingly. Do **not** call `Gtk.init()`.

**Graceful degradation — three distinct cases, do not conflate them:**
  - The GTK binding is genuinely unavailable (`python3 -c "import gi"` fails): print a single `[SKIP]` line explaining the CSS-parse guard needs `python-gobject`, and do not touch the PASS/FAIL tally. Match the voice of the existing `[SKIP]` lines.
  - A deployed stylesheet does not exist: `[SKIP]` that sheet with a message naming the path and pointing at `stow.sh` (this is the live state of `swayosd/style.css` today — prerequisite finding 6). Absent is not the same as broken.
  - A sheet parses but emits only deprecations: **PASS**, with the deprecation surfaced in the description so it stays visible without failing the run (`style-floating.css` is in exactly this state today; IN-02, deferred).

Suppress GTK's own noisy `Gtk-WARNING` chatter on stderr so the doctor's output stays readable — the probe's structured lines are the signal.

Do not touch the stale "ten per-file checks" header comment at lines 48-49 (IN-03) — a deferred Info item, not this plan's job.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stylesheet file paths -> `python3` probe | The guard passes filesystem paths into a Python interpreter invoked from bash. Paths are engine-owned constants, but the shell/Python boundary is where a quoting mistake would become code execution. |
| `~/.local/state/theme/*.css` -> `@import` -> GTK parser | Machine-rendered palette files consumed transitively by the parsed stylesheets. Rendered by the trusted matugen pipeline, not user input. |
| synthetic-regression temp file (Task 3) | A deliberately malformed stylesheet written into `~/.config/waybar/` — must not survive the test or it would poison the real surface. |
