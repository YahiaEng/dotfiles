# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Domain note:** This is not a web/component-library UI. The visual surface for this phase is (a) a **terminal UI** — the fzf-in-floating-kitty wallpaper picker (`hypr/.config/hypr/scripts/wallpaper-picker.sh`) — and (b) a **dynamic multi-theme color contract** — the 20-key matugen palette schema rendered across GTK3/GTK4/waybar/kitty/etc. under both light and dark mode. The template below is adapted accordingly: sections that don't apply to a terminal/bash pipeline (shadcn, px-based typography scale) are marked N/A with the reasoning, and the Color section carries the real weight of this contract — it is a per-active-theme dynamic mapping, not a fixed brand palette.

Not applicable in the CSS/px sense — this is a terminal-cell UI with no box model. The terminal-equivalent layout contract (fzf's own spacing primitives) carries over **unchanged** from the current picker; the redesign (D-13/D-14) only replaces the preview renderer and adds restriction logic, not the outer layout:

| fzf Layout Param | Value | Usage |

## Typography

Not applicable — fixed single monospace nerd font already set project-wide (`FiraCode Nerd Font 11`, `gtk-3.0/settings.ini` + kitty's own config), terminal-cell UI has no independent type scale (no separate body/label/heading/display sizes — everything renders at the terminal's one configured cell size). ## Color

This phase's real design contract. Two independent things must be declared: (1) the **20-key palette schema** every new preset JSON must follow, and (2) the **light/dark mode-flip contract** for GTK signals, plus (3) the **picker's own color sourcing** from the active palette (D-15).

### 1. Palette schema (source of truth for all 15 new/existing presets)

Every preset JSON (`theme-engine/.config/theme-engine/palettes/*.json`) declares these 20 keys, verified against the existing `rosepine.json`. New presets (9 dark Omarchy-lineup + 5 canonical-light siblings) MUST reuse this exact key set — no new keys, no omitted keys:

`primary, on_primary, primary_container, on_primary_container, secondary, on_secondary, secondary_container, on_secondary_container, tertiary, on_tertiary, tertiary_container, surface, on_surface, surface_variant, on_surface_variant, background, on_background, outline, error, on_error`

Optional 21st key per D-06: `"mode": "light"|"dark"` at the JSON's top level — override wins over computed lightness when present.

**Role-mapping method (Pattern 5, locked):** for each of the 5 canonical-light siblings (catppuccin-latte, rosepine-dawn, gruvbox-light, tokyonight-day, kanagawa-lotus), copy the existing dark JSON's exact key→upstream-color-name mapping and substitute the light variant's own upstream hex — never re-derive role assignment from scratch, never invent a new mapping for the light sibling.

### 2. Mode-flip contract (D-07 — colors + GTK signals only)

| Element | Dark mode | Light mode | Owner |
|---------|-----------|------------|-------|
| `gsettings … color-scheme` | `prefer-dark` | `prefer-light` | `gtk.sh` (existing single-owner gsettings function — extend, don't duplicate) |
| GTK3 theme name (`settings.ini` `gtk-theme-name`) | `adw-gtk3-dark` | `adw-gtk3` | rendered contract target (D-08), written by the same code path that owns the gsettings call — no second hardcode site |
| GTK4 accent mapping | existing hue-based `colorsys` function in `gtk.sh` | same function, unchanged — it derives from hue, not mode, so it already works correctly for light palettes with no new logic | `gtk.sh` (unchanged mechanism) |
| Icon theme | untouched | untouched | out of scope (Phase 6 UTIL-04) |
| Cursor theme | untouched | untouched | out of scope |
| `gtk-font-name` | untouched | untouched | out of scope |

**Mode-detection contract (locks Claude's Discretion from CONTEXT.md/RESEARCH.md):**
1. Read `"mode"` key from the palette JSON — if `"light"` or `"dark"`, use it, done (D-06 override).
2. Else compute `colorsys.rgb_to_hls(background_hex)[1]` (lightness channel) on the palette's `background` key — reuse the existing `colorsys` technique already proven in `lib/gtk.sh`'s accent function, don't add a new color-math dependency.
3. Threshold: `lightness > 0.5` → light, else dark.
4. Validate this threshold classifies **every shipped palette correctly** (all 6 existing + 9 new dark + 5 new light) before locking — if any palette misclassifies, either fix its `background` value's role or add an explicit `"mode"` override key to that one JSON rather than moving the global threshold.

`materialyou`/`materialyou-light` are the one exception: mode is **explicit user choice** via the preset name (D-05), not computed — `generate.sh` passes `-m dark`/`-m light` to `matugen image` directly for these two entries only (verified: `-m` is a no-op for static-preset JSON rendering, see RESEARCH.md Pitfall 1 — never wire `-m` into the static-preset branch).

### 3. Picker color-slot contract (D-15 — replaces every hardcoded catppuccin hex in `wallpaper-picker.sh`)

60/30/10-style split, translated to fzf's own color roles:

| Role | Palette key | fzf slot(s) | Usage |
|------|-------------|-------------|-------|
| Dominant (60%) | `background` / `on_background` | `bg:-1` (terminal true bg, kept transparent), `fg` | Unselected list rows, base picker surface |
| Secondary (30%) | `surface_variant` / `on_surface_variant` | `bg+`, `header` | Selected-row background, header text |
| Accent (10%) | `tertiary` | `hl`, `hl+`, `pointer`, `marker`, `spinner` | **Reserved for:** fuzzy-match highlighted characters, the `▶` pointer glyph, the `●` marker glyph, the busy spinner. Never applied to plain list text, borders, or the header body. |
| — | `primary` | `prompt` | The `  ` prompt glyph only |
| — | `secondary` | `info` | The match-count info line only |
| — | `outline` | `border` | Frame border only |

Sourced at runtime via a new small render target: `~/.local/state/theme/fzf-colors.conf` (shell-exportable `KEY=value`, rendered by a new matugen template, added to `contract.json`) and `source`d by `wallpaper-picker.sh` with the **current catppuccin-mocha hex values kept as inline fallback defaults** (graceful degradation on fresh install before first `theme-apply`, matching this codebase's existing pattern). No literal catppuccin hex may remain as the *only* source — it may only appear as a `${VAR:-fallback}` default.

Destructive color: not applicable — the wallpaper picker has no destructive action this phase (see Copywriting below).

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `Enter` → **Apply wallpaper** (sets `current.jpg` symlink; re-runs `theme-apply` if Material You is active) |
| Cancel | `Esc` / `q` → **Cancel** (restores the wallpaper that was active before the picker opened) |
| Picker header — full/unrestricted mode (Material You, or Ctrl-A browse-all) | ` 🖼  Wallpaper Picker  │  ↑↓ browse  │  Enter confirm  │  Esc cancel` (unchanged from current script) |
| Picker header — restricted mode (static theme active, D-16) | ` 🖼  {ThemeName} Wallpapers  │  Ctrl-A browse all  │  ↑↓ browse  │  Enter confirm  │  Esc cancel` — `{ThemeName}` is the human-readable preset name (title-case the palette filename, e.g. `rosepine` → `Rosé Pine`, `tokyonight` → `Tokyo Night`) |
| Picker header — fall-open state (D-12: theme folder empty/missing) | ` 🖼  {ThemeName} Wallpapers (none yet — showing full library)  │  ↑↓ browse  │  Enter confirm  │  Esc cancel` — makes the fallback visible instead of silently showing unrelated wallpapers with no explanation |
| Empty state (truly zero wallpapers anywhere, incl. shared pool) | Heading: `No wallpapers found in ~/Pictures/Wallpapers` / Body: `Add images and try again.` (unchanged from current script — still the correct terminal message for this one genuinely-empty case) |
| Error state | Render/apply failures reuse the existing sanitized truncation pattern already in `theme-apply` (`head -c 200 \| tr -d ...` before reaching `notify-send`) — no new unsanitized error surface is introduced by the picker rewrite or the new render targets |
| Notification — wallpaper set (static theme) | `notify-send -a "Wallpaper Picker" "Wallpaper Changed" "Set to {filename}"` (unchanged) |
| Notification — wallpaper set (Material You / materialyou-light) | No separate wallpaper toast — theme-apply's own existing completion notification covers it (unchanged mechanism) |
| Destructive confirmation | **None** — this phase introduces no destructive actions (no delete/wipe UI in the picker or the theme pipeline). If a future phase adds wallpaper deletion, it inherits Phase 6's UTIL-03 clipboard wipe-policy pattern as precedent, not this phase's contract. |
