<objective>
Make dynamic cursors an optional dependency that can never fail an unattended install, and prove it by making the build fail on purpose.

This is **success criterion 2's deliverable**. Three provisioning gaps close in `install.sh` — `cmake` and `cpio`, which hyprpm's own binary demands and which this repo has never declared, plus `rose-pine-hyprcursor` for D-32's package half. Then the guarded hyprpm block lands, using the repo's *real* warn-and-continue precedent, paired with the post-login completion helper that actually finishes the build once a session exists. D-34's forced-failure injection proves the guard end to end.

Purpose: hyprpm is genuinely hostile to unattended install — confirmed live, not inferred. It needs sudo for its root-owned state store, then refuses every plugin operation until `hyprpm update` builds headers against the exact running Hyprland commit, which itself needs a full toolchain. `install.sh` frequently runs from a TTY with no compositor at all. That is precisely why D-33 splits the work in two: a guarded best-effort attempt at install time, and a helper that completes it after login. Neither half may ever abort, prompt, or hang.

Output: `cmake`, `cpio` and `rose-pine-hyprcursor` declared; a guarded hyprpm block whose failure path is exercised on every container-gate run; `hyprpm-complete.sh` with a real already-built/already-loaded detection ladder; a single wiring line that is not an `autostart.lua` entry; and recorded fault-injection evidence for both halves of criterion 2.

**Precedence note — RESEARCH.md corrects CONTEXT.md, and this is the correction that matters most here.** `17-CONTEXT.md`'s canonical_refs cites `install.sh` §~600-660 as carrying both "`verify_packages`' hard-fail design **and** the `|| echo "  ⚠ …"` warn-and-continue precedent D-33 follows," as though they were the same place. ## Assumption delta — the `optional` signal

The deterministic assumption-delta scan fired one signal of kind **`optional`** for this phase: *"Dynamic cursors install as an **optional** guarded dependency."* A dependency that was previously only ever required has become optional, so the identity question is: **is the field still the right anchor, or has the anchor moved?**

**The noun that is now primary: _dependency disposition_** — the property "what happens when this dependency cannot be installed." Today `install.sh` does not model that property at all. It models dependencies by *source bucket* (`PACMAN_PKGS`, `AUR_PKGS`, `NVIDIA_PKGS`, `FALLBACK_KERNEL_PKGS`), and disposition is an emergent consequence of the `VERIFY_PKGS` union at line 665 feeding `verify_packages()` — every declared package is hard-fail because every declared package ends up in that union. AMB-02 introduces a third disposition the model has no vocabulary for: *installed-if-possible, never fatal*.

**Decision: `add-alongside`.**

**Rationale (one line):** the single item carrying the new disposition is not a package at all — `hypr-dynamic-cursors` has no pacman or AUR entry (`paru -Si hypr-dynamic-cursors` and `paru -Si dynamic-cursors` both fail, verified in RESEARCH.md), it is a git repository built by hyprpm — so it could not live in either array under any disposition model, and promoting disposition to a first-class property would restructure a 700-line install script to describe exactly one member.

**Accepted debt, stated plainly.** The guarded block expresses warn-and-continue as inline control flow rather than as declared data. A second optional dependency would therefore be copy-paste, not an array entry, and `verify_packages()`'s `[OK]`/`[MISS]` table will stay silent about optional items — an operator reading the install summary sees no row at all for dynamic cursors, only a `⚠` line scrolled further up. This phase is the **designated first to cut** in v3.0, which is a genuine and sufficient argument for not paying a structural refactor cost on work that may be removed wholesale; that is the reason, and it is being recorded rather than assumed.

**What would force a later promote:** either (a) a **second** optional dependency arriving — especially an actual pacman/AUR package that must be installed-if-possible, since that one *would* fit an array and copy-pasting the guard instead would be indefensible; or (b) any requirement that the install summary report optional-dependency outcomes alongside the hard ones (a `[SOFT-MISS]` row beside `[OK]`/`[MISS]`). At either trigger, disposition must become data — a per-package disposition map or an `OPTIONAL_PKGS` array with its own soft verifier — rather than control flow.
</assumption_delta_decision>
