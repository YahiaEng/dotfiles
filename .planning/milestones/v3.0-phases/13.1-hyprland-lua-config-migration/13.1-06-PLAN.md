<objective>
Port the animation surface onto the generated token table, and extend `motion-lint` so the Lua
surface is policed by the same deny-by-default gate the CSS, QML and hyprlang surfaces already
have.

Purpose: `animations.conf` is where the load-order hazard D-13 exists to delete actually lives —
today an undefined `$motion_enabled` there is a hard parse error that stops the compositor from
starting, which is why `hyprland.conf` carries a comment demanding the motion fragment be sourced
first. Under Lua that whole class of failure disappears, and the animation surface becomes an
ordinary consumer of a data table. `motion-lint` is what keeps it that way: without a Lua-aware
path, a future phase could hand-roll a duration in a `.lua` file and no gate would notice.

Output: `config/animations.lua`, a Lua-aware `motion-lint`, and three new fixtures.
</objective>

Write `hypr/.config/hypr/config/animations.lua`.

Obtain tokens with `require("lib.tokens").get()`.

**The enabled flag.** `animations.conf` sets `enabled = $motion_enabled`, and at the `off`
motion-scale preset that resolves false — disabling animation at the toolkit level rather than
shrinking durations. Derive it with an **explicit nil test**, not a boolean-or: in Lua,
`tokens.motion.enabled or true` evaluates to `true` when the token is `false`, which would silently
resurrect animations for a user who turned them off. Read the value, and only when it is `nil`
substitute the default. This repo has already shipped one bug of exactly this shape — a `jq`
`// empty` idiom that treated JSON `false` as absent and broke the `off` preset — so treat it as a
known trap, not a hypothetical.

**Curve registration.** For every entry in `tokens.motion.curves`, call
`hl.curve("motion-" .. <key>, <spec>)`, where `<spec>` is the `{ type = "bezier", points = { … } }`
table straight from the token file. The `motion-` prefix reproduces the `bezier = motion-<key>`
names the hyprlang fragment emits today, which is what makes the existing curve-name references
keep resolving. Register curves before any animation references them.

**The 15 animation leaves.** One `hl.animation({ … })` per `animation =` line in
`animations.conf`, preserving leaf name, curve name and style argument exactly:
`windowsIn` / `windowsOut` (`popin 60%`), `windowsMove` (`slide`), `fadeIn`, `fadeOut`,
`fadeSwitch`, `fadeShadow`, `fadeDim`, `border`, `borderangle` (`loop`), `workspaces` (`slide`),
`specialWorkspace` (`slidevert`), `layers` / `layersIn` / `layersOut` (`popin 80%`). Speed comes
from `tokens.motion.speed.<name>` where `<name>` is the current `$motion_speed_<name>` variable
minus its prefix; curve comes from the `motion-<name>` string the corresponding line uses today.

**Missing-token behaviour.** When a leaf's speed token is `nil`, or when the curve it references
was not registered because the token table had no such curve, **skip that registration entirely**
rather than substituting a hardcoded number. Hyprland then applies its own built-in default, the
compositor still starts, and no second copy of a value `motion.json` owns is created. This is
deliberately different from the colour fallbacks in the entry point: a colour default is an inert
literal that duplicates nothing, whereas a duration literal here would be a second source of truth
for a number `motion.json` is supposed to own exclusively — and would be flagged by `motion-lint`'s
own raw-value check, correctly.

Carry across the substantive comments from `animations.conf` (the `enabled`-ownership rationale,
the 13-01/13-07 curve-provenance note), and add one short note recording that the hyprlang
load-order hazard is gone: under Lua nothing depends on another module having been loaded first,
because this module fetches tokens itself.

Verify against the committed baseline through the harness: capture
`hypr-lua-harness hyprctl -j animations` and compare it to `.hypr-baseline/animations.json`, leaf
by leaf, on name, enabled, speed, bezier and style.
