# Phase 13.1 Plan 04: Option Blocks + Full Keybind Port + Binds Equivalence Split Summary

**Ported the remaining `hl.config` option blocks and all 80 keybinds to Lua with every dispatcher/key-string form empirically confirmed live (not inferred), then closed the binds.json dispatcher/arg opacity gap early via a structural+source-level two-half proof — an authorized scope addition reassigned here from the Wave 7 cutover plan.**

## Performance

- **Duration:** ~90 min (extensive live empirical testing against a nested `hypr-lua-harness` instance — dispatcher argument-shape discovery, behavioral proofs via `hyprctl dispatch`, and building/self-testing a new static equivalence gate)
- **Completed:** 2026-07-28
- **Tasks:** 3 (2 from the plan + 1 authorized scope addition)
- **Files modified:** 8 (1 created, 7 modified)

## Accomplishments

- `hyprland.lua.disabled` now sets all 33 remaining option keys (`input`, `decoration` with nested `blur`/`shadow`, `dwindle`, `misc`, `cursor`) — every key read back against the committed baseline via a scripted loop, zero unexplained diffs. `decoration:shadow:color`'s quoted-string form and `shadow:offset`'s two-element array form both confirmed correct on the first try.
- All 80 keybinds ported to `hl.bind()`, with every dispatcher/flag/key-string form proven live via direct `hyprctl dispatch 'hl.dsp....'` calls against real client windows in the nested harness — not inferred from the hyprlang keyword. This surfaced two genuinely new, previously-undocumented findings: (1) `hl.dsp.window.resize`/`move` validate their argument shape at config-load time exactly like the window-rule/layer-rule/permission spec-builders 13.1-03 discovered, rejecting a positional-string guess with a precise expected-shape error; (2) multi-modifier key strings need every modifier joined by its own `" + "` — hyprlang's space-separated `"SUPER SHIFT + Q"` convention fails to parse under Lua.
- **Authorized addition (Task 3):** split the binds equivalence proof into a structural half (`hypr-equivalence-check`'s `binds.json` comparison now compares every field except `dispatcher`/`arg` byte-exact) and a new source-level half (`keybind-source-equivalence`, a static parser that extracts `(mods, key, dispatcher, arg)` from both `keybinds.conf` and `keybinds.lua` and diffs the two sets). Both proven live and both proven able to fail — the structural half via D-10 fault injection (altered field, dropped bind), the source-level half via three deliberate corruptions (changed exec arg, dropped bind, dropped modifier), each correctly naming the offending bind.
- Discovered (Task 3) that the structural check legitimately FAILs on exactly one open item — the `mouse` field for the two `bindm`-ported binds reads back `false`, not the baseline's `true` — and deliberately left it un-loosened per the task's explicit "no loosening" instruction, documenting it as a real, unresolved finding rather than papering over it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Fixed `hl.bind`/`hl.window_rule` literal-substring grep-count contamination in header comments**
- **Found during:** Task 2, running the plan's own automated verify block
- **Issue:** `keybinds.lua`'s header comment literally contained the substrings `hl.bind(` and `hl.window_rule` in prose, inflating `grep -c "hl.bind"` from 80 to 81 and `grep -c "hl.window_rule"` from 1 to 2 — both would have failed the plan's acceptance criteria (same class of issue 13.1-03 hit and fixed).
- **Fix:** Reworded the two affected comment lines to describe the calls without using the exact literal substrings, zero change to any executable line.
- **Files modified:** `hypr/.config/hypr/config/keybinds.lua`
- **Verification:** `grep -c` counts re-checked to exactly 80 and 1 respectively; `luac -p` still clean.
- **Committed in:** `c51177d` (Task 2 commit)

**2. [Rule 1 - Bug] Fixed a comment-stripping bug in `keybind-source-equivalence` that truncated string literals**
- **Found during:** Task 3, first run of the new script against the real files
- **Issue:** The initial `strip_lua_comment` implementation did a naive `line.find("--")`, which incorrectly truncated string literals containing a genuine `--` as shell-command text (e.g. `"uwsm app -- kitty.desktop"`), corrupting the parsed `arg` value for 4 exec-based locals and cascading into unbalanced-paren errors on several unrelated later lines.
- **Fix:** Rewrote the stripper to track quote state character-by-character, only treating `--` as a comment start when outside a quoted string.
- **Files modified:** `hypr/.config/hypr/scripts/keybind-source-equivalence`
- **Verification:** Re-ran against the real files — went from 13 parse errors / 67 parsed binds to 0 parse errors / 80 parsed binds, PASS.
- **Committed in:** `fa5e555` (Task 3 commit — fixed before the script was ever committed, so no separate fix commit was needed)

## Issues Encountered

- `hypr-lua-harness` copies `hyprland.lua.disabled` into its throwaway root at `start` time rather than symlinking it (unlike every `require()`d module, which IS symlinked). Editing the entry point and running `hyprctl reload` against an already-running harness is a silent no-op — the reload re-executes the stale copy. First diagnosed when a full `options.jsonl` readback showed defaults for every key this task had just added. Fixed by restarting the harness (`stop && start`) after entry-point edits; documented in `13.1-LUA-FINDINGS.md` as a durable operational finding for every remaining plan in this phase that touches `hyprland.lua.disabled` directly.
- `wtype` (virtual-keyboard protocol) did not deliver key events to the nested harness instance despite registering a `wl_keyboard` device and exiting 0 — root cause not isolated. Worked around by using `hyprctl dispatch 'hl.dsp....'` directly against real client windows instead, which turned out to be equally strong (arguably stronger) evidence since it isolates dispatcher correctness from key-string-parser correctness.
