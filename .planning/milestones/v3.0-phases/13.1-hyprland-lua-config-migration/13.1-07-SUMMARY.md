# Phase 13.1 Plan 07: Window Rules + Permission Grants Port Summary

**Ported all 30 window rules and 13 layer rules plus the four permission grants to Lua, discovered — via live runtime spot-checks, not assumed — that the window-rule `size` field's percentage form silently does not work on this installed Hyprland 0.56.1 Lua config manager, and (after an orchestrator spot-check caught a leftover experimental value the original verification missed) now has a genuine property-VALUE-level parity proof, not just name/pattern/count parity.**

## Correction (post-commit, caught by orchestrator spot-check — not self-verified)

**What was wrong:** the original commit for Task 1 (`46396de`) shipped `windowrules.lua` with the yazi-fm rule's `size` field set to `"70%w 65%h"` — one of the six experimental spellings tried while investigating the percentage-form gap (see below) — instead of the byte-identical original `size = 70% 65%` from `windowrules.conf` line 100. The original SUMMARY and COVERAGE.md both claimed "byte-identical" / "mechanically verified byte-parity ports" for the whole file. **Those claims were false for this one value.** The orchestrator caught it; this plan's own verification did not.

**Why the original verification missed it:** Task 1's automated/manual checks (regex multiset diff, property-occurrence census, named-rule check) compared match-pattern regex STRINGS and property NAME/COUNT parity — they never compared property VALUES against the `.conf` source. A property that exists with the right name, in the right rule, the right number of times, but holding a *different value* than the original, was invisible to every check that was actually run.

**Fix applied (commit `fe73aa3`):** restored `size = "70% 65%"`, byte-identical to `windowrules.conf`.

**Verification extended:** a new value-level comparison parses all 43 rules (30 window + 13 layer) from both `windowrules.conf` and `windowrules.lua` into ordered `{property: value}` dicts (aligned positionally, since both files preserve the same source order) and diffs all 68 property-value pairs. Result: **0 mismatches** after the fix (the yazi-fm size field was the only one that had drifted). Re-verified live via `hypr-lua-harness`: `floating=true` still applies to a yazi-fm-classed test window, `size` stays at the client's own default (unaffected either way, confirming the byte-identical string is inert on this build exactly as already documented — no functional change from this fix). `configerrors` clean; safety invariant held before/during/after.

**What this means for the rest of the file:** the value-level check now covers all 68 property-value pairs across the whole file, not just the one that was caught — there is no remaining known drift. The regex-pattern and property-count parity claims from the original verification were accurate as far as they went; they were simply not sufficient on their own to catch a same-name, same-count, wrong-value defect. Readers of this SUMMARY and of `COVERAGE.md` should trust the value-level comparison result above, not the original "byte-parity" language in isolation.

### Deferred Issues (fix-attempt limit reached — Rule 3 exclusion, not a Rule-1 auto-fix)

**1. Window-rule `size` field's percentage form has no runtime effect**
- **Found during:** Task 1's runtime spot-check for the yazi-fm rule
- **Issue:** `size = "70% 65%"` (and `"85% 85%"` on 5 other rules) registers with zero `configerrors` but the matched window opens at its own client-preferred size instead of the requested percentage.
- **Investigation:** 6 spelling variants tried live (percent-with-space, percent-with-comma, array table, keyed table, `%w`/`%h` CSS-style suffix, mixed pixel+percent token) — all 6 silently no-op. Isolated the cause specifically to the literal `%` character: a plain-pixel string (`"444 333"`) and even a non-percent malformed string (`"0.7 0.65"`, truncated via naive int parsing to `[1,0]`) both visibly changed the reported size, proving the `size` field mechanism itself is live and functioning; only `%`-suffixed values are rejected outright.
- **Not fixed:** building a compensating `hl.on("window.open", ...)` resize-on-open listener would be a materially different implementation mechanism than this plan's declarative-rule scope, and per this plan's own text, "must not use the format migration as cover to change behaviour" — inventing a new mechanism mid-port carries its own risk. Handed to 13.1-08 with two concrete options (build the listener, or accept as a documented cosmetic regression).
- **Files affected (not modified beyond documentation):** `hypr/.config/hypr/config/windowrules.lua` (kept byte-identical), `COVERAGE.md`, `.planning/WINDOWS.md`
- **Verification of the negative finding:** live, via `hypr-lua-harness`, with `kitty -o remember_window_size=no` to rule out a real confound this task discovered (kitty's own default `remember_window_size=yes` caused an earlier round of results to appear to work when they were actually just reflecting the client's remembered geometry from a prior test) — see COVERAGE.md for the full evidence table.

## Issues Encountered

- Kitty's own `remember_window_size` default (`yes`) initially masked the percentage-size investigation: a window relaunched after an earlier successful pixel-size test kept reporting that old pixel size even when the active rule had since changed to an invalid percentage string, making it briefly look like the percentage form was "working" via stale state.
