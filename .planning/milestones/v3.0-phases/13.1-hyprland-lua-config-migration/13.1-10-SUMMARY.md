## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] hypr-equivalence-check crashed/silently-degraded on the deleted hyprland.conf**
- **Found during:** Task 3, running the plan's own required `<verify>` gate
- **Issue:** `CONFIG_FILES` unconditionally included `$HYPRLAND_CONF`; the Python key-parser it feeds opens that path directly and would either error or (via process substitution) silently produce zero keys, making every option comparison report the full baseline as missing
- **Fix:** `CONFIG_FILES` construction is now existence-guarded for both `HYPRLAND_CONF` and the `config/*.conf` glob; a new `_derive_key_list()` helper falls back to the committed baseline's own `options.jsonl` `"option"` field set whenever no hyprlang tree remains
- **Files modified:** `hypr/.config/hypr/scripts/hypr-equivalence-check`
- **Verification:** Re-ran under `dracula` (matching the baseline capture theme) — PASS:2 FAIL:1, identical to the pre-retirement figure, zero new divergences
- **Committed in:** `b2d1c58`

**2. [Rule 1 - Bug] theme-parity's D-31 motion byte-identity check permanently FAILed on hyprland-motion.conf**
- **Found during:** Task 3, running `theme-parity`
- **Issue:** `MOTION_BYTE_IDENTITY_FILES` asserted `hyprland-motion.conf` was byte-identical across a static-preset and a materialyou render; the file no longer exists in either render dir, so both sides always report `(missing)`, which the check treats as a divergence
- **Fix:** Removed `hyprland-motion.conf` from the array. `hyprland-tokens.lua` cannot replace it — it merges theme-dependent colours with motion, so asserting byte-identity across palettes would be asserting something false by construction. Documented as a genuine coverage change, not silently patched around
- **Files modified:** `theme-engine/.config/theme-engine/theme-parity`
- **Verification:** `theme-parity` 2608/0, full 22-palette matrix still runs against every surviving file
- **Committed in:** `b2d1c58`

**3. [Rule 1 - Bug] motion-lint --self-test permanently FAILed on the hyprlang .conf fixture set**
- **Found during:** Task 3, running `motion-lint --self-test`
- **Issue:** `compliant-hypr.conf` expects exit 0, but CHECK A resolves references against `load_hypr_defs()`, which reads the now-permanently-absent `hyprland-motion.conf` — no hyprlang `.conf` file can ever satisfy CHECK A again
- **Fix:** Removed the four hyprlang `.conf` fixtures (`compliant-hypr.conf`, `poisoned-raw-hypr.conf`, `poisoned-raw-speed-hypr.conf`, `poisoned-dangling-hypr.conf`) from the self-test list and deleted them from `tests/motion-fixtures/`; the poisoned siblings had also lost their distinguishing value (everything in that format now fails CHECK A regardless of being poisoned or compliant). CHECK A/B's `.conf`-scan path itself stays as defense-in-depth (already degrades gracefully via a `[NOTE]` on absence, a design choice made proactively in `13.1-06`)
- **Files modified:** `hypr/.config/hypr/scripts/motion-lint`, 4 fixture files deleted
- **Verification:** `motion-lint --self-test` 10/0 (was 14 fixtures, now 10)
- **Committed in:** `b2d1c58`

**4. [Rule 1 - Bug, found by Criterion 7's own required reproduction proof] ~/.config/hypr folds into a repo-tree symlink on a genuinely fresh machine**
- **Found during:** Task 3, running the throwaway-home-directory reproduction test the plan's own acceptance criteria require
- **Issue:** On a machine with no prior `~/.config/hypr`, nothing stopped GNU stow from folding the entire `hypr` package into one whole-directory symlink; `stow.sh`'s later `mkdir -p "$HOME/.config/hypr/state"` and `ln -sf ... state/tokens.lua` then followed that fold and wrote into the CLONED REPO TREE instead of the user's real config directory. Every real development machine avoided this by accident (`~/.config/hypr/state/` already existed as a real directory from a much earlier stow run)
- **Fix:** Pre-create `~/.config/hypr` as a real directory before the stow loop, same idiom already used for fish/gtk-3.0/gtk-4.0/quickshell/systemd
- **Files modified:** `stow.sh`
- **Verification:** Re-ran the throwaway reproduction; `state/tokens.lua` now resolves to the real `~/.local/state/theme/hyprland-tokens.lua`, byte-identical content, nothing under the cloned repo tree
- **Committed in:** `a208d51`

**5. [Rule 1 - Bug, found by Criterion 7's own required reproduction proof] ~/.local folds into a repo-tree symlink on a genuinely fresh machine — wider blast radius**
- **Found during:** Task 3, same reproduction run as #4, immediately after fixing it
- **Issue:** The same fold class, one level up: `vscodium`'s single `.local/share/applications` file was enough for stow to fold the ENTIRE `~/.local` into a symlink at `dotfiles/vscodium/.local` on a fresh machine — meaning EVERY theme-engine generated file under `~/.local/state/theme/`, not only the Hyprland ones, would land inside the cloned repo tree instead of the user's real state directory. This directly contradicts the project's own stated core value ("the whole setup reproduces from scratch with one script")
- **Fix:** Pre-create `~/.local` as a real directory before the stow loop; `vscodium`'s own `share/applications` entry still folds normally one level down
- **Files modified:** `stow.sh`
- **Verification:** Re-ran the throwaway reproduction a second time; confirmed `~/.local` is a real directory post-run, `state/theme/hyprland-tokens.lua` lands under the throwaway `$HOME`, not inside `dotfiles/`; real development machine unaffected (idempotent `mkdir -p`, confirmed `catppuccin` theme and `directory` type unchanged after re-running `stow.sh` live)
- **Committed in:** `79a9863`
