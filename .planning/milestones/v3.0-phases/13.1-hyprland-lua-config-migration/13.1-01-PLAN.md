<assumption_delta_decision>
**Noun that is now primary:** *generated token file as **data*** (a Lua table returned from a
module) rather than *generated token file as **executable config syntax*** (`$var = value`
hyprlang assignments). Correspondingly, two Hyprland-format `contract.json` entries
(`hyprland.conf` → `hypr-vars`, `hyprland-motion.conf` → `hypr-motion`) collapse into one
`lua-table` entry (`hyprland-tokens.lua`).

**Decision: `promote`.** `lua-table` becomes the primary generated-token format for the Hyprland
consumer, and the "generated files are data, not executable config" convention this phase Owns is
what Phases 14–18 inherit. The two hyprlang entries are removed, not kept alongside.

**Rationale:** a Lua table has no load-order semantics and a missing key is a graceful `nil`, which
is what makes D-13 achievable at all; keeping a parallel hyprlang emitter for the same consumer
would preserve exactly the load-order and syntax-injection hazards the promotion exists to delete.

**Recorded accepted debt (intentional `add-alongside`, not an oversight):** D-04's two-emitter
split keeps `matugen/.config/matugen/templates/hyprlock-colors.conf` emitting hyprlang and leaves
`contract.json`'s `hyprlock.conf` (`hypr-vars`) entry untouched. Reason: `hyprlock` is a separate
binary with its own hyprlang parser on its own release schedule. **Trigger for a later promote:**
if `hyprlock` ever gains a Lua config manager, the hyprlang emitter and the `hypr-vars` format
branch can both be retired in that phase.
</assumption_delta_decision>

| Boundary | Description |
|----------|-------------|
| repo config tree → compositor privilege grants | `permission = <path>, screencopy\|plugin, allow` declarations in `config/permissions.conf` gate what named client binaries may do; a silent divergence here is a real privilege change |

| third-party converter tooling → repo source | optional `hyprconf2lua` / `hyprlang2lua` output would become committed compositor config if used unreviewed |
