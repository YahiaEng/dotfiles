# Phase 13.1: Code Review Report

**Reviewed:** 2026-07-28T14:10:00Z
**Depth:** standard
**Files Reviewed:** 34
**Status:** issues_found

## Summary

This phase migrated Hyprland's compositor config from hyprlang `.conf` to
Lua, and the legacy `.conf` tree has already been deleted — the Lua config
and its supporting tooling are load-bearing for the machine booting at all.
The core runtime config files (`hyprland.lua`, `config/*.lua`,
`hypridle.conf`, `lib/tokens.lua`) correctly apply the phase's own
documented mitigations: the `hl.dsp.dpms({action=...})` table form is used
everywhere DPMS is touched, `animations.lua` sorts its curve-name keys
before iterating a hash table, `lib/tokens.lua` degrades safely via
`pcall(require, ...)`, and every retargeted `hyprctl dispatch` call in the
scripts reviewed here (`ai-webapp-launch.sh`, `ai-workspace.sh`,
`theme-stress-test`) correctly uses the Lua-expression form instead of the
now-broken legacy string form.

One genuine BLOCKER was found: `stow.sh` was hardened this phase against
the "whole-directory symlink fold" reproducibility bug for `~/.config/hypr`
and `~/.local`, but the identical bug remains live and unaddressed for the
`wallpapers` stow package (`~/Pictures`) — a fresh install would silently
write live wallpaper/screenshot state into the git checkout.

The remaining findings are all in the phase's own regression/equivalence
tooling: two of the gates this phase built to prove the migration correct
(`hypr-lua-harness`, `keybind-source-equivalence`) were left pointing at
files the same phase's own later retirement step (13.1-10) deleted, so they
are now permanently non-functional or crash outright. One file's own header
comment no longer describes its actual (already-cutover) state. A minor
silent-failure gap was also found in `ai-webapp-launch.sh`.

## Critical Issues

### CR-01: `stow.sh` does not pre-create `~/Pictures` before stowing the `wallpapers` package — same directory-fold bug just fixed for `~/.config/hypr`/`~/.local`, left open for wallpapers/screenshots

**File:** `stow.sh:19-41, 95-143, 145-165, 351-363`
**Issue:**

This phase's own commit history (13.1-10) fixed a "whole-directory symlink
fold" reproducibility bug for two stow targets: on a genuinely fresh
machine, if `~/.config/hypr` or `~/.local` do not exist yet, GNU stow's
tree-folding optimization creates a single symlink for the entire missing
directory (`~/.config/hypr -> dotfiles/hypr/.config/hypr`) instead of
descending and linking individual files. Any later `mkdir -p`/writer that
assumes it is writing into a real host directory instead silently writes
*inside the cloned git checkout*. `stow.sh` now pre-creates
`~/.config/hypr` (line 116) and `~/.local` (line 143) as real directories
*before* the `stow --restow` loop specifically to prevent this.

The `wallpapers` stow package (`wallpapers/Pictures/Wallpapers/**`,
`wallpapers/Pictures/Screenshots/`) is stowed in that same loop
(`PACKAGES` array, line 19-41) with **no equivalent pre-creation of
`~/Pictures`**. On a genuinely fresh machine — which is exactly the
scenario this phase's own reproduction proof used to find the other two
instances of this bug — `~/Pictures` does not exist yet when `stow.sh`
runs (install.sh's own documented flow is "1. Run `./stow.sh`" *before*
"3. Select 'Hyprland (uwsm-managed)' in your display manager", i.e. before
any graphical session — and thus before any XDG autostart mechanism that
might run `xdg-user-dirs-update` — has ever run). `stow --restow
wallpapers` therefore folds `~/Pictures` into a single symlink pointing at
`dotfiles/wallpapers/Pictures`.

The script's own later wallpaper-pointer seed block (lines 351-363) only
calls `mkdir -p "$HOME/Pictures/Wallpapers"` *after* the stow loop has
already run — by which point `~/Pictures` is already a symlink into the
repo, so `mkdir -p` is a silent no-op (a symlink to an existing directory
satisfies `mkdir -p`). The subsequent `ln -sfr "$WALLPAPER_SEED_TARGET"
"$HOME/Pictures/Wallpapers/current.jpg"` then creates `current.jpg`
*inside the git checkout itself*, and every later `wallpaper-switch.sh` /
`theme-apply` write to `~/Pictures/Wallpapers/current.jpg` (the Material
You source image) and every screenshot written to
`~/Pictures/Screenshots/` (hyprshot/grim, bound to the Print-key family in
`keybinds.lua`) does the same from then on — directly contradicting this
project's stated core value ("the whole setup reproduces from scratch with
one script") and its git-clean invariant, for exactly the same reason the
`hypr`/`.local` fix was needed.

**Fix:** Pre-create `~/Pictures/Wallpapers` and `~/Pictures/Screenshots` as
real directories *before* the `stow --restow` loop, mirroring the existing
pattern for `fish`, `gtk-3.0`/`gtk-4.0`, `quickshell`,
`systemd/user/swaync.service.d`, `~/.config/hypr`, and `~/.local`:

```bash
# Pre-create ~/Pictures/{Wallpapers,Screenshots} as real directories so
# stow links individual files instead of dir-folding ~/Pictures into the
# repo on a fresh machine (same class of bug fixed for hypr/.local above).
mkdir -p "$HOME/Pictures/Wallpapers" "$HOME/Pictures/Screenshots"
```
placed alongside the other pre-create calls, above the `for pkg in
"${PACKAGES[@]}"` loop.

## Warnings

### WR-01: `hypr-lua-harness` is now permanently non-functional — both of its own guard conditions always fire post-cutover

**File:** `hypr/.config/hypr/scripts/hypr-lua-harness:70-84`
**Issue:** `start` refuses to run whenever `~/.config/hypr/hyprland.lua`
already exists ("the live session appears to already be on Lua", line
70-73), and separately requires `~/.config/hypr/hyprland.lua.disabled` to
exist (line 80-84, "$DISABLED_ENTRY not found"). The 13.1 cutover already
happened: `hyprland.lua.disabled` no longer exists on disk (confirmed —
only `hyprland.lua` is present), and `hyprland.lua` itself is now the live
file. This means the very first guard (line 70) now *always* fires and
`hypr-lua-harness start` can never succeed again, on any machine, in any
state. The tool's own header describes itself as "a real committed tool,
not throwaway scaffolding" used by "Plans 13.1-03 through 13.1-08", but
nothing in the file documents that it is now permanently inert post-cutover
— a future contributor trying to use it to regression-test a Lua config
change will only get a misleading "the live session appears to already be
on Lua" refusal.
**Fix:** Either retire the tool explicitly (move it out of the active
scripts dir, or add a clear header note that it only ever worked
pre-cutover and is kept for historical reference), or rewrite it to operate
directly against the live `hyprland.lua` tree (e.g. accept an explicit
source-of-truth entry point argument instead of hardcoding the
`.disabled`-suffix convention) so it can still be used for nested-instance
regression testing going forward.

### WR-02: `keybind-source-equivalence` crashes with an unhandled exception on its own documented default invocation

**File:** `hypr/.config/hypr/scripts/keybind-source-equivalence:45-46, 87-139`
**Issue:** `DEFAULT_CONF = REPO_ROOT / "hypr/.config/hypr/config/keybinds.conf"`
and `parse_conf()` opens that path unconditionally
(`with open(path, encoding="utf-8") as fh:`, line 91) with no
existence check. `keybinds.conf` was deleted along with the rest of the
legacy hyprlang tree in the 13.1-10 retirement. Running this tool with no
arguments — its own documented default usage ("Defaults to the real
`hypr/.config/hypr/config/{keybinds.conf,keybinds.lua}`") — now raises an
unhandled `FileNotFoundError` and exits with a Python traceback instead of
a clean PASS/FAIL report. Both sibling gates in this same phase
(`keybind-doctor`, `hypr-equivalence-check`) were explicitly hardened with
`[[ ! -f ... ]]` existence checks precisely because a silent/ugly failure
mode here would erode confidence in the whole equivalence-gate family — this
script was not given the same treatment when its comparison source was
deleted.
**Fix:** Guard `parse_conf`'s `open()` call (or the `main()` entry point)
with an explicit existence check on `conf_path` that prints a clear message
and exits non-zero (or documents that the tool is retired now that
`keybinds.conf` no longer exists), matching the discipline already applied
elsewhere in this phase's tooling.

### WR-03: `hyprland.lua`'s own header comment is stale and describes a state that no longer holds

**File:** `hypr/.config/hypr/hyprland.lua:1-33`
**Issue:** The file's header still says (verbatim): "hypr/.config/hypr/hyprland.lua.disabled
— top-level Lua config entry point," "The `.disabled` suffix is
LOAD-BEARING," and "This file stays `.disabled` for the whole phase; it is
renamed to hyprland.lua ONLY at the cutover plan, after the equivalence
gate... passes." The cutover has already happened — the file on disk is
named `hyprland.lua` (confirmed: no `hyprland.lua.disabled` exists
anywhere in the repo) and is the live, load-bearing compositor entry point
Hyprland boots from today. A future maintainer reading this file's own
header — the single most load-bearing file in the repo per the phase
context — would be misled into thinking it is still an inert,
not-yet-activated copy.
**Fix:** Update the header comment to reflect the post-cutover state: this
is the live `hyprland.lua`, the `.disabled` history is past-tense context,
not a currently-enforced invariant.

### WR-04: `ai-webapp-launch.sh` silently swallows the workspace-switch failure that is the script's entire documented purpose

**File:** `hypr/.config/hypr/scripts/ai-webapp-launch.sh:34-35`
**Issue:** The script's own header explains at length that the *only*
mechanism that correctly places a Zen AI web-app window on the `name:ai`
workspace is "switch to `name:ai` FIRST, then launch" — window rules
cannot do it (Zen shares one class for every window, and the real page
title arrives after Hyprland's one-shot placement rule has already fired).
The switch itself is `hyprctl dispatch 'hl.dsp.focus({workspace="name:ai"})'
>/dev/null 2>&1 || true` — any failure (compositor busy, IPC hiccup,
transient socket error) is silently discarded, and the script proceeds
straight to `exec uwsm app -- zen-browser --new-window "$URL"` regardless.
Per this file's own design rationale, if that one dispatch call fails, the
new Zen window lands on whatever workspace happens to be currently active
instead of `name:ai` — the exact failure mode the whole script exists to
prevent — with no error surfaced to the user or logged anywhere. Contrast
with `ai-workspace.sh`'s equivalent call (`exec hyprctl dispatch
'hl.dsp.focus(...)'`, line 66), which is *not* `|| true`-guarded and so
correctly propagates a failure as a non-zero script exit.
**Fix:** Either drop the `|| true` (matching `ai-workspace.sh`'s posture,
so a failed switch becomes a visible non-zero exit before the browser ever
launches) or, if launching Zen unconditionally is intentional even on a
failed switch, at least emit a `notify-send`/log line so a misplaced window
is diagnosable instead of silent.

### WR-05: `ai-workspace.sh`'s idempotency check uses substring matching, not exact matching, against a comma-joined class list

**File:** `hypr/.config/hypr/scripts/ai-workspace.sh:44-53`
**Issue:** `PRESENT` is built as a comma-joined list of every window class
currently on the `name:ai` workspace (`jq -r '[...] | join(",")'`), and
presence is then tested with plain bash substring matching:
`[[ "$PRESENT" != *"$CLAUDE_CODE_CLASS"* ]]` /
`[[ "$PRESENT" != *"$LOCAL_MODELS_CLASS"* ]]`, where
`CLAUDE_CODE_CLASS="ai-claude-code"` and
`LOCAL_MODELS_CLASS="ai-local-models"`. This is not delimiter-aware: if any
other window class on that workspace happens to *contain*
`"ai-claude-code"` or `"ai-local-models"` as a substring (for example, a
window whose `--class` a user or another script sets to something like
`"my-ai-claude-code-notes"`), the substring test matches and the script
concludes the real Claude Code / local-models window is already present,
silently skipping the launch — a false negative against this file's own
stated D-24 idempotency requirement ("picking this twice must yield ONE
set of windows, not two" — here it can yield *zero* for the affected
window).
**Fix:** Split `PRESENT` on the comma delimiter and compare tokens exactly
(e.g. `IFS=',' read -ra classes <<< "$PRESENT"` then check each element
with `[[ "$c" == "$CLAUDE_CODE_CLASS" ]]`), or have the `jq` filter itself
test for exact membership (`any(. == $class)`) instead of building a
joined string for a later substring test.
