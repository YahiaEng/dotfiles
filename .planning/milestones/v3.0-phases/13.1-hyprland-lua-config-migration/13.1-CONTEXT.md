# Phase 13.1: Hyprland Lua Config Migration - Context

**Gathered:** 2026-07-28
**Status:** Ready for planning
**Source:** PRD Express Path (`docs/superpowers/specs/2026-07-28-hyprland-lua-config-migration-design.md`, approved 2026-07-28)

<domain>
## Phase Boundary

Move the Hyprland compositor config off hyprlang (`.conf`) to Lua (`hyprland.lua`) before
0.57 removes `.conf` support, and convert the theme-engine's two Hyprland-format generated
outputs from generated config *syntax* into generated *data* — while proving the resulting
config is behaviourally identical to what runs today.

**In scope:**

- The 8 static config files under `hypr/.config/hypr/` (**923 lines**) become Lua modules,
  preserving the current modular split.
- `theme-engine/.config/theme-engine/contract.json`: the two Hyprland-format entries
  (`hyprland.conf` `hypr-vars` + `hyprland-motion.conf` `hypr-motion`) collapse into **one**
  `lua-table` entry; the new format is registered and validated.
- `theme-engine/.config/theme-engine/lib/motion.sh` emits Lua table fields instead of
  `hypr-motion` text; `lib/contract.sh` gains `lua-table` validation; `lib/reload.sh` is
  confirmed against Lua reload semantics.
- `matugen/.config/matugen/templates/hyprland-colors.conf` becomes a Lua-table template.
- A new `hypr-equivalence-check` verification tool, modelled on the existing
  `waybar-equivalence-check`.
- `hypr/.config/hypr/scripts/motion-lint` gains a Lua-aware path plus fixtures.
- `install.sh` / `stow.sh` reproduce the Lua config on a fresh machine.

**Out of scope** (see `<deferred>` — these are fences, not backlog):

- The other 27 `contract.json` entries (GTK CSS, SCSS, QML, TOML, JSON, kitty, fzf, …).
- Converting `hyprlock.conf` / `hypridle.conf` — separate binaries, separate hyprlang parsers.
- Redesigning the theming pipeline beyond the two Hyprland-format outputs.
- Rewriting keybinds, window rules, or animation curves. This is a **format migration** and
  behaviour must be provably identical. Improvements belong in a later phase.

**Why now, not later:** Hyprland selects a config format once at startup and will not load a
legacy config if Lua is active — the formats cannot coexist. 0.56 is the last release that
supports **both**, which makes it the only window in which this migration has a working
fallback (rollback is one `mv` plus a compositor restart). After 0.57 the same work would be
done on a compositor that will not start.

</domain>

<decisions>
## Implementation Decisions

Every decision below is **locked** — sourced from the approved design spec. Where the spec
records a known unknown, it appears here as a decision *about how to resolve it*, not as an
assumption to build on.

### Timing and rollback

- **D-01: Migrate now, on Hyprland 0.56.** Both formats load today and rollback is a single
  `mv ~/.config/hypr/hyprland.lua ~/.config/hypr/hyprland.lua.disabled` plus a compositor
  restart. Post-0.57 that fallback disappears. The deadline is on an upstream clock this
  project does not control.
  — **Reversibility:** reversible (single file rename) *during* the phase; see D-12 for when
  that stops being true.

- **D-12: The legacy `.conf` tree stays on disk, untouched, for the duration of the phase.**
  `hypr/.config/hypr/hyprland.conf` and its `config/` tree are deleted **only** after the
  equivalence gate (D-08/D-10) passes *and* the Lua config has survived normal use. Retiring
  the legacy tree is the last act of the phase, not a step in the port.
  — **Reversibility:** one-way at the point of deletion — before that, fully reversible.

### Token contract

- **D-02: The Hyprland token contract becomes generated data, not generated config syntax.**
  A Lua table has no load-order semantics; a missing key is `nil` — defaultable at
  the point of use — rather than a parse failure. This eliminates both the load-order hazard
  and the syntax-injection class of bug in one change.
  — **Reversibility:** costly — undoing means reverting `contract.json`, `lib/motion.sh`, the
  matugen template, and `lib/contract.sh` together.

- **D-05: Colours and motion merge into ONE generated Lua table.** The two current
  Hyprland-format `contract.json` entries — `hyprland.conf` (`hypr-vars`, 22 `$colour` vars)
  and `hyprland-motion.conf` (`hypr-motion`, 9 speed vars + `animations { bezier = }`) —
  are replaced by a single `lua-table` entry. Merging is the point, not a convenience: it
  removes the ordering constraint between motion tokens and `animations.conf`, the
  "generated file is executable config syntax" coupling, and most of what `motion-lint`
  exists to detect.

- **D-13: A missing token degrades to a default, never blocking compositor startup.**
  `hypr/.config/hypr/hyprland.conf` today documents the inverse hazard in-file:
  `source = ~/.local/state/theme/hyprland-motion.conf` **MUST** come before
  `config/animations.conf`, because an undefined variable there is a hard parse error
  ("cannot parse as an int"). After this phase no config file may depend on another being
  sourced first for a variable to exist.

- **D-04: Two emitters, and the split stays.** The theme engine already renders
  `hyprland.conf` and `hyprlock.conf` from separate matugen templates over shared colour
  data. After migration the Hyprland template emits a Lua table and the hyprlock template
  continues emitting hyprlang. `hyprlock.conf`'s `hypr-vars` `contract.json` entry is
  **unchanged**. `hyprlock` and `hypridle` are separate binaries with their own hyprlang
  parsers and nothing indicates they move to Lua on Hyprland's schedule — so hyprlang output
  must survive for them.

### Static config port

- **D-06: Preserve the current modular 8-file split as Lua modules.** The port is a
  translation, not a reorganisation. Current shape (923 lines):
  `config/windowrules.conf` 307 · `config/keybinds.conf` 209 · `config/permissions.conf` 121 ·
  `hyprland.conf` 101 · `config/autostart.conf` 92 · `config/animations.conf` 61 ·
  `config/monitors.conf` 17 · `config/env.conf` 15.
  A naive `find -name '*.conf'` reports 1,277 lines, but that sweeps in `hyprlock.conf`,
  `hypridle.conf` and the 5 motion-lint fixtures — none of which are ported here.

- **D-07: A community converter is a draft, not a result.** Either
  [hyprconf2lua](https://github.com/Prateek-squadron/hyprconf2lua) (Python) or
  [hyprlang2lua](https://github.com/EIonTusk/hyprlang2lua) (Go) may provide a mechanical
  first pass, but every line requires hand-review. Their coverage claims are against standard
  configs, and this config references `$primary`, `$motion_enabled` and friends that are
  defined in files generated at runtime and therefore unresolvable by any static converter.
  `windowrules.conf` + `keybinds.conf` alone are **56%** of the work and are dense,
  repetitive, high-count declarations — that is where converter output needs the most
  scrutiny.

- **D-15: The actual Lua API is UNVERIFIED and research must establish it before planning commits to syntax.**
  The wiki pages consulted during design confirmed the
  migration and the config location but **not** how options, keybinds, window rules,
  `exec-once`, or nested blocks like `decoration { blur { … } }` are expressed. **Any Lua
  syntax appearing in the design spec, in the discussion that produced it, or in this
  CONTEXT.md is illustrative only.** Research must establish the real API from the current
  wiki and the `hl.meta.lua` stubs. This also satisfies ROADMAP standing constraint 2
  ("verify options against the installed binary") — hyprlock 0.9.5 silently ignoring unknown
  options is the precedent that made that constraint a gate.

### Verification

- **D-08: Build a new `hypr-equivalence-check` modelled on the existing `waybar-equivalence-check`.**
  Same pattern: snapshot a pre-refactor baseline, diff after,
  **report-only, never mutate**. One necessary difference: waybar's effective config resolves
  statically, whereas Hyprland's is observable only at runtime.
  - `--snapshot` — while still booted on `.conf`, parse the config files for every option key
    actually set, dump each via `hyprctl -j getoption`, and capture `hyprctl -j binds` and
    `hyprctl -j animations`. Commit as the baseline.
  - default mode — after switching to Lua, re-dump and diff.
  Verified available during design: `hyprctl -j getoption decoration:rounding` returns
  `{"option": "decoration:rounding", "int": 12, "set": true }`.

- **D-09: The baseline must be captured and committed BEFORE any config edit.** The central
  risk is silent divergence across 923 ported lines; a baseline taken after an edit proves
  nothing. This ordering constraint is what makes the baseline plan a hard predecessor of
  every other plan in the phase.

- **D-10: The gate exits 0 only on exact match, with every divergence individually recorded as intended and reasoned.**
  This converts the correctness question from a reading
  exercise into a gate. `hyprctl -j binds` covers keybinds directly, which is exactly where
  D-07 says converter output is least trustworthy.

- **D-16: The gate must carry a documented, explicit list of what it cannot cover.**
  If some set options are not introspectable via `hyprctl getoption`, that list is required. Silent gaps in a verification
  tool are worse than a smaller tool with known limits. Whether every set option is
  introspectable is an open question research must answer.

- **D-11: `motion-lint` gains a Lua-aware path plus new fixtures; its hyprlang path stays.**
  `hypr/.config/hypr/scripts/motion-lint` and its fixtures under
  `hypr/.config/hypr/scripts/tests/motion-fixtures/` currently parse hyprlang. Its purpose —
  catching raw or dangling motion values — still applies on the Lua consumer side. The
  hyprlang path is retained because it still guards the hyprlock output (D-04).

### Reproducibility

- **D-14: A fresh machine reproduces the Lua config through `install.sh` + `stow.sh`.** No
  manual host-only state, per the project's standing reproducibility constraint. ROADMAP
  standing constraint 3 (same-commit stow registration) applies to any new file or package
  this phase creates.

### Phase shape

- **D-17 [informational]: Approximately five plans, in this dependency order.** Planning
  guidance, not a tracked implementation decision.
  1. **Baseline** — build `hypr-equivalence-check`, capture and commit the `.conf` baseline.
     Must land before any config edit (D-09).
  2. **Static port** — converter pass plus hand-review of the 8 files into Lua modules.
  3. **Token contract** — theme-engine and matugen emit the merged Lua table;
     `contract.json` and `lib/contract.sh` updated.
  4. **motion-lint** — Lua-aware path and fixtures; hyprlang path retained for hyprlock.
  5. **Cutover** — equivalence gate green, soak under normal use, then retire the legacy tree
     and update `install.sh` / `stow.sh` as needed.
  The planner may deviate from this decomposition if research surfaces a better one, but
  D-09's ordering constraint (baseline strictly first) is **not** negotiable.

### Claude's Discretion

The design spec deliberately leaves these open — planner and executor choose:

- Whether to use a community converter at all, and which one. D-07 fixes only that its output
  is a draft requiring hand-review.
- The internal structure, language, and CLI surface of `hypr-equivalence-check` — beyond the
  `--snapshot` / default-diff contract and report-only discipline from D-08.
- Exact Lua module file names and the `require`/load mechanism, so long as D-06's split is
  preserved and D-13's no-load-order-dependency property holds.
- Lua-fixture naming and count for `motion-lint`, following the existing
  `compliant-*` / `poisoned-*` convention in `tests/motion-fixtures/`.
- How the merged Lua token table is keyed and namespaced, so long as `contract.json` declares
  exactly one `lua-table` entry and `lib/contract.sh` validates it.
- Soak duration and what "survived normal use" means concretely before the legacy tree is
  deleted (D-12) — subject to the human sign-off in ROADMAP standing constraint 1.

</decisions>

## Specific Ideas

- **Verified command output** (captured during design, safe to build on):
  `hyprctl -j getoption decoration:rounding` → `{"option": "decoration:rounding", "int": 12, "set": true }`.
- **Baseline capture triple:** `hyprctl -j getoption <key>` for every option key actually set
  in the config files, plus `hyprctl -j binds`, plus `hyprctl -j animations`.
- **Rollback command, verbatim:**
  `mv ~/.config/hypr/hyprland.lua ~/.config/hypr/hyprland.lua.disabled` followed by a
  compositor restart.
- **Config location:** `$XDG_CONFIG_HOME/hypr/hyprland.lua`.
- **Token counts to preserve:** 22 `$colour` vars (`hypr-vars`) + 9 speed vars and the
  `animations { bezier = }` block (`hypr-motion`) → one merged table.
- **Line-count sanity check for the port:** 923 lines across 8 files. If a converter or an
  audit reports ~1,277, it has swept in `hyprlock.conf`, `hypridle.conf` and the 5
  motion-lint hyprlang fixtures — none of which are in scope.
- **Scrutiny concentration:** `windowrules.conf` + `keybinds.conf` = 56% of the port.
  `hyprctl -j binds` gives direct coverage of the keybinds half.

</specifics>

<deferred>
## Deferred Ideas

Explicitly out of scope for Phase 13.1 — these are **fences**, not backlog items to
opportunistically pick up:

- **Any change to the other 27 `contract.json` entries.** GTK CSS, SCSS, QML, TOML, JSON,
  kitty, fzf and the rest are untouched.
- **Converting `hyprlock.conf` / `hypridle.conf` to Lua.** Separate binaries with their own
  hyprlang parsers; nothing indicates they move on Hyprland's schedule. If they later do, the
  hyprlang emitter can be retired then — until then it stays (D-04).
- **Redesigning the theming pipeline beyond the two Hyprland-format outputs.**
- **Rewriting keybinds, window rules, or animation curves.** This is a format migration;
  behaviour must be provably identical. Improvements belong in a later phase. Any "while we're
  in here" cleanup found during the port is a deferred item, not a task.

### Open questions research must close (from the design spec, not yet verified)

1. **The actual Lua API** — options, keybinds, window rules, `exec-once`, nested blocks
   (`decoration { blur { … } }`). See D-15. Blocking for the static port.
2. **`hyprctl reload` under Lua** — whether live reload behaves identically. Affects
   `lib/reload.sh` and the theme-apply path.
3. **Introspection completeness** — whether every set option is reachable via
   `hyprctl getoption`. Determines the documented coverage limits of the equivalence gate
   (D-16).
4. **Exact removal version** — 0.57 per the 0.56.1 runtime warning vs. upstream's "1–2
   releases from 0.55". Reconfirm before cutover; does not change the plan.
5. **hyprlock/hypridle roadmap** — if they later move to Lua, the hyprlang emitter can be
   retired. Informational only for this phase.

</deferred>
