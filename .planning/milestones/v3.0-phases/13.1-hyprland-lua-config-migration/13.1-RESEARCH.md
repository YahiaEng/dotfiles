## Summary

Hyprland 0.56.1 (the version installed and verified live on this machine) ships Lua config support
as a first-class, already-built-in feature — **no new package is required**: `hyprland` already
depends on `lua`, and the package itself installs `/usr/share/hypr/hyprland.lua` (a complete,
runnable example config) and `/usr/share/hypr/stubs/hl.meta.lua` (a 1770-line, auto-generated
LuaLS type-stub covering the entire `hl.*` API surface). These two files, read directly off this
machine's filesystem, are **the single most authoritative source available** — more authoritative
than the wiki, since they are generated from Hyprland's own source at the exact installed
version. Every claim tagged `[VERIFIED: local]` below comes from one of these two files or from a
live `hyprctl`/`pacman` command run on this machine.

The core mapping from this repo's 8 hyprlang files to Lua is now well understood and low-risk:
scalar options and nested blocks become `hl.config({ ... })` calls with the same dotted nesting
(`general.gaps_in`, `decoration.blur.enabled`); binds become `hl.bind(keys, dispatcher, opts)`
calls with a typed options table replacing the `bind`/`bindr`/`bindl`/`bindel`/`binde`/`bindm`
flag-letter zoo; `exec-once` becomes an `hl.on("hyprland.start", function() ... end)` callback
block; `monitor =` becomes `hl.monitor({ output=..., mode=..., position=..., scale=... })`;
`env =` becomes `hl.env(name, value)`; `bezier =`/`animation =` become `hl.curve(name, spec)` /
`hl.animation({ leaf=..., ... })`; and multi-file splitting is native Lua `require("path.module")`
— **with one load-bearing gotcha**: Hyprland's `require()` is NOT standard Lua `require` —
it silently prefixes every module path with the Hyprland config root (`~/.config/hypr`), so a
file living outside that tree (i.e. anything in `~/.local/state/theme/`) **cannot be
`require()`d directly**. This is the single most important finding for the D-02/D-05 token
contract and is elaborated in its own section below.

Two areas remain genuinely open and are flagged, not guessed at, per D-15's explicit mandate:
(1) the full property vocabulary accepted inside `hl.window_rule({...})` beyond the three
statically-typed fields (`name`, `match`, `enabled`) — the shipped example config passes extra
keys (`no_focus`, `move`, `float`, `suppress_event`) directly into the same table, proving the
mechanism works, but the complete list of accepted keys for this repo's 307-line `windowrules.conf`
(`size`, `center`, `pin`, `workspace`, `opacity`, `no_blur`, `animation`, `scroll_touchpad`) was
not found in any authoritative source reachable this session; and (2) exactly how `hyprctl reload`
behaves under a live Lua config — whether it re-executes the whole script from a clean slate or
risks accumulating duplicate binds/rules — could not be tested locally because `hyprctl eval` and
`hyprctl repl` (the only tools that could probe this) both refused with `"eval is only supported
with the lua config manager"` while this machine is still running on `.conf`. Both gaps are
scoped into the phase's first (Baseline/tracer) plan as spike work under D-12's safe-rollback
window, not left as silent risk.

**Primary recommendation:** Port using `hl.config()`/`hl.bind()`/`hl.monitor()`/`hl.env()`/
`hl.permission()`/`hl.curve()`+`hl.animation()` for the five well-verified files
(`hyprland.conf`, `keybinds.conf`, `monitors.conf`, `env.conf`, `permissions.conf`,
`animations.conf`) with high confidence; treat `windowrules.conf`'s port as the phase's highest-
risk work item requiring a per-property empirical verification pass against a live Lua-booted
compositor (using `hyprctl eval`/`hyprctl repl`, now available once Lua is active) before trusting
any translated rule; and solve the token-contract's cross-tree `require()` problem with a stowed
symlink inside `~/.config/hypr` pointing at the state-dir generated table, mirroring this repo's
existing `source = ~/.local/state/theme/hyprland.conf` pattern exactly.

## Verified Lua API Reference

**Live-Verification Ceiling — read this first.** `hyprctl eval` and `hyprctl repl` are the only
tools that can execute arbitrary Lua inside the running compositor and inspect its actual runtime
environment (global functions available, `package.path` contents, etc.). Both are gated: running
either against this machine (currently booted on `.conf`, Hyprland 0.56.1) returns exactly
`"eval is only supported with the lua config manager"` `[VERIFIED: local, hyprctl eval / hyprctl
repl, 2026-07-28]`. This means the *shape* of the API (function names, table structures) is fully
verifiable offline from the shipped stub/example, but the *live runtime environment* (whether
`dofile`, `loadfile`, `io`, `os`, standard `package.path` resolution are exposed or sandboxed out)
can only be tested once this machine is actually running the Lua config manager — i.e., inside the
phase's own execution, under D-12's rollback safety net, not during this research step. **The
phase's first (Baseline) plan should include a small, throwaway spike** — boot a minimal
`hyprland.lua` that runs `hl.eval`-testable probes and rolls back immediately — to close this gap
before the static port begins in earnest.

### Scalar options and nested blocks

`hl.config({...})` takes a Lua table whose keys mirror the hyprlang section names
(`general`, `decoration`, `animations`, `input`, `gestures`, `group`, `misc`, `binds`, `xwayland`,
`opengl`, `render`, `cursor`, `ecosystem`, `debug`, `layout`, `dwindle`, `master`, `scrolling`,
`experimental`, `input_capture`, `quirks`), each mapping to a further nested table for that
section's own keys — nesting exactly mirrors hyprlang's `{ }` blocks. `[VERIFIED: local, hl.meta.lua
HL.ConfigOpt.* classes, lines 1307-1770]`.

```lua
-- Source: /usr/share/hypr/hyprland.lua (shipped example, verified local)
hl.config({
    general = {
        gaps_in  = 5,
        gaps_out = 20,
        border_size = 2,
        col = {
            active_border   = { colors = {"rgba(33ccffee)", "rgba(00ff99ee)"}, angle = 45 },
            inactive_border = "rgba(595959aa)",
        },
        resize_on_border = false,
        allow_tearing = false,
        layout = "dwindle",
    },
    decoration = {
        rounding = 10,

        active_opacity = 1.0,
        inactive_opacity = 1.0,
        shadow = { enabled = true, range = 4, render_power = 3, color = 0xee1a1a1a },
        blur = { enabled = true, size = 3, passes = 1, vibrancy = 0.1696 },
    },
    animations = { enabled = true },
```

`rounding`, `active_opacity`, `inactive_opacity`, `fullscreen_opacity`, `blur.*`, `shadow.*`,

### Keybinds (bind / bindr / bindl / bindel / binde / bindm and friends)

`hl.bind(keys: string, dispatcher: HL.Dispatcher|function, opts?: HL.BindOptions): HL.Keybind`
`[VERIFIED: local, hl.meta.lua line 815]`. The hyprlang flag-letter system (`bind`, `bindm`,
`bindl`, `bindel`, `binde`, `bindr`, ...) is replaced by a single function plus an options table:

| hyprlang flag | Lua `HL.BindOptions` field | `[VERIFIED: local]` |
|---|---|---|
| `bindr` (release-triggered) | `release = true` | yes, field present in `HL.BindOptions` |
| `bindl` (locked, works on lockscreen) | `locked = true` | yes |
| `binde` (repeat while held) | `repeating = true` | yes |
| `bindm` (mouse-only, drag/resize) | pass a mouse dispatcher; `HL.Keybind.mouse` reflects it | yes (`mouse` is a read field on the returned `HL.Keybind`, not confirmed as a settable opt — see gap below) |
| `bindel` (locked + repeat, e.g. volume/brightness) | `{ locked = true, repeating = true }` (both flags combined) | yes, both fields independently confirmed |

```lua
-- Source: /usr/share/hypr/hyprland.lua (verified local)
local mainMod = "SUPER"
hl.bind(mainMod .. " + Q", hl.dsp.exec_cmd(terminal))
hl.bind("XF86AudioRaiseVolume", hl.dsp.exec_cmd("wpctl set-volume -l 1 @DEFAULT_AUDIO_SINK@ 5%+"),
    { locked = true, repeating = true })
hl.bind(mainMod .. " + mouse:272", hl.dsp.window.drag(),   { mouse = true })
```

Dispatchers are namespaced under `hl.dsp` (`hl.dsp.exec_cmd`, `hl.dsp.window.close()`,
`hl.dsp.window.float({action="toggle"})`, `hl.dsp.focus({direction="left"})`,
`hl.dsp.workspace.toggle_special("magic")`, `hl.dsp.global(...)`) — full namespace list
`[VERIFIED: local, hl.meta.lua lines 863-931]`: `HL.DspNamespace` (dpms, event, exec_cmd,
exec_raw, exit, focus, force_idle, force_renderer_reload, global, layout, no_op, pass,
release_input_capture, send_key_state, send_shortcut, submap) plus sub-namespaces
`HL.DspCursorNamespace` (move, move_to_corner), `HL.DspGroupNamespace` (active, lock, lock_active,
move_window, next, prev, toggle), `HL.DspWindowNamespace` (alter_zorder, bring_to_top, center,
clear_tags, close, cycle_next, deny_from_group, drag, float, fullscreen, fullscreen_state, kill,
move, pin, pseudo, resize, set_prop, signal, swap, tag, toggle_swallow), `HL.DspWorkspaceNamespace`
(change_id, move, rename, swap_monitors, toggle_special).

This repo's `keybinds.conf` (209 lines) maps every dispatcher it uses cleanly onto this namespace:
`exec` → `hl.dsp.exec_cmd`, `killactive` → `hl.dsp.window.close()` (or `.kill()`),
`togglefloating` → `hl.dsp.window.float({action="toggle"})`, `fullscreen` →
`hl.dsp.window.fullscreen(...)`, `pseudo` → `hl.dsp.window.pseudo()`, `movefocus` →
`hl.dsp.focus({direction=...})`, `movewindow` → `hl.dsp.window.move(...)`, `resizeactive` →
`hl.dsp.window.resize(...)`, `workspace`/`movetoworkspace` → `hl.dsp.focus({workspace=...})` /
`hl.dsp.window.move({workspace=...})`, `togglespecialworkspace` →
`hl.dsp.workspace.toggle_special(...)`, `global` (used by the Quickshell probe binds) →
`hl.dsp.global(...)`.

**One field-level gap:** `HL.BindOptions` (line 437) does not list an explicit `mouse` boolean —
the shipped example achieves mouse binds by passing `{ mouse = true }` anyway (line 290-291 of
`hyprland.lua`), and the field appears as a *read* property on the returned `HL.Keybind` object
(line 658) but not in the writable `HL.BindOptions` spec. Lua being dynamically typed, passing
`mouse = true` almost certainly still works (the example does exactly this and presumably ships
working) — flagged `[VERIFIED: local — usage confirmed by example, but not present in the typed
opts class]` as a minor stub-completeness gap, not a functional blocker.

**Physical keycode binds** (this repo's `bind = , code:107, exec, ...` for the Print key) — the
`key` string field on `HL.Keybind` is typed `string`, and the shipped example never demonstrates a
`code:NNN` form. **UNVERIFIED**: whether `hl.bind("code:107", ...)` accepts the same
`code:<keycode>` string syntax hyprlang used, or requires a different keycode-binding mechanism.
Flag for empirical testing in the static-port plan — this repo has 4 such binds (screenshot
region/window/full, recording toggle) that are high-value to get right (SHOT-01/02/03 depend on
them) but low count, so a quick live test is cheap.

### Window rules and layer rules

`hl.window_rule(spec: HL.WindowRuleSpec): HL.WindowRule` and
`hl.layer_rule(spec: HL.LayerRuleSpec): HL.LayerRule` `[VERIFIED: local, hl.meta.lua lines 848,
855]`. **This is the phase's single largest verification gap.**

`HL.LayerRuleSpec` (line 548) is *fully* typed: `above_lock`, `animation`, `blur`, `blur_popups`,
`dim_around`, `enabled`, `ignore_alpha`, `match`, `name`, `no_anim`, `no_screen_share`, `order`,
`xray` — every field this repo's 12 `layerrule = ...` lines in `windowrules.conf` (blur, animation,
ignore_alpha, matched by namespace) need has a confirmed typed slot `[VERIFIED: local]`.

`HL.WindowRuleSpec` (line 590), by contrast, declares only **three** fields: `enabled?: boolean`,
`match?: table<string, string|number|boolean>`, `name?: string`. Every other property this repo's
307-line `windowrules.conf` sets — `float`, `size`, `center`, `pin`, `move`, `workspace`,
`opacity`, `no_blur`, `animation`, `scroll_touchpad`, `no_focus`, `suppress_event` — is **absent
from the typed stub**. The shipped example config itself proves the *mechanism* works: it passes
`no_focus = true`, `move = "20 monitor_h-120"`, `float = true`, and `suppress_event = "maximize"`
directly as extra keys in the same table alongside `name`/`match` (`hl.window_rule({ name=...,
match={...}, no_focus = true })`, `/usr/share/hypr/hyprland.lua` lines 317-356,
`[VERIFIED: local]`) — so Lua's dynamic typing clearly accepts arbitrary additional keys and the
underlying implementation reads them; the stub's `HL.WindowRuleSpec` class is simply
under-documented for brevity (likely because window-rule properties are numerous and
implementation-driven, unlike the LayerRuleSpec's fixed set). **What could not be confirmed this
session:** the *complete* list of accepted window-rule property names, or whether any of them
differ in spelling from this repo's current hyprlang keywords (e.g., whether it is `no_blur` as
today or `noblur`/`no_blur`/`blur=false`). `match:class`/`match:title` colon-syntax (hyprlang
0.54+, used throughout this repo's `windowrules.conf`) becomes a nested table:
`match = { class = "^(pavucontrol)$" }` — confirmed directly from the shipped example
(`match = { class = "^$", title = "^$", xwayland = true, ... }`, lines 329-336)
`[VERIFIED: local]`.

**Recommendation:** treat every non-`name`/`match`/`enabled` window-rule property as
`[UNVERIFIED — empirically test]`. Since `hyprctl eval`/`hyprctl repl` become available the
moment this machine boots on the Lua config manager, the cheapest and most reliable verification
path is: during the static-port plan, after the first minimal `hyprland.lua` boots successfully,
run `hyprctl repl` interactively and construct/apply one `hl.window_rule({...})` per distinct
property this repo uses, observing `hyprctl clients -j` for the effect on a real test window —
this is strictly more reliable than trusting an unverified wiki page, and D-15/ROADMAP standing
constraint 2 both mandate exactly this "verify against the installed binary" discipline.

### exec-once / exec

No `exec-once`/`exec` dispatcher/function is directly documented as a drop-in replacement; the
shipped example's own comment block is explicit about the replacement pattern:

```lua
-- Source: /usr/share/hypr/hyprland.lua, lines 40-49 (verified local)
-- Autostart necessary processes (like notifications daemons, status bars, etc.)
-- Or execute your favorite apps at launch like this:
--
-- hl.on("hyprland.start", function ()
--   hl.exec_cmd(terminal)
--   hl.exec_cmd("nm-applet")
--   hl.exec_cmd("waybar & hyprpaper & firefox")
-- end)
```

`hl.on(event: HL.EventName, cb: fun(...)): HL.EventSubscription` `[VERIFIED: local, hl.meta.lua
line 850]`, with `"hyprland.start"` confirmed as a valid `HL.EventName` value (the full enum is at
lines 5-37, also including `"config.reloaded"`, `"config.props_refreshed"`,
`"hyprland.shutdown"`). `hl.exec_cmd(cmd: string, rules?: table): nil` is a top-level API function
(line 823), distinct from the `hl.dsp.exec_cmd(...)` dispatcher form used inside `hl.bind(...)`.

This repo's `autostart.conf` (92 lines, 22 `exec-once` lines) maps to a single
`hl.on("hyprland.start", function() hl.exec_cmd("...") ... end)` block, one `hl.exec_cmd(...)`
call per current `exec-once` line, preserving the exact top-to-bottom ordering (this repo's

### animation = and bezier = declarations

`hl.curve(name: string, spec: table): any` and `hl.animation(spec: table): any` — both present as
top-level API functions (lines 814, 818) but untyped in the stub signature (`fun(...): any`); the
shipped example demonstrates the full shape unambiguously for both bezier and spring curves:

```lua
-- Source: /usr/share/hypr/hyprland.lua (verified local)
hl.curve("easeOutQuint", { type = "bezier", points = { {0.23, 1}, {0.32, 1} } })
hl.curve("easy",         { type = "spring", mass = 1, stiffness = 238.1191, dampening = 24.21279333 })

hl.animation({ leaf = "windows",    enabled = true, speed = 4.79, spring = "easy" })
hl.animation({ leaf = "border",     enabled = true, speed = 5.39, bezier = "easeOutQuint" })
hl.animation({ leaf = "windowsIn",  enabled = true, speed = 4.1,  spring = "easy", style = "popin 87%" })
```

This is a **structural change from hyprlang**, not just a syntax translation: hyprlang's
`bezier = name, x0, y0, x1, y1` (4 raw floats) becomes `hl.curve(name, { type = "bezier", points =
{ {x0,y0}, {x1,y1} } })` — a nested points array, not 4 flat args. Hyprlang's single-line
`animation = <leaf>, <onoff>, <speed>, <style>[, <curve>]` becomes a keyed table
`{ leaf=, enabled=, speed=, bezier=|spring=, style=? }`, and — new in Lua — a leaf can reference
either a `bezier` curve OR a `spring` curve (mass/stiffness/dampening), a capability hyprlang's
flat syntax did not expose this cleanly. This repo's `animations.conf` (61 lines) uses only
bezier curves (no springs currently, matching TOKEN-06's "MD3 is better, spring too fast" verdict
already recorded in `12-MOTION-VERDICT.md`) — so every one of this repo's 16 `animation = ...`
lines and every `bezier =` line the theme-engine emits maps to the `bezier` form shown above, not
the `spring` form. `[VERIFIED: local]`.

**Interaction with the token contract:** this repo's `animations.conf` currently references
Hyprland-side *variables* (`$motion_speed_standard`, `motion-standard`, etc.) rather than literal
numbers/curve names, sourced from the theme-engine's generated `hyprland-motion.conf`. Under Lua
there is no `$variable` syntax — the generated *table* must be consumed directly inside the
`hl.animation({...})` call arguments (e.g. `speed = tokens.motion_speed_standard`,
`bezier = tokens.motion_curve_standard`), which is exactly the D-02/D-13 "generated data, not
generated config syntax" improvement the phase exists to make. See "Token-Contract Consumption
Mechanism" below.

### Multi-file config loading — require()

Confirmed directly from the shipped example's own header comment, and independently corroborated
by community discussion:

```lua
-- Source: /usr/share/hypr/hyprland.lua, lines 8-10 (verified local)
-- You can (and should!!) split this configuration into multiple files
-- Create your files separately and then require them like this:
-- require("myColors")
```

`[CITED: github.com/hyprwm/Hyprland discussion #14396]` (MEDIUM confidence — community
discussion, not official docs, not independently exercised live this session, but consistent with
the local example and not contradicted by anything found): Hyprland's `require()` is **not**
plain Lua `require` — it silently prefixes the module name with the Hyprland config root
(`~/.config/hypr`) before resolving, and supports both `/` and `.` as path separators:
`require("awesomeconf/keybinds")` and `require("awesomeconf.keybinds")` both resolve to
`$XDG_CONFIG_HOME/hypr/awesomeconf/keybinds.lua`. Each `require()`d file is a separate Lua scope,
so a runtime error in one module does not necessarily abort the others — consistent with, though
not identical proof of, D-13's "a missing token degrades to a default" goal (this describes
module-level error isolation, not specifically nil-key defaulting — see next section for the
actual mechanism that satisfies D-13).

**Direct consequence for D-06:** the 8-file split becomes 8 (or fewer, if some are trivially
merged) sibling `.lua` files under `~/.config/hypr/` (e.g. `hypr/.config/hypr/config/keybinds.lua`
mirroring the current `config/keybinds.conf` path), each `require("config.keybinds")`d from the
top-level `hyprland.lua` in the same order the current `source = ` lines specify. Because
`require()` is prefix-anchored at the Hyprland config root and NOT at the calling file's own
directory, nested-directory requires stay simple regardless of which file does the requiring.

**Direct consequence for D-02/D-05 (the harder case):** the generated token table lives in
`~/.local/state/theme/`, which is *outside* `~/.config/hypr` — so it **cannot** be
`require()`d by its real path. See next section.

## Token-Contract Consumption Mechanism

This is the phase's second P0 blocking question (D-02/D-05/D-13) and the answer follows directly
from the `require()` path-prefixing finding above.

**The problem:** `require()` only resolves inside `~/.config/hypr`. The theme-engine's generated
files live in `~/.local/state/theme/` (a separate directory, matching every other render target
in `contract.json`). A bare `require("hyprland-tokens")` from `hyprland.lua` will look for
`~/.config/hypr/hyprland-tokens.lua` and never find the real generated file.

**Recommended mechanism** (Claude's Discretion per CONTEXT.md, so this is a recommendation, not a
locked decision) — mirror the pattern this repo *already* uses for the hyprlang case exactly:
today, `hyprland.conf` does `source = ~/.local/state/theme/hyprland-motion.conf` — a `source`
directive with an absolute path outside the config tree, which hyprlang supports natively (no
prefixing). Lua's `require()` cannot do this directly, but two straightforward options close the
gap, both consistent with `[CITED]` community findings and this repo's existing conventions:

1. **Stowed symlink (recommended — lowest new-mechanism risk).** Ship a real file inside the
   `hypr/` stow package, e.g. `hypr/.config/hypr/state/tokens.lua`, that is *itself* a symlink to
   `~/.local/state/theme/hyprland-tokens.lua` (the theme-engine's actual render target),
   pre-created by `stow.sh` the same way it already pre-creates real directories for other
   packages (fish, gtk-3.0/4.0, quickshell, the swaync systemd drop-in — all documented,
   established precedent in `stow.sh`). Then `hyprland.lua` does
   `local tokens = require("state.tokens")`, which resolves to
   `~/.config/hypr/state/tokens.lua` → (symlink) → the real generated file. This requires zero
   new Hyprland-side mechanism — it works through `require()`'s existing, verified path
   resolution and this repo's own established stow pattern for cross-tree file wiring.
2. **`loadfile()` with an absolute path** — `[CITED]` community discussion confirms `loadfile()`
   bypasses the config-root prefixing entirely, so
   `local file = loadfile(os.getenv("HOME") .. "/.local/state/theme/hyprland-tokens.lua"); local
   tokens = file()` would also work — **but** this depends on `loadfile` actually being present
   in Hyprland's Lua sandbox, which is exactly the item flagged UNVERIFIED under "Live-Verification
   Ceiling" above (could not test `type(loadfile)` live this session). Do not commit to this path
   without confirming `loadfile` is available once the phase can run `hyprctl repl` against a live
   Lua config.

**Whichever mechanism is chosen, the file must ALWAYS exist** — this is the critical corollary of
D-13. A missing *file* makes `require()`/`loadfile()` itself error (module-not-found), which is a
harder failure than a missing *key* inside an existing table (which is just `nil`, gracefully
defaultable via `tokens.motion_speed_standard or 150`). **This repo already has the exact
precedent to follow**: `stow.sh` currently seeds `hyprland-motion.conf`, `gtk-4.0-motion.css`, and
`motion.json` on a fresh install by *invoking the real renderer* (`theme_engine_render_motion_
files`) rather than shipping a hand-authored stub, specifically because "a missing
hyprland-motion.conf is a hard `source=` globbing error" `[VERIFIED: local, stow.sh comment,
lines 156-171]`. The new merged `lua-table` file needs the identical seed treatment — extend the
same `stow.sh` all-or-nothing existence check to include the new Lua token file, seeded by
invoking `motion.sh`'s (renamed/extended) renderer, never a static stub.

**A missing key inside an existing, valid table degrades correctly** — this is native Lua
semantics, not something that needs to be built: `local speed = tokens.motion_speed_standard or
2.0` reads `nil` and falls through to the default with zero special-casing. This satisfies D-13's
"never prevents the compositor from starting" requirement *once the file itself is guaranteed to
exist* — the seed-on-fresh-install step above is what makes that guarantee hold, not anything
Lua-specific.

**Recommended emitted shape** (illustrative — Claude's Discretion per CONTEXT.md, subject to
`lib/contract.sh` validation, not a locked syntax):

```lua
-- Illustrative shape only — NOT verified against the live Lua environment.
-- Generated by theme-engine; do not edit manually.
return {
    colors = {
        primary = "rgba(...)",
        on_primary = "rgba(...)",
        -- ... 22 colour tokens total (same set hypr-vars emits today)
    },
    motion = {
        enabled = true,
        speed = {
            standard = 2.00,
            emphasized_in = 3.00,
            -- ... one entry per current $motion_speed_* variable
        },
        curves = {
            standard = { type = "bezier", points = {{0.2, 0}, {0, 1}} },
            -- ... one entry per motion-* bezier the engine currently emits
        },
    },
}
```

`hyprland.lua`'s `animations.lua` module would then do
`hl.curve("motion-standard", tokens.motion.curves.standard)` and
`hl.animation({ leaf = "windowsMove", speed = tokens.motion.speed.standard or 2.0, bezier =
"motion-standard" })` — the `or` fallback is where D-13's "degrades to a default" property
actually lives, at every point of use, not in the generation step.

### Pattern 1: Baseline-first equivalence gate (D-08/D-09)

**What:** `hypr-equivalence-check` follows `waybar-equivalence-check`'s exact shape: a
`--snapshot <outdir>` mode that captures ground truth once, and a default mode that re-derives the
current state and diffs it, exiting non-zero on ANY difference, printing a unified diff.
**When to use:** Snapshot mode must run while still booted on `.conf`, before any config file is
touched (D-09's hard ordering constraint) — this differs from waybar's static-file-diff model:
Hyprland's effective config is only observable at runtime via `hyprctl`, so the "resolve" step
(waybar's `resolve_layout` Python function) is replaced by three `hyprctl -j` invocations:

```bash
# Source: pattern adapted from hypr/.config/hypr/scripts/waybar-equivalence-check
# (read directly, D-08's explicit model)
hyprctl -j binds > "$OUTDIR/binds.json"
hyprctl -j animations > "$OUTDIR/animations.json"
# One getoption call per option key ACTUALLY SET across the 8 config files —
# extracted by parsing the .conf files for every "key = value" line, not a
# hardcoded list (mirrors waybar-equivalence-check's own "never a hardcoded
# list" comment for its glob).
for key in $(extract_set_option_keys); do
    hyprctl -j getoption "$key" >> "$OUTDIR/options.jsonl"
done
```

Verified live output shapes (2026-07-28, this machine, still on `.conf`):
```json
{"option": "decoration:rounding", "int": 12, "set": true }
{"option": "general:gaps_in", "custom": "5 5 5 5", "set": true }
```
`hyprctl -j binds` returns a JSON array of bind objects (`modmask`, `submap`, `key`, `keycode`,
`dispatcher`, `arg`, ...) — **verified correctly field-aligned on this 0.56.1 build**
`[VERIFIED: local]`, which is worth flagging: `keybind-doctor` was fixed in Phase 11 (MAINT-01) to
avoid `hyprctl binds -j` specifically because it was "field-misaligned" on **Hyprland 0.56.0**.
This machine is now on **0.56.1** and `-j binds` output looks well-formed in a live check this
session — plausibly fixed upstream between point releases, but not confirmed against
`keybind-doctor`'s own stricter parsing expectations. **Recommendation:** `hypr-equivalence-check`
can safely use `hyprctl -j binds` per D-08's explicit instruction; this does not require reverting
`keybind-doctor`'s own plain-text parsing choice, which is a separate tool with a separate purpose.
`hyprctl -j animations` returns a JSON array-of-arrays (bezier definitions, then per-leaf
animation objects with `name`, `overridden`, `bezier`, `enabled`, `speed`, `style`)
`[VERIFIED: local]`.

### Pattern 2: Seed-by-invoking-the-real-renderer, never a stub (D-13's fresh-install corollary)

**What:** `stow.sh` already does this for the three current motion render targets — check all
three exist; if any is missing, source `lib/motion.sh` and call its renderer function into a
throwaway tmp dir, then copy the outputs into the live state dir, loudly warning (not silently
failing) if the render itself fails `[VERIFIED: local, stow.sh lines 149-194]`.
**When to use:** Apply the identical pattern to the new merged `lua-table` file. This is not a new
mechanism to design — it is a direct extension of an existing, working, already-tested pattern in
this exact repo.

### Anti-Patterns to Avoid

- **Assuming `require()` behaves like stock Lua `require`:** it does not — it prefixes the config
  root, breaking any attempt to `require()` a file outside `~/.config/hypr` (see Token-Contract
  section). Use a stowed symlink, not a raw cross-tree require.
- **Trusting the design spec's illustrative Lua syntax as real:** D-15 is explicit that every Lua
  snippet in the design spec/CONTEXT.md is illustrative only — this document's `[VERIFIED: local]`
  and `[CITED]` tagged examples are the only syntax that should drive the port.
- **Guessing window-rule property names from hyprlang muscle memory:** `HL.WindowRuleSpec`'s stub
  only documents 3 of the many properties this repo actually uses. Verify each one empirically
  (`hyprctl repl` against a live Lua-booted compositor) rather than assuming a 1:1 rename.
- **Shipping the merged token file as a static/hand-authored stub for fresh installs:** breaks
  D-13's own guarantee the moment the file is missing (a missing `require()` target is a hard
  error, not a graceful nil). Always seed by invoking the real renderer, matching this repo's
  existing `stow.sh` precedent.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Parsing/diffing the compositor's *effective* config for the equivalence gate | A custom Lua-AST parser for `hyprland.lua` | `hyprctl -j getoption`/`-j binds`/`-j animations` (D-08) | Hyprland's own runtime state is the ground truth; a static parse of the Lua source cannot account for `require()` resolution, token defaulting, or any dynamic construction — exactly the class of bug the equivalence gate exists to catch. |
| Detecting whether a generated Lua token table is well-formed before Hyprland ever loads it | A hand-rolled Lua syntax checker in bash/python | `luac -p <file>` (Lua's own bytecode compiler, syntax-check-only mode) if a pre-flight check is wanted, or simply let `theme_engine_validate_motion_values`'s existing jq-based schema check (already proven, already guards the pre-Lua `hyprland-motion.conf`/`gtk-4.0-motion.css` targets) validate the *source* JSON before the new Lua-table renderer ever writes a `.lua` file — the JSON-level validation is the one that actually matters, since a syntactically-valid-but-semantically-wrong Lua table is the real risk, not a Lua parse error. | This repo already has a working, tested validation gate (`theme_engine_validate_motion_values`) one layer upstream of every current motion target; extending its scope to also gate the new merged output is strictly cheaper and more consistent than a new Lua-specific validator. |
| Multi-file module loading | A custom file-concatenation/build step | Native `require()` | Hyprland's Lua environment already provides this, verified working in the shipped example. No need to pre-process/bundle. |

**Key insight:** every "don't hand-roll" item in this phase already has a working precedent
somewhere else in this exact repo (`waybar-equivalence-check`'s pattern, `motion.sh`'s validate-
before-write discipline, `stow.sh`'s seed-by-invoking-the-renderer pattern). The phase's actual
risk is not inventing new mechanisms — it is correctly re-pointing three already-proven mechanisms
at a new file format.

## Common Pitfalls

### Pitfall 1: `require()`'s config-root path prefixing breaks naive cross-tree loading

**What goes wrong:** A first attempt to load the generated token file with
`require("~/.local/state/theme/hyprland-tokens")` or a relative-looking path silently resolves
against `~/.config/hypr/` instead, producing a "module not found" error — which, per D-13, must
never happen for a config file Hyprland depends on to start.
**Why it happens:** Hyprland's `require()` is not stock Lua `require`; it always prefixes with the
Hyprland config directory `[CITED: github.com/hyprwm/Hyprland discussion #14396]`.
**How to avoid:** Use the stowed-symlink pattern (see Token-Contract section) so the `require()`d
path is always inside `~/.config/hypr`, resolving through a symlink to the real file.
**Warning signs:** Hyprland fails to start with a Lua "module not found"/`require` error in
`hyprctl rollinglog`/the systemd journal immediately after a theme switch or fresh install.

### Pitfall 2: A missing generated file is a harder failure than a missing key

**What goes wrong:** D-13 says "a missing token degrades to a default" — but this is only true for
keys *inside* an existing, valid table. If the generated `.lua` file itself is absent (e.g., on a
brand-new install before `theme-apply` has ever run, or a directly-corrupted state dir), the
`require()`/`loadfile()` call errors before any `nil`-key defaulting logic can run, and (per D-13's
own wording) this must never prevent the compositor from starting.
**Why it happens:** Lua's module system distinguishes "module not found" (hard error) from "key
absent in a loaded table" (`nil`, no error) — these are two different failure classes, and only
the second one is naturally graceful.
**How to avoid:** The generated token file's *existence* must be guaranteed independently of the
key-defaulting logic — via `stow.sh`'s existing seed-on-fresh-install pattern (see "Don't
Hand-Roll" and Pattern 2 above), not by anything inside the Lua config itself.
**Warning signs:** Compositor fails to start (or falls back to a wildly wrong default theme) on a
genuinely fresh install, before the first `theme-apply` run — this is exactly the scenario the
existing `stow.sh` motion-file seed block was written to prevent for the pre-Lua targets, and the
same failure mode reappears here if the seed block is not extended to the new file.

### Pitfall 3: Trusting an untyped stub function's signature from its type alone

**What goes wrong:** `hl.permission`, `hl.env`, `hl.curve`, `hl.animation` are all typed as
`fun(...): any` in the stub — i.e., the stub itself admits it does not know/enforce their argument
shape. The one case checked directly against the shipped example (`hl.permission`) turned out to
use a *different* calling convention (positional args) than the *typed* `HL.PermissionSpec`
sibling class implies (a table). Assuming any untyped-stub function's shape from a same-named
typed class elsewhere in the file is unsafe.
**Why it happens:** The stub is auto-generated from source and may lag behind or only partially
capture certain functions' actual accepted call shapes, particularly ones with legacy positional-
argument compatibility layered under a newer typed-table API.
**How to avoid:** For any `fun(...): any`-typed API function this repo actually needs, cross-check
against the shipped example config's own usage (if it demonstrates the function) before writing
the port; if the example doesn't demonstrate it, budget a live `hyprctl repl` test.
**Warning signs:** A config line that "type-checks" against a LuaLS-typed sibling class but
silently no-ops or errors at runtime because the real function expected positional args (or vice
versa).

### Pitfall 4: `windowrulev2`'s `match:` colon syntax does not carry over textually

**What goes wrong:** This repo's `windowrules.conf` uses Hyprland 0.54+'s `match:class = ...`/
`match:title = ...` colon-prefixed key syntax throughout (the file's own header comment says so:
"Hyprland 0.54+ syntax (match:)"). A naive line-for-line textual port might try
`match:class = "..."` inside the Lua table, which is not valid Lua table syntax.
**Why it happens:** The colon-prefixed form is a hyprlang-specific keyword convention; Lua has no
equivalent and instead nests match criteria as an ordinary sub-table.
**How to avoid:** Every `match:X = Y` line becomes an entry inside a nested `match = { X = Y, ... }`
table — confirmed directly from the shipped example (`match = { class = "^$", title = "^$",
xwayland = true, float = true, fullscreen = false, pin = false }`, one nested table holding every
match criterion for that rule) `[VERIFIED: local]`.
**Warning signs:** A Lua syntax error citing `match:class` specifically, or a window rule that
"parses" (no crash) but never matches anything because criteria intended together ended up as
separate, unconnected keys.

   the script against a persistent Lua state (risking accumulation)?**

     (format-agnostic wording); a `"config.reloaded"` event exists in the Lua event enum
     `[VERIFIED: local]`; an unverified web snippet mentioned a `reload full-reset` variant that
     recreates the entire config context, but **this was NOT found in this installed binary's own
     `--help` output** `[VERIFIED: local — contradicts the web claim]`, so that specific claim is
     downgraded to unconfirmed/possibly version-specific and should not be relied on.
   - What's unclear: whether plain `hyprctl reload` (the verb this repo's `lib/reload.sh` already

     `hyprctl -j binds`/`-j animations` array lengths before/after to detect accumulation. This

   the typed table form — and does mixing matter?**
   - What we know: the shipped example uses 3 positional string args; the stub types it as a
