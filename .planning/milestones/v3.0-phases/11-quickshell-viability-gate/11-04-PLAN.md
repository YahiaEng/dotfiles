<objective>
Prove the three durability properties a shell has to have before anything is built on it: it survives a monitor appearing and disappearing, it picks up config and state changes without being restarted, and it survives a suspend/resume cycle.

Purpose: QS-03 and QS-04 are not stop-triggers (D-10) — every outcome here is record-and-continue. That is precisely why they need to be *measured* rather than assumed: a phase where nothing can fail is a phase where nothing gets tested. Roadmap open question #1 ("does `FileView`/`JsonAdapter` propagation truly need zero `reload.sh` involvement?") is owned by this phase and is answered here by watching a label change on screen while a text editor writes the file — not by trusting documentation that already looks conclusive.

Output: a `quickshell-doctor` that exercises monitor hotplug on demand, a written answer to open question #1, an optional reload-fan-out step if the answer demands one, and a dated suspend/resume record.
</objective>

  <action>
Add a headless-output hotplug check group to `quickshell-doctor`, gated behind a new `--no-headless-output` flag that downgrades the whole group to named `[SKIP]` lines.

The check group is invasive but self-restoring, so build the teardown first: install a trap on EXIT/INT/TERM that removes any headless output this run created, *before* creating one. Never remove a headless output the run did not create.

Guard the entry: if `hyprctl monitors -j` already lists a monitor whose name begins with `HEADLESS`, emit a named `[SKIP]` and do not touch it. Someone may be using a virtual output for their own reasons and this gate must not clobber it.

Then run the cycle, each step its own `check` call:

1. **Baseline** — record the monitor count, the per-monitor `reserved` arrays, and the set of `quickshell-` namespaced level-3 surfaces with the probe summoned.
2. **Add** — `hyprctl output create headless`. Assert the monitor count increased by exactly one and capture the new output's name (do not assume `HEADLESS-1`; read it from the monitor list by diffing names against the baseline).
3. **Per-screen surface creation** — summon the probe and assert `hyprctl layers -j` now carries exactly one `quickshell-probe` entry under the new monitor's key **and** exactly one under `DP-1`'s. Exactly one per screen: not zero on the new screen (the hotplug event was missed), not two on either (a duplicate), and not a single shared surface (the same address appearing under both monitor keys). Compare the surface *addresses* to prove they are distinct objects, not the same surface listed twice.
4. **Reserved unchanged** — the `reserved` array on both monitors matches the baseline; a newly-appearing screen must not cause Quickshell to claim space on it.
5. **Remove** — dismiss the probe, `hyprctl output remove <name>`, and assert the monitor count returns to baseline, the `DP-1` probe surface is still creatable and functional, the shell process still has the same PID it had at step 1, and no crash/abort marker was appended to `~/.cache/quickshell.log` during the cycle.

The per-screen *label content* (does the headless instance actually render its own output's name, or does it render DP-1's?) is on-screen rendered text and cannot be asserted from `hyprctl`. Leave that to the human check in Task 3's verification block; the mechanical check here proves surface topology, not label correctness. Do not conflate the two, and do not claim the label was verified when only the topology was.

Everything this check group needs stays out of the git working tree.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Gate script → compositor output topology | `hyprctl output create/remove` mutates the live session's monitor set |
| Hand-editable state file → running QML process | `~/.local/state/quickshell/probe.json` is written by an arbitrary text editor while the shell reads it |
| `theme-apply` fan-out → Quickshell process | A new reload step (conditional, D-13) would send a signal or command into the shell on every theme switch |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-15 | Denial of Service | A leaked headless output left registered after a gate run | high | mitigate | A stray virtual monitor silently changes workspace layout, window placement and every later `reserved`/`layers` reading, poisoning subsequent gate runs on this and later phases. Mitigated by installing the removal trap on EXIT/INT/TERM *before* the create, by only ever removing an output the run itself created, and by an acceptance criterion that asserts the monitor count is identical before and after — including under SIGINT. |
| T-11-16 | Tampering | `~/.local/state/quickshell/probe.json` parsed by `JsonAdapter` | medium | mitigate | The file is *designed* to be hand-edited, which makes it an untrusted-input boundary the moment any later phase writes richer state there. No QML `Process` component consumes a value from it. |
| T-11-17 | Denial of Service | A conditional quickshell step in the theme reload fan-out | medium | mitigate | `lib/reload.sh`'s own comment records that `swaync-client -rs` once blocked forever without a session bus and made container installs hang.
