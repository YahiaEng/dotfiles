This plan's `files_modified` overlaps plan 13-01 on `lib/motion.sh` and `motion-lint`, and it
runs inside 13-01's soak window. That overlap is compatible with D-18, and this note records why
so a future reader diffing the two `files_modified` lists does not reach the opposite conclusion.

- **`lib/motion.sh` gains data, not behaviour.** This plan appends six rows to the
  `GTK3_SCSS_TARGETS` array plan 13-02 created — 13-02 built the compile function array-driven
  precisely so this is a data edit. The compile function itself is unchanged and the Hyprland
  target emitter, whose output the soak is measuring, is not touched.

  `theme_engine_generate` or `commit.sh`, and it writes nothing into `~/.local/state/theme/`.
  This plan's edit to it removes one exemption entry.

D-18's guarantee is about the **rendered artifact**, not about file-path disjointness, so it is
asserted mechanically rather than argued: Task 2 records a sha256 of
`~/.local/state/theme/hyprland-motion.conf` at a pinned motion-scale and curve-set *before* the
edit and re-asserts it *after*. Same shape as D-31's byte-identity assertion, which
`theme-parity` already performs across render dirs.

**A. Interpolation-escape every GTK-CSS colour-value reference, in all six files.** A bare
rename does not compile: sass parses a leading at-sign in expression position as an at-rule
keyword and aborts the WHOLE compile on the first occurrence. Wrap the entire value string in
`#{"..."}` interpolation, which passes through byte-identically. A bare reference becomes
`color: #{"@fg"};` and an alpha call becomes `border: 1px solid #{"alpha(@primary, 0.25)"};` —
the whole call, not just the inner name. The same treatment applies to the value side of the
alias layer's colour definitions.

Re-derive the per-file counts by scanning rather than trusting a number: 13-RESEARCH.md
reports roughly 289 references across the six files, with the alias layer carrying the largest
share. **Every one must be escaped** — one missed reference fails the compile for that whole
file, which then reaches GTK3 as nothing at all. Do not leave dynamic or templated content
inside any interpolation block.

**B. Rewrite every import for the OUTPUT location.** sass never rewrites relative paths inside
`@import url()` — verified by compiling into a different directory and diffing, the path
segments came through untouched. Since every compiled sheet lands as a flat sibling inside the
state dir alongside the files it imports, the rewrite is a simplification:

| current | becomes |
|---|---|
| `@import url("theme.css");` | `@import url("waybar-theme.css");` |
| `@import url("../../.local/state/theme/waybar-font.css");` | `@import url("waybar-font.css");` |
| `@import url("waybar-modules.css");` | unchanged text, now resolving as a state-dir sibling |
| `@import url("../../.local/state/theme/waybar-visibility.css");` | `@import url("waybar-visibility.css");` |
| alias layer: `@import url("../../.local/state/theme/waybar.css");` | `@import url("waybar.css");` |

Keep the visibility fragment imported **last** in each layout, exactly where it is now, and

fragment is rewritten at runtime by the OLED hide/show owner, entirely outside theme-apply —
